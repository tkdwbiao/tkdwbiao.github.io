LangChain Retriever 详解：提升 RAG 召回质量的关键

2025-09-27 10:00
阅读时长: 11 分钟

前面几篇文章里，我们已经把 RAG 的数据链路走到了向量检索这一步：

1
2
3
4
5
6
7

Document Loader
  ↓
Text Splitter
  ↓
Embedding
  ↓
Vector Store

有了向量库之后，我们可以用 similarity_search 查找相关文档。

但在真实 RAG 应用中，检索并不只是“向量库搜一下”这么简单。检索质量会直接决定模型回答质量，而 Retriever 正是 LangChain 中负责组织检索策略的核心组件。

一、前言

很多 RAG 项目效果不好，第一反应是调 Prompt 或换模型。

但实际排查时经常发现，问题根本不在模型，而在检索。

用户问：

1

公司差旅住宿标准是多少？

如果 Retriever 返回的是：

1
2
3

报销系统登录说明
员工入职流程
公司年假制度

那模型再强，也很难回答准确。

RAG 有一句很重要的话：

没有召回正确资料，后面的生成只是补救，甚至可能变成幻觉。

所以 RAG 的关键不是让模型“更会编”，而是让系统先把正确资料找出来。

本文会重点讲：

  1. Retriever 是什么。
  2. Retriever 和 Vector Store 有什么区别。
  3. as_retriever() 怎么用。
  4. search_type 有哪些常见模式。
  5. similarity、mmr、similarity_score_threshold 分别适合什么场景。
  6. k、fetch_k、lambda_mult、score_threshold 如何理解。
  7. MultiQueryRetriever 的思路。
  8. 如何评估 Retriever 召回质量。
  9. Retriever 的常见问题和最佳实践。

二、Retriever 是什么？

Retriever 可以理解为：

接收用户问题，返回相关 Document 的组件。

它的输入通常是字符串问题：

1

"RAG 是什么？"

输出是 Document 列表：

1
2
3
4

[
    Document(page_content="RAG 是检索增强生成...", metadata={...}),
    Document(page_content="RAG 通常包含检索和生成两个阶段...", metadata={...}),
]

在 LangChain 中，Retriever 也是 Runnable。

所以你可以：

1

docs = retriever.invoke("RAG 是什么？")

也可以：

1
2
3
4

results = retriever.batch([
    "RAG 是什么？",
    "Retriever 有什么用？",
])

这让 Retriever 可以自然接入 LCEL：

1
2
3
4

rag_chain = {
    "context": retriever | format_docs,
    "question": RunnablePassthrough(),
} | prompt | model | parser

三、Retriever 和 Vector Store 的区别

很多初学者会把 Vector Store 和 Retriever 混为一谈。

它们关系很近，但不完全一样。

1. Vector Store 是存储和相似度搜索能力

Vector Store 负责：

  • 保存向量
  • 保存文本 chunk
  • 保存 metadata
  • 执行相似度搜索
  • 支持过滤和索引

例如：

1

results = vectorstore.similarity_search("RAG 是什么？", k=3)

这是直接调用向量库检索。

2. Retriever 是检索接口和策略层

Retriever 更像一个统一接口。

你可以把 Vector Store 转成 Retriever：

1

retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

然后上层只关心：

1

retriever.invoke(question)

它背后可以是：

  • 向量检索
  • 关键词检索
  • 混合检索
  • MMR 检索
  • 多查询检索
  • 父子文档检索
  • 自定义数据库检索

3. 为什么要用 Retriever？

因为 RAG 应用里，“检索”本身会越来越复杂。

如果你把上层链路直接写死为：

1

vectorstore.similarity_search(...)

后面想换成 MMR、混合检索或 MultiQuery，就会影响很多代码。

使用 Retriever 后，上层链路更稳定：

1

retriever.invoke(question)

底层策略可以逐步替换。

import os
from dotenv import load_dotenv
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma
from langchain_core.documents import Document

load_dotenv()

documents = [
    Document(
        page_content="LangChain 是一个用于构建大模型应用的框架。",
        metadata={"source": "intro.md"},
    ),
    Document(
        page_content="RAG 是检索增强生成，会先检索资料，再让模型基于资料回答。",
        metadata={"source": "rag.md"},
    ),
    Document(
        page_content="Retriever 接收用户问题，返回相关 Document，是 RAG 召回质量的关键。",
        metadata={"source": "retriever.md"},
    ),
]

embeddings = OpenAIEmbeddings(
    model=os.getenv("EMBEDDING_MODEL", "text-embedding-3-small"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
)

vectorstore = Chroma.from_documents(
    documents=documents,
    embedding=embeddings,
)

retriever = vectorstore.as_retriever(search_kwargs={"k": 2})

docs = retriever.invoke("RAG 中如何检索相关资料？")

for doc in docs:
    print("=" * 40)
    print(doc.page_content)
    print(doc.metadata)

这里最关键的是：

1

retriever = vectorstore.as_retriever(search_kwargs={"k": 2})

它把 Vector Store 转成了 Retriever。

五、search_type：检索模式

as_retriever() 可以通过 search_type 设置检索模式。

常见有：

search_type作用
similarity默认相似度检索
mmr最大边际相关性，兼顾相关性和多样性
similarity_score_threshold只返回超过相似度阈值的结果

示例：

1
2
3
4

retriever = vectorstore.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 3},
)

不同 Vector Store 对参数支持可能略有差异，但核心思路一致。

六、similarity：最基础的相似度检索

默认方式通常是 similarity search。

1
2
3
4

retriever = vectorstore.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 3},
)

它会返回和用户问题最相似的前 k 个文档。

1. k 是什么？

k 表示返回多少条结果。

1

search_kwargs={"k": 3}

表示返回最相关的 3 个 Document。

2. k 太小的问题

如果 k 太小，可能漏掉答案。

例如答案分散在两个段落：

  • chunk 1 讲报销范围
  • chunk 2 讲住宿标准

但你只取 k=1，可能只拿到其中一个。

3. k 太大的问题

如果 k 太大，会带来：

  • 上下文变长
  • token 成本增加
  • 无关内容变多
  • 模型更容易被干扰

所以 k 不是越大越好。

常见起点：

1

k=3

或者：

1

k=5

最终要用真实问题测试。

七、similarity_score_threshold：按阈值过滤

有时你不希望无论如何都返回 k 条结果。

如果知识库里没有相关内容，强行返回最相似的几条，可能会误导模型。

这时可以使用阈值检索。

1
2
3
4
5
6
7

retriever = vectorstore.as_retriever(
    search_type="similarity_score_threshold",
    search_kwargs={
        "score_threshold": 0.7,
        "k": 5,
    },
)

它的意思是：只返回相似度达到阈值的结果。

什么时候适合用阈值？

适合：

  • 希望减少无关上下文
  • 希望知识库没有答案时返回空结果
  • 希望模型更容易说“不知道”
  • 业务上不能随便编答案

例如：

1

docs = retriever.invoke("今天北京天气怎么样？")

如果你的知识库是 LangChain 技术文档，显然不应该返回 LangChain 文档来回答天气问题。

阈值可以降低这种错误召回。

阈值不是通用标准

不同向量库和距离度量的分数含义可能不同。

有的越大越相似，有的越小越相似。

所以 score_threshold=0.7 只是示例，不是万能值。

必须结合实际向量库和测试数据调参。

八、MMR：兼顾相关性和多样性

MMR 是 Maximal Marginal Relevance，最大边际相关性。

它的目标是：

既要相关，也要避免返回一堆高度重复的结果。

普通 similarity search 可能返回：

1
2
3

chunk 1：RAG 定义
chunk 2：RAG 定义的另一种表述
chunk 3：还是 RAG 定义

这些都相关，但信息重复。

MMR 更希望返回：

1
2
3

chunk 1：RAG 定义
chunk 2：RAG 流程
chunk 3：RAG 和微调区别

这样上下文信息更丰富。

MMR 示例

1
2
3
4
5
6
7
8

retriever = vectorstore.as_retriever(
    search_type="mmr",
    search_kwargs={
        "k": 3,
        "fetch_k": 10,
        "lambda_mult": 0.5,
    },
)

参数含义：

参数作用
k最终返回多少条
fetch_k先取多少候选文档
lambda_mult相关性和多样性的平衡

lambda_mult 怎么理解？

lambda_mult 越接近 1，越偏向相关性。

越接近 0，越偏向多样性。

可以从：

1

lambda_mult=0.5

开始测试。

MMR 适合什么场景？

适合：

  • 文档里有大量重复内容
  • 想覆盖多个角度
  • top-k 结果高度相似
  • 用户问题比较宽泛

例如用户问：

1

RAG 有哪些常见问题？

你可能希望检索到：

  • 检索不到资料
  • 文档切分问题
  • 向量模型问题
  • Prompt 约束问题

而不是 5 个都在讲同一个问题。

九、metadata filter：带条件的检索

检索不能只看语义，还要看业务条件。

例如：

  • 当前用户只能看 HR 文档。
  • 当前知识库只查询某个项目。
  • 只检索 2025 年之后的文档。
  • 只检索某个语言版本。

这就需要 metadata filter。

示例：

1
2
3
4
5
6

retriever = vectorstore.as_retriever(
    search_kwargs={
        "k": 3,
        "filter": {"category": "RAG"},
    },
)

查询：

1

docs = retriever.invoke("如何提升召回质量？")

只会在 category=RAG 的文档中检索。

权限过滤

企业知识库必须考虑权限。

例如文档 metadata：

1
2
3
4
5

metadata={
    "department": "HR",
    "access_level": "internal",
    "tenant_id": "company-a",
}

检索时根据当前用户身份过滤。

注意：不同向量库的 filter 语法不同。

生产环境要基于具体 Vector Store 文档实现。

但原则不变：

权限过滤不能只靠 Prompt，必须在检索层完成。

十、MultiQueryRetriever：让模型生成多个查询

用户的问题表达方式不一定和文档表达一致。

比如用户问：

1

怎么让模型查公司资料再回答？

文档中可能写的是：

1

RAG 是 Retrieval-Augmented Generation，通过检索增强生成引入外部知识。

表达差异较大。

MultiQueryRetriever 的思路是：

用 LLM 根据用户问题生成多个不同角度的查询，再分别检索，最后合并结果。

例如把用户问题改写成：

1
2
3

RAG 是什么？
检索增强生成如何工作？
如何让大模型基于外部知识回答？

这样更容易召回相关文档。

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain.retrievers.multi_query import MultiQueryRetriever

load_dotenv()

llm = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
    temperature=0,
)

base_retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

retriever = MultiQueryRetriever.from_llm(
    retriever=base_retriever,
    llm=llm,
)

docs = retriever.invoke("怎么让模型查公司资料再回答？")

MultiQueryRetriever 的代价

它通常会增加一次 LLM 调用。

优点：

  • 提升召回覆盖率
  • 缓解用户问法和文档表达不一致
  • 对复杂问题更友好

缺点：

  • 成本增加
  • 延迟增加
  • 生成的查询可能偏离原意
  • 需要更多调试

所以不要一开始就上复杂策略。

先把基础 similarity 检索跑稳，再考虑 MultiQuery。

from langchain_core.runnables import RunnablePassthrough
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI


def format_docs(docs):
    return "\n\n".join(
        f"来源：{doc.metadata.get('source', 'unknown')}\n{doc.page_content}"
        for doc in docs
    )

prompt = ChatPromptTemplate.from_messages([
    ("system", """
你是一名严谨的知识库问答助手。
请只根据上下文回答问题。
如果上下文没有答案，请说“根据已提供资料无法确定”。
"""),
    ("human", """
上下文：
{context}

问题：{question}
"""),
])

model = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
    temperature=0.2,
)

rag_chain = (
    {
        "context": retriever | format_docs,
        "question": RunnablePassthrough(),
    }
    | prompt
    | model
    | StrOutputParser()
)

answer = rag_chain.invoke("RAG 如何提升回答准确性？")
print(answer)

这里的关键是：

1

"context": retriever | format_docs

Retriever 返回 Document 列表。

format_docs 把 Document 列表格式化成 Prompt 可以使用的字符串。

十二、如何评估 Retriever 效果？

不要只看最终回答。

RAG 调试时要先看 Retriever 返回了什么。

1. 打印检索结果

 1
 2

def debug_retrieval(question: str):
    docs = retriever.invoke(question)

    print("问题：", question)
    print("检索结果数量：", len(docs))

    for index, doc in enumerate(docs, start=1):
        print("=" * 60)
        print("排名：", index)
        print("metadata：", doc.metadata)
        print(doc.page_content[:500])

调用：

1

debug_retrieval("RAG 和微调有什么区别？")

先确认检索结果是否包含答案。

2. 准备评估问题集

至少准备几十个问题：

  • 简单直接问题
  • 同义表达问题
  • 多跳问题
  • 知识库没有答案的问题
  • 容易混淆的问题
  • 需要特定文档来源的问题

每次调整 k、chunk_size、Embedding 模型、检索模式后，都跑一遍。

3. 记录命中情况

可以人工标记：

问题是否检索到正确文档排名备注
RAG 是什么是1正常
RAG 和微调区别是2可接受
公司报销标准否-文档未入库

RAG 质量优化不是靠感觉，而是靠评估。

十三、常见问题

1. 检索结果全是无关内容怎么办？

排查顺序：

  1. 知识库里是否有答案。
  2. 文档是否正确加载。
  3. chunk 是否切得合理。
  4. Embedding 模型是否适合语言和领域。
  5. k 是否太小。
  6. metadata filter 是否过滤错了。
  7. 用户问题是否需要改写。

不要一上来就怪模型。

2. 检索结果重复很多怎么办？

可以尝试：

  • 降低 chunk_overlap。
  • 使用 MMR。
  • 清理重复文档。
  • 调整 chunk_size。
  • 加入 rerank。

3. 知识库没有答案时为什么还会返回结果？

相似度检索通常会返回最相似的 k 条，即使它们并不真正相关。

可以考虑：

  • 使用 similarity_score_threshold。
  • 在 Prompt 中要求资料不足时说不知道。
  • 检索结果为空时直接返回无法回答。

4. k 越大越好吗？

不是。

k 太大可能带来无关上下文，反而降低回答质量。

建议从 3 或 5 开始，用评估集调参。

5. Retriever 能不能访问数据库？

可以。

Retriever 不一定非要基于向量库。

你可以自定义 Retriever，从数据库、搜索引擎、API 或其他系统中返回 Document。

关键是遵循输入问题、输出 Document 的接口。

6. 权限能不能交给 Prompt 处理？

不能。

Prompt 不能作为权限边界。

权限必须在检索前或检索时过滤。

不该给用户看的文档，不应该进入 Prompt。

十四、最佳实践

1. 调 RAG 先看 Retriever，不要只看最终回答

如果最终答案错了，先打印检索结果。

很多时候问题出在召回，而不是生成。

2. 从简单 similarity 开始

先用：

1

vectorstore.as_retriever(search_kwargs={"k": 3})

跑通后再加 MMR、阈值、多查询、rerank。

3. 对宽泛问题尝试 MMR

如果用户问题很宽泛，MMR 可以提升结果多样性。

例如：

1

RAG 常见问题有哪些？

比单纯 similarity 更可能覆盖多个方面。

4. 对无答案问题使用阈值

如果业务不允许胡答，可以考虑 score threshold。

并在没有检索结果时直接返回：

1

当前知识库中没有找到相关资料。

5. metadata filter 要从业务权限出发

企业知识库必须先过滤用户无权访问的内容。

不要让敏感文档进入 Prompt 后再要求模型不要泄露。

6. 建立 Retriever 评估集

每次调整检索策略，都用同一组问题评估。

关注：

  • 是否召回正确文档
  • 正确文档排名是否靠前
  • 是否返回过多无关内容
  • 无答案问题是否能避免误召回

十五、总结

本文我们深入讲了 LangChain 中的 Retriever。

核心结论是：

Retriever 决定 RAG 能不能先找到正确资料。召回质量不好，后面的 Prompt 和模型都只能补救，甚至会放大错误。

本文重点包括：

  • Retriever 接收问题，返回相关 Document。
  • Vector Store 是存储和搜索能力，Retriever 是统一检索接口和策略层。
  • as_retriever() 可以把向量库转换成 Retriever。
  • similarity 是最基础的相似度检索。
  • k 控制返回结果数量，不是越大越好。
  • similarity_score_threshold 可以减少无关召回。
  • MMR 兼顾相关性和多样性，适合减少重复结果。
  • metadata filter 对权限、分类和多租户非常重要。
  • MultiQueryRetriever 可以用 LLM 生成多个查询提升召回覆盖率。
  • 调试 RAG 时要先打印 Retriever 结果，再看最终回答。
