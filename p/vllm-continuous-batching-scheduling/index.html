vLLM 系列(三)：流水线上的旋转寿司 —— 连续批处理 (Continuous Batching)

2026-04-06 18:15
阅读时长: 4 分钟

如果说 PagedAttention 解决了显存的“空间”浪费，那么 Continuous Batching（连续批处理） 解决的就是 GPU 的“时间”空转。 在传统的推理框架里，GPU 就像一辆非要等所有人到齐才出发的大巴车；但在 vLLM 里，它变成了流动的旋转寿司，谁吃完谁走，空位立刻补上。今天阿彪就带你拆解这个让吞吐量翻倍的调度奥秘。

一、 知识点详解：从静态到动态的降维打击

1. 静态批处理（Static Batching）的平庸

在传统的推理（如 HuggingFace）中，批处理是以“请求”为单位的。 假设 Batch Size = 4，其中 3 个请求只要生成 5 个词，而 1 个请求要生成 500 个词。 那 3 个短请求在 1 秒钟内就结束了，但它们必须在显存里占着坑“陪跑”，直到那个 500 词的长请求跑完，四个人才能一起收工。这种“一人迟到，全家等死”的机制，是吞吐量的头号杀手。

2. 连续批处理（Continuous Batching）的优雅

vLLM 引入了 Iteration-level Scheduling（迭代级调度）。 它不再以整个请求的结束为边界，而是以 “每一个 Token 的生成” 为边界。

核心逻辑：每当 GPU 完成一次迭代（生成一个词），调度器就会检查：有没有请求已经输出了结束符（STOP）？如果有，立刻释放它的显存，并从等待队列中拉入新请求补充空位。

这种机制保证了 GPU 的每一个 Slot（槽位）都在马不停蹄地干活，极大压榨了计算资源的利用率。

二、 进阶拓展：显存爆了怎么办？（抢占与交换机制）

在高并发场景下，即使有 PagedAttention，显存也可能被填满。当新请求的 Prefill（预填充）需要显存，而正在运行的请求又不能中断时，vLLM 会启动 抢占（Preemption） 机制。

调度器有两条路可以选：

  1. Recompute（重算）：直接把那个倒霉请求的 KV Cache 删掉，把它踢回等待队列。等以后显存空了，再从头算一遍。
  2. Swap（交换）：利用 PCIe 带宽，把请求的 KV Cache 搬到 CPU 内存里。等显存宽裕了，再搬回来。

阿彪面试小贴士：Swap 还是 Recompute？这是一个算力与带宽的博弈。如果 KV Cache 很大且 PCIe 够快，Swap 更划算；如果重算代价极小（Prompt 短），则 Recompute 更直接。

import collections

class Request:
    def __init__(self, req_id, steps):
        self.req_id = req_id
        self.remaining_steps = steps # 模拟需要生成的 token 数

def vllm_scheduler_sim(waiting_list, batch_size=2):
    running = []
    finished = []
    iteration = 0
    
    while waiting_list or running:
        iteration += 1
        # 1. 尝试从等待队列补充空位
        while len(running) < batch_size and waiting_list:
            new_req = waiting_list.popleft()
            print(f"Iter {iteration}: 请求 {new_req.req_id} 加入战斗！")
            running.append(new_req)
            
        # 2. 模拟 GPU 生成一个 token
        for req in running:
            req.remaining_steps -= 1
            
        # 3. 检查谁跑完了（Iteration-level！）
        for req in list(running):
            if req.remaining_steps <= 0:
                print(f"Iter {iteration}: 请求 {req.req_id} 搞定，光速下班！")
                running.remove(req)
                finished.append(req)

# --- 阿彪的模拟测试 ---
queue = collections.deque([
    Request("A", 3), # 短请求
    Request("B", 10),# 长请求
    Request("C", 2)  # 正在排队的短请求
])

vllm_scheduler_sim(queue, batch_size=2)

阿彪点评：看到没有？请求 A 在第 3 次迭代结束后，请求 C 立刻在第 4 次迭代就插进去了，根本不需要等请求 B 跑完那 10 步。这就是 Throughput 起飞的原因！

四 : 面试官会问到的问题及详细答案

❓ Q1：Continuous Batching 既然这么牛，它有缺点吗？

答： 有的，它会对 TTFT（首字延迟） 造成一定的波动。 因为当调度器在 Decode 阶段强行插入一个新的 Prefill 请求（新用户进来）时，由于 Prefill 阶段的计算量远大于 Decode 阶段，会导致那一瞬间正在生成的旧用户感到明显的“卡顿（Jitter）”。 （加分点：目前的优化方案是 Chunked Prefill，将长 Prompt 切片，分批插入迭代中，平滑延迟波动。）

❓ Q2：vLLM 是如何避免长请求被“饿死（Starvation）”的？

答： vLLM 内部维护了一个 FCFS（先来后到）的等待队列。 调度器在分配显存块（Blocks）时，会优先保证队列最前面的请求。如果显存不足以容纳新请求，调度器会宁可让 GPU 暂时不满载，也要保护老请求的顺利运行，或者通过抢占机制公平地调度资源。

❓ Q3：在抢占发生时，vLLM 为什么优先抢占最后进入的请求？

答： 因为最后进入的请求通常生成的 Token 数最少，积累的 KV Cache 也最少。 抢占它意味着：

  1. 重算代价最小：如果需要 Recompute，重算几个词比重算几百个词快得多。
  2. 迁移开销最小：如果需要 Swap，搬运少量的 KV Cache 对 PCIe 带宽的压力也最小。

五、 阿彪碎碎念 [抱拳]

学到这里，你有没有发现，vLLM 的本质其实是一场关于“公平”与“效率”的权衡游戏。

静态批处理追求的是“整齐划一”，结果输给了效率；而连续批处理追求的是“各尽其能”，却带来了调度的复杂性。 在大模型开发的面试中，面试官最想听到的不是你背出了多少个名词，而是你能不能像阿彪这样，把冷冰冰的代码逻辑，转化为对业务场景（长短请求交替、显存挤占、延迟波动）的深度思考。

拒绝死记硬背，从理解每一个 Iteration 开始。 下一篇，我们将聊聊分布式推理，看 vLLM 是如何让几十台机器像一个人一样协同工作的，冲就完事了！
