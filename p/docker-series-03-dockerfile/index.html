【Docker 系列 03】从零手写 Dockerfile：构建你的第一个专属镜像

2025-06-19 09:30
阅读时长: 6 分钟

“我不想要别人的 Nginx，我想把我自己写的 Python/Go/Java 项目打包成镜像，该怎么做？”

在上一篇文章中，我们学会了如何使用命令行对现有的镜像和容器进行“生杀大权”的管理。当时我们留了一个悬念：如果我们要部署自己的代码，难道是先启动一个 Ubuntu 基础容器，用 docker exec 进去 apt-get install，然后再把代码通过 FTP 传进去吗？

绝对不要这么做！这种行为被称为制作“黑盒镜像”，它不仅体积庞大，而且别人根本不知道你在这个系统里干了什么，完全违背了 Docker “可复现”的核心理念。

今天，我们将学习 Docker 宇宙中最伟大的发明之一：Dockerfile。 有了它，你的代码从此就像是拥有了“自动安装说明书”，随时随地，一键生成完美运行环境。

一、Dockerfile 是什么？为什么我们需要它？

Dockerfile 本质上就是一个普通的文本文件，里面写满了一条条指令（Instructions）。

你可以把它想象成一张 “菜谱” ：

  1. 买底料（准备基础系统，比如 Python 3.11 环境）。
  2. 切菜准备（在系统里建个文件夹作为工作区）。
  3. 下锅炒菜（把你的源代码复制进系统，并执行 pip install 安装依赖）。
  4. 出锅装盘（指定这个容器启动时要运行哪条命令）。

Docker 引擎（厨师）只要拿着这份 Dockerfile，加上你的源代码，就能自动“炒”出一个包含你应用的全新镜像（Image）。只要菜谱不改，炒出来的味道（运行环境）就永远一模一样！

二、掌握 Dockerfile 的 6 大核心指令

Dockerfile 的指令并不多，日常开发掌握以下 6 个就能应对 90% 的场景：

1. FROM：站在巨人的肩膀上

所有的 Dockerfile 必须以 FROM 开头，它指定了你的基础环境。

1
2

# 语法：FROM <镜像名>:<标签>
FROM python:3.11-slim

💡 阿彪建议：尽量不要用臃肿的 ubuntu 或 centos 作为基础镜像。官方提供的 -slim（精简版）或 -alpine（极简版）体积更小，安全性更高。

2. WORKDIR：指定工作目录

进入容器后的默认目录，相当于 Linux 里的 cd 命令。

1
2

# 如果 /app 目录不存在，Docker 会自动帮你创建
WORKDIR /app

3. COPY：把你的代码搬进去

把你电脑（宿主机）上的文件，复制到容器内部。

1
2
3

# 语法：COPY <本地路径> <容器内路径>
# 把当前目录下的所有文件，复制到容器的 /app 目录下
COPY . /app

4. RUN：在“构建阶段”执行的命令

在打包镜像的过程中运行的命令，通常用于安装软件或依赖。

1

RUN pip install -r requirements.txt

5. EXPOSE：声明暴露的端口

告诉看这个 Dockerfile 的人，你的程序监听了哪个端口。注意：它只是一个声明（类似于写注释），并不会真的在宿主机上把端口映射出去。 真实的映射还是得靠 docker run -p。

1

EXPOSE 8080

6. CMD 与 ENTRYPOINT：容器启动时干什么

这两兄弟经常让人混淆。它们都是用来指定容器 启动时（Run 阶段） 执行的命令。

  • CMD ["python", "app.py"]：默认执行命令。如果在终端运行 docker run my-app echo "hello"，那么 echo "hello" 会覆盖掉 CMD 里的内容。
  • ENTRYPOINT ["python", "app.py"]：固定的入口点。它很难被轻易覆盖，通常用于把容器当成一个特定的可执行程序来使用。

👉 结论：绝大多数普通 Web 项目，用 CMD 就足够了。

三、实战：从零构建一个 Python Web 镜像

说再多不如动手敲。假设我们现在有一个简单的 Python Web 项目，目录结构如下：

1
2
3
4

my-web-app/
├── app.py             # 核心业务代码
├── requirements.txt   # 依赖列表
└── Dockerfile         # 我们要写的构建清单

app.py 内容（基于 FastAPI）：

 1

from fastapi import FastAPI
import uvicorn

app = FastAPI()

@app.get("/")
def read_root():
    return {"message": "Hello Docker! 这是一篇来自阿彪博客的测试！"}

if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=8080)

requirements.txt 内容：

1
2

fastapi==0.103.1
uvicorn==0.23.2

编写黄金标准版 Dockerfile

现在，在项目根目录下创建一个名为 Dockerfile（注意大小写，没有后缀）的文件，填入以下内容。

⚠️ 请注意第 3 步和第 4 步的顺序，这是高级玩家和新手的本质区别！

 2

# 1. 基础镜像
FROM python:3.11-slim

# 2. 设置工作目录
WORKDIR /app

# 3. ⭐️ 核心优化：先拷贝 requirements.txt
COPY requirements.txt .

# 4. ⭐️ 安装依赖（利用国内源加速）
RUN pip install --no-cache-dir -i https://pypi.tuna.tsinghua.edu.cn/simple -r requirements.txt

# 5. 拷贝剩下的所有源代码
COPY . .

# 6. 声明端口
EXPOSE 8080

# 7. 启动命令
CMD ["python", "app.py"]

为什么要把 COPY 分成两步？（深刻理解 Docker 缓存层）

Docker 构建镜像时，是一层一层叠加的（Layer），并且具有缓存机制。如果某一层的内容没变，Docker 就会直接使用上一次的缓存，极大地加快构建速度。

  • 新手错误写法： 直接 COPY . . 然后 RUN pip install。这种写法会导致你每次只修改了一行 app.py 的代码，Docker 都会认为代码目录变了，从而让缓存失效，强行重新下载一遍所有的第三方依赖包，非常浪费时间！
  • 老鸟优化写法： 先只 COPY requirements.txt，然后 RUN pip install。因为你的依赖项十天半个月才变一次，所以这一层的缓存几乎永远有效。最后再 COPY . .（复制经常变动的业务代码）。这样每次重新打包时，安装依赖的那一步就直接秒跳过！

四、见证奇迹：构建并运行

1. 构建镜像 (docker build)

在终端中进入你的 my-web-app 目录，执行：

1
2

# -t 表示给镜像打标签 (tag)，最后一个 . 表示使用当前目录的 Dockerfile
docker build -t my-fastapi-app:v1 .

你会看到屏幕上一层一层地执行你写的指令，成功后会显示 Successfully tagged my-fastapi-app:v1。 用 docker images 查看，你就能看到你的亲骨肉静静地躺在镜像列表里了！

2. 运行你自己的镜像 (docker run)

有了镜像，跑起来就顺理成章了：

1

docker run -d --name my-app-container -p 8080:8080 my-fastapi-app:v1

打开浏览器，访问 http://localhost:8080，看到那句亲切的 “Hello Docker! 这是一篇来自阿彪博客的测试！” 了吗？

恭喜你，你已经掌握了把任意代码打包成工业级标准制品的终极技能！

五、千万别忘了这把锁：.dockerignore

在你执行 docker build 时，Docker 引擎会把你当前目录下的所有文件（称为构建上下文 Context）发送给守护进程。

如果你的目录下有个 500MB 的 node_modules 文件夹，或者有一个 2GB 的虚拟环境 .venv 文件夹，甚至包含着你的密钥配置文件 .env，它们全都会被一股脑塞进 Docker 里。这会导致构建慢如蜗牛，且容易泄露机密数据。

解决办法：在项目根目录建一个名叫 .dockerignore 的文件，语法和 .gitignore 一模一样：

1
2
3
4
5
6
7

# .dockerignore
.git
.venv
__pycache__
*.pyc
.env
logs/

这不仅能让你的镜像体积暴瘦，还能避免我们在开发 AI 项目时遇到过的各种权限和目录挂载坑。

结语

学到这里，你可以自豪地说你已经“会用 Docker”了。你的应用已经摆脱了操作系统的束缚，变成了一个标准化的“集装箱”。

但是，等等！ 如果你的项目是一个博客系统，有人发了一篇新文章，数据写进了容器的内部数据库。由于我们在第二篇里学过，容器被 docker rm 删掉后，里面的一切都会灰飞烟灭。那我们的数据该怎么办？ 日志文件该放哪？
