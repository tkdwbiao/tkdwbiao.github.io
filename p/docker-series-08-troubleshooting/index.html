【Docker 系列 08】排障指南：Docker 常见报错大赏与终极解决套路

2025-07-24 10:00
阅读时长: 6 分钟

“我的 Dockerfile 写得完美无瑕，docker-compose.yml 结构严谨。满怀期待地敲下 up -d，结果换来的却是满屏刺眼的红字：Permission denied、Address already in use、Restarting (3)…… 苍天啊，到底哪里出了问题？”

欢迎来到真实的后端开发世界。 在前面的 7 篇文章中，我们一路高歌猛进，学会了写 Dockerfile、挂载 Volume、配置网络、甚至做了多阶段构建的极限瘦身。

但理论总是丰满的，现实总是骨感的。当你把这些完美的代码部署到开发机或生产服务器上时，你会发现，90% 的时间并不是在写配置，而是在 Debug（排障）。

今天，我将把自己这些年在开发微服务和 AI 大模型项目时，用血泪换来的“Docker 常见报错大赏及排障套路”倾囊相授。掌握了这套心法，面对再诡异的报错，你也能像老中医把脉一样，一击毙命！

一、排障心法：Docker 医生的“望闻问切”三板斧

当你敲下运行命令，却发现服务没起来时，千万不要瞎猜，更不要盲目重启。请严格遵守以下三步排障法：

1. 望（看整体状态）：docker ps -a

不要只敲 docker ps！因为启动失败的容器是不会出现在存活列表里的。 加上 -a（all），你要重点观察容器的 STATUS 字段：

  • 如果显示 Up 2 minutes：说明它活着，但可能内部逻辑报错（如连不上数据库）。
  • 如果显示 Exited (1) 2 seconds ago：说明程序发生了致命错误，启动后立刻崩溃退出了。
  • 如果显示 Restarting (3) 4 seconds ago：说明程序崩溃了，但因为你配置了 restart: always，Docker 正在无限次尝试拉起它。

2. 闻（听错误原音）：docker logs <容器名>

这是排障的绝对核心。容器挂了，99% 的原因都写在日志里。 如果是不断重启的容器，用 docker logs -f <容器名> 实时抓取它临死前吐出的最后一行报错（Traceback）。

3. 切（深入内部解剖）：覆盖 Entrypoint 启动

如果容器一起动就秒退，你连 docker exec 进去查看配置的机会都没有怎么办？ 大招：覆盖它的默认启动命令，强行让它活着。

1
2

# 原本启动会崩溃，现在我们强行把它变成一个只运行 sh 的空壳容器进去排查
docker run -it --entrypoint sh my-crashing-image

进去之后，你就可以手动执行启动命令，看看究竟缺了什么环境变量或依赖。

二、经典报错大赏：那些年我们踩过的深坑

接下来，我们将对最常见的几个经典报错进行“尸检报告”分析。

🚨 经典报错 1：端口已被占用

报错原声：

Error response from daemon: driver failed programming external connectivity on endpoint... Bind for 0.0.0.0:9000 failed: port is already allocated 或者你的 Python 程序报 [Errno 98] Address already in use

症状分析： Docker 试图把容器内部的端口映射到你宿主机的 9000 端口，但宿主机的 9000 端口已经被别人占用了。

终极解法：

  1. 揪出元凶：在宿主机终端执行 sudo lsof -i :9000 或 sudo netstat -tunlp | grep 9000。
  2. 你会看到占用端口的进程（可能是上一次没关干净的僵尸 Python 进程，或者是另外一个残留的 Docker 容器）。
  3. 处决元凶：拿到它的 PID（比如 1234），执行 sudo kill -9 1234；如果是个旧容器，执行 docker rm -f <旧容器名>。

🚨 经典报错 2：恐怖的权限拒绝陷阱

报错原声：

PermissionError: Permission denied (os error 13) about ["/home/user/my-project/volumes/etcd/member"]

症状分析： 这个报错多发于我们在本地进行混合开发时。你用 docker-compose 启动了包含持久化目录（Volumes）的容器（比如 etcd、MySQL）。Docker 是以 Root 上帝权限 在你的项目目录下创建了这些数据文件夹。 此时，你在本地用自己的普通用户启动了带 热重载（WatchFiles/Reload） 的 Web 框架（如 Uvicorn、Nodemon）。热重载器试图扫描整个项目目录以监听文件变化，但它作为一个普通人，一头撞在了 Root 所有的 volumes 禁区上，当场暴毙。

终极解法（两种）：

  • 治标法：每次启动完 Docker，在本地执行 sudo chown -R $USER:$USER volumes/，把文件夹的拥有者改回你自己。
  • 治本法（推荐）：修改你框架的热重载配置，明确告诉它忽略数据目录。例如 Python Uvicorn 中：
    1

    uvicorn.run("app.main:app", reload=True, reload_dirs=["app"]) # 只监听代码目录

🚨 经典报错 3：连不上 localhost 的服务

报错原声：

ConnectionRefusedError: [Errno 111] Connection refused 或 Fail connecting to server on localhost:19530

症状分析： 你把后端代码和数据库都放进了 Docker 部署。但你的后端配置文件里依然写着 DB_HOST=localhost。 我们曾在第 5 篇网络模型中强调过：在容器的世界里，localhost 只代表容器它自己这个狭小的密室，不代表你的电脑，更不代表其他容器！

终极解法：

  1. 检查两个容器是否在同一个 Docker Network 中。
  2. 将配置文件里的 localhost 修改为目标容器的名称（比如 DB_HOST=milvus-standalone）。Docker 内部的 DNS 会自动帮你解析。

🚨 经典报错 4：依赖服务未准备好导致主程序崩溃

症状分析： 你写了一个 docker-compose.yml，里面有 standalone (主程序) 和 minio、etcd (依赖服务)。你还聪明地写了 depends_on。 但一键启动后，主程序还是报错退出了。日志显示：timeout fetching ...（连接数据库超时）。

深层原理： depends_on 默认只管 “启动顺序”，不管 “是否就绪”。Compose 把 MySQL 容器开机后，会瞬间启动你的主程序。但众所周知，像 MySQL、Milvus 这种重型数据库，从开机到真正能处理连接，可能需要 10 到 60 秒！你的程序去连的时候，数据库其实还在加载内存，自然连接失败而崩溃。

终极解法：使用健康检查（Healthcheck）结合重试机制。 在 docker-compose.yml 中配置真正的依赖等待：

services:
  db:
    image: mysql:8.0
    # 增加健康检查，告诉 Docker 什么时候数据库才算真活了
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      retries: 5

  web:
    image: my-app
    depends_on:
      db:
        # 要求不但要启动，还要健康检查通过！
        condition: service_healthy

另外，在你的主程序代码中（特别是数据库连接处），一定要加上 try...catch 和重试逻辑，不要一失败就自尽。

结语

遇到报错不可怕，可怕的是遇到报错只会去搜索引擎里盲目复制粘贴别人的命令。

通过这篇排障大赏，我希望你能建立起真正的**“容器调试思维”**：

  1. 查状态确认生死（ps -a）。
  2. 看日志寻找元凶（logs）。
  3. 检查网络拓扑与端口是否对应（localhost 陷阱）。
  4. 警惕文件挂载的权限交锋（os error 13）。

当你熟练掌握了这套排障套路，单机的 Docker 部署对你来说已经没有任何秘密可言了。

但随着项目慢慢成型，你可能会面临一个新的折磨： 每次你修改了几行代码，你都要手动在本地构建镜像（docker build），然后手动把这个庞大的镜像推送到服务器，再连上服务器手动拉取（pull），最后重启容器。一天如果改 10 次代码，你就要重复这套枯燥的动作 10 次。
