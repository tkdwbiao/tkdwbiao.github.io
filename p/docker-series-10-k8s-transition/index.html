【Docker 系列 10 终章】生产环境部署方案：从 Docker 到 K8s 的过渡准备

2025-08-07 09:00
阅读时长: 5 分钟

“我的项目用 Docker Compose 跑得很稳，直到有一天，服务器的主板烧了。那一刻我才明白，单机的完美，在硬件级灾难面前不堪一击。”

时间过得真快，这是我们《Docker 从入门到完全掌控》系列的第 10 篇文章，也是本系列的最终章。

回顾过去的旅程，我们从一行青涩的 docker run hello-world 开始，写出了定制化的 Dockerfile，攻克了 Volumes 的权限陷阱，理清了内部 Network 的迷宫，最后甚至用 GitHub Actions 打造了全自动的 CI/CD 工业级流水线。

对于一个百万日活以下的中小型项目，你现在的技术储备已经可以用“游刃有余”来形容。

但是，技术演进的脚步永远不会停止。当你的产品日活突破千万，当你从单台服务器扩展到拥有上百台服务器的机房时，单机的 Docker 会暴露出致命的缺陷。今天，我们将站上更高的山峰，俯瞰容器编排的终极霸主——Kubernetes (K8s)，并教你在跳入 K8s 之前，如何榨干 Docker 单机的最后一丝生产力。

一、盛世危言：Docker 单机部署的三大死穴

在单台服务器上使用 docker-compose up -d 部署，是小公司的最爱。但当业务增长到一定体量，这套方案会面临三大无法逾越的鸿沟：

  1. 单点故障（SPOF，Single Point of Failure）： 你把所有的鸡蛋（Web服务、Milvus 向量库、MySQL 数据库）都放在了一台 64 核 128G 的高配服务器上。如果这台服务器电源坏了、网线断了，你的产品将面临 100% 的不可用。
  2. 资源瓶颈与无法横向扩容： 双十一大促来了，你的 FastAPI 接口瞬间涌入几万个请求，CPU 狂飙到 100%。在单机时代，你只能咬牙花几倍的价格去升级服务器硬件（纵向扩容）。你无法做到“临时拉 10 台便宜的机器过来共同分担请求”（横向扩容）。
  3. 做不到真正的“零宕机发布”： 虽然我们在 CI/CD 中使用了重拉镜像，但在新容器启动、旧容器销毁的那几秒钟里，如果有用户发起请求，依然会看到 502 Bad Gateway。

我们需要一个更强大的“上帝”，来管理一堆服务器（集群），而不仅仅是管理一台服务器上的几个容器。

二、降维打击：为什么 Kubernetes (K8s) 是终极答案？

Kubernetes（简称 K8s）是由 Google 开源的容器集群管理系统。

如果说 Docker Compose 是一个小乐队的指挥家（指挥一台电脑上的几个容器协调工作），那么 K8s 就是一家全球性的演艺经纪公司（指挥几百台电脑上的几万个容器同时工作）。

当你把 Docker 架构迁移到 K8s 后，世界会变成这样：

  • 自动容灾恢复：你告诉 K8s “我需要 5 个后端容器同时活着”。如果其中 1 台服务器突然断电爆炸，K8s 会瞬间感知到，并在另外 4 台健康的服务器上自动再启动新的容器，补齐 5 个的数量。用户完全无感。
  • 极致的负载均衡：用户的请求来到 K8s，K8s 会自动根据每台服务器的 CPU 闲忙程度，把请求分发给最轻松的那台机器。
  • 无感知的滚动更新：发布新版本时，K8s 会先启动 1 个 V2 版本的容器，确认它能正常工作后，再杀掉 1 个 V1 版本的容器。如此交替循环，实现真正的 零秒宕机（Zero-downtime）更新。

三、在跳进 K8s 前：Docker 的生产级“保命”配置

K8s 虽然美好，但它的学习曲线极其陡峭，维护成本极高（业界戏称 K8s = 烧钱）。 如果你公司目前只有 1-2 台服务器，强行上 K8s 纯属“大炮打蚊子”。

在我们还没准备好全面拥抱 K8s 之前，如何让目前的 Docker Compose 架构达到生产级的稳定性？ 请务必在你的 docker-compose.yml 中加上这三大保命配置：

1. 资源限制：防止“同归于尽”

如果你的应用存在内存泄漏，或者你的向量数据库吃光了所有 CPU，会导致同一台机器上的其他容器全部卡死。 必须给每个服务加上“紧箍咒”：

services:
  web_api:
    image: my-fastapi:latest
    deploy:
      resources:
        limits:
          cpus: '2.0'       # 最多只能使用 2 个 CPU 核心
          memory: 2G        # 内存绝对不能超过 2GB，超了直接被 OOM 杀掉
        reservations:
          cpus: '0.5'
          memory: 512M

2. 日志切割：防止“磁盘爆炸”

这是无数新手甚至老鸟都会踩的坑！Docker 默认会把容器的标准输出一直存入宿主机的 JSON 文件中。如果你的程序每天打印海量日志，几个月后，/var/lib/docker 会被一个高达 50GB 的日志文件塞满，导致整个系统磁盘 100% 崩溃宕机。 必须配置日志轮转：

services:
  web_api:
    image: my-fastapi:latest
    logging:
      driver: "json-file"
      options:
        max-size: "100m"  # 每个日志文件最大 100MB
        max-file: "5"     # 最多保留最新的 5 个文件，旧的自动删除

3. 重启策略：打不死的小强

程序因为 Unhandled Exception 崩溃退出怎么办？让 Docker 自动把它拉起来：

services:
  web_api:
    image: my-fastapi:latest
    # 除非是我手动敲了 docker stop 让你停，否则哪怕机器重启了、程序报错了，你都要自动拉起
    restart: unless-stopped

四、未来展望：普通人该如何走向云原生？

如果你已经按捺不住对集群和 K8s 的向往，想要规划未来的技术演进，我给你三个阶段的建议：

  1. 第一阶段：夯实 Docker Compose（现在） 确保你的业务代码是无状态的（Stateless）。任何上传的文件都存入对象存储（如 MinIO / 阿里云 OSS），所有数据写入独立的数据库服务。这样你的后端容器才可以随时被毁灭、随时被克隆。
  2. 第二阶段：尝试轻量级集群（K3s 或 Docker Swarm） 当你有 2~3 台服务器，想要把它们连成一片时。不要去碰原生 K8s！先试试 Docker 自带的 Docker Swarm，或者 Rancher 出品的轻量级 K8s 发行版 —— K3s。它们的用法和理念与 K8s 极其相似，但安装只需要 5 分钟。
  3. 第三阶段：全面拥抱托管云原生（云厂商 ACK/TKE） 当业务真正达到爆发期，永远不要自己去安装和维护原生的 Kubernetes 集群底座（那需要专门的底层运维团队）。直接花钱使用阿里云的 ACK、腾讯云的 TKE 或 AWS 的 EKS。你只需要关心如何写 Deployment 配置文件，把集群的稳定性交给云厂商的顶级专家。

全系列结语

敲下这行字的时候，这个包含了 10 篇文章的连载也迎来了尾声。

回忆初衷，我们常常被繁杂的环境配置折磨得痛不欲生。而 Docker 的出现，就像是在混沌的软件工程世界中，建立了一套精密的“标准化物流系统”。

  • 我们用 Dockerfile 定义了集装箱的制造工艺。
  • 用 Volumes 保留了弥足珍贵的货物。
  • 用 Networks 修建了集装箱之间的通讯桥梁。
  • 用 Docker Compose 画出了整个港口的调度蓝图。
  • 最后，用 GitHub Actions 让整个港口实现了全自动化运转。

技术终有更迭，但工程师解决问题、将复杂事物标准化的工程思维永不过时。

docker logs -f my_container
