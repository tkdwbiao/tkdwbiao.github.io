【Docker 系列 09】解放双手：结合 GitHub Actions 实现自动化构建与推流

2025-07-31 09:00
阅读时长: 5 分钟

“每天下班前，我都要敲一遍：docker build、docker push，然后 SSH 登录服务器，敲 docker pull，最后 docker compose up -d。整套动作行云流水，但我感觉自己像个流水线上的机器。”

在前面的 8 篇文章中，我们彻底攻克了 Docker 的各项核心技术，甚至能在遇到极其诡异的报错时（如权限崩溃、网络隔离）从容排障。

现在，你已经可以用 Docker 完美运行任何复杂架构了。但是，随着项目的高频迭代（比如你正在开发的“智能 OnCall 项目”，一天可能要修改十几处 Prompt 提示词和逻辑），手动打包、上传、下载、重启的噩梦开始了。

“能不能让我只要敲一个 git push 把代码提交到仓库，服务器就能自动帮我把新代码打包成 Docker 镜像，并自动重启上线？”

能！这就是现代软件工程的最高奥义：CI/CD（持续集成与持续部署）。 今天，我们就来请一位免费且不知疲倦的机器人管家 —— GitHub Actions，彻底解放你的双手。

一、什么是 CI/CD 与 GitHub Actions？

  • CI（Continuous Integration，持续集成）：代码推送到远程仓库后，自动触发编译、测试和打包 Docker 镜像的过程。
  • CD（Continuous Deployment，持续部署）：将打包好的镜像，自动发布到目标服务器并运行起来。

以前做 CI/CD，你需要专门买一台服务器去搭建庞大复杂的 Jenkins。而现在，微软收购 GitHub 后，直接在代码仓库里集成了免费的自动化流水线工具 —— GitHub Actions。

只要你在代码仓库里放一份特定的 YAML 剧本文件，一旦有代码 push 上来，GitHub 就会免费分配一台云端服务器（Runner）给你，按照剧本帮你执行那些枯燥的命令。

二、战前准备：配置安全机密（Secrets）

既然要让 GitHub 替你干活，它就需要有登录你 Docker 镜像仓库的账号密码，以及登录你生产服务器的 SSH 密钥。 但千万记住我们在第 6 篇说过的：绝对不能把密码明文写在代码里！

我们需要用到 GitHub 的机密保险箱：

  1. 打开你的 GitHub 仓库主页。
  2. 进入 Settings -> 左侧菜单栏展开 Secrets and variables -> 点击 Actions。
  3. 点击 New repository secret，依次添加以下三个机密：
    • DOCKERHUB_USERNAME：你的 Docker Hub 账号名（或者阿里云镜像库账号）。
    • DOCKERHUB_TOKEN：你的 Docker Hub 密码（建议生成 Access Token）。
    • SERVER_SSH_KEY：你服务器的 SSH 私钥（用于 CD 远程登录部署）。
    • SERVER_HOST：你的服务器外网 IP。

装好保险箱后，我们就可以开始写自动化剧本了。

三、实战演练：编写自动化流转剧本

在你的项目根目录下，创建一个特殊的文件夹层级：.github/workflows/，并在里面新建一个名为 docker-publish.yml 的文件。

当我们敲下 git push 时，GitHub Actions 就会自动读取这个剧本并执行。

阶段一：自动构建并推流镜像 (CI)

我们先来写剧本的前半部分，让它自动打包我们的 FastAPI 镜像并推送到 Docker Hub。

# .github/workflows/docker-publish.yml
name: Build and Deploy to Server

# 触发条件：当主分支（main）有代码 push 时触发
on:
  push:
    branches:
      - main

jobs:
  # 任务1：构建并推流 (CI)
  build-and-push:
    runs-on: ubuntu-latest # GitHub 免费提供一台 Ubuntu 服务器来干活
    
    steps:
      # 步骤1：把你的代码拉取到这台临时服务器上
      - name: Check out the repo
        uses: actions/checkout@v3

      # 步骤2：登录到 Docker Hub
      - name: Log in to Docker Hub
        uses: docker/login-action@v2
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      # 步骤3：设置 Docker 镜像构建器
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v2

      # 步骤4：构建镜像并推送到 Docker Hub
      - name: Build and push
        uses: docker/build-push-action@v4
        with:
          context: .  # 使用项目根目录的 Dockerfile
          push: true
          # 动态打标签：以你的 GitHub 账户名/项目名:latest 为名
          tags: ${{ secrets.DOCKERHUB_USERNAME }}/my-smart-oncall-api:latest

发生了什么？ 只要你把这段代码 git push 上去，打开 GitHub 仓库的 Actions 标签页，你会看到一个绿色的进度条在转。等它跑完，去你的 Docker Hub 主页看看，新鲜出炉的 Docker 镜像已经被自动上传上去了！

阶段二：自动远程重启服务 (CD)

镜像虽然做好了，但服务器上的容器还是旧版本。我们需要让 Actions 继续“顺着网线”爬进你的服务器，敲下重启命令。

在上面的剧本末尾，紧接着加上第二个 Job：

  # 任务2：部署到服务器 (CD)
  deploy:
    # 告诉 GitHub，必须等 build-and-push 任务成功后，才执行这步
    needs: build-and-push 
    runs-on: ubuntu-latest

    steps:
      # 使用别人写好的 SSH 插件远程执行命令
      - name: Execute remote ssh commands
        uses: appleboy/ssh-action@v0.1.10
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: root # 你服务器的用户名，建议也放进 secrets
          key: ${{ secrets.SERVER_SSH_KEY }}
          script: |
            # 这里的命令就是在你服务器上执行的
            cd /data/smart-oncall-project
            
            # 拉取刚刚制作好的最新镜像
            docker compose pull
            
            # 重启容器，-d 后台运行，--remove-orphans 清理旧容器
            docker compose up -d --remove-orphans
            
            # (可选) 清理被淘汰下来的旧镜像垃圾
            docker image prune -f

四、体验魔法的时刻

现在，你的 CI/CD 流水线彻底打通了。我们来体验一下现代 DevOps 的丝滑：

  1. 你在本地用 VS Code 修改了一行业务逻辑代码（比如修复了一个 Bug）。
  2. 在终端敲击：
    1
2
3

    git add .
git commit -m "fix: 修复了查询 CPU 指标的一个 Bug"
git push
  3. 然后，你可以去喝杯咖啡了。
  4. 几分钟后，你刷新生产环境的网页，Bug 已经被修复。

你不需要再开终端，不需要等待无聊的构建过程，不需要担心手动部署时敲错 docker-compose 的参数。一切复杂性，都在那一份 YAML 文件中被消解于无形。

结语

从第一篇敲下 docker run hello-world，到今天利用 CI/CD 流水线全自动更新包含大模型向量库的复杂微服务，你已经跨越了一个现代后端开发者的全部必经之路。

你现在所掌握的技术栈：Docker + Docker Compose + GitHub Actions，已经完全能够支撑起百万日活以下的创业级项目，能够让小团队以极高的效率迭代交付。

但是，这就到终点了吗？

设想一个场景： 你的 AI 产品突然爆火，一台服务器的内存根本扛不住 Milvus 暴增的查询量和 FastAPI 的并发。你需要增加 10 台服务器来共同分担压力。 在这个集群里：

  • 如果一台服务器突然断电宕机了怎么办？
  • 怎么让用户的请求自动负载均衡到比较闲的那几台机器上？
  • 怎么保证在更新服务时，用户完全感觉不到停机（零宕机发布）？

在面对多机集群（Cluster）这个怪兽时，我们一直引以为傲的 docker-compose 显得像个玩具一样力不从心。我们需要一个真正的“集群大脑”。
