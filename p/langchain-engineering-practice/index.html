LangChain 工程化实践：从 Demo 到可维护项目

2025-10-15 10:00
阅读时长: 12 分钟

前面二十多篇文章里，我们已经从最基础的 LLM 调用，一路讲到了 RAG、Agent、Tool Calling 和 LangGraph。

这些内容让我们能写出很多 demo：

1
2
3
4

Prompt -> Model -> Parser
Question -> Retriever -> Prompt -> Model
Agent -> Tools -> Final Answer
LangGraph -> State -> Node -> Edge

但真实项目和 demo 最大的区别，不在于是否能跑通，而在于是否能长期维护。

这一篇我们专门聊 LangChain 应用的工程化实践：如何从一个能跑的 demo，走向一个结构清晰、配置可控、可测试、可观测、可扩展的项目。

一、前言

很多 LangChain 学习项目一开始都是一个文件：

1

main.py

里面可能写了：

  • API Key。
  • Prompt。
  • Model 初始化。
  • Retriever 构建。
  • Chain 组合。
  • Agent 工具。
  • 命令行输入。
  • 调试打印。

这种写法适合学习。

因为你能在一个文件里看到完整流程。

但只要项目稍微变复杂，就会遇到问题：

  • Prompt 散落在代码里，改起来很乱。
  • 模型配置写死，切换环境麻烦。
  • RAG 索引构建和在线查询混在一起。
  • 工具函数没有边界，越来越像“万能函数”。
  • 出错时不知道是检索错、Prompt 错、模型错还是工具错。
  • 没有日志，线上问题无法复盘。
  • 没有测试，每次改 Prompt 都靠手动试。
  • 没有清晰目录结构，新人看不懂。

工程化不是为了把项目弄复杂。

工程化的目标是：

让大模型应用在变复杂后仍然可理解、可修改、可调试、可交付。

本文会重点讲：

  1. Demo 和工程项目的区别。
  2. 一个 LangChain 项目应该如何组织目录。
  3. 如何管理配置和环境变量。
  4. 如何管理 Prompt。
  5. 如何拆分 Model、Chain、Retriever、Tool 和 Agent。
  6. RAG 项目如何区分离线索引和在线查询。
  7. 如何做日志、错误处理和观测。
  8. 如何测试 LangChain 应用。
  9. 从脚本到 API 服务需要注意什么。
  10. 常见工程化误区和最佳实践。

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

load_dotenv()

model = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
)

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个专业助手。"),
    ("human", "请解释：{topic}"),
])

chain = prompt | model | StrOutputParser()

print(chain.invoke({"topic": "LangChain"}))

这段代码很好。

它适合教学，也适合验证想法。

但如果它变成一个真实服务，就会出现很多新需求：

  • 不同环境用不同模型。
  • Prompt 需要版本管理。
  • 用户输入需要校验。
  • 模型调用失败要重试或返回友好错误。
  • 每次请求要记录 request_id。
  • 要知道消耗了多少 token。
  • 要能排查检索结果是否正确。
  • 要有自动化测试。
  • 要能部署到服务器。

这些都不是 demo 代码自然具备的能力。

所以从 demo 到项目，本质上是从“验证能不能做”变成“保证长期能运行”。

import os
from dataclasses import dataclass
from dotenv import load_dotenv

load_dotenv()


@dataclass(frozen=True)
class Settings:
    openai_api_key: str | None = os.getenv("OPENAI_API_KEY")
    openai_base_url: str | None = os.getenv("OPENAI_BASE_URL") or None
    model_name: str = os.getenv("MODEL_NAME", "gpt-4o-mini")
    embedding_model: str = os.getenv("EMBEDDING_MODEL", "text-embedding-3-small")
    chroma_persist_dir: str = os.getenv("CHROMA_PERSIST_DIR", "data/chroma_db")
    retrieval_k: int = int(os.getenv("RETRIEVAL_K", "3"))
    debug: bool = os.getenv("DEBUG", "false").lower() == "true"


settings = Settings()

from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from app.config import settings


def create_chat_model(temperature: float = 0.2):
    return ChatOpenAI(
        model=settings.model_name,
        api_key=settings.openai_api_key,
        base_url=settings.openai_base_url,
        temperature=temperature,
    )


def create_embedding_model():
    return OpenAIEmbeddings(
        model=settings.embedding_model,
        api_key=settings.openai_api_key,
        base_url=settings.openai_base_url,
    )

后续如果要切换模型供应商、增加 timeout、设置 max_tokens，就只改一个地方。

model = create_chat_model(temperature=0)

def assistant_system_prompt() -> str:
    return """
你是一个企业智能助手，可以帮助用户查询订单、检索知识库和完成简单计算。

规则：

from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough
from app.models import create_chat_model
from app.prompts.qa import create_rag_prompt


def format_docs(docs):
    return "\n\n".join(
        f"来源：{doc.metadata.get('source', 'unknown')}\n{doc.page_content}"
        for doc in docs
    )


def create_rag_chain(retriever):
    prompt = create_rag_prompt()
    model = create_chat_model(temperature=0.2)

    return (
        {
            "context": retriever | format_docs,
            "question": RunnablePassthrough(),
        }
        | prompt
        | model
        | StrOutputParser()
    )

调用方只需要：

1
2

chain = create_rag_chain(retriever)
answer = chain.invoke("RAG 是什么？")

这让 Chain 的构建逻辑和业务调用逻辑分开。

八、RAG：离线索引和在线查询分离

RAG 项目里，一个非常重要的工程化原则是：

构建索引和在线查询分开。

不要在用户每次提问时都执行：

1

加载文档 -> 切分文档 -> 生成 Embedding -> 写入向量库

这是离线流程。

1

from langchain_community.document_loaders import DirectoryLoader, TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_chroma import Chroma
from app.models import create_embedding_model
from app.config import settings


def main():
    loader = DirectoryLoader(
        "data/docs",
        glob="**/*.md",
        loader_cls=TextLoader,
        loader_kwargs={"encoding": "utf-8"},
    )

    docs = loader.load()

    splitter = RecursiveCharacterTextSplitter(
        chunk_size=600,
        chunk_overlap=100,
        separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
    )

    chunks = splitter.split_documents(docs)

    Chroma.from_documents(
        documents=chunks,
        embedding=create_embedding_model(),
        persist_directory=settings.chroma_persist_dir,
    )

    print("索引构建完成")


if __name__ == "__main__":
    main()

from langchain_chroma import Chroma
from app.config import settings
from app.models import create_embedding_model


def load_vectorstore():
    return Chroma(
        persist_directory=settings.chroma_persist_dir,
        embedding_function=create_embedding_model(),
    )


def create_retriever():
    vectorstore = load_vectorstore()
    return vectorstore.as_retriever(
        search_kwargs={"k": settings.retrieval_k}
    )

from langchain_core.tools import tool


@tool
def get_order_status(order_id: str) -> dict:
    """Get order status, shipping company, and tracking number by order id."""
    order_id = str(order_id).strip()

    if not order_id:
        return {"success": False, "error": "订单号不能为空"}

    return {
        "success": True,
        "order_id": order_id,
        "status": "已发货",
        "shipping_company": "顺丰",
        "tracking_no": "SF123456",
    }

工具设计要注意：

  • 名称清楚。
  • 描述清楚。
  • 参数结构化。
  • 返回值稳定。
  • 内部做参数校验。
  • 不返回敏感字段。
  • 高风险动作加确认。

不要写万能工具：

1
2
3

@tool
def business_api(action: str, payload: dict):
    ...

这种工具让模型承担太多决策，容易出错。

from langchain.agents import create_agent
from app.models import create_chat_model
from app.prompts.agent import assistant_system_prompt
from app.tools.order_tools import get_order_status


def create_assistant_agent(extra_tools=None):
    tools = [get_order_status]

    if extra_tools:
        tools.extend(extra_tools)

    return create_agent(
        model=create_chat_model(temperature=0),
        tools=tools,
        system_prompt=assistant_system_prompt(),
    )

这样业务层不需要知道 Agent 具体怎么创建。

十一、Service 层：把 LangChain 细节藏起来

真实项目里，API 层最好不要直接操作 Chain 或 Agent 的内部细节。

from app.retrievers.vectorstore import create_retriever
from app.chains.rag_chain import create_rag_chain


class ChatService:
    def __init__(self):
        self.retriever = create_retriever()
        self.rag_chain = create_rag_chain(self.retriever)

    def answer_question(self, question: str) -> dict:
        answer = self.rag_chain.invoke(question)

        return {
            "answer": answer,
        }

API 层调用：

1

chat_service = ChatService()

Service 层的价值是：

  • 封装 LangChain 细节。
  • 统一输入输出。
  • 便于测试。
  • 便于替换底层实现。
  • API 层更干净。

from pydantic import BaseModel
from fastapi import FastAPI
from app.services.chat_service import ChatService

app = FastAPI()
chat_service = ChatService()


class ChatRequest(BaseModel):
    question: str


class ChatResponse(BaseModel):
    answer: str


@app.post("/chat", response_model=ChatResponse)
def chat(request: ChatRequest):
    result = chat_service.answer_question(request.question)
    return ChatResponse(answer=result["answer"])

十三、日志和调试

大模型应用一定要记录关键日志。

不要只打印最终答案。

至少记录：

  • request_id。
  • 用户问题。
  • 使用的模型。
  • 检索到的文档 metadata。
  • 工具调用名称和参数。
  • 工具返回摘要。
  • 最终回答。
  • 耗时。
  • 错误信息。

可以先用 Python logging：

十四、错误处理

LangChain 应用可能在很多地方出错：

  • API Key 不存在。
  • 模型服务超时。
  • 模型返回格式不符合预期。
  • 向量库目录不存在。
  • Retriever 返回空结果。
  • 工具调用参数错误。
  • 外部 API 失败。

错误处理不要一股脑吞掉。

例如工具可以返回明确错误：

十五、测试：不只是测代码能跑

LangChain 项目的测试可以分几层。

1. 工具函数测试

工具函数最适合写单元测试。

1
2
3

def test_get_order_status_empty_order_id():
    result = get_order_status.invoke({"order_id": ""})
    assert result["success"] is False

工具是系统边界，必须稳定。

2. Prompt 变量测试

至少确认 Prompt 需要的变量和 Chain 传入变量一致。

    prompt = create_rag_prompt()
    assert "context" in prompt.input_variables
    assert "question" in prompt.input_variables

准备小型测试文档，确认关键问题能召回正确来源。

    sources = [doc.metadata.get("source", "") for doc in docs]

4. Chain 集成测试

可以对固定输入检查输出包含关键字。

5. 评估集

对于 RAG 和 Agent，最好准备评估问题集。

例如：

问题期望行为
RAG 是什么召回 RAG 文档并回答
一线城市住宿标准召回报销制度
订单 1001 状态调用订单工具
天气怎么样不应胡答知识库没有的内容

这比随手问几个问题更可靠。

十六、Prompt 版本管理

Prompt 会不断调整。

建议记录：

  • 修改了什么。
  • 为什么修改。
  • 影响哪些场景。
  • 是否通过评估集。

简单项目可以用 Git 管理 Prompt 文件。

复杂项目可以引入 Prompt registry 或 LangSmith 之类的工具。

关键是不要让 Prompt 变成没人敢改的黑盒。

十七、观测与 LangSmith

当项目进入真实使用后，只靠本地日志不够。

你需要知道：

  • 每一步调用耗时多少。
  • 模型输入输出是什么。
  • Retriever 返回了哪些文档。
  • Agent 调用了哪些工具。
  • 哪些请求失败了。
  • token 消耗如何。

LangSmith 可以帮助追踪 LangChain 应用的运行过程。

后面我们会专门写一篇 LangSmith 入门。

这里先记住一个原则：

大模型应用的调试对象不是一行输出，而是一条链路。

链路里每一步都可能出问题。

十九、常见工程化误区

1. 一个文件写到底

学习阶段没问题。

项目阶段要拆分边界。

2. 一开始就过度架构

也不要反过来，一开始就设计复杂框架。

先按真实复杂度演进。

3. Prompt 和代码混在一起

Prompt 是核心资产，应该清晰管理。

4. 每次请求都重建向量库

这是 RAG 初学者常见错误。

索引构建和在线查询要分离。

5. 只看最终回答

RAG 要看检索结果。

Agent 要看工具调用。

LangGraph 要看节点状态。

6. 把权限交给 Prompt

Prompt 不能作为安全边界。

权限必须在系统和工具层控制。

7. 没有评估集

靠感觉调 Prompt 和 Retriever，很容易越调越乱。

1. 从清晰目录结构开始

2. 配置集中管理

不要到处读取环境变量。

3. Prompt 单独管理

方便审查、测试和迭代。

4. RAG 离线和在线分离

索引构建是离线流程。

用户问答是在线流程。

5. 工具要小而明确

一个工具做一件事。

返回结构稳定。

6. 增加调试脚本

例如：

1
2

debug_retrieval.py
debug_agent_tools.py

调试脚本比临时 print 更可复用。

7. 建立最小评估集

哪怕只有 20 个问题，也比靠感觉强。

8. 记录链路日志

模型、检索、工具、最终回答都要能追踪。

9. 安全边界写在工具和服务里

不要依赖模型自觉。

10. 逐步引入 LangGraph 和 LangSmith

当流程复杂时，用 LangGraph 编排。

当链路需要观测时，用 LangSmith 追踪。

二十一、总结

本文我们从工程化角度梳理了 LangChain 应用如何从 demo 走向可维护项目。

核心结论是：

LangChain 工程化不是堆目录和框架，而是把配置、模型、Prompt、Chain、Retriever、Tool、Agent、服务、测试和观测这些边界拆清楚，让系统在复杂后仍然可维护。

本文重点包括：

  • Demo 关注跑通，工程项目关注长期维护。
  • 推荐用清晰目录拆分配置、模型、Prompt、Chain、Retriever、Tool、Agent 和 Service。
  • 配置要集中管理，API Key 不要写死。
  • Prompt 是核心资产，应该单独管理和版本化。
  • RAG 项目必须区分离线索引构建和在线查询。
  • Tool 要有明确职责、结构化参数、稳定返回和安全校验。
  • API 层要隐藏 LangChain 内部细节，提供稳定输入输出。
  • 日志、错误处理、测试和评估集是项目可靠性的基础。
  • 权限和安全不能交给 Prompt，必须在系统边界控制。

到这里，我们已经开始从“会写 LangChain demo”进入“能维护 LangChain 项目”的阶段。
