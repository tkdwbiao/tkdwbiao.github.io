大模型时代的数据采集工程 13：限速、重试与任务调度

2026-01-04 10:00
阅读时长: 14 分钟

上一篇文章里，我们分析了常见反爬策略。

其中反复出现几个关键词：

1
2
3
4
5
6
7

429。
Retry-After。
访问频率。
失败重试。
错误阈值。
任务暂停。
审计日志。

这些不是零散细节。

它们共同指向一个问题：

一个爬虫系统不能只会发请求，还必须能控制节奏、处理失败、恢复任务、记录过程。

很多爬虫脚本的问题不是“爬不到”。

而是：

1
2
3
4
5
6
7
8

一失败就无限重试。
一启动就打满并发。
没有限速。
没有任务状态。
没有失败队列。
没有暂停机制。
没有日志。
出问题后不知道发生了什么。

这一篇，我们就来讲：

如何从工程角度设计限速、重试与任务调度，让数据采集系统更稳定、低影响、可恢复、可审计。

一、前言

最简单的爬虫可能是这样的：

urls = ["https://example.com/page/1", "https://example.com/page/2"]

for url in urls:
    response = requests.get(url)
    print(response.status_code, response.text[:100])

这个脚本可以帮助入门。

但真实项目里很快会遇到问题：

某些 URL 超时。
某些页面返回 500。
请求太快触发 429。
登录态过期返回 401。
页面改版导致解析失败。
任务跑到一半程序退出。
重复运行导致重复采集。
失败原因没有记录。

如果没有调度系统，这些问题会变成：

1
2
3
4
5
6

人工补跑。
重复采集。
数据缺失。
错误放大。
目标系统压力升高。
排查困难。

所以工程化爬虫一定要从“循环请求 URL”升级为“任务系统”。

任务系统至少要回答：

1

哪些任务待执行？
哪些任务正在执行？
哪些任务成功了？
哪些任务失败了？
失败是否可以重试？
什么时候重试？
重试几次后停止？
是否触发限流或风控，需要暂停？
任务执行过程是否可追溯？

这就是本文的核心。

二、限速、重试和调度分别解决什么？

先把三个概念分清楚。

1. 限速

限速解决的是：

1
2
3
4

请求不要太快。
并发不要太高。
不要对目标系统造成过大压力。
不要把错误放大。

常见控制方式：

1
2
3
4
5

每秒最多 N 个请求。
每个数据源单独限制 QPS。
每个账号设置最小操作间隔。
遇到 429 后暂停一段时间。
不同任务优先级不同。

2. 重试

重试解决的是：

1
2
3

临时失败可以恢复。
网络波动不影响整体任务。
服务端短暂异常可以稍后再试。

但重试必须有边界。

不能无限重试。

适合重试的错误：

1
2
3
4

网络抖动。
连接超时。
临时 500 / 502 / 503 / 504。
短暂的资源不可用。

不适合盲目重试的错误：

1
2
3
4
5
6

401 未授权。
403 权限不足。
429 限流。
验证码或风险提示。
字段权限不足。
明确的参数错误。

3. 任务调度

调度解决的是：

1
2
3
4
5
6

任务从哪里来。
什么时候执行。
失败后去哪。
成功后如何记录。
如何恢复未完成任务。
如何控制优先级和状态。

调度系统把采集从“一次性脚本”变成“可持续运行的工程系统”。

from enum import Enum


class FailureType(str, Enum):
    NETWORK_ERROR = "network_error"
    TIMEOUT = "timeout"
    SERVER_ERROR = "server_error"
    RATE_LIMITED = "rate_limited"
    AUTH_REQUIRED = "auth_required"

    PARSE_ERROR = "parse_error"
    UNKNOWN = "unknown"

不同失败类型对应不同策略。

失败类型是否重试建议处理
NETWORK_ERROR可以指数退避后重试

from dataclasses import dataclass


@dataclass
class RetryDecision:
    failure_type: FailureType | None
    should_retry: bool
    should_pause: bool
    reason: str


def classify_status_code(status_code: int) -> RetryDecision:
    if status_code == 429:
        return RetryDecision(FailureType.RATE_LIMITED, False, True, "rate_limited")
    if status_code == 401:
        return RetryDecision(FailureType.AUTH_REQUIRED, False, True, "auth_required")
    if status_code == 403:
        return RetryDecision(FailureType.PERMISSION_DENIED, False, True, "permission_denied")
    if status_code in {500, 502, 503, 504}:
        return RetryDecision(FailureType.SERVER_ERROR, True, False, "server_error")
    if 200 <= status_code < 300:
        return RetryDecision(None, False, False, "ok")
    return RetryDecision(FailureType.UNKNOWN, False, False, "unknown_status")

这段代码最重要的思想是：

1
2

不是所有失败都应该重试。
涉及授权、权限、限流和风控时，要暂停或人工确认。

五、指数退避

如果失败可以重试，也不能立刻连续重试。

更合理的是指数退避。

例如：

1
2
3

第 1 次失败：5 秒后重试。
第 2 次失败：10 秒后重试。
第 3 次失败：20 秒后重试。

可以加一点随机抖动，避免大量任务同时重试。

import random


def calculate_backoff_seconds(
    retry_count: int,
    base_seconds: float = 5.0,
    max_seconds: float = 300.0,
    jitter_seconds: float = 2.0,
) -> float:
    delay = base_seconds * (2 ** max(0, retry_count - 1))
    delay = min(delay, max_seconds)
    jitter = random.uniform(0, jitter_seconds)
    return delay + jitter


for retry_count in range(1, 5):
    print(retry_count, calculate_backoff_seconds(retry_count))

指数退避的作用是：

1
2
3
4

给目标系统恢复时间。
避免错误瞬间放大。
降低大量任务同时重试的冲击。
让系统更平滑。

但注意：

1
2

退避不是绕过限流。
遇到明确限流、权限不足或风险提示时，应暂停任务。

import time
from email.utils import parsedate_to_datetime


def parse_retry_after(value: str | None) -> float | None:
    if not value:
        return None

    if value.isdigit():
        return float(value)

    try:
        retry_time = parsedate_to_datetime(value)
        return max(0.0, retry_time.timestamp() - time.time())
    except (TypeError, ValueError):
        return None

import time


class TokenBucket:
    def __init__(self, rate: float, capacity: int) -> None:
        self.rate = rate
        self.capacity = capacity
        self.tokens = float(capacity)
        self.updated_at = time.monotonic()

    def acquire(self) -> None:
        while True:
            now = time.monotonic()
            elapsed = now - self.updated_at
            self.updated_at = now
            self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)

            if self.tokens >= 1:
                self.tokens -= 1
                return

            wait_seconds = (1 - self.tokens) / self.rate
            time.sleep(wait_seconds)

使用：

1
2
3
4
5

bucket = TokenBucket(rate=1.0, capacity=3)

for index in range(10):
    bucket.acquire()
    print(time.strftime("%H:%M:%S"), "request", index)

含义是：

1
2

平均每秒 1 个请求。
允许短时间最多积累 3 个令牌。

真实系统中，通常要按数据源限速。

1
2
3
4
5
6

    "source_b": TokenBucket(rate=0.2, capacity=1),
}

这样可以避免一个数据源影响另一个数据源。

from datetime import datetime, timedelta


def reschedule_task(task: ScheduledTask) -> ScheduledTask:
    retry_count = task.retry_count + 1
    delay = calculate_backoff_seconds(retry_count)

    return ScheduledTask(
        next_run_at=datetime.now() + timedelta(seconds=delay),
        priority=task.priority,
        task_id=task.task_id,
        url=task.url,
        retry_count=retry_count,
    )

如果超过最大重试次数，就不要再入队。

def make_dedup_key(source: str, url: str) -> str:
    raw = f"{source}:{url}".encode("utf-8")

    url: str = field(compare=False)
    retry_count: int = field(default=0, compare=False)
    status: TaskStatus = field(default=TaskStatus.PENDING, compare=False)
    last_error: str | None = field(default=None, compare=False)


class TokenBucket:
    def __init__(self, rate: float, capacity: int) -> None:
        self.rate = rate
        self.capacity = capacity
        self.tokens = float(capacity)
        self.updated_at = time.monotonic()

    def acquire(self) -> None:
        while True:
            now = time.monotonic()
            elapsed = now - self.updated_at
            self.updated_at = now
            self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)

            if self.tokens >= 1:
                self.tokens -= 1
                return

            time.sleep((1 - self.tokens) / self.rate)


def backoff_seconds(retry_count: int) -> float:
    return min(60.0, 3.0 * (2 ** retry_count))


def fetch(url: str) -> tuple[bool, str]:
    try:
        response = requests.get(url, timeout=10)
    except requests.Timeout:
        return False, "timeout"
    except requests.RequestException as exc:
        return False, f"network_error:{exc.__class__.__name__}"

    if response.status_code == 429:
        return False, "rate_limited_pause"
    if response.status_code in {500, 502, 503, 504}:
        return False, f"server_error:{response.status_code}"
    if response.status_code != 200:
        return False, f"not_retryable:{response.status_code}"

    return True, "ok"


queue: list[Task] = []
now = datetime.now()

for index in range(1, 4):
    heapq.heappush(
        queue,
        Task(
            next_run_at=now,
            priority=10,
            task_id=f"task-{index}",
            url="https://example.com",
        ),
    )

bucket = TokenBucket(rate=0.5, capacity=1)
max_retries = 3

while queue:
    task = heapq.heappop(queue)

    if task.next_run_at > datetime.now():
        wait_seconds = (task.next_run_at - datetime.now()).total_seconds()
        time.sleep(max(0.0, wait_seconds))

    bucket.acquire()
    ok, reason = fetch(task.url)

    if ok:
        task.status = TaskStatus.SUCCEEDED
        print(task.task_id, task.status, reason)
        continue

    if reason.startswith("rate_limited") or reason.startswith("not_retryable"):
        task.status = TaskStatus.DEAD
        task.last_error = reason
        print(task.task_id, task.status, reason)
        continue

    task.retry_count += 1
    task.last_error = reason

    if task.retry_count > max_retries:
        task.status = TaskStatus.DEAD
        print(task.task_id, task.status, reason)
        continue

    task.status = TaskStatus.RETRYING
    task.next_run_at = datetime.now() + timedelta(seconds=backoff_seconds(task.retry_count))
    heapq.heappush(queue, task)
    print(task.task_id, task.status, reason, "retry", task.retry_count)

十七、常见错误写法

1. 无限重试

无限重试会导致：

1
2
3
4
5

请求风暴。
账号状态异常。
目标系统压力升高。
日志爆炸。
任务永远结束不了。

必须设置最大重试次数。

2. 所有错误都重试

401、403、429、风险提示不应该盲目重试。

它们通常需要暂停、降频、重新授权或人工确认。

3. 没有限速

没有限速的并发采集很容易失控。

应该按数据源、账号、任务类型分别限速。

4. 没有任务状态

只靠日志打印无法支撑恢复。

任务必须有状态字段。

5. 没有死信队列

失败任务如果没有出口，会在系统里反复循环。

死信队列可以把不可恢复任务沉淀下来，等待人工排查或规则修复。

6. 不做幂等

任务重试和恢复会带来重复执行。

结果写入必须考虑去重和唯一键。

十八、面试表达

如果面试官问：

1

爬虫遇到失败你怎么重试？

可以这样回答：

我不会对所有失败做统一重试，而是先分类。网络超时、临时 5xx 可以有限重试，并使用指数退避；429 表示限流，应该读取 Retry-After、暂停任务并降低频率；401 / 403 通常涉及登录态或权限，需要重新授权或人工确认；验证码、风险提示这类情况不应该自动对抗，而是暂停并记录。每个任务都有最大重试次数，超过后进入死信队列。

如果问：

1

你怎么做爬虫限速？

可以这样回答：

我会按数据源、账号或任务类型分别限速，而不是全局一个固定 sleep。简单场景可以用最小请求间隔，复杂一点可以用令牌桶控制平均 QPS 和突发容量。遇到 429 或错误率升高时，会动态降低频率或暂停对应数据源。限速的目标不是规避检测，而是降低对目标系统的影响，让任务稳定、可控、可审计。

如果问：

1

如何设计一个任务调度系统？

可以这样回答：

我会把 URL 抽象成任务，任务有 pending、running、succeeded、retrying、paused、dead 等状态，并记录 retry_count、max_retries、next_run_at、last_error。调度器按优先级和 next_run_at 取任务，执行前经过限速器，执行后根据失败类型决定成功、重试、暂停或进入死信队列。系统还要保证任务领取原子性、结果写入幂等，并记录成功率、失败率、重试数、429 数量、死信数等指标。

如果问：

1

LLM / Agent 在任务调度里有什么用？

可以这样回答：

LLM / Agent 可以辅助诊断调度异常，比如根据日志和指标判断是限流、登录态失效、页面改版、选择器失效还是服务端异常。它可以给出降频、暂停、重新授权、检查选择器或人工确认的建议，但不应该自动生成绕过风控或访问控制的策略。调度执行仍然要靠确定性规则，Agent 更适合做解释和辅助决策。

十九、总结

本文讲了限速、重试与任务调度的工程设计。

核心结论包括：

  • 爬虫系统不能只是循环请求 URL，还要有任务状态、限速、重试、暂停和审计能力。
  • 限速用于控制请求节奏，降低目标系统影响，避免任务失控。
  • 重试必须先做失败分类，不是所有错误都能重试。
  • 网络错误、超时和临时 5xx 可以有限重试，401 / 403 / 429 / 风险提示应暂停或人工确认。
  • 指数退避可以避免错误瞬间放大，Retry-After 应优先尊重。
  • 令牌桶可以用于按数据源控制 QPS 和突发请求。
  • 调度系统要管理任务状态、优先级、下一次执行时间、重试次数和失败原因。
  • 死信队列用于保存不可恢复任务，避免无限循环。
  • 任务重试和恢复会带来重复执行，结果写入必须考虑幂等和去重。
  • 监控指标能帮助发现限流、登录态失效、页面改版和数据源异常。
  • LLM / Agent 可以辅助诊断调度异常，但不能替代确定性规则和合规边界。
