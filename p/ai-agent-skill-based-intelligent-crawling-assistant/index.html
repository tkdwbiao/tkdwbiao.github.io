这一篇，我们把这些能力组合起来，做一个更完整的项目实战：基于 Skill 的智能爬虫助手。

它不是一个“自动抓全网”的工具。

而是一个面向自有系统、授权采集、公开文档整理和内部数据治理场景的智能数据采集助手。

它的目标是：

1

理解任务 → 选择 Skill → 抽取网页 → 校验结果 → 诊断异常 → 生成报告 → 支持人工复核。

这也是我们从“会写 Prompt”走向“会设计 Agent 系统”的关键一步。

一、项目目标：智能爬虫助手要解决什么问题

传统爬虫系统通常关注这些能力：

1
2
3
4
5
6

请求网页。
解析 HTML。
提取字段。
保存数据。
失败重试。
定时调度。

这些当然重要。

但在大模型和 Agent 时代，我们希望系统进一步具备：

1
2
3
4
5
6
7

能理解采集任务。
能根据任务选择合适能力。
能把网页抽成结构化数据。
能发现字段缺失和结构变化。
能诊断失败原因。
能生成可读报告。
能在高风险场景下要求人工复核。

这就是智能爬虫助手的定位。

它不是替代工程代码，而是把 LLM / Agent 放在合适的位置：

1
2
3
4
5

理解任务。
解释异常。
抽取半结构化信息。
生成诊断报告。
辅助人工复核。

而确定性动作仍然交给代码：

1
2
3
4
5
6

请求网页。
清洗 HTML。
校验 JSON。
写入数据库。
执行调度。
记录日志。

二、项目边界：先讲清楚什么不做

这个项目涉及爬虫和数据采集，所以必须先讲边界。

智能爬虫助手适合用于：

1
2
3
4
5
6

自有站点的数据整理。
内部系统页面结构化。
授权采集任务。
公开文档知识库构建。
测试环境中的采集流程验证。
爬虫日志诊断和稳定性分析。

不用于：

1
2
3
4
5
6

绕过第三方访问控制。
规避反爬或风控系统。
批量滥用公开服务。
采集隐私或敏感信息。
绕过登录、付费墙、验证码或速率限制。
隐藏自动化行为。

这不是形式主义。

因为 Skill 的能力越可复用，越要把使用范围写清楚。

在这个项目里，所有诊断建议都应该偏向：

1
2
3
4
5
6

降低频率。
尊重 Retry-After。
确认授权范围。
修复解析规则。
改善监控。
进入人工复核。

而不是“绕过限制”。

def receive_task(state: CrawlingAssistantState) -> CrawlingAssistantState:

        "task_id": state.get("task_id", "manual-task")

6.2 route_skill

负责选择 Skill。

def route_skill(state: CrawlingAssistantState) -> CrawlingAssistantState:
    text = state.get("user_input", "")
    selected = []

    if "抽取" in text or "网页" in text or "HTML" in text:
        selected.append("webpage-schema-extraction-skill")

    if "失败" in text or "诊断" in text or "报错" in text:
        selected.append("crawler-diagnosis-skill")

    return {"selected_skills": selected}

真实系统里，这里可以换成 LLM Router 或 embedding Router。

def clean_html(state: CrawlingAssistantState) -> CrawlingAssistantState:

def validate_result(state: CrawlingAssistantState) -> CrawlingAssistantState:
    result = state.get("extraction_result", {})
    errors = []

    if not result.get("title"):
        errors.append("missing title")
    if not result.get("content"):
        errors.append("missing content")

    return {
        "validation_errors": errors,
        "extraction_valid": not errors
    }

真实项目里应该用 JSON Schema 校验。

def diagnose_failure(state: CrawlingAssistantState) -> CrawlingAssistantState:
    errors = state.get("validation_errors", [])
    report = {
        "error_type": "empty_result",
        "risk_level": "low",
        "evidence": errors,
        "possible_causes": ["The page structure may not contain required fields"],
        "recommended_actions": ["Check the HTML structure and extraction schema"],
        "needs_manual_review": False
    }
    return {
        "diagnosis_report": report,
        "risk_level": report["risk_level"],
        "needs_manual_review": report["needs_manual_review"]
    }

from langgraph.graph import END, StateGraph


graph = StateGraph(CrawlingAssistantState)

graph.add_node("receive_task", receive_task)
graph.add_node("route_skill", route_skill)
graph.add_node("fetch_or_read_page", fetch_or_read_page)
graph.add_node("clean_html", clean_html)
graph.add_node("extract_schema", extract_schema)
graph.add_node("validate_result", validate_result)
graph.add_node("diagnose_failure", diagnose_failure)
graph.add_node("human_review", human_review)
graph.add_node("save_result", save_result)
graph.add_node("generate_report", generate_report)

graph.set_entry_point("receive_task")
graph.add_edge("receive_task", "route_skill")
graph.add_edge("route_skill", "fetch_or_read_page")
graph.add_edge("fetch_or_read_page", "clean_html")
graph.add_edge("clean_html", "extract_schema")
graph.add_edge("extract_schema", "validate_result")
graph.add_conditional_edges("validate_result", after_validation)
graph.add_conditional_edges("diagnose_failure", after_diagnosis)
graph.add_edge("save_result", "generate_report")
graph.add_edge("human_review", "generate_report")
graph.add_edge("generate_report", END)

app = graph.compile()

这个骨架体现了几个重点：

1
2
3
4

流程不是一条线。
抽取失败会进入诊断。
诊断高风险会进入人工复核。
所有路径最终都会生成报告。

这就比单纯写一个“爬虫 Agent Prompt”稳定得多。

十一、如何处理人工复核

人工复核不是失败。

它是智能系统的一部分。

当出现这些情况时，应该进入人工复核：

1
2
3
4
5
6

权限或授权范围不明确。
诊断风险等级为 high。
必填字段持续缺失。
页面类型不确定。
抽取结果会影响重要业务决策。
用户请求超出安全边界。

复核节点可以做几件事：

1
2
3
4
5

暂停任务。
生成复核报告。
记录需要人工判断的原因。
等待人工确认。
根据确认结果继续或终止。

在报告里可以明确写：

1

十五、常见问题

Q1：智能爬虫助手是不是自动爬虫？

不是简单的自动爬虫。

它更像是数据采集流程里的智能辅助层。

负责理解任务、抽取结构化信息、诊断异常、生成报告和触发人工复核。

真正的请求、调度、存储和权限控制仍然应该由工程系统负责。

Q2：为什么不直接让一个大 Prompt 做所有事情？

因为长 Prompt 难维护。

当规则越来越多时，会出现：

1
2
3
4
5

抽取规则和诊断规则混在一起。
安全边界被埋在长文本里。
输出格式不稳定。
失败时不知道是哪一步错了。
无法单独测试某个能力。

Skill + Router + LangGraph 的组合可以把问题拆开。

Q3：什么时候需要人工复核？

当任务涉及权限、安全、授权范围、重要业务结果或高风险异常时，应该人工复核。

Agent 不应该在边界不清楚时继续自动执行。

Q4：这个系统最先应该实现哪一部分？

建议先实现网页结构化抽取 Skill。

因为它输入输出最明确：

1

HTML → JSON

然后再加入诊断 Skill，最后加入 LangGraph 编排。

十六、面试表达

如果面试官问：

你如何设计一个基于 Skill 的智能爬虫助手？

可以这样回答：

1
2
3
4
5

我会把它设计成一个多 Skill Agent，而不是一个大 Prompt。

系统里至少有三个核心能力：网页结构化抽取 Skill、爬虫异常诊断 Skill 和报告生成 Skill。前者负责把 HTML 或网页文本按 Schema 抽成 JSON，诊断 Skill 负责根据 HTTP 状态码、响应头、响应片段、错误日志和抽取结果生成结构化诊断报告，报告 Skill 负责把结果整理成人能读懂的 Markdown。

在流程上，我会用 Skill Router 判断当前任务需要哪些 Skill，再用 LangGraph 管状态和条件分支。State 里会保存 user_input、target_url、html、cleaned_text、selected_skills、extraction_result、validation_errors、diagnosis_report、risk_level 和 needs_manual_review。抽取成功就保存结果并生成报告；抽取失败就进入诊断；如果诊断高风险，就进入人工复核。

如果想强调安全和工程化，可以补充：

1

这个系统只用于自有系统、授权采集、公开文档整理和内部数据治理，不提供绕过访问控制、规避反爬或批量滥用能力。所有建议动作都偏向降低频率、确认授权、修复选择器、改善监控和人工复核。这样 Agent 才是可控的工程助手，而不是不可控的自动化脚本。
