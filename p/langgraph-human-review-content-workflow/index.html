LangGraph 实战笔记 16：构建带人工审核的内容生成工作流

2025-12-01 10:00
阅读时长: 18 分钟

上一篇文章里，我们讲了 LangGraph 中的 Human-in-the-loop。

核心思路是：

1
2
3
4
5
6
7

Agent 生成建议
  ↓
流程暂停
  ↓
人工审核
  ↓
根据人工结果继续执行

这让 Agent 不再是一个完全自动的黑盒，而是一个可以在关键节点暂停、等待人决策、再恢复执行的状态图。

这一篇，我们把这个能力放进一个更完整的业务场景：内容生成工作流。

我们会构建一个带人工审核的内容生成 Agent，它可以完成：

1

选题 -> 生成大纲 -> 写初稿 -> AI 自检 -> 自动修改 -> 人工审核 -> 修改或发布

这类流程很适合 LangGraph。

因为它既有自动化生成，又有质量检查，还有人工参与和发布前风险控制。

一、前言

内容生成是大模型最常见的应用场景之一。

例如：

  • 写博客草稿。
  • 写产品公告。
  • 写营销文案。
  • 写知识库文章。
  • 写客服回复模板。
  • 写周报、日报、会议纪要。

最简单的做法是直接调用模型：

1

用户输入主题 -> 模型生成文章

这当然可以跑通 demo。

但真实内容生产通常不是这样。

真实流程更像：

 1

13

确定主题
  ↓
生成大纲
  ↓
写初稿
  ↓
检查结构和事实
  ↓
修改
  ↓
人工审核
  ↓
发布或退回

尤其是公开发布内容，通常不能让模型直接发布。

因为内容可能存在：

  • 表达不准确。
  • 事实不可靠。
  • 语气不合适。
  • 品牌口径不一致。
  • 误导用户。
  • 涉及敏感内容。
  • 缺少人工确认。

所以，一个更可靠的内容生成系统应该是：

1

AI 提升效率，人控制质量和风险。

这正是 LangGraph + Human-in-the-loop 的用武之地。

二、为什么内容生成需要工作流？

如果只是让模型写一段短文，一次调用就够了。

但如果要把内容生成做成可维护系统，就需要工作流。

原因主要有四个。

1. 内容生成不是一步完成的

一篇质量稳定的内容通常需要多个阶段。

例如：

1

先想结构，再写正文，再检查，再修改。

如果把这些都塞进一个 Prompt，问题会变成：

  • Prompt 很长。
  • 中间结果不可观察。
  • 不知道哪一步出错。
  • 很难单独优化某个环节。

拆成节点之后，每个节点的职责更清楚。

1

generate_outline -> write_draft -> ai_review -> revise

这比一个巨大的 content_node 更容易维护。

2. 内容质量需要检查

模型写出来的内容不一定直接可用。

常见问题包括：

  • 结构混乱。
  • 重点不突出。
  • 论证不充分。
  • 事实可能不准确。
  • 语气不符合目标读者。
  • 结尾没有行动建议。

所以需要 AI 自检节点。

1

write_draft -> ai_self_check

如果检查不通过，可以进入修改节点。

1

ai_self_check -> revise_draft -> ai_self_check

这就是第 08 篇 Reflection Agent 的思想在内容生成中的应用。

3. 发布前需要人工审核

即使 AI 自检通过，也不代表可以直接发布。

尤其是：

  • 公司公告。
  • 产品发布说明。
  • 技术博客。
  • 品牌营销内容。
  • 对外客服话术。

这些内容最终会被人看到。

发布前最好经过人工审核。

这就是第 15 篇 Human-in-the-loop 的应用。

4. 流程需要可恢复

内容审核不是瞬时完成的。

常见情况是：

1
2
3

上午生成初稿
下午编辑审核
晚上修改后发布

这就要求系统能暂停和恢复。

LangGraph 的 checkpoint 和 thread_id 可以保存状态，让流程跨请求继续执行。

三、本篇要构建的内容工作流

这一篇我们构建一个简化的内容生成工作流。

输入是一个内容主题：

1

写一篇介绍 LangGraph Human-in-the-loop 的技术博客。

工作流会执行下面几步：

  1. 生成文章大纲。
  2. 根据大纲写初稿。
  3. AI 自检初稿质量。
  4. 如果不合格，自动修改。
  5. 如果达到最大修改次数，交给人工审核。
  6. 人工可以批准、修改、退回重写或拒绝。
  7. 批准后进入发布节点。

这个图有三个关键点：

  • AI 可以自动生成和自检。
  • AI 可以在有限次数内自动修改。
  • 发布前必须经过人工审核。

from typing import TypedDict


class ContentWorkflowState(TypedDict, total=False):
    topic: str
    audience: str
    outline: str
    draft: str
    ai_feedback: str
    ai_passed: bool
    revision_count: int
    max_revisions: int
    human_decision: dict
    final_content: str
    publish_result: str

这里使用 total=False，是为了示例中可以逐步写入字段。

真实项目里，你也可以把必填字段和可选字段拆得更严谨。

这个 State 里有三个字段特别重要。

第一个是：

它保存当前草稿。

每次修改后，都会覆盖为新的版本。

第二个是：

只要图里有循环，就要有终止条件。

def write_draft_node(state: ContentWorkflowState):
    draft = f"""
标题：{state['topic']}

这篇文章面向 {state.get('audience', '技术读者')}，介绍如何把内容生成流程拆成可控制的 LangGraph 状态图。

## 为什么需要工作流

内容生成不是一次模型调用就结束。真实流程通常包括选题、大纲、初稿、自检、修改和人工审核。

## 核心流程

{state['outline']}

## 小结

通过 LangGraph，我们可以把内容生产过程变成一张可观察、可恢复、可人工干预的状态图。
""".strip()

这里仍然是模拟。

如果接入真实模型，可以这样设计 Prompt：

你是一名技术博客作者。

  • 是否有标题。
  • 是否覆盖核心流程。
  • 是否有总结。
  • 是否适合目标读者。
  • 是否存在明显缺失。

def ai_self_check_node(state: ContentWorkflowState):
    draft = state["draft"]
    problems = []

    if "为什么" not in draft:
        problems.append("缺少为什么需要这个能力的解释。")

    if "流程" not in draft:
        problems.append("缺少流程说明。")

    if "小结" not in draft and "总结" not in draft:
        problems.append("缺少总结部分。")

    if len(draft) < 300:
        problems.append("内容偏短，需要补充细节。")

    if problems:
        return {
            "ai_passed": False,
            "ai_feedback": "\n".join(problems),
        }

    return {
        "ai_passed": True,
        "ai_feedback": "初稿结构完整，可以进入人工审核。",
    }

from typing import Literal


def route_after_ai_check(
    state: ContentWorkflowState,
) -> Literal["human_review", "revise", "needs_human"]:
    if state["ai_passed"]:
        return "human_review"

    revision_count = state.get("revision_count", 0)
    max_revisions = state.get("max_revisions", 2)

    if revision_count < max_revisions:
        return "revise"

    return "needs_human"

这里的 needs_human 很重要。

它表示：

1

AI 已经自动修改到上限，但仍然不理想，需要交给人判断。

这比无限循环更可靠。

所有自动修改流程都应该有边界。

from langgraph.types import interrupt


def human_review_node(state: ContentWorkflowState):
    decision = interrupt({
        "message": "请审核内容草稿",
        "topic": state["topic"],
        "audience": state.get("audience", "技术读者"),
        "draft": state["draft"],
        "ai_feedback": state.get("ai_feedback", ""),
        "revision_count": state.get("revision_count", 0),
        "allowed_actions": ["approve", "edit", "request_revision", "reject"],
    })

    return {"human_decision": decision}

这里传给人的信息包括：

  • 主题。
  • 目标读者。
  • 当前草稿。
  • AI 自检反馈。
  • 已自动修改次数。
  • 可选操作。

人工可以选择：

动作含义
approve批准发布
edit直接修改后发布
request_revision退回让 AI 继续修改
reject拒绝发布，归档结束

这里要注意一个细节。

LangGraph 恢复执行时，包含 interrupt() 的节点会从头重新运行，而不是从 interrupt() 下一行继续。

所以：

  • interrupt() 前不要执行不可逆副作用。
  • 传给 interrupt() 的 payload 应该可重复构造。
  • 真正发布内容应该放到后续节点。

def route_after_human_review(
    state: ContentWorkflowState,
) -> Literal["approve", "edit", "request_revision", "reject"]:
    decision = state["human_decision"]
    action = decision.get("action", "reject")

    if action == "approve":
        return "approve"
    if action == "edit":
        return "edit"
    if action == "request_revision":
        return "request_revision"
    return "reject"

默认是 reject。

原因和上一篇文章一样：

发布内容属于外部可见动作，默认应该保守。

如果人工输入不合法，不应该默认发布。

    return {
        "draft": revised,
        "revision_count": state.get("revision_count", 0) + 1,
    }

修改后可以回到 AI 自检。

1

这样流程就形成了：

1

这是一种很常见的人机协作模式。

from typing import Literal, TypedDict
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command, interrupt


class ContentWorkflowState(TypedDict, total=False):
    topic: str
    audience: str
    outline: str
    draft: str
    ai_feedback: str
    ai_passed: bool
    revision_count: int
    max_revisions: int
    human_decision: dict
    final_content: str
    publish_result: str


def generate_outline_node(state: ContentWorkflowState):
    topic = state["topic"]
    audience = state.get("audience", "技术读者")

    outline = f"""
# {topic}

目标读者：{audience}

1. 为什么需要这个能力
2. 核心概念和流程
3. 代码示例
4. 常见问题
5. 最佳实践
6. 总结
""".strip()

    return {"outline": outline, "revision_count": 0}


def write_draft_node(state: ContentWorkflowState):
    draft = f"""
标题：{state['topic']}

这篇文章面向 {state.get('audience', '技术读者')}，介绍如何把内容生成流程拆成可控制的 LangGraph 状态图。

## 为什么需要工作流

内容生成不是一次模型调用就结束。真实流程通常包括选题、大纲、初稿、自检、修改和人工审核。

## 核心流程

{state['outline']}

## 小结

通过 LangGraph，我们可以把内容生产过程变成一张可观察、可恢复、可人工干预的状态图。
""".strip()

    return {"draft": draft}


def ai_self_check_node(state: ContentWorkflowState):
    draft = state["draft"]
    problems = []

    if "为什么" not in draft:
        problems.append("缺少为什么需要这个能力的解释。")

    if "流程" not in draft:
        problems.append("缺少流程说明。")

    if "小结" not in draft and "总结" not in draft:
        problems.append("缺少总结部分。")

    if len(draft) < 300:
        problems.append("内容偏短，需要补充细节。")

    if problems:
        return {"ai_passed": False, "ai_feedback": "\n".join(problems)}

    return {"ai_passed": True, "ai_feedback": "初稿结构完整，可以进入人工审核。"}


def route_after_ai_check(
    state: ContentWorkflowState,
) -> Literal["human_review", "revise", "needs_human"]:
    if state["ai_passed"]:
        return "human_review"

    revision_count = state.get("revision_count", 0)
    max_revisions = state.get("max_revisions", 2)

    if revision_count < max_revisions:
        return "revise"

    return "needs_human"


def revise_draft_node(state: ContentWorkflowState):
    revision_count = state.get("revision_count", 0) + 1
    feedback = state["ai_feedback"]

    revised = f"""
{state['draft']}

## 修改补充

根据自检反馈，本次补充以下内容：

{feedback}

这一步说明：内容生成工作流需要把生成、检查和修改拆开，而不是全部塞进一次模型调用。
""".strip()

    return {"draft": revised, "revision_count": revision_count}


def human_review_node(state: ContentWorkflowState):
    decision = interrupt({
        "message": "请审核内容草稿",
        "topic": state["topic"],
        "audience": state.get("audience", "技术读者"),
        "draft": state["draft"],
        "ai_feedback": state.get("ai_feedback", ""),
        "revision_count": state.get("revision_count", 0),
        "allowed_actions": ["approve", "edit", "request_revision", "reject"],
    })

    return {"human_decision": decision}


def route_after_human_review(
    state: ContentWorkflowState,
) -> Literal["approve", "edit", "request_revision", "reject"]:
    decision = state["human_decision"]
    action = decision.get("action", "reject")

    if action == "approve":
        return "approve"
    if action == "edit":
        return "edit"
    if action == "request_revision":
        return "request_revision"
    return "reject"


def apply_human_edit_node(state: ContentWorkflowState):
    decision = state["human_decision"]
    edited_content = decision.get("edited_content", state["draft"])

    return {"final_content": edited_content}


def revise_from_human_node(state: ContentWorkflowState):
    decision = state["human_decision"]
    comment = decision.get("comment", "请继续完善内容。")

    revised = f"""
{state['draft']}

## 根据人工审核补充

人工审核意见：{comment}

这里补充一个业务案例：内容团队可以先让 Agent 生成公告草稿，再由运营审核语气、事实和发布时间，审核通过后再发布。
""".strip()

    return {
        "draft": revised,
        "revision_count": state.get("revision_count", 0) + 1,
    }


def publish_content_node(state: ContentWorkflowState):
    content = state.get("final_content", state["draft"])

    return {
        "final_content": content,
        "publish_result": "内容已通过人工审核，模拟发布成功。",
    }


def archive_rejected_node(state: ContentWorkflowState):
    comment = state["human_decision"].get("comment", "未提供原因。")

    return {"publish_result": f"内容未发布，已归档。拒绝原因：{comment}"}


builder = StateGraph(ContentWorkflowState)

builder.add_node("generate_outline", generate_outline_node)
builder.add_node("write_draft", write_draft_node)
builder.add_node("ai_self_check", ai_self_check_node)
builder.add_node("revise_draft", revise_draft_node)
builder.add_node("human_review", human_review_node)
builder.add_node("apply_human_edit", apply_human_edit_node)
builder.add_node("revise_from_human", revise_from_human_node)
builder.add_node("publish_content", publish_content_node)
builder.add_node("archive_rejected", archive_rejected_node)

builder.add_edge(START, "generate_outline")
builder.add_edge("generate_outline", "write_draft")
builder.add_edge("write_draft", "ai_self_check")

builder.add_conditional_edges(
    "ai_self_check",
    route_after_ai_check,
    {
        "human_review": "human_review",
        "revise": "revise_draft",
        "needs_human": "human_review",
    },
)

builder.add_edge("revise_draft", "ai_self_check")

builder.add_conditional_edges(
    "human_review",
    route_after_human_review,
    {
        "approve": "publish_content",
        "edit": "apply_human_edit",
        "request_revision": "revise_from_human",
        "reject": "archive_rejected",
    },
)

builder.add_edge("apply_human_edit", "publish_content")
builder.add_edge("revise_from_human", "ai_self_check")
builder.add_edge("publish_content", END)
builder.add_edge("archive_rejected", END)

checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

这张图把内容生成拆成了几个可观察节点。

每一步写入的 State 都可以被查看和调试。

二十二、生产环境要注意什么？

内容生成工作流看起来比退款安全。

但只要涉及自动发布，就仍然有风险。

生产环境至少要注意下面几点。

1. 发布节点必须幂等

如果恢复或重试导致发布节点执行两次，不能重复发布两篇内容。

可以使用：

1

content_id + version

或者记录发布状态：

1

pending_review -> approved -> published

如果已经发布，就不要重复调用发布 API。

2. 人工审核记录要持久化

不要只把审核结果存在 LangGraph State 里。

真实系统应该记录：

  • 审核人。
  • 审核时间。
  • 审核动作。
  • 审核意见。
  • 审核前后内容差异。

这些记录对内容追溯很重要。

3. 中断前不要做副作用

包含 interrupt() 的节点恢复时会从节点开头重跑。

所以不要在 interrupt() 前写数据库、发消息、提交发布。

正确做法是：

1
2

human_review 只负责暂停和接收审核结果
publish_content 才负责发布

4. 审核 payload 要可读

给人工看的内容不要只有内部字段。

应该包含：

  • 标题。
  • 主题。
  • 草稿。
  • AI 自检结论。
  • 修改次数。
  • 可选动作。

这会显著提升审核效率。

5. 人工输入要结构化

不要只让人输入一段文字。

建议使用结构化格式：

1
2
3
4
5

{
    "action": "approve | edit | request_revision | reject",
    "comment": "审核意见",
    "edited_content": "可选，人工修改后的内容"
}

这样后续路由更稳定。

二十三、常见问题

1. AI 自检通过后为什么还要人工审核？

因为 AI 自检只能降低问题概率，不能承担发布责任。

尤其是对外内容，最终质量和风险仍然需要人确认。

2. 人工退回修改后会不会无限循环？

有可能。

所以生产环境应该给人工退回次数也设置上限，或者在审核系统里限制状态流转。

本文示例重点展示流程，没有展开这个限制。

3. interrupt() 返回的内容应该放什么？

放人工做决策所需的最小充分信息。

不要放不可序列化对象，也不要放过大的原始数据。

如果草稿很长，可以只传摘要和内容 ID，由前端再加载完整内容。

4. 恢复时为什么必须使用同一个 thread_id？

因为 checkpointer 需要通过 thread_id 找到之前暂停的状态。

换一个 thread_id，就相当于启动一条新的流程。

5. 内容发布要不要做成 Tool？

可以，但不一定。

如果发布动作始终发生在固定流程的最后，普通节点更清晰。

如果是否发布、发布到哪里、调用哪个平台由模型决定，才更适合做成 Tool，并在工具调用前加人工审核。

二十四、最佳实践

1. 把内容流程拆成多个节点

不要用一个节点完成大纲、初稿、自检、修改和发布。

拆开后更容易观察和优化。

2. 用 AI 自检做第一道质量门

AI 自检可以拦截明显问题，减少人工审核压力。

但不要把它当作最终发布许可。

3. 自动修改必须有次数限制

所有循环都要有终止条件。

例如：

1

revision_count < max_revisions

4. 人工审核放在发布前

发布、发送、提交、写入外部系统，都应该在人工审核后执行。

5. 审核结果进入 State

不要把人工结果只留在外部系统。

写入 State 后，条件边才能根据它决定下一步。

6. 用 checkpoint 支撑跨时间审核

内容审核经常跨分钟、小时甚至天。

这类流程应该使用持久化 checkpointer。

7. 保留内容版本

真实内容系统建议保存：

  • 初稿版本。
  • AI 修改版本。
  • 人工修改版本。
  • 最终发布版本。

这样方便追溯质量问题。

二十五、总结

本文构建了一个带人工审核的内容生成工作流。

核心结论是：

内容生成不应该只是一次模型调用，而应该是一条可观察、可修改、可审核、可恢复的工作流。LangGraph 可以把 AI 生成、AI 自检、自动修改和人工审核组合成一张清晰的状态图。

本文重点包括：

  • 内容生成通常需要大纲、初稿、自检、修改、审核和发布多个阶段。
  • LangGraph 适合把这些阶段拆成独立节点。
  • AI 自检可以作为第一道质量门。
  • 自动修改需要最大次数限制。
  • 发布前应该使用 interrupt() 暂停，等待人工审核。
  • 使用 checkpointer 和稳定 thread_id 支持跨请求恢复。
  • 人工可以批准、修改、退回重写或拒绝。
  • 发布节点应该放在人工批准之后，并做好幂等和审计。

到这里，我们已经从单个 Agent 能力，走到了更完整的人机协作工作流。

下一篇文章，我们会进入 Multi-Agent：让多个 Agent 分工协作。届时我们会讨论 Planner、Executor、Reviewer 等角色如何协同，以及为什么复杂任务往往不适合交给一个万能 Agent。
