LangChain Memory 机制：构建有上下文的多轮对话应用

2025-09-15 10:00
阅读时长: 16 分钟

前面几篇文章里，我们已经掌握了 LangChain 应用链路里的几个关键能力：

1

chain = prompt | model | parser

我们知道了 Prompt 如何组织任务，LCEL 如何编排链路，Output Parser 如何解析模型输出，Runnable 如何支撑更复杂的组合。

但到目前为止，我们的大多数示例都有一个共同特点：每次调用都是独立的。

用户问一句，模型答一句。下一次再问，模型并不知道前面发生了什么。

这在真实聊天应用里显然不够。

一、前言

假设你正在做一个 AI 学习助手。

第一轮用户问：

1

我想学习 LangChain。

模型回答：

1

可以先从 Model、Prompt、LCEL 和 Runnable 开始。

第二轮用户接着问：

1

那它和直接调用 OpenAI API 有什么区别？

如果模型没有记住上一轮对话，它看到的只有：

1

那它和直接调用 OpenAI API 有什么区别？

这里的“它”指什么？

人类知道是 LangChain，但模型如果没有历史上下文，就不一定知道。

所以，多轮对话应用必须解决一个核心问题：

如何把历史对话作为上下文传给模型，让模型知道前面聊过什么？

这就是 Memory 要解决的问题。

需要先说明一点：在 LangChain 新版本实践中，很多旧的 memory class，例如 ConversationBufferMemory、ConversationSummaryMemory 等，仍然能在资料里看到，但更推荐理解底层的 messages / chat history / RunnableWithMessageHistory 思路。尤其是配合 LCEL 和 Runnable 时，基于消息历史的方式更清晰，也更符合现代 LangChain 的用法。

本文会重点讲：

  1. 大模型为什么本身没有“记忆”。
  2. LangChain 中 Memory 的本质是什么。
  3. Chat History 和 MessagesPlaceholder 怎么配合。
  4. 如何用 RunnableWithMessageHistory 构建多轮对话。
  5. Session ID 为什么重要。
  6. 旧式 Memory 类和新式 Runnable 方式有什么区别。
  7. Token 限制下如何管理历史消息。
  8. 生产环境中 Memory 应该怎么落地。

二、为什么需要 Memory？

1. 模型不会自动记住上一次调用

很多初学者会误以为：只要使用同一个模型对象，模型就会记住前面的对话。

比如：

1
2
3
4

model = ChatOpenAI(model="gpt-4o-mini")

model.invoke("我叫阿彪。")
model.invoke("我叫什么？")

直觉上你可能希望第二次模型回答“你叫阿彪”。

但实际上，第二次调用只把这一句话发给了模型：

1

我叫什么？

模型不会自动知道第一次调用内容。

原因很简单：大模型 API 通常是无状态的。

每次请求都像是一次新的调用。模型能看到什么，取决于你本次请求传了什么。

2. 多轮对话依赖历史消息

聊天产品之所以能连续对话，是因为每次请求都会带上部分历史消息。

例如第二轮请求时，真正发给模型的可能是：

1
2
3
4

System: 你是一名学习助手。
Human: 我想学习 LangChain。
AI: 可以先从 Model、Prompt、LCEL 和 Runnable 开始。
Human: 那它和直接调用 OpenAI API 有什么区别？

这样模型才知道“它”指的是 LangChain。

所以 Memory 的第一层含义是：

保存历史消息，并在下一次调用时把相关历史消息重新放回 Prompt。

3. Memory 不等于模型内部真的长记性

这里要特别强调：Memory 不是让模型参数发生变化。

它不是微调，也不是把信息写进模型大脑。

更准确地说，Memory 是应用层能力：

1
2
3
4
5
6
7

保存历史上下文
  ↓
下次调用时取出历史上下文
  ↓
放入 Prompt
  ↓
模型基于上下文生成回答

所以 Memory 的本质不是“模型记住了”，而是“应用帮模型带上了历史”。

三、Memory 的核心概念

在 LangChain 里，和多轮对话 Memory 相关的核心概念主要有几个。

概念作用
Message表示一条聊天消息，例如 HumanMessage、AIMessage、SystemMessage
Chat History保存一组历史消息
MessagesPlaceholder在 Prompt 中插入历史消息列表
RunnableWithMessageHistory给 Runnable 包装消息历史能力
Session ID区分不同用户或不同会话
Short-term memory当前会话内的短期上下文
Long-term memory跨会话长期保存的用户偏好、资料或事实

本文主要关注短期记忆，也就是多轮对话上下文。

1. Message：聊天消息的基本单位

LangChain 使用消息对象表示对话。

常见消息类型包括：

1

from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

示例：

1
2
3
4
5
6

messages = [
    SystemMessage(content="你是一名耐心的学习助手。"),
    HumanMessage(content="我想学习 LangChain。"),
    AIMessage(content="可以先从 Prompt、LCEL 和 Runnable 开始。"),
    HumanMessage(content="那 Runnable 是什么？"),
]

这些消息会一起传给模型。

2. Chat History：保存历史消息

Chat History 可以理解为一个消息列表的存储容器。

开发阶段可以用内存保存：

1
2
3
4
5
6
7

from langchain_core.chat_history import InMemoryChatMessageHistory

history = InMemoryChatMessageHistory()
history.add_user_message("我想学习 LangChain。")
history.add_ai_message("可以先从 Prompt、LCEL 和 Runnable 开始。")

print(history.messages)

真实项目中，历史消息通常要放到：

  • Redis
  • PostgreSQL
  • MongoDB
  • 文件存储
  • 业务数据库
  • LangGraph checkpoint

内存只适合本地演示和单进程测试。

3. MessagesPlaceholder：把历史消息放进 Prompt

PromptTemplate 里不能只写当前问题，还要留一个位置放历史消息。

这就需要 MessagesPlaceholder。

1
2
3
4
5
6
7

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一名耐心的 AI 应用开发学习助手。"),
    MessagesPlaceholder("chat_history"),
    ("human", "{question}"),
])

这里的关键是：

1

MessagesPlaceholder("chat_history")

它表示：调用 Prompt 时，可以把一组历史消息插入到这个位置。

调用示例：

1
2
3
4
5
6
7
8
9

from langchain_core.messages import HumanMessage, AIMessage

messages = prompt.invoke({
    "chat_history": [
        HumanMessage(content="我想学习 LangChain。"),
        AIMessage(content="可以先从 Prompt 和 LCEL 开始。"),
    ],
    "question": "那 Runnable 是什么？",
})

最终模型看到的是：

1
2
3
4

System: 你是一名耐心的 AI 应用开发学习助手。
Human: 我想学习 LangChain。
AI: 可以先从 Prompt 和 LCEL 开始。
Human: 那 Runnable 是什么？

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.output_parsers import StrOutputParser
from langchain_core.messages import HumanMessage, AIMessage

load_dotenv()

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一名耐心的 LangChain 学习助手。"),
    MessagesPlaceholder("chat_history"),
    ("human", "{question}"),
])

model = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
    temperature=0.5,
)

chain = prompt | model | StrOutputParser()

chat_history = []

question1 = "我想学习 LangChain，应该从哪里开始？"
answer1 = chain.invoke({
    "chat_history": chat_history,
    "question": question1,
})
print("AI:", answer1)

chat_history.append(HumanMessage(content=question1))
chat_history.append(AIMessage(content=answer1))

question2 = "那它和直接调用模型 API 有什么区别？"
answer2 = chain.invoke({
    "chat_history": chat_history,
    "question": question2,
})
print("AI:", answer2)

这段代码做了几件事：

  1. Prompt 中预留 chat_history。
  2. 第一次调用时历史为空。
  3. 得到回答后，把用户问题和 AI 回答加入历史。
  4. 第二次调用时，把历史一起传给模型。

这就是最朴素的 Memory。

手动管理的问题

手动管理历史消息可以帮助理解原理，但真实项目里会有很多麻烦：

  • 每次都要手动 append。
  • 多个用户的历史容易混在一起。
  • 需要处理 session。
  • 需要控制历史长度。
  • 需要持久化到数据库。
  • 需要考虑并发读写。

所以我们需要更系统的方式。

五、RunnableWithMessageHistory：给链路加上消息历史

在 LCEL 和 Runnable 体系中，更推荐使用 RunnableWithMessageHistory 来给链路加上历史消息能力。

它的作用是：

包装一个 Runnable，让它在调用前自动读取历史消息，在调用后自动写入本轮对话消息。

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.output_parsers import StrOutputParser
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory

load_dotenv()

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一名耐心、清晰的 LangChain 学习助手。"),
    MessagesPlaceholder("chat_history"),
    ("human", "{question}"),
])

model = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
    temperature=0.5,
)

chain = prompt | model | StrOutputParser()

store = {}


def get_session_history(session_id: str):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]


chain_with_history = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="question",
    history_messages_key="chat_history",
)

config = {"configurable": {"session_id": "user-001"}}

answer1 = chain_with_history.invoke(
    {"question": "我想学习 LangChain，应该从哪里开始？"},
    config=config,
)
print("AI:", answer1)

answer2 = chain_with_history.invoke(
    {"question": "那 Runnable 在里面起什么作用？"},
    config=config,
)
print("AI:", answer2)

这里有几个关键点。

2. get_session_history

1
2
3
4

def get_session_history(session_id: str):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]

这个函数根据 session_id 返回对应的历史消息。

也就是说，不同 session 有不同的历史。

1
2
3

user-001 -> history A
user-002 -> history B
user-003 -> history C

这样不同用户的对话就不会混在一起。

3. input_messages_key

1

input_messages_key="question"

它告诉 LangChain：本次用户输入在哪个字段里。

因为我们调用时传的是：

1

{"question": "我想学习 LangChain，应该从哪里开始？"}

所以这里写 question。

4. history_messages_key

1

history_messages_key="chat_history"

它告诉 LangChain：Prompt 中历史消息占位符叫什么。

因为 Prompt 里写的是：

1

MessagesPlaceholder("chat_history")

所以这里也要写 chat_history。

5. config 里的 session_id

调用时必须传入 session_id：

1

config = {"configurable": {"session_id": "user-001"}}

这就是告诉链路：当前这次调用属于哪个会话。

如果你换成：

1

config = {"configurable": {"session_id": "user-002"}}

那就是另一个独立会话。

六、Session ID：多用户对话的关键

Memory 最容易踩坑的地方，就是 session 管理。

如果你只有一个全局 chat_history：

1

chat_history = []

那所有用户都会共享同一份历史。

这在真实产品里是严重问题。

用户 A 说：

1

我叫张三。

用户 B 问：

1

我叫什么？

如果历史混在一起，模型可能回答：

1

你叫张三。

这不仅是功能错误，也是隐私问题。

1. 每个会话必须独立

至少要做到：

1
2

用户 A 的 session_id -> 用户 A 的历史
用户 B 的 session_id -> 用户 B 的历史

在 Web 应用中，session_id 可能来自：

  • 登录用户 ID
  • 浏览器会话 ID
  • 对话 ID
  • 业务侧 conversation_id
  • 移动端设备生成的临时 ID

2. 用户 ID 不一定等于会话 ID

一个用户可能有多个对话。

比如：

1
2
3

user-001 / conversation-001：学习 LangChain
user-001 / conversation-002：准备面试
user-001 / conversation-003：写技术博客

如果只按 user_id 存历史，不同主题会混在一起。

更合理的是使用 conversation_id 或 thread_id。

3. session_id 要从可信边界生成

不要让用户随便传别人的 session_id。

如果外部用户可以指定任意 session_id，就可能读取或污染别人的对话历史。

真实系统中，session_id 应该由后端生成、鉴权，并和当前用户绑定。

七、旧式 Memory 类：为什么还会看到 ConversationBufferMemory？

如果你看旧教程，经常会看到这些类：

  • ConversationBufferMemory
  • ConversationBufferWindowMemory
  • ConversationSummaryMemory
  • ConversationTokenBufferMemory

它们的思路大致是：帮你保存和注入对话历史。

例如旧式写法里可能会出现：

1
2
3

from langchain.memory import ConversationBufferMemory

memory = ConversationBufferMemory(return_messages=True)

这些类在早期 LangChain Chain 体系里很常见。

但随着 LCEL 和 Runnable 成为更推荐的组合方式，新项目更应该优先理解：

  • MessagesPlaceholder
  • ChatMessageHistory
  • RunnableWithMessageHistory
  • LangGraph 的 short-term memory / checkpoint

旧式 Memory 和新式方式的区别

对比项旧式 Memory 类RunnableWithMessageHistory
常见搭配传统 ChainLCEL / Runnable
历史注入由 memory 对象配合 chain由 MessagesPlaceholder 明确注入
会话隔离需要额外处理通过 session_id 更清晰
可组合性依赖具体 Chain更符合 Runnable 体系
新项目推荐需要谨慎看版本更推荐掌握

不是说旧式 Memory 完全不能用，而是学习新版本 LangChain 时，不应该只停留在旧 API 上。

八、Memory 和 Prompt 的关系

Memory 最终一定会影响 Prompt。

因为模型本身只能看到当前请求里的消息。

所以 Memory 的过程可以理解为：

1
2
3
4
5
6
7

读取历史消息
  ↓
插入 Prompt
  ↓
发送给模型
  ↓
保存本轮输入和输出

因此，Prompt 设计对 Memory 很重要。

1. 历史消息放在哪里？

常见写法是：

1
2
3
4
5

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一名学习助手。"),
    MessagesPlaceholder("chat_history"),
    ("human", "{question}"),
])

这表示：

  1. 先给系统规则。
  2. 再放历史对话。
  3. 最后放当前用户问题。

这种顺序通常比较自然。

2. system message 不要放进普通历史

系统规则应该由应用控制，不应该被用户历史覆盖。

不推荐把 system message 和普通聊天记录混在一起随便存取。

更清晰的做法是：

  • system message 固定写在 Prompt 模板里。
  • 用户和 AI 历史放在 chat_history。
  • 当前问题单独放在 {question}。

3. 历史越多不一定越好

很多人会想：既然要记忆，那是不是把所有历史都传给模型最好？

不一定。

历史太多会带来问题：

  • token 成本增加。
  • 请求变慢。
  • 超出上下文窗口。
  • 旧信息干扰当前问题。
  • 无关内容降低回答质量。

所以 Memory 不只是“保存”，还包括“选择”和“压缩”。

九、Token 限制：历史消息不能无限增长

大模型有上下文窗口限制。

如果你不断把完整历史都塞进去，迟早会超过限制。

例如一个用户聊了 100 轮，每轮都比较长，再加上系统 Prompt、检索上下文、工具结果，很容易超出模型上下文。

所以 Memory 需要管理策略。

1. 最近 N 轮策略

最简单的策略是只保留最近 N 轮。

例如只保留最近 10 条消息：

1
2

def trim_messages(messages, max_messages=10):
    return messages[-max_messages:]

优点：简单。

缺点：早期重要信息可能丢失。

适合：普通闲聊、客服初版、学习 demo。

2. 摘要策略

当历史变长时，可以把旧历史总结成一段摘要。

例如：

1

用户正在学习 LangChain，已经了解了 PromptTemplate、LCEL 和 Runnable，目前想继续学习 Memory。

然后 Prompt 中放：

1
2
3

对话摘要：...
最近几轮消息：...
当前问题：...

优点：保留长期上下文。

缺点：摘要可能丢细节，也会引入额外模型调用。

适合：长对话、学习助手、写作助手。

3. 基于重要性的记忆

不是所有对话都值得长期保存。

比如：

1
2
3
4

你好
好的
继续
再详细点

这些通常不需要长期记住。

但下面这类信息可能有价值：

1

我是一名后端开发，熟悉 Python，但刚开始学大模型应用。

这类信息可以抽取成用户画像或长期记忆。

注意：长期记忆涉及隐私和数据治理，不能随便保存。

4. RAG 与 Memory 的边界

Memory 和 RAG 都是在给模型提供上下文，但它们不一样。

能力主要解决什么
Memory当前用户或当前会话的历史上下文
RAG外部知识库、文档、私有资料、事实依据

例如：

  • 用户刚才问过什么：Memory。
  • 公司内部文档怎么规定：RAG。
  • 用户偏好用 Python 示例：Memory。
  • LangChain 官方 API 怎么用：RAG 或联网资料。

真实应用里，Memory 和 RAG 经常会一起用。

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.output_parsers import StrOutputParser
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory

load_dotenv()

prompt = ChatPromptTemplate.from_messages([
    ("system", """
你是一名专业、耐心的 LangChain 学习助手。
请用中文回答，面向有 Python 基础但刚接触大模型应用的开发者。
回答要清晰、具体，必要时给出简短代码示例。
"""),
    MessagesPlaceholder("chat_history"),
    ("human", "{question}"),
])

model = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
    temperature=0.4,
)

chain = prompt | model | StrOutputParser()

histories = {}


def get_session_history(session_id: str):
    if session_id not in histories:
        histories[session_id] = InMemoryChatMessageHistory()
    return histories[session_id]


chatbot = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="question",
    history_messages_key="chat_history",
)


def ask(question: str, session_id: str = "demo-user"):
    return chatbot.invoke(
        {"question": question},
        config={"configurable": {"session_id": session_id}},
    )


if __name__ == "__main__":
    print("AI:", ask("我想学习 LangChain，应该先理解哪些概念？"))
    print("AI:", ask("那它里面的 Runnable 是什么？"))
    print("AI:", ask("能基于刚才的解释再给一个代码例子吗？"))

1

第三次问：

1

模型能理解“它”和“刚才的解释”，是因为历史消息被保存并重新注入到了 Prompt 中。

这个例子还缺什么？

它适合学习，但还不是生产版本。

生产环境还需要：

  • 把 histories 换成数据库或 Redis。
  • 给 session_id 做鉴权。
  • 控制历史消息长度。
  • 记录错误和调用日志。
  • 处理用户清空会话。
  • 做隐私和敏感信息保护。

十一、生产环境中的 Memory 设计

Memory 在 demo 中很简单，但在真实系统里要认真设计。

1. 存储层选择

内存存储：

1

histories = {}

只适合本地 demo。

生产环境需要持久化：

存储适合场景
Redis高频短期会话、过期自动清理
PostgreSQL / MySQL需要查询、审计、长期保存
MongoDB消息结构灵活、多字段扩展
对象存储大规模归档，不常查询
LangGraph checkpoint图工作流中的状态持久化

2. 会话生命周期

要明确：历史消息保存多久？

常见策略：

  • 浏览器关闭后清除。
  • 24 小时无操作后过期。
  • 用户手动删除。
  • 按项目或对话永久保存。
  • 只保存摘要，不保存完整原文。

不同产品选择不同。

学习助手可以保存更久；客服系统可能要按合规要求保存；涉及隐私的应用则要更谨慎。

3. 隐私和权限

聊天历史可能包含敏感信息。

比如：

  • 个人身份信息
  • 公司内部资料
  • API Key
  • 业务数据
  • 客户信息
  • 健康或金融信息

所以 Memory 不是单纯技术问题，还涉及权限和合规。

至少要考虑：

  • 谁能读取历史？
  • 历史是否加密？
  • 用户能否删除？
  • 日志里是否会泄露？
  • 是否会被用于训练或分析？

4. 清空和重置会话

聊天产品通常需要“新建对话”或“清空上下文”。

否则用户换了一个主题，旧历史可能干扰新回答。

例如用户先聊：

1

帮我学习 LangChain。

后面又问：

1

帮我写一封请假邮件。

如果历史一直保留，模型可能仍然用技术学习助手的风格回答。

所以产品上要提供清晰的会话边界。

十二、常见问题

1. Memory 会让模型永久记住用户吗？

不会。

Memory 是应用层保存上下文。模型本身不会因为一次调用就改变参数。

如果你删除历史记录，下一次不再传入这些历史，模型就不会知道之前聊过什么。

2. 为什么我用了同一个 model 对象，模型还是不记得？

因为模型对象不是会话状态。

你需要显式保存历史消息，并在下一次调用时传给模型。

同一个 ChatOpenAI 实例不会自动保存每次调用内容。

3. MessagesPlaceholder 是 Memory 吗？

不是。

MessagesPlaceholder 只是 Prompt 中的占位符，用来插入历史消息。

真正的 Memory 还需要：

  • 保存历史消息
  • 根据 session_id 读取历史
  • 调用后写入新消息
  • 控制历史长度

4. RunnableWithMessageHistory 会自动持久化到数据库吗？

不会。

它负责把 Runnable 和 Chat History 连接起来。

具体历史存在哪里，取决于你提供的 get_session_history 函数。

如果你返回的是 InMemoryChatMessageHistory，那就是内存。

如果你返回的是数据库实现，那就是持久化存储。

5. 是否应该把所有历史都传给模型？

不应该盲目全部传。

历史越多，成本越高，也越容易干扰模型。

更好的方式是：

  • 最近几轮完整保留。
  • 更早内容做摘要。
  • 重要用户偏好单独长期保存。
  • 无关闲聊不进入长期记忆。

6. Memory 和 RAG 能不能一起用？

可以，而且真实项目里经常一起用。

典型结构是：

1
2
3

用户问题 + 对话历史
  ↓
必要时改写问题
  ↓

  ↓

  ↓

Memory 负责对话连续性，RAG 负责外部知识依据。

十三、最佳实践

1. 先用手动历史理解原理

学习阶段可以先手写：

1
2

chat_history.append(HumanMessage(...))
chat_history.append(AIMessage(...))

理解之后再用 RunnableWithMessageHistory。

这样你不会把 Memory 当成黑盒。

2. 每个会话必须有独立 session_id

不要让所有用户共享一个全局历史。

真实应用中，session_id 应该和当前用户权限绑定。

3. 不要无限追加历史

历史消息一定要有控制策略。

至少要考虑：

  • 最大消息数
  • 最大 token 数
  • 摘要压缩
  • 过期时间
  • 用户手动清除

4. Prompt 中明确区分历史和当前问题

推荐结构：

1
2
3
4
5

prompt = ChatPromptTemplate.from_messages([
    ("system", "..."),
    MessagesPlaceholder("chat_history"),
    ("human", "{question}"),
])

不要把历史和当前问题拼成一大段字符串，消息结构会更清晰。

5. 不要把敏感信息随意写入长期记忆

用户说过的话不代表你就应该永久保存。

尤其是：

  • 密钥
  • 个人信息
  • 公司内部资料
  • 账号密码
  • 客户数据

这些内容要有过滤、加密、过期和删除机制。

6. 新项目优先理解 RunnableWithMessageHistory 和 LangGraph memory

如果你看旧教程，可能会看到大量 ConversationBufferMemory 示例。

学习时可以了解，但新项目更建议掌握：

  • MessagesPlaceholder
  • InMemoryChatMessageHistory
  • RunnableWithMessageHistory
  • LangGraph 的 short-term memory 和 checkpoint

这套思路更适合和 LCEL、Runnable、Agent 工作流结合。

十四、总结

本文我们系统讲了 LangChain 的 Memory 机制。

核心结论是：

大模型 API 本身通常是无状态的。所谓 Memory，本质上是应用层保存历史消息，并在下一次调用时把相关上下文重新传给模型。

本文重点包括：

  • 模型不会自动记住上一次调用。
  • 多轮对话依赖历史消息。
  • Memory 不是修改模型参数，而是应用层上下文管理。
  • MessagesPlaceholder 用于在 Prompt 中插入历史消息。
  • InMemoryChatMessageHistory 可以保存内存中的消息历史。
  • RunnableWithMessageHistory 可以给 LCEL 链路增加自动读写历史的能力。
  • session_id 是多用户、多会话隔离的关键。
  • 旧式 Memory 类仍能看到，但新项目更应该理解 Runnable 和消息历史方式。
  • 历史消息不能无限增长，需要窗口、摘要、长期记忆等策略。
  • 生产环境必须考虑存储、权限、隐私、过期和清空机制。

到这里，我们已经掌握了多轮对话的基础。
