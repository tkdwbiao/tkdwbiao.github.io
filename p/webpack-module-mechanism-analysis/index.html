重点不是还原某个具体平台的参数，而是理解：

请求从哪里发起。

现代前端项目通常不是直接把一个个源码文件原样发给浏览器。

在开发阶段，前端代码通常按模块拆分。

例如：

但浏览器运行时还需要考虑：

缓存优化。

Webpack 的作用可以理解为：

1

三、从一个最小模块系统开始

为了理解 Webpack，我们先写一个极简模块系统。

假设有两个模块。

3

function add(a, b) {
  return a + b;
}

模块 2 使用它：

1

console.log(add(1, 2));

Webpack 打包后的核心思想类似这样：

const modules = {
  1: function (module, exports, require) {
    function add(a, b) {
      return a + b;
    }

    module.exports = { add };
  },

  2: function (module, exports, require) {
    const { add } = require(1);
    console.log(add(1, 2));
  },
};

const cache = {};

function require(moduleId) {
  if (cache[moduleId]) {
    return cache[moduleId].exports;
  }

  const module = { exports: {} };
  cache[moduleId] = module;
  modules[moduleId](module, module.exports, require);
  return module.exports;
}

require(2);

这段代码就是 Webpack 模块机制的简化版。

关键点：

1
2
3
4
5
6

modules：保存所有模块函数。
module：当前模块对象。
exports：当前模块导出的内容。
require：加载其他模块。
cache：模块缓存，避免重复执行。
require(2)：启动入口模块。

真实 Webpack 运行时代码更复杂，但核心思想类似。

四、module、exports 和 require

1. module

module 表示当前模块对象。

它通常有一个 exports 属性。

1

const module = { exports: {} };

模块执行后，外部拿到的就是 module.exports。

2. exports

exports 是导出对象的引用。

常见写法：

1
2
3
4

exports.name = "demo";
exports.add = function (a, b) {
  return a + b;
};

等价理解：

1

module.exports.name = "demo";

3. require

require 用于加载另一个模块。

1

const utils = require(1);

在 Webpack 打包代码里，经常会看到类似：

1

__webpack_require__(123)

它的含义就是：

1
2
3

加载模块 ID 为 123 的模块。
如果缓存里有，就直接返回 exports。
如果没有，就执行模块函数并缓存结果。

理解这三个概念后，再看到打包代码就不会完全陌生。

(() => {
  var __webpack_modules__ = {
    "./src/utils.js": (module) => {
      module.exports = {
        normalizeText(text) {
          return text.trim();
        },
      };
    },

    "./src/api.js": (module, __unused_webpack_exports, __webpack_require__) => {
      const { normalizeText } = __webpack_require__("./src/utils.js");

      async function fetchItems() {
        const response = await fetch("/api/items");
        const data = await response.json();
        return data.items.map((item) => normalizeText(item.title));
      }

      module.exports = { fetchItems };
    },
  };

  var __webpack_module_cache__ = {};

  function __webpack_require__(moduleId) {
    var cachedModule = __webpack_module_cache__[moduleId];
    if (cachedModule !== undefined) {
      return cachedModule.exports;
    }

    var module = (__webpack_module_cache__[moduleId] = { exports: {} });
    __webpack_modules__[moduleId](module, module.exports, __webpack_require__);
    return module.exports;
  }

  const { fetchItems } = __webpack_require__("./src/api.js");
  fetchItems().then(console.log);
})();

这里可以看到：

1

__webpack_modules__：模块表。
__webpack_module_cache__：模块缓存。
__webpack_require__：模块加载函数。
入口模块：最后被 require 的模块。

真实生产代码里，模块 ID 可能不是路径，而是数字。

例如：

1

这时就需要通过搜索关键词、Source Map、调用栈和代码上下文来判断模块作用。

六、为什么模块会被包成函数？

Webpack 会把每个模块包成函数。

原因包括：

1
2
3
4
5

隔离作用域。
模拟 CommonJS / ES Module。
延迟执行模块。
支持模块缓存。
支持依赖注入 require。

如果不包函数，多个文件的变量可能互相污染。

包成函数后，每个模块都有自己的局部作用域。

1
2
3
4

function moduleFunction(module, exports, require) {
  const localVar = "只在当前模块内可见";
  module.exports = { localVar };
}

这和 Python 文件模块也有点类似。

每个文件有自己的命名空间，通过 import / export 连接。

七、ES Module 在 Webpack 中如何表示？

现代前端常用 ES Module。

源码可能是：

1
2
3
4
5
6
7

export function buildParams(page) {
  return { page };
}

export default function request(url) {
  return fetch(url);
}

打包后可能会出现：

1
2
3
4

__webpack_require__.d(__webpack_exports__, {
  buildParams: () => buildParams,
  default: () => request,
});

这里的 .d 通常用于定义导出属性。

你不需要一开始记住所有 runtime 辅助函数。

只要理解：

1
2
3

Webpack 会把 import / export 转成自己的模块导入导出机制。
__webpack_exports__ 存放导出内容。
__webpack_require__ 加载依赖模块。

常见运行时辅助函数可能包括：

1
2
3
4
5

__webpack_require__.d：定义导出 getter。
__webpack_require__.r：标记 ES Module。
__webpack_require__.n：处理默认导出兼容。
__webpack_require__.o：判断对象属性。
__webpack_require__.e：加载异步 chunk。

入门阶段只要能识别它们属于 Webpack runtime，就不会被吓住。

八、chunk 是什么？

一个大型前端项目不会总是打成一个文件。

Webpack 会把代码拆成多个 chunk。

例如：

1
2
3
4

main.js：主入口。
vendor.js：第三方依赖。
article.chunk.js：文章页面按需加载。
admin.chunk.js：后台页面按需加载。

为什么要拆？

1
2
3
4

减少首屏加载体积。
提高缓存命中率。
按路由或功能延迟加载。
第三方依赖单独缓存。

代码中可能出现动态 import：

1
2
3

import("./pages/ArticlePage").then((module) => {
  module.renderArticlePage();
});

打包后会变成类似：

1
2
3

__webpack_require__.e("article-page").then(
  __webpack_require__.bind(__webpack_require__, "./src/pages/ArticlePage.js")
);

含义是：

1
2

先加载 article-page 这个 chunk。
加载完成后再 require 对应模块。

这解释了为什么在 Network 面板里会看到页面操作后才加载新的 JS 文件。

九、Source Map 的作用

Source Map 用于把打包后的代码映射回源码。

如果项目开启了 Source Map，DevTools 里可能能看到：

1
2
3

webpack://src/api/request.js
webpack://src/utils/sign.js
webpack://src/pages/ListPage.vue

这对自有系统调试非常有用。

可以直接定位源码。

但生产环境是否开启 Source Map，要结合安全和调试策略。

对于自有系统：

1
2
3

开发环境建议开启，方便调试。
生产环境要评估是否暴露源码细节。
内部系统可按权限控制调试资源。

对于第三方系统：

1
2

即使能看到 Source Map，也不代表可以越权使用其中逻辑。
仍然要遵守授权、服务条款和访问边界。

const modules = {
  1: function (module) {
    function buildParams(page) {
      return {
        page,
        timestamp: Date.now().toString(),
      };
    }

    module.exports = { buildParams };
  },

  2: function (module, exports, require) {
    const { buildParams } = require(1);

    function buildUrl(path, params) {
      const query = new URLSearchParams(params).toString();
      return `${path}?${query}`;
    }

    function fetchItems(page) {
      const params = buildParams(page);
      const url = buildUrl("/api/items", params);
      console.log("request", url);
    }

    module.exports = { fetchItems };
  },
};

const cache = {};

function require(moduleId) {
  if (cache[moduleId]) {
    return cache[moduleId].exports;
  }

  const module = { exports: {} };
  cache[moduleId] = module;
  modules[moduleId](module, module.exports, require);
  return module.exports;
}

const { fetchItems } = require(2);

十三、压缩和混淆的区别

Webpack 打包后，通常还会经过压缩。

压缩可能包括：

1
2
3
4

删除空白和换行。
缩短变量名。
删除无用代码。
合并表达式。

例如源码：

1
2
3
4

function buildParams(page) {
  const timestamp = Date.now().toString();
  return { page, timestamp };
}

压缩后可能变成：

1

function n(n){return{page:n,timestamp:Date.now().toString()}}

压缩的目标是减少体积和提升加载速度。

混淆则更强调降低可读性。

混淆可能包括：

1
2
3
4
5

字符串数组。
控制流扁平化。
无意义代码插入。
复杂表达式替换。
属性访问变形。

十四、Webpack 分析的合规边界

Webpack 分析是前端工程能力。

不合规场景包括：

如果你在分析中发现接口明显依赖权限、付费、风控或敏感数据访问，应停止并走授权流程。

技术能力越强，越要能说明边界。

十六、常见错误写法

1. 一看到 webpack_require 就慌

它只是模块加载函数。

先找模块表、模块缓存和入口模块，就能理解大概结构。

2. 只搜索 sign，不看调用链

参数可能来自多个模块。

要看：

1
2
3
4
5

页面事件。
业务 API。
请求封装。
Header 构造。
状态读取。

3. 忽略 Source Map

自有系统如果有 Source Map，优先看源码，不要硬读压缩 bundle。

4. 把压缩当成混淆

压缩主要是减小体积。

混淆才是刻意降低可读性。

两者分析方法不同。

5. 不区分授权调试和越界分析

理解 Webpack 机制不代表可以分析任何受限接口。

授权和合规边界始终优先。

复杂前端代码很容易迷路。

十七、面试表达

如果面试官问：

1

Webpack 打包后的代码你怎么看？

可以这样回答：

我会先识别 Webpack 的模块结构，比如模块表、模块缓存和 __webpack_require__。每个源码模块通常会被包装成函数，通过 module、exports 和 require 连接。然后我会结合 Network 的 Initiator、XHR / Fetch 断点和调用栈，定位请求函数、参数构造函数和统一请求封装。如果有 Source Map，会优先回到源码分析。

如果问：

1

module、exports、require 分别是什么？

可以这样回答：

module 表示当前模块对象，exports 是模块对外导出的内容，require 用来加载其他模块。Webpack 会把每个模块包装成函数，执行时传入 module、exports 和 __webpack_require__。模块执行后，外部拿到的是 module.exports；同时 Webpack 会用模块缓存避免重复执行同一个模块。

如果问：

1

chunk 是什么？

可以这样回答：

chunk 是 Webpack 输出的一段代码块。大型项目不会总是打成一个 JS 文件，而是会把主入口、第三方依赖和按需加载页面拆成不同 chunk。比如路由懒加载时，用户进入某个页面才加载对应 chunk。调试时如果请求函数在异步 chunk 中，需要先触发页面操作，让 chunk 加载后再看调用栈和模块内容。

如果问：

1

Webpack 分析和 JS 逆向有什么边界？

可以这样回答：

Webpack 分析本质上是前端工程和调试能力，适合自有系统、授权测试、请求链路排查和前后端参数一致性检查。它可以帮助理解模块依赖、请求封装和参数来源。但如果涉及第三方受限接口、付费内容、访问控制或风控系统，就不应该做绕过式分析，应该走授权接口或正式数据通道。

十八、总结

本文讲了 Webpack 模块机制分析。

核心结论包括：

  • Webpack 会从入口文件出发，分析依赖关系，把多个模块打包成浏览器可加载的 bundle。
  • 打包后的核心结构通常包括模块表、模块缓存、模块加载函数和入口模块。
  • module 表示当前模块对象，exports 表示导出内容，require / __webpack_require__ 用来加载依赖模块。
  • 每个模块被包装成函数，是为了隔离作用域、支持缓存和模拟模块系统。
  • ES Module 的 import / export 会被转换成 Webpack runtime 的导入导出逻辑。
  • chunk 是代码拆分后的输出单元，常用于路由懒加载、第三方依赖缓存和按需加载。
  • Source Map 可以把打包代码映射回源码，自有系统调试时应优先使用。
  • 定位请求函数可以结合 Network Initiator、接口关键词、统一请求封装、XHR / Fetch 断点和调用栈。
  • 压缩和混淆不同，压缩主要减小体积，混淆更强调降低可读性。
  • Webpack 分析应服务于授权调试、前端工程理解和自动化测试排查，不应被用于绕过访问控制或风控系统。
  • LLM / Agent 可以辅助解释模块结构和调用链，但必须保持合规边界。
