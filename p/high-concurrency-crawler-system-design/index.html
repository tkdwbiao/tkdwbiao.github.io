这一篇把这些能力串起来，讨论一个完整问题：

如果要设计一个稳定、合规、可扩展的高并发爬虫系统，整体架构应该是什么样？

这里仍然要强调边界。

本文讨论的是自有系统、授权数据源、公开允许访问的数据、内部测试环境中的数据采集系统设计。

不讨论绕过访问控制、突破风控、规避封禁、批量滥用第三方服务等做法。

很多人对高并发爬虫的第一反应是：

如何处理失败？
如何监控和告警？

而是设计一个：

可恢复。
可观测。

可审计。
合规。

的数据采集系统。

二、高并发爬虫系统的目标

在工程里，“高并发”不能只用 QPS 衡量。

更完整的目标包括：

1
2
3
4
5
6
7

吞吐：单位时间能处理多少任务。
稳定：长时间运行不崩溃、不积压失控。
延迟：任务从创建到完成需要多久。
准确：解析结果正确，重复率可控。
恢复：失败后能重试、暂停或人工处理。
观测：能知道系统现在发生了什么。
合规：遵守授权范围、robots、频率和数据边界。

这意味着系统设计要同时考虑两类问题。

第一类是性能问题：

1
2
3
4
5
6

并发模型。
队列长度。
Worker 数量。
数据库写入能力。
Redis 压力。
网络超时。

第二类是控制问题：

1
2
3
4
5
6
7

限流。
重试。
任务状态。
失败分类。
暂停策略。
人工复核。
日志审计。

高并发爬虫系统不是把所有限制拿掉。

恰恰相反，它需要更多控制面。

这里有一个重要思想：

1

抓取、解析、存储、监控要解耦。

不要让一个函数从请求、解析、入库、重试、告警全部做完。

小脚本可以这么写。

工程系统不应该这么写。

为什么要有数据源配置？

因为不同站点和业务的规则不同。

1
2
3
4
5

有的数据源只允许低频访问。
有的数据源有正式 API。
有的数据源需要登录授权。
有的数据源只采集公开列表页。
有的数据源出错后必须暂停。

如果系统没有数据源层，就只能在代码里写大量 if / else。

后期很难维护。

任务生成器不应该直接高并发抓取。

它只负责创建任务。

真正执行由队列和 Worker 完成。

六、任务队列

队列是高并发系统的缓冲层。

它的作用包括：

1
2
3
4
5

削峰。
解耦生产和消费。
控制消费速度。
支持失败重试。
观察积压情况。

常见选择包括：

1
2
3
4
5

Redis List。
Redis Stream。
RabbitMQ。
Kafka。
数据库任务表。

不同方案适合不同规模。

方案适合场景
数据库任务表规模较小、实现简单、需要强状态查询
Redis List简单队列、轻量任务
Redis Stream需要消费组和确认机制
RabbitMQ任务型消息、路由和确认机制较强
Kafka高吞吐日志流、事件流处理

对于多数中小型爬虫系统，可以从：

1

MySQL 任务表 + Redis 队列

开始。

MySQL 保存任务事实。

Redis 负责调度加速。

七、调度器

调度器负责决定“现在谁可以执行”。

它不是简单从队列里取任务。

它还要检查：

1

数据源是否启用。
是否达到全局限流。
是否达到数据源限流。
是否达到账号或授权限流。
任务是否已过期。
任务状态是否允许执行。
是否处于暂停或人工复核状态。

def can_dispatch(task: CrawlTask, source: SourceConfig) -> bool:
    if not source.enabled:
        return False

    if task.status not in {"queued", "retrying"}:
        return False

    if not is_url_allowed(task.url, source.allowed_paths):
        return False

    if not source_rate_limiter.allow(source.source_id):
        return False

    return True

注意这个函数里没有任何“绕过限制”的逻辑。

高并发系统的专业性在于尊重边界并稳定执行。

@dataclass

Worker 不应该无限重试。

它应该把失败交给失败分类和调度系统。

例如：

1
2
3
4
5
6
7

200：进入解析。
301/302：按规则处理重定向。
401/403：授权或权限问题，暂停。
404：标记不存在或失效。
429：限流，降频。
5xx：临时错误，有限重试。
验证码或风控页：暂停并人工确认。

这和前面几篇文章的思路一致：

1
2

失败要分类。
不是所有失败都重试。

九、解析 Worker

解析 Worker 负责把原始响应变成结构化数据。

根据页面类型，可能使用：

1
2
3
4
5
6
7

解析层要注意：

1
2
3
4

解析规则版本化。
字段缺失要记录。
异常页面要分类。
不要把解析失败直接当成抓取失败。

例如页面抓取成功，但解析不到标题，可能原因是：

1
2
3
4
5

返回登录页。
返回空页面。

所以解析结果也应该结构化：

4

存储层要处理三类数据：

常见设计是：

1
2
3
4

MySQL：任务表、结果表、批次表、失败日志。
Redis：队列、限流、短期去重、锁。
对象存储：大体积 HTML、截图、附件。

结果入库要注意：

1

3
4
5
6

唯一键。

upsert。
更新时间。
采集批次。

任务状态更新要注意：

1
2
3
4

领取任务时原子更新。
执行结束后写回状态。
超时 running 任务要恢复。
失败原因要记录。

存储层不是最后一步。

它也是系统恢复的依据。

十二、限流与背压

高并发系统必须有背压。

背压的意思是：

1

当下游处理不过来时，上游要减速。

否则队列会越来越长，数据库会越来越慢，失败会越来越多。

常见背压信号包括：

1
2
3
4
5
6

队列积压过高。
数据库写入延迟升高。
HTTP 429 增加。
5xx 错误增加。
解析失败率升高。
Worker CPU 或内存过高。

系统可以采取这些动作：

1
2
3
4
5
6

降低数据源并发。
暂停低优先级任务。
延迟重试。
扩容 Worker。
拆分队列。
进入人工复核。

限流不是失败。

限流是系统自我保护。

高并发爬虫系统的失败类型很多。

解析失败。
存储失败。
数据质量失败。

不同失败要有不同处理：

失败类型示例处理方式
网络临时失败超时、连接断开有限重试
5xx服务端临时异常延迟重试
404页面不存在标记失效
401/403登录态或权限问题暂停并检查授权
429限流降频、延迟
验证码或风控安全验证页暂停人工确认
解析失败字段缺失记录样本、更新规则
入库失败唯一键冲突、连接异常分类处理

重试策略要满足：

1
2
3
4
5

有限次数。
指数退避。
记录原因。
可观测。
可人工介入。

告警可以包括：

3
4
5
6

监控的目标不是“看起来很专业”。

而是让系统问题能被快速定位。

十五、合规和安全边界

高并发爬虫系统必须有边界控制。

应明确：

1
2
3
4
5
6
7

数据源是否授权。
采集范围是否清晰。
频率是否符合规则。
是否有正式 API。
是否涉及个人信息。
是否需要脱敏。
是否需要人工审批。

系统中可以设计合规保护：

1
2
3
4
5
6
7

数据源启停开关。
最大频率限制。
敏感字段脱敏。
异常页面暂停。
验证码和风控暂停。
操作审计日志。
人工复核队列。

如果任务触发验证码、登录异常、权限异常或风控提示，应暂停。

不要把高并发能力用于扩大未授权访问。

这是本系列反复强调的底线。

十六、LLM / Agent 在系统中的位置

LLM / Agent 可以增强采集系统，但不应该替代调度规则。

适合使用的场景包括：

1
2
3
4
5
6
7

失败日志总结。
异常页面分类。
解析字段缺失诊断。
非结构化文本抽取。
数据质量检查。
生成修复建议。
生成复盘报告。

例如，一个 Agent 可以读取任务日志后回答：

1
2
3
4
5

最近失败是否集中在某个数据源？
是否 429 明显升高？
是否页面结构发生变化？
是否应暂停任务？
是否需要人工复核？

安全提示词可以是：

1
2
3
4

你是数据采集系统的合规诊断助手。
请根据任务日志、状态码、解析结果和监控指标分析失败原因。
只允许建议降频、暂停、更新解析规则、检查授权、人工复核或申请正式接口。

def run_scheduler():
    tasks = load_ready_tasks(limit=100)

    for task in tasks:
        source = load_source_config(task.source_id)

        if not can_dispatch(task, source):
            continue

        if not mark_task_running(task.task_id):
            continue

        result = fetch(task.url)
        decision = classify_fetch_result(result)

        if decision == "parse":
            parse_result = parse_page(result.body)
            if parse_result.ok:
                item = clean_item(parse_result.data)
                save_item(item)
                mark_task_succeeded(task.task_id)
            else:
                mark_task_failed(task.task_id, parse_result.error_reason)

        elif decision == "retry":
            schedule_retry(task.task_id)

        elif decision == "pause":
            mark_task_manual_review(task.task_id)

        else:
            mark_task_failed(task.task_id, result.error_type)

十八、常见错误写法

1. 只追求并发数

并发数高不代表系统好。

如果没有限流、重试和监控，高并发只会放大故障。

2. 抓取和解析强耦合

一个函数同时做请求、解析、入库和重试，会让系统难以扩展和排查。

3. 没有任务状态

没有状态就无法恢复。

系统重启后不知道哪些任务成功、哪些失败、哪些正在执行。

4. 所有失败都重试

这会造成故障风暴。

权限、验证码、风控、参数错误都不应该盲目重试。

5. 不做去重

任务重复、结果重复、内容重复会造成大量浪费和数据污染。

6. 不做监控

没有指标和日志，系统只能靠猜。

7. 忽视合规边界

高并发采集能力必须服务于授权和合规场景。

不能用来冲击第三方服务或绕过规则。

十九、面试表达

如果面试官问：

1

如何设计一个高并发爬虫系统？

可以这样回答：

我会把系统拆成数据源配置、任务生成、去重、队列、调度器、抓取 Worker、解析 Worker、清洗入库、监控告警和人工复核几个模块。任务先经过 URL 规范化和去重，再进入队列。调度器根据数据源限流、任务状态和优先级分发任务。Worker 抓取后做失败分类，成功则进入解析和清洗，最终通过唯一约束和内容指纹入库。系统通过监控观察队列积压、成功率、状态码分布、解析成功率和重试情况。

如果问：

1

高并发爬虫如何控制稳定性？

可以这样回答：

稳定性主要靠队列削峰、限流、背压、失败分类、有限重试和监控。不能无限并发，也不能所有失败都重试。遇到 429 要降频，遇到 401/403 要检查授权，遇到验证码或风控要暂停人工确认。数据库写入和解析也要有指标，避免只关注请求层。

如果问：

1

MySQL 和 Redis 在系统里怎么用？

可以这样回答：

MySQL 保存长期事实，比如任务主表、结果表、批次和审计日志；Redis 用于短期高频状态，比如任务队列、URL 去重、限流计数和分布式锁。最终一致性靠 MySQL 的唯一约束和任务状态兜底，Redis 主要负责加速和削峰。

如果问：

1

LLM / Agent 能怎么增强爬虫系统？

可以这样回答：

Agent 可以辅助失败诊断、异常页面分类、字段缺失分析、非结构化内容抽取、数据质量检查和复盘报告生成。它应该作为诊断和抽取能力接入系统，而不是用来绕过访问控制、验证码、风控或频率限制。

二十、总结

本文讲了高并发爬虫系统设计。

核心结论包括：

  • 高并发爬虫不是简单提高线程数或 QPS，而是系统化的任务调度和数据处理能力。
  • 一个完整系统应包含数据源配置、任务生成、去重、队列、调度器、抓取 Worker、解析 Worker、清洗入库、监控告警和人工复核。
  • 数据源配置用于管理授权范围、频率限制、启停状态和负责人。
  • 任务生成器负责 URL 规范化、任务幂等、范围检查和优先级设置。
  • 队列用于削峰、解耦、控制消费速度和观察积压。
  • 调度器要检查任务状态、数据源状态、限流和合规边界。
  • 抓取 Worker 应处理超时、状态码、响应大小、错误分类和日志。
  • 解析 Worker 应关注页面类型、字段缺失、规则版本和解析质量。
  • 存储层要区分任务状态、原始响应和结构化结果。
  • 限流和背压是系统稳定性的核心，不是性能障碍。
  • 失败必须分类，重试必须有限、退避、可观测。
  • 监控指标应覆盖任务、队列、抓取、解析、入库、重试和人工复核。
  • 合规边界应内置到系统中，遇到验证码、风控、权限异常应暂停。
  • LLM / Agent 适合做诊断、抽取、质量检查和复盘，不适合做绕过策略。
  • 面试表达要从“我能写高并发脚本”升级为“我能设计稳定、合规、可观测的数据采集系统”。
