二、Python 基础问题

1. Python 在爬虫里常用哪些能力？

可以回答：

Python 在爬虫里主要用到请求库、HTML 解析、正则、异步并发、数据清洗、数据库操作和任务调度。比如 Requests / HTTPX 负责请求，BeautifulSoup / lxml 负责解析，re 做局部模式提取，asyncio 或多线程处理 IO 并发，SQLAlchemy / PyMySQL 写 MySQL，redis-py 管理队列和状态。

重点不是列库。

而是说明每类能力服务什么工程环节。

2. 多线程、多进程、异步 IO 怎么选？

可以回答：

爬虫大多数是 IO 密集型任务，请求和等待网络响应占主要时间，所以多线程或异步 IO 都可以提升吞吐。异步 IO 更适合大量并发 HTTP 请求，线程模型更容易理解和接入传统阻塞库。多进程更适合 CPU 密集型任务，比如复杂解析、图片处理或本地模型推理。工程上还要结合限流，不能只追求并发数。

关键点：

1
2
3

IO 密集。
CPU 密集。
并发不是越高越好。

三、HTTP / HTTPS 问题

1. 一个 HTTP 请求包括什么？

可以回答：

一个 HTTP 请求包括请求方法、URL、Header、Cookie、Query 参数、请求体等部分。服务端返回状态码、响应头和响应体。爬虫中要关注 User-Agent、Accept、Referer、Content-Type、Cookie、Authorization、状态码、重定向和编码。

2. 常见状态码怎么处理？

可以回答：

200 表示请求成功，可以进入解析；301/302 要按规则处理重定向；400 通常是参数错误；401 表示未认证；403 表示权限不足或访问被拒；404 表示资源不存在；429 表示请求过频，应降频或暂停；5xx 多是服务端临时异常，可以有限重试。

3. HTTPS 的作用是什么？

可以回答：

HTTPS 在 HTTP 之上增加 TLS，用于加密传输、验证服务端身份、防止中间人窃听和篡改。数据采集和抓包分析要尊重 HTTPS 和证书校验机制，尤其在 App 场景中，不应提供绕过证书校验或访问控制的方案。

四、Requests 问题

1. Requests 和 Session 有什么区别？

可以回答：

requests.get 每次都是相对独立的请求，而 Session 可以复用连接、保留 Cookie、统一 Header 和代理配置。涉及登录态、连续访问和性能优化时，Session 更合适。但登录态和 Cookie 应该只用于授权范围内的采集。

2. 请求为什么要设置 timeout？

可以回答：

不设置 timeout，网络异常时请求可能长时间阻塞，导致 Worker 卡死、队列积压。工程上要设置连接超时和读取超时，并配合有限重试和失败分类。

3. 重试怎么设计？

可以回答：

重试要分类，不是所有失败都重试。网络超时、连接断开、部分 5xx 可以有限重试；参数错误、权限不足、登录失效、验证码、风控、资源不存在不应盲目重试。重试要有最大次数、指数退避、日志记录和死信队列。

五、Cookie、Session 与登录态

1. Cookie 和 Session 的关系是什么？

可以回答：

Cookie 是浏览器或客户端保存的小段状态，Session 通常是服务端保存的会话状态。服务端通过 Cookie 中的 session_id 识别用户会话。爬虫中遇到登录态时，要确认授权范围，不应使用来源不明的 Cookie 或批量滥用账号状态。

2. Token、JWT 和 Cookie 有什么区别？

可以回答：

Cookie 是一种浏览器存储和传输机制，Token 是认证凭证的一种形式，JWT 是一种自包含的 Token 格式。JWT 通常包含用户信息、过期时间和签名。无论哪种方式，本质都是身份凭证，需要安全存储、日志脱敏和授权使用。

3. 登录态失效怎么办？

可以回答：

登录态失效时应把任务标记为 auth_required 或 manual_review，暂停相关任务，通知重新授权或检查权限。不要无限重试，也不要尝试绕过认证流程。

六、HTML 解析问题

1. BeautifulSoup 适合什么场景？

可以回答：

BeautifulSoup 适合解析结构相对清晰的 HTML，查找标签、属性、文本、表格和局部节点。它容错性较好，适合处理不完全规范的 HTML。对于性能要求更高或 XPath 支持更强的场景，可以结合 lxml。

2. XPath 和 CSS Selector 怎么选？

可以回答：

CSS Selector 写法简洁，适合按 class、id、标签层级选择元素；XPath 表达能力更强，适合按文本、父子关系、兄弟节点和复杂路径定位。工程上更重要的是选择器稳定性，不要过度依赖易变的 class 或过深路径。

3. 选择器失效怎么办？

可以回答：

选择器失效时不要只看单个页面，要看失败比例、字段缺失分布、页面标题和 HTML 样本。可能是页面结构变化、返回登录页、返回错误页、字段本身缺失或清洗逻辑误删。应保存样本、更新规则、增加监控，必要时进入人工复核。

七、正则表达式问题

1. 正则适合做什么？

可以回答：

正则适合局部文本模式提取，比如价格、日期、编号、URL、JSON 片段中的简单字段。不适合解析完整 HTML 或复杂 JavaScript，因为 HTML 和 JS 都有嵌套结构，更适合用 DOM 解析器或 AST。

2. 贪婪和非贪婪有什么区别？

可以回答：

贪婪匹配会尽可能多地匹配内容，非贪婪匹配会尽可能少地匹配。爬虫中如果用正则提取局部片段，要注意边界，否则容易匹配过多或过少。

八、动态页面问题

1. Selenium 和 Playwright 有什么区别？

可以回答：

Selenium 是传统 WebDriver 生态，兼容性强，适合自动化测试；Playwright 更现代，支持多浏览器、自动等待、网络监听、上下文隔离和更好的开发体验。数据采集中，如果页面数据来自异步请求，优先分析网络请求；确实需要渲染时再使用浏览器自动化。

2. 动态页面采集一定要用浏览器吗？

可以回答：

不一定。应先分析 Network，看数据是否来自接口。如果接口在授权范围内且规则允许，直接请求接口通常更稳定、更低成本。只有数据必须通过渲染获得，或者需要截图、页面状态诊断时，才使用 Selenium 或 Playwright。

3. 自动化遇到验证码怎么办？

可以回答：

验证码是风险信号，不是普通解析失败。自动化任务应标记为 captcha_required 或 manual_review，保存截图、URL、状态码、账号和数据源上下文，暂停任务并人工确认，检查频率、授权和正式接口，不应接入验证码绕过流程。

九、反爬机制问题

1. 常见反爬策略有哪些？

可以回答：

常见策略包括请求频率限制、IP 风险、User-Agent 和 Header 检查、Cookie 和登录态校验、Referer 校验、Token 或签名参数、JS 动态渲染、设备指纹、行为轨迹、验证码和风险评分。理解这些机制是为了设计合规、低影响、可审计的采集系统，而不是绕过规则。

2. 遇到 429 怎么办？

可以回答：

429 表示请求过频，应降低频率、延迟重试、暂停相关数据源或检查任务策略。不能继续高频重试。系统上可以通过数据源级限流、指数退避和队列调度控制。

3. 如何设计低影响采集？

可以回答：

首先确认授权和数据范围，优先使用正式 API、公开导出或站点允许的访问方式。技术上控制频率、设置合理超时、缓存结果、做增量采集、避免重复请求、监控状态码和失败率，异常时暂停而不是放大请求。

十、JS 逆向与 Webpack 问题

1. JS 逆向你怎么理解？

可以回答：

我把 JS 逆向理解为在授权场景中分析前端请求链路、参数来源、模块结构和调用栈。常用 DevTools、Network、Sources、XHR/fetch breakpoint、调用栈和 Source Map。涉及第三方访问控制、付费接口或风控系统时，应遵守授权边界，不做绕过式还原。

2. Webpack 打包代码怎么看？

可以回答：

Webpack 会把模块包装成 module、exports、require 结构，运行时通过 webpack_require 管理模块缓存和依赖。分析时优先看 Source Map；没有 Source Map 时，通过 Network Initiator、调用栈、关键词和模块边界缩小范围，不要一上来全局扣代码。

3. AST 有什么用？

可以回答：

AST 把代码从字符串变成结构化语法树，可以识别函数调用、变量声明、字符串字面量、作用域和表达式。它比正则处理 JavaScript 更可靠。自有系统中可以用于代码审计、接口调用统计、批量重构和安全检查。

十一、App 抓包与 Hook 问题

1. App 抓包和 Web 抓包有什么区别？

可以回答：

Web 主要通过浏览器 DevTools 看 Network、Cookie、localStorage 和 JS 调用链；App 运行在 Android / iOS 环境，请求可能经过 OkHttp、Retrofit、Native SDK 或自研网络层，状态可能来自 Token、设备信息、本地存储和 SDK。App 分析涉及隐私、证书校验和风控，边界更严格。

2. Frida Hook 是什么？

可以回答：

Frida 是动态插桩工具，可以在运行时观察函数调用、参数和返回值。Hook 的思想是在函数执行前后插入观察逻辑。它适合自有 App 调试、安全审计和授权测试，不应该用于绕过证书校验、登录权限、验证码或风控系统。

十二、验证码问题

1. 你怎么理解验证码？

可以回答：

验证码是风控系统中的挑战机制，不是单纯图片识别问题。它通常在风险评分升高时触发，比如请求频率异常、账号状态异常、设备变化、登录失败或敏感操作。自动化任务遇到验证码应暂停、记录、人工确认，而不是继续识别或绕过。

2. OCR 能不能识别验证码？

可以回答：

OCR 可以用于自有系统的验证码难度评估、无障碍研究和测试样本分类。但在真实业务中批量用 OCR 识别验证码并继续自动化流程，会破坏访问控制和风控边界，不属于合规采集。

十三、任务调度问题

1. 爬虫任务状态怎么设计？

可以回答：

可以设计 pending、queued、running、succeeded、retrying、rate_limited、auth_required、captcha_required、manual_review、failed、dead 等状态。状态机能让任务可恢复、可暂停、可重试、可复核，不会把所有异常都混成失败。

2. 队列有什么作用？

可以回答：

队列用于削峰、解耦生产和消费、控制执行速度、支持延迟重试和观察积压。任务生成器只负责生成任务，Worker 从队列消费。这样系统更可控，也方便扩容。

3. 死信队列是什么？

可以回答：

死信队列用于存放超过最大重试次数、参数非法、权限不足或人工确认不可继续的任务。它不是垃圾桶，而是复盘和排查入口。

十四、MySQL / Redis 问题

1. MySQL 和 Redis 怎么分工？

可以回答：

MySQL 保存长期事实，比如任务表、结果表、数据源配置、采集批次和审计日志；Redis 用于短期高频状态，比如任务队列、URL 去重、限流计数、分布式锁和 Worker 心跳。最终一致性靠 MySQL，Redis 负责加速和削峰。

2. URL 去重怎么做？

可以回答：

先做 URL 规范化，比如统一域名大小写、移除 fragment、排序 query 参数、删除无意义跟踪参数，再计算 hash。短期可以用 Redis Set 或 Bloom Filter 判断，长期用 MySQL 的 source + url_hash 唯一索引兜底。

3. 布隆过滤器适合什么场景？

可以回答：

布隆过滤器适合大规模 URL 去重，内存占用低、判断快，但可能误判存在，不会误判不存在。适合允许少量漏抓的场景，不适合必须 100% 精确的业务。工程上可以作为第一层过滤，后面用 Redis 或 MySQL 精确兜底。

十五、FastAPI 问题

1. FastAPI 在爬虫系统里做什么？

可以回答：

FastAPI 适合作为管理平台接口层，提供任务创建、任务查询、结果分页、数据源配置、人工复核和诊断报告接口。它不应该直接执行耗时爬虫，而是写任务表、推送队列，由 Worker 异步执行。

2. Pydantic 有什么价值？

可以回答：

Pydantic 用于请求和响应模型定义、字段校验、类型转换和接口文档生成。它既是校验层，也是前后端接口契约。LLM 抽取中也可以用 Pydantic 校验模型输出 JSON。

十六、Docker / Linux 问题

1. 爬虫系统怎么部署？

可以回答：

可以把系统拆成 API、Worker、Scheduler、MySQL、Redis、日志和配置。开发测试用 docker-compose 一键启动依赖；生产环境用 Docker 镜像部署 API 和 Worker，通过环境变量注入配置，日志结构化输出，MySQL 和 Redis 做持久化和监控。

2. 不用 Docker 怎么部署？

可以回答：

可以在 Linux 上用 venv 管理 Python 依赖，用 systemd 管理 API 和 Worker 进程，实现开机自启和异常重启，用 cron 或独立 Scheduler 触发定时任务，用 journalctl 或日志文件排查问题。关键是配置、日志、数据和代码分离。

十七、LLM 数据抽取问题

1. LLM 怎么用于数据抽取？

可以回答：

我不会用 LLM 替代所有解析规则。稳定字段优先用 XPath、CSS Selector、JSON 解析和正则。LLM 更适合半结构化页面、正文理解、字段归一化、摘要、关键词和主题分类。工程上会先清洗输入，再让模型输出 JSON，通过 Pydantic Schema 和业务规则校验后入库或人工复核。

2. 如何保证 LLM 输出可靠？

可以回答：

先定义 Schema，再要求模型只输出 JSON，字段缺失返回 null，不允许编造。输出后做 JSON 解析、Pydantic 校验、业务规则校验和置信度判断。低置信度或校验失败进入人工复核，不直接入库。

3. LLM 成本怎么控制？

可以回答：

能用规则解决的字段不用 LLM；调用前做正文清洗和截断；相同 content_hash 复用缓存；LLM 抽取异步化并单独限流；失败有限重试；只对高价值或复杂字段调用模型。

十八、AI Agent 问题

1. Agent 在爬虫系统里有什么用？

可以回答：

Agent 更适合做诊断和编排助手。它可以读取任务日志、状态码、页面摘要、解析结果和数据源配置，分析失败原因，比如网络异常、解析规则失效、字段缺失、权限问题或限流问题，然后输出结构化建议，如重试、降频、人工复核、检查授权或更新解析规则。

2. 如何防止 Agent 误操作？

可以回答：

我会限制 Agent 输出动作枚举，而不是让它自由执行。系统只接受白名单动作，并用 Schema 校验输出。低置信度进入人工复核，高风险动作如暂停数据源、修改规则、恢复授权任务必须人工确认。上下文要脱敏，系统提示词明确禁止绕过访问控制、验证码和风控。

十九、系统设计综合问题

1. 如何设计一个高并发爬虫系统？

可以回答：

我会拆成数据源配置、任务生成、去重、队列、调度器、抓取 Worker、解析 Worker、清洗入库、监控告警和人工复核。任务先规范化和去重，再进入队列。调度器根据数据源限流和任务状态分发任务。Worker 抓取后做失败分类，成功则解析清洗并入库。系统监控队列积压、成功率、状态码、解析成功率、重试和人工复核。

2. 如何设计一个大模型增强的智能采集系统？

可以回答：

系统包含 FastAPI 管理平台、任务调度层、Crawler Worker、解析清洗层、LLM 抽取层、Agent 诊断层和 MySQL / Redis 存储层。传统规则负责稳定字段抽取，LLM 负责复杂文本的 Schema 化抽取，Agent 负责失败诊断和复核建议。任务通过队列异步执行，失败分类处理，敏感边界进入人工复核，系统通过 Docker 部署并监控运行指标。

二十、行为边界类问题

1. 如果面试官问“你会不会破解验证码”？

可以回答：

我了解验证码的类型和识别技术，比如 OCR、目标检测和多模态理解，也知道它们可以用于自有系统测试、难度评估和无障碍研究。但真实业务验证码是风控挑战机制，不应该被自动化绕过。工程上我会把验证码触发作为风险信号，暂停任务、记录上下文、人工复核，并检查授权、频率和正式接口。

2. 如果问“你会不会做抢票系统”？

可以回答：

我会从高并发预约系统设计角度回答，比如队列、状态机、限流、重试、幂等、库存占位、监控和公平性设计。我不会讨论真实平台抢占公共资源或绕过规则的脚本。自有或授权场景下，我可以设计稳定的预约任务调度系统。

3. 如果问“如何对抗反爬”？

可以回答：

我更倾向于说理解反爬机制和合规采集策略。包括频率控制、缓存、增量采集、失败分类、人工复核、正式 API 优先、日志审计和低影响访问。对于访问控制、验证码、风控或授权不明的场景，应暂停并走授权流程，而不是绕过。

我做过一个大模型增强的数据采集系统。系统用 FastAPI 提供任务管理、数据源配置、结果查询和人工复核接口；MySQL 保存任务、结果、配置和审计日志；Redis 用于任务队列、URL 去重、限流和 Worker 心跳。任务创建后进入队列，由 Crawler Worker 按数据源限流执行，抓取成功后先用 BeautifulSoup、XPath、CSS Selector 等规则解析和清洗，再对复杂正文调用 LLM 做 Schema 化抽取。LLM 输出 JSON 后通过 Pydantic 和业务规则校验，低置信度进入人工复核。Agent 读取任务日志、状态码、页面摘要和缺失字段，生成失败诊断和处理建议。系统用 Docker 部署，监控队列积压、成功率、解析失败率、LLM 成本和人工复核比例。涉及验证码、权限、风控等边界时，任务会暂停并进入人工复核，不做自动绕过。
