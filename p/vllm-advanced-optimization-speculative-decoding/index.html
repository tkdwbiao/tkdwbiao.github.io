vLLM 系列(五)：极致优化的前沿 —— Chunked Prefill 与投机解码

2026-04-06 18:40
阅读时长: 4 分钟

进入 2026 年，大模型已经全面迈入百万上下文（1M+ Context）时代。在如此恐怖的长度下，传统的推理调度方案已经捉襟见肘。

用户不再满足于“能跑通”，他们要求在处理万字长文的同时，回答速度还能像打字机一样流畅。今天阿彪带你拆解 vLLM 压榨性能的两大高阶黑科技：Chunked Prefill（分块预填充） 与 Speculative Decoding（投机解码）。

一、 Chunked Prefill：终结长文本带来的“顿挫感”

在 vLLM 的早期版本中，新请求的 Prefill（预填充）阶段具有最高优先级。

1. 为什么“新人”会卡死“老人”？

当一个 128k 长度的请求进来时，计算 $Q, K, V$ 并填充 KV Cache 需要消耗巨大的计算量。此时，GPU 会全量投入这个 Prefill 任务，导致正在生成答案的其他请求（Decode 阶段）全部挂起。

对于用户来说，这种“顿挫感（Jitter）”是不可接受的。

2. 调度策略的进化：分块与交织

vLLM 引入了 Chunked Prefill 机制。它不再试图一次性吞下整个长 Prompt，而是将其切分为若干个块（Chunks）。

在每一次迭代（Iteration）中，调度器会巧妙地将一小块 Prefill 任务与当前的 Decode 批次混合在一起。

  • 公平性：新请求依然在推进，不会被饿死。
  • 流畅性：老请求的生成节奏不被打断，首字延迟（TTFT）与逐字延迟（TPOT）达到了完美的平衡。

二、 Speculative Decoding：用概率挑战物理带宽

大模型推理本质上是 Memory-Bound（访存受限） 的。每次预测一个 token，都要把几十 GB 的参数从 HBM 读到计算核心，而计算本身只花了一点点时间。

1. “猜想-验证”模式

投机解码的核心思想是：用极小的代价去“赌”未来的输出。

  1. 草稿阶段：由一个轻量级模型（或 Medusa 头）快速预测接下来的 $N$ 个 token。由于它体积小，速度极快。
  2. 验证阶段：主模型（如 Llama-3-70B）一次性读取权重，同时验证这 $N$ 个预测是否正确。

如果 $N=5$，且草稿模型猜对了 3 个，那么这一轮迭代我们就直接拿到了 3 个 token。相对于原来“读一次权重出一颗词”，现在变成了“读一次权重出三颗词”，效率直接起飞。

2. 2026 年的新标配：Medusa 与 FP8

在 2026 年，我们已经很少看到额外挂载小模型的投机解码了。目前主流是 Medusa（美杜莎） 方案：在主模型的输出层并联几个微型预测头。

配合 Blackwell 架构的 FP8 推理，验证过程的延迟进一步降低。在代码编写、结构化数据提取等任务中，投机解码的实际加速比通常能稳定在 2.0x 以上。

def verify_speculative_tokens(main_logits, draft_tokens):
    """
    模拟主模型验证草稿序列
    main_logits: 主模型一次性算出的所有位置概率
    draft_tokens: 草稿模型猜的序列
    """
    accepted_tokens = []
    for i, draft_token in enumerate(draft_tokens):
        # 找到主模型在第 i 个位置认为概率最大的词
        true_token = torch.argmax(main_logits[i])
        
        if draft_token == true_token:
            # 猜对了，收下
            accepted_tokens.append(draft_token)
        else:
            # 猜错了，止损！
            # 这一步非常关键：即便猜错了，主模型当前的正确结果也要带走
            accepted_tokens.append(true_token)
            break
            
    return accepted_tokens

阿彪点评：这种机制最优雅的地方在于，即使草稿模型全是瞎猜，系统最差的情况也只是退化回原始的逐字生成，绝对不会影响输出的正确性。

四、 面试官会问到的问题及详细答案

❓ Q1：在长文本场景下，除了 Chunked Prefill，还有什么办法优化 TTFT？

答： 可以引入 Prefix Caching（前缀缓存）。对于 RAG 场景或长系统提示词，vLLM 会缓存这些公共前缀的 KV Cache。如果命中缓存，Prefill 阶段几乎被缩减为零，TTFT 会从秒级降至毫秒级。

❓ Q2：投机解码为什么能增加吞吐量（Throughput）？

答： 因为它提升了 算力利用率（MFU）。 在传统的 Decode 阶段，GPU 的计算单元大部分时间在等待显存读取。投机解码通过一次验证多个 token，增加了每一轮迭代的计算负载，使得原本闲置的计算核心得到了利用，从而在单位时间内产出了更多的 token。

❓ Q3：如何评估投机解码在特定业务中的收益？

答： 主要看两个指标：接受率（Acceptance Rate） 和 加速比（Speedup Ratio）。 我会先在业务数据集上跑一个测试集，如果接受率低于 30%，说明任务太发散，投机解码带来的额外开销可能不划算；如果接受率在 50% 以上，我会毫不犹豫地开启它。

五、 阿彪碎碎念 [抱拳]

学到这一篇，你已经触碰到了大模型推理最前沿的“暴力美学”。

Chunked Prefill 是对调度公平性的极致追求，而投机解码则是对硬件瓶颈的疯狂挑衅。 在 2026 年的面试现场，如果你能清晰地解释出为什么“一次验证多个 token”比“逐个生成 token”更节省时间，面试官就会明白，你已经跨过了“调包侠”的门槛，开始理解计算架构的本质了。
