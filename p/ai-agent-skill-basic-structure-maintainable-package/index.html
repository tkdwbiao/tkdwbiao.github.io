AI Agent Skill 实战笔记 02：Skill 的基本结构：如何设计一个可维护的技能包？

2026-03-03 10:00
阅读时长: 16 分钟

上一篇我们先建立了 Skill 的整体认知：

1
2
3
4

Prompt 是一次性指令。
Tool 是可调用动作。
Workflow 是流程编排。
Skill 是可复用能力封装。

这一篇开始，我们不再只停留在概念层面，而是进入更具体的问题：

1
2
3
4

一个 Skill 到底应该长什么样？
SKILL.md 应该怎么写？
模板、示例、脚本、Schema 应该放在哪里？
什么样的 Skill 才算可维护？

很多人第一次写 Skill，容易把它写成一个超长 Prompt：

1

把所有背景、规则、示例、模板、代码、注意事项全部塞进一个文件。

这样当然也能用，但很快会出现维护问题：

1
2
3
4
5
6
7

文件越来越长。
触发描述越来越模糊。
示例和规则混在一起。
模板无法复用。
脚本无法测试。
Schema 无法单独校验。
版本更新没有记录。

所以，一个好的 Skill 不只是“能跑”，还应该做到：

结构清晰、职责分离、按需加载、方便复用、容易更新、可以验证。

一、为什么 Skill 需要结构设计

如果只是写一个很简单的个人提示词，你当然可以随便写。

例如：

1

以后帮我写博客时，记得用中文、加 Front Matter、写总结。

这没有问题。

但当你想把 Skill 用到真实工作里，它就不再是几句话的问题。

比如一个“网页结构化抽取 Skill”，可能要包含：

1
2
3
4
5
6
7
8
9

什么时候使用这个 Skill。
如何判断网页类型。
文章页、商品页、招聘页分别有哪些字段。
字段缺失时怎么处理。
输出必须满足什么 JSON Schema。
HTML 清洗脚本怎么调用。
示例输入输出是什么。
哪些内容不能编造。
失败时如何报告。

如果这些都塞进一个文件，短期能用，长期会乱。

一个可维护 Skill 应该像一个小型工程模块，而不是一段孤立 Prompt。

它需要明确区分：

1
2
3
4
5
6
7

说明文档放哪里。
模板放哪里。
示例放哪里。
脚本放哪里。
Schema 放哪里。
测试样例放哪里。
版本说明放哪里。

这就是结构设计的意义。

二、一个 Skill 的典型目录结构

一个常见 Skill 目录可以这样设计：

skill-name/
├── SKILL.md
├── README.md
├── templates/
│   └── output_template.md
├── examples/
│   ├── input.md
│   └── output.md
├── scripts/
│   └── helper.py
├── schemas/
│   └── output_schema.json
└── assets/
    └── diagram.png

不同 Skill 不一定每个目录都需要。

但这些目录代表了几类典型内容：

目录 / 文件作用是否必须
SKILL.mdSkill 的入口说明，描述用途、触发场景、流程和规则必须
README.md给人看的说明文档，可写安装、维护、版本、背景可选
templates/输出模板、文章模板、报告模板、配置模板可选
examples/示例输入、示例输出、好坏案例可选
scripts/可执行脚本、校验脚本、转换脚本可选
schemas/JSON Schema、字段定义、数据结构约束可选
assets/图片、流程图、表格、参考材料可选

最小 Skill 只需要一个 SKILL.md。

但越是工程化的 Skill，越应该把不同职责拆开。

# Webpage Schema Extraction Skill

## Purpose

This skill helps convert webpage content into structured JSON.

## When to use this skill

Use this skill when the user wants to:

- Extract article fields from a webpage.
- Convert semi-structured page text into JSON.
- Clean noisy HTML before extraction.
- Validate extracted results against a schema.

## Inputs

- Raw HTML, cleaned text, or markdown.
- Target page type.
- Target JSON schema.
- Additional extraction requirements.

## Outputs

A valid JSON object that matches the target schema.

## Workflow

1. Identify the page type.
2. Remove noise such as navigation, footer, ads, and scripts.
3. Select the matching schema.
4. Extract fields.
5. Validate output.
6. Report missing fields explicitly.

## Rules

- Do not invent missing fields.
- Use `null` when information is unavailable.
- Keep original text when possible.
- Normalize dates only when evidence is clear.
- Return valid JSON.

这里面最关键的是两部分：

1
2

front matter 里的 name 和 description。
正文里的 Workflow / Rules。

description 决定 Skill 是否容易被正确触发。

Workflow 和 Rules 决定 Skill 执行是否稳定。

四、front matter：name 和 description 怎么写

很多人会忽略 SKILL.md 开头的 front matter。

但它非常关键。

一个常见写法是：

1
2
3
4

---
name: agent-skill-series-writer
description: Use this skill when writing, continuing, planning, polishing, or updating the Hugo blog series "AI Agent Skill 实战笔记：从技能封装到智能工作流".
---

4.1 name 要短、稳定、可识别

name 最好使用短横线命名：

1
2
3
4
5

blog-writing-skill
webpage-schema-extraction
crawler-diagnosis-skill
fastapi-project-generator
langgraph-workflow-designer

不建议写成：

1
2
3
4

my skill
new skill
test skill
write thing

因为这些名字太泛，不利于长期维护。

一个好的 name 应该满足：

1
2
3
4

能看出用途。
不会频繁变化。
不和其他 Skill 混淆。
适合作为目录名。

4.2 description 要写清触发场景

description 是 Skill 触发的关键。

它不能太短，也不能太泛。

不推荐：

1

description: Helps with writing.

这个描述的问题是：它没有说明写什么、什么时候用、做哪些动作。

更好的写法：

1

description: Use this skill when writing, continuing, planning, polishing, or updating a Hugo technical blog series that requires reading a series plan, selecting the next unfinished article, generating Markdown, running Hugo build, and updating the progress table.

这个描述包含了：

1
2
3

任务类型：Hugo technical blog series
触发动作：writing / continuing / planning / polishing / updating
关键流程：read plan / select next article / generate Markdown / run build / update progress

这样 Agent 更容易判断：当前任务是否应该使用这个 Skill。

4.3 description 不要写成广告语

不要写：

1

This is a powerful and amazing skill that can do everything about writing.

这种描述没有工程价值。

好的描述应该像路由规则，而不是宣传文案。

可以套一个模板：

1

Use this skill when [任务场景], especially when the work requires [关键步骤 / 关键资源 / 关键输出].

例如：

1

Use this skill when diagnosing crawler failures from HTTP status codes, response headers, error logs, and page snippets, especially when the output should be a structured diagnosis report with evidence, causes, suggestions, and risk level.

5.5 Workflow：说明步骤

Workflow 是 Skill 的执行骨架。

5.6 Rules：说明约束

Rules 是质量和边界。

规则要尽量具体。

不要只写：

1

from jsonschema import validate

from bs4 import BeautifulSoup


def clean_html(html: str) -> str:
    soup = BeautifulSoup(html, "html.parser")

    for tag in soup(["script", "style", "nav", "footer", "aside"]):
        tag.decompose()

    text = soup.get_text("\n")
    lines = [line.strip() for line in text.splitlines()]
    return "\n".join(line for line in lines if line)

脚本的价值是：

可以测试。
可以独立维护。
可以被 Agent 调用。

需要理解和判断的交给模型，需要确定执行和验证的交给脚本。

# Webpage Schema Extraction Skill

## Purpose

Convert webpage content into structured JSON.

## Workflow

1. Determine page type: article, product, or job.
2. Select the matching schema.
3. Clean HTML if raw HTML is provided.
4. Extract fields based on visible evidence.
5. Use `null` for missing fields.
6. Validate JSON against the schema.
7. Return JSON and a short extraction note.

## Rules

- Do not invent missing fields.
- Do not infer prices, dates, or author names without evidence.
- Preserve original wording for title and content.
- Normalize whitespace.
- Return valid JSON.

这个 Skill 就不只是一个 Prompt 了。

它已经具备工程模块的形态。

十六、常见问题

Q1：一个 Skill 是不是必须有 scripts？

不是。

最小 Skill 只需要 SKILL.md。

只有当任务里有确定性处理、校验、转换、生成等动作时，才需要脚本。

例如：

1
2
3
4

JSON 校验适合脚本。
HTML 清洗适合脚本。
日期标准化适合脚本。
文章写作风格判断不适合完全脚本化。

Q2：README 和 SKILL.md 有什么区别？

简单理解：

1
2

SKILL.md 主要给 Agent 看。
README.md 主要给人看。

SKILL.md 应该简洁、可执行、面向任务。

README.md 可以写更多背景、维护方式、版本记录和贡献说明。

Q3：示例应该放多少？

不要贪多。

建议每类典型任务至少一个好示例。

如果容易犯错，可以再加一个反例。

例如：

1
2
3

article_input.md + article_output.json
product_input.md + product_output.json
bad_output_missing_evidence.json

示例太少，约束不够。

示例太多，维护成本会上升。

Q4：所有规则都应该写进 SKILL.md 吗？

不一定。

核心流程和关键边界应该写进 SKILL.md。

大段模板、长示例、复杂 Schema、辅助脚本应该拆出去。

Q5：Skill 会自动执行脚本吗？

不能简单这么理解。

Skill 可以告诉 Agent 什么时候应该使用脚本，以及脚本的用途。

但实际是否执行，还取决于运行环境、工具权限和用户授权。

所以不要把 Skill 当成自动化后台任务。

它更像是给 Agent 的专业操作手册。
