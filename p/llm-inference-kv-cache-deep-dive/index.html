从重复计算到记忆外挂：深度拆解大模型推理之『KV Cache』

2026-04-06 16:20
阅读时长: 7 分钟

在 LeetCode 里，我们经常用“哈希表”来做空间换时间的优化（比如经典的 Two Sum）；在后端开发中，我们也常把热点数据塞进 Redis。 而到了大模型（LLM）推理领域，这招“空间换时间”的哲学依然适用，它的终极形态就是面试中必考的硬核知识点：KV Cache。大部分同学只知道它能加速，但今天阿彪带你扒开它的底层逻辑，并手写代码模拟它的工作机制，最后还会深度探讨工业界如何解决它带来的“显存灾难”。

一、 知识点详解：为什么我们需要 KV Cache？

1. “笨办法”：自回归的灾难

大模型（如 Llama、GPT）生成文本的方式是自回归（Autoregressive），即“吃前面的字，吐下一个字”。 假设我们要让模型输出：“我爱吃苹果”。

  • 第 1 步：输入“我”，经过 Transformer 层层计算 $Q, K, V$，输出“爱”。
  • 第 2 步：输入“我爱”，重新计算“我”和“爱”的 $Q, K, V$，输出“吃”。
  • 第 3 步：输入“我爱吃”，再次重新计算“我”、“爱”、“吃”的 $Q, K, V$……

这就像你每读一本书的新的一页，都要把前面所有的页数重新朗读一遍。随着文本越来越长，计算复杂度呈 $O(N^2)$ 级爆炸，GPU 的算力被白白浪费在历史 token 的重复计算上。

2. “聪明办法”：KV Cache 的诞生

在 Transformer 的自注意力机制（Self-Attention）中，当前字只需要和前面字的 $K$ (Key) 和 $V$ (Value) 发生矩阵相乘（Attention）。 而且有一个极其重要的物理特性：历史 token 的 $K$ 和 $V$ 一旦算出来，在后续生成新词时，它们是永远不会改变的！

既然不会变，我们何不把算过的 $K$ 和 $V$ 存到显存里（Cache 起来）呢？

  • 第 2 步算“爱”的时候，只需算“爱”自己的 $Q, K, V$。
  • 然后拿“爱”的 $Q$，直接去显存里找存好的“我”的 $K, V$ 进行运算。
  • 算完后，把“爱”的 $K, V$ 也追加进显存。

这就是 KV Cache。有了它，生成每一个新词的计算复杂度瞬间从 $O(N^2)$ 降到了 $O(N)$。

import numpy as np
import time

# 模拟 Transformer 维度的参数
dim = 64
seq_len = 1000

# 模拟输入序列的 Q, K, V (随机生成)
Q = np.random.randn(seq_len, dim)
K = np.random.randn(seq_len, dim)
V = np.random.randn(seq_len, dim)

def attention_without_kv_cache():
    """模拟没有 KV Cache：每次生成新词，都要重算所有历史词的 Attention"""
    start_time = time.time()
    outputs =[]
    for i in range(1, seq_len + 1):
        # 每次都要取前 i 个 token 的 Q, K, V 进行矩阵乘法
        q_curr = Q[:i]
        k_curr = K[:i]
        v_curr = V[:i]
        
        # scores = softmax(Q * K^T)
        scores = np.dot(q_curr, k_curr.T)
        # out = scores * V
        out = np.dot(scores, v_curr)
        outputs.append(out[-1]) # 只取当前生成的最后一个 token 结果
    
    print(f"【无 KV Cache】耗时: {time.time() - start_time:.4f} 秒 (时间复杂度 O(N^2))")
    return outputs

def attention_with_kv_cache():
    """模拟有 KV Cache：只需算当前词的 Q，与缓存的 K, V 运算"""
    start_time = time.time()
    outputs =[]
    
    # 显存里开辟的 KV Cache 空间
    k_cache = np.zeros((0, dim))
    v_cache = np.zeros((0, dim))
    
    for i in range(seq_len):
        # 只取当前这 1 个新词的 Q, K, V
        q_new = Q[i:i+1]
        k_new = K[i:i+1]
        v_new = V[i:i+1]
        
        # 将新词的 K, V 追加到缓存中 (模拟显存写入)
        k_cache = np.vstack([k_cache, k_new])
        v_cache = np.vstack([v_cache, v_new])
        
        # 拿当前词的 Q，去和缓存里所有的 K, V 做运算
        scores = np.dot(q_new, k_cache.T)
        out = np.dot(scores, v_cache)
        
        outputs.append(out[0])
        
    print(f"【有 KV Cache】耗时: {time.time() - start_time:.4f} 秒 (时间复杂度 O(N))")
    return outputs

# --- 阿彪的测试 ---
print("开始模拟生成 1000 个 token...")
res1 = attention_without_kv_cache()
res2 = attention_with_kv_cache()

三、 工业界痛点：KV Cache 带来的“显存灾难”

天下没有免费的午餐。空间换时间，换着换着，显存就被撑爆了。 在真实的工业场景中，如果不加干预，KV Cache 往往会比模型权重本身还要大！当并发数一上来，由于显存不够用（Out of Memory），模型只能被迫拒绝服务。

为了给大模型“续命”，工业界主要有三大杀手锏：

  1. 模型架构重构：MQA 与 GQA

    • MHA (传统多头注意力)：每个 Head 都有自己独立的 K 和 V。
    • MQA (Multi-Query Attention)：所有 Head 共享同一组 K 和 V。直接把 KV Cache 的体积缩小了 N 倍（N 为头数）！
    • GQA (Grouped-Query Attention)：MQA 有时候会让模型泛化能力变差，所以 Llama-2/3 采用了 GQA——把 Head 分组，每 8 个头共享一组 K, V，在精度和显存之间取得完美平衡。

  2. 系统底层重构：vLLM 与 PagedAttention

    • 过去，KV Cache 在显存里是连续分配的。但你不知道用户的话有多长，往往会预先分配一大块显存。这会导致极严重的“内存碎片化”，显存利用率不到 30%。
    • PagedAttention 借鉴了操作系统的“虚拟内存分页（Paging）”技术。把 KV Cache 切成一个个不连续的 Block（Page），按需分配。这让显存利用率逼近 96%，直接将模型的并发吞吐量提升了 2~4 倍！

  3. 量化与卸载策略

    • 不仅对权重做量化，对 KV Cache 也可以做 INT8 甚至 INT4 的量化（如 KVCache Quantization）。
    • 如果显存实在装不下，就利用 CPU 内存做 Offload，或者用 Sliding Window Attention（只保留最近的 N 个 token 的 Cache）。

四、 面试官会问到的问题及详细答案

如果你把上面这些讲给面试官听，他大概率会通过以下几个问题来测测你的底子：

❓ Q1：请写出 KV Cache 占用显存的计算公式，并估算 Llama-7B（FP16）在 Batch=1，Seq_Len=1024 时的显存占用。

答： 核心公式：KV Cache 显存 = 2 (K和V) × 批次(Batch) × 层数(Layers) × 头数(Heads) × 头维度(Head_Dim) × 序列长度(Seq_Len) × 字节数(Bytes)。

以典型的 7B 模型为例：层数 = 32，头数 = 32，头维度 = 128，FP16 占用 2 Bytes。 代入公式：$2 \times 1 \times 32 \times 32 \times 128 \times 1024 \times 2 = 536,870,912$ bytes。 约等于 0.5 GB。 (顺便向面试官抛出：如果并发请求量达到 Batch=32，且生成长度达到 4K，单单是 KV Cache 就会暴增到 64 GB，一张 80G 的 A100 瞬间就满了！这也是为什么要做 PagedAttention 的核心原因。)

❓ Q2：在 LLM 的推理中，通常分为 Prefill（预填充）和 Decode（解码）两个阶段，KV Cache 在这两个阶段有什么区别？

答：

  • Prefill 阶段（用户刚输入 Prompt 时）：模型需要一次性并行计算这段 Prompt 所有 token 的 $Q, K, V$，并将算好的 $K, V$ 全量存入 KV Cache。此阶段是计算密集型（Compute-Bound），瓶颈在 GPU 的张量算力。
  • Decode 阶段（模型逐字吐出回答时）：每次只计算当前这一个新字的 $Q, K, V$，然后去显存里读取之前存好的所有 KV Cache 进行计算。此阶段是访存密集型（Memory-Bound），瓶颈在显存的读取带宽。

❓ Q3：你提到 PagedAttention，它除了解决显存碎片，还有什么额外的好处吗？

答： 有的，PagedAttention 天然支持显存共享（Memory Sharing）。 在实际业务中，我们经常使用复杂的 Prompt（比如 System Prompt：你是一个精通翻译的助手…）。对于不同的并发请求，只要它们的 System Prompt 一样，PagedAttention 就可以让这些请求的 KV Cache 指向同一个物理内存块（Page）。这在并行处理多用户的 RAG 或系统预设请求时，能节省海量显存。

五、 总结

如果说大模型是一台疾驰的跑车，那么 Transformer 的数学架构就是发动机，而 KV Cache 则是决定它能跑多远、载多少人的油箱。
从单纯地把变量存入内存（原始 KV Cache），到修改模型架构减小油箱负担（MQA/GQA），再到引入操作系统级别的内存页管理（vLLM PagedAttention），我们见证了 AI 推理框架如何从“粗放的数学验证”走向“极致的工程压榨”。
