大模型时代的数据采集工程 10：Pyppeteer 与 Playwright 自动化采集

2025-12-29 10:00
阅读时长: 14 分钟

上一篇文章里，我们用 Selenium 进入了动态网页采集。

它解决的是：

1
2
3
4

页面需要执行 JavaScript。
数据需要等待渲染。
页面需要点击、输入、滚动。
需要处理 iframe、窗口和截图调试。

但浏览器自动化工具不只有 Selenium。

在现代浏览器自动化场景中，Pyppeteer 和 Playwright 也非常常见。

它们更贴近 Chrome DevTools Protocol 和现代浏览器能力，尤其适合：

1
2
3
4
5
6

监听网络请求。
等待页面事件。
操作多页面和多上下文。
截图和 PDF。
处理现代前端应用。
在测试环境中做端到端自动化。

这一篇，我们就来讲：

Pyppeteer 与 Playwright 的基本用法、核心差异、动态页面采集思路、工程边界和面试表达。

一、前言

在动态网页采集里，工具选择通常有三个层次。

第一层是 Requests。

1
2

适合接口清晰、静态 HTML 或授权 API。
速度快、成本低、容易并发。

第二层是 Selenium。

1
2
3

适合通用浏览器自动化。
生态成熟，语法直观。
能处理点击、输入、等待、iframe、截图。

第三层是 Pyppeteer / Playwright。

1
2

更贴近现代浏览器自动化。
适合网络监听、页面事件、上下文隔离、现代前端测试。

但无论工具多强，都要先记住一个原则：

浏览器自动化不是默认方案，而是在 Requests 和接口采集不能满足需求时的补充方案。

如果数据可以通过授权接口稳定获取，就不应该为了“像浏览器”而启动浏览器。

如果页面必须执行 JS、触发交互、等待渲染，再考虑浏览器自动化。

二、Pyppeteer 和 Playwright 是什么？

1. Pyppeteer

Pyppeteer 是 Puppeteer 的 Python 移植版本。

Puppeteer 最早是 Node.js 生态中用于控制 Chrome / Chromium 的工具。

它通过 Chrome DevTools Protocol 控制浏览器。

Pyppeteer 的特点是：

1
2
3
4

异步 API。
主要围绕 Chromium。
适合学习 CDP 风格自动化。
生态活跃度弱于 Playwright。

2. Playwright

Playwright 是 Microsoft 推出的现代浏览器自动化工具。

它支持：

1
2
3
4
5
6
7
8

Chromium。
Firefox。
WebKit。
同步和异步 Python API。
浏览器上下文隔离。
强大的等待机制。
网络监听和路由。
截图、视频、Trace。

在新项目里，通常更推荐 Playwright。

原因是：

1
2
3
4
5

维护更活跃。
跨浏览器支持更好。
API 设计更现代。
等待机制更友好。
测试和自动化生态更完善。

本文会同时介绍两者，但重点放在 Playwright。

三、什么时候用 Playwright？

适合 Playwright 的场景：

1
2
3
4
5
6

页面数据必须由 JavaScript 渲染。
需要点击、输入、滚动、等待页面变化。
需要监听网络请求和响应。
需要隔离多个浏览器上下文。
需要截图、Trace 或调试失败现场。
需要在自有系统中做端到端自动化测试。

不应该优先使用 Playwright 的场景：

1
2
3
4
5

数据已经在原始 HTML 中。
数据来自稳定 JSON 接口。
只需要简单 HTTP 请求。
需要大规模高并发低成本采集。
没有授权或合规边界不清晰。

工具选择建议：

1
2
3
4

能用 Requests，就不要上浏览器。
必须执行 JS 或交互，再用浏览器自动化。
新项目优先考虑 Playwright。
维护旧代码或特定场景时再看 Pyppeteer。

安装 Python 包：

1

安装浏览器：

1

1

最小同步示例：

    browser = p.chromium.launch(headless=True)
    page = browser.new_page()

这里的结构是：

1
2
3
4

这样出错时也更容易释放资源。

from pathlib import Path
from playwright.sync_api import sync_playwright

html_path = Path("demo.html").resolve().as_uri()

with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)
    page = browser.new_page()

    page.goto(html_path)
    page.click("#load")
    page.wait_for_selector("li.item")

    items = page.locator("li.item")

        item = items.nth(index)

Playwright 的几个常用方法：

1
2

4

相比 Selenium，Playwright 的 locator 机制更现代。

但这不代表不需要设计等待策略。

动态页面依然要明确等待什么。

七、Locator：Playwright 的核心抽象

Playwright 推荐使用 locator。

1

字段提取也可以在局部 locator 内完成：

九、等待策略

Playwright 有自动等待，但显式等待仍然很重要。

常见等待：

1
2
3

page.wait_for_selector(".item")
page.wait_for_load_state("networkidle")
page.wait_for_url("**/result**")

几种 load state：

状态含义
domcontentloadedDOMContentLoaded 触发
loadload 事件触发
networkidle网络在一段时间内相对空闲

使用建议：

1
2
3
4

等具体元素优先于等固定时间。
等业务结果优先于等页面整体 load。
networkidle 不一定适合所有页面。
不要滥用固定 wait_for_timeout。

不推荐：

1

page.wait_for_timeout(5000)

除非是调试或确实没有更好的事件条件。

更推荐：

1

page.wait_for_selector(".result-item")

十、网络监听：动态采集中的重要能力

Playwright 很适合观察网络请求。

from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)
    page = browser.new_page()

在自有系统或授权测试中，你可以用它确认：

这对动态页面采集非常关键。

很多时候，最终方案不是用浏览器解析 DOM，而是：

1
2
3

确认授权接口。
用 Requests 或 HTTPX 进行稳定采集。

但必须强调：

网络监听用于调试自有、授权或学习环境，不应被用于绕过访问控制、破解付费接口或规避平台规则。

import asyncio
from pathlib import Path
from pyppeteer import launch


async def main():
    browser = await launch(headless=True)
    page = await browser.newPage()

    url = Path("demo.html").resolve().as_uri()
    await page.goto(url)
    await page.click("#load")

并发数量要受控。

from dataclasses import dataclass
from pathlib import Path
from playwright.sync_api import sync_playwright, TimeoutError as PlaywrightTimeoutError


@dataclass
class ArticleItem:
    item_id: str
    title: str


class PlaywrightCrawler:
    def __init__(self, headless: bool = True) -> None:
        self.playwright = sync_playwright().start()
        self.browser = self.playwright.chromium.launch(headless=headless)
        self.context = self.browser.new_context()
        self.page = self.context.new_page()

    def close(self) -> None:
        self.context.close()
        self.browser.close()
        self.playwright.stop()

    def load_demo_items(self, html_path: str) -> list[ArticleItem]:
        url = Path(html_path).resolve().as_uri()
        self.page.goto(url)
        self.page.click("#load")
        self.page.wait_for_selector("li.item", timeout=10_000)

        items = self.page.locator("li.item")
        results = []

        for index in range(items.count()):
            item = items.nth(index)
            results.append(
                ArticleItem(
                    item_id=item.get_attribute("data-id") or "",
                    title=item.inner_text(),
                )
            )

        return results


crawler = PlaywrightCrawler(headless=True)
try:

        print(item)
except PlaywrightTimeoutError:
    crawler.page.screenshot(path="debug.png", full_page=True)
    raise
finally:
    crawler.close()

二十二、常见错误写法

1. 不判断是否真的需要浏览器

如果接口清晰，直接用浏览器批量采集通常是低效的。

2. 滥用 networkidle

有些页面会持续轮询。

networkidle 可能一直等不到或意义不大。

更好的方式是等待具体业务元素或具体响应。

3. 不隔离上下文

多个账号或状态共用一个 Context，容易 Cookie 串号。

应该使用独立 Context 管理状态。

4. 不保护 storage_state

state.json 可能包含敏感 Cookie 和本地存储。

不要提交到 Git。

5. 不保存失败现场

Playwright 的截图、HTML 和 Trace 很有价值。

失败时应该保留足够排查信息。

6. 把浏览器自动化当成规避检测工具

自有系统。
低影响。
可审计。
可暂停。

二十三、面试表达

如果面试官问：

1

Playwright 和 Selenium 有什么区别？

可以这样回答：

Selenium 更早，生态成熟，适合通用浏览器自动化；Playwright 更现代，支持 Chromium、Firefox、WebKit，自动等待、浏览器上下文隔离、网络监听、截图和 Trace 支持更好。新项目中如果需要处理现代前端应用、网络响应和失败调试，我会优先考虑 Playwright；但如果项目已有 Selenium 体系，也可以继续维护。工具选择要看场景，而不是绝对谁替代谁。

如果问：

1

动态网页采集你会怎么做？

可以这样回答：

我会先确认数据来源。如果原始 HTML 或接口 JSON 已经有数据，优先用 Requests。如果必须执行 JS 或完成交互，才使用 Selenium 或 Playwright。用 Playwright 时，我会通过 locator 定位元素，使用显式等待或等待具体接口响应，必要时监听网络请求。失败时保存截图、HTML、Trace 和异常类型，方便排查。最终仍然会把数据交给解析、清洗和 Schema 校验流程。

如果问：

1

Playwright 如何管理多个登录态？

可以这样回答：

Playwright 可以通过 browser context 隔离 Cookie、LocalStorage 和页面状态。每个账号或授权状态可以使用独立 context，也可以在授权场景下通过 storage_state 保存和加载登录态。但这些状态文件可能包含敏感信息，不能提交到 Git，也不能在未授权场景中使用。任务日志里要记录 auth_id，状态失效后要暂停或重新授权，而不是无限重试。

如果问：

1

浏览器自动化有什么工程风险？

可以这样回答：

主要风险是资源占用高、速度慢、并发成本大、等待条件不稳定、页面改版导致选择器失效，以及登录态和授权状态管理复杂。工程上要限制并发、设置超时、保存失败现场、记录日志、控制频率，并明确合规边界。浏览器自动化不应该用于绕过规则，而应该服务于授权采集、自动化测试和动态页面调试。

二十四、总结

本文讲了 Pyppeteer 与 Playwright 在动态网页采集中的应用。

核心结论包括：

  • Pyppeteer 和 Playwright 都可以控制浏览器执行 JavaScript、操作页面和读取渲染后的内容。
  • 新项目中通常更推荐 Playwright，因为它更现代、维护更活跃、网络监听和调试能力更强。
  • 使用浏览器自动化前，应该先判断是否可以用 Requests 或授权接口完成采集。
  • Playwright 的 locator、自动等待、context、网络监听、截图和 Trace 是核心能力。
  • 等待具体元素或具体接口响应，通常比固定 sleep 更稳定。
  • Context 可以隔离 Cookie、LocalStorage 和授权状态。
  • storage_state 可以保存登录态，但必须保护好，不能提交到 Git。
  • 浏览器自动化资源成本高，要限制并发、设置超时并及时释放资源。
  • 失败时要保存截图、HTML、Trace、URL 和异常类型，便于诊断。
  • LLM / Agent 可以辅助分析失败原因，但不能替代验证和合规边界。
