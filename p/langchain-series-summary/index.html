LangChain 实战笔记：从 LLM 应用到 Agent 工程化

最开始，我们只是想回答一个问题：

为什么大模型应用开发需要 LangChain 这样的框架？

到最后，我们已经把视角扩展到了：

  • Prompt 如何管理。
  • Model 如何调用。
  • Output Parser 如何稳定输出。
  • LCEL 和 Runnable 如何编排链路。
  • Memory 如何支持多轮对话。
  • RAG 如何连接知识库。
  • Document Loader、Text Splitter、Embedding、Vector Store、Retriever 如何组成检索系统。
  • Agent 如何调用工具。
  • ReAct 如何组织推理与行动循环。

我们做一次完整回顾：把前面 27 篇文章串成一条学习路径，也总结 LangChain 应用从 demo 走向工程化时最重要的思维方式。

一、前言

学习 LangChain，很容易陷入两个极端。

一种是只看 API。

今天学一个 ChatPromptTemplate，明天学一个 Retriever，后天学一个 Agent。

每个概念都能跑通，但放到真实项目里不知道怎么组合。

另一种是直接追复杂架构。

一开始就想做企业知识库、多工具 Agent、LangGraph 工作流、权限系统、评估平台。

结果还没理解 Prompt、Retriever、Tool 的边界，系统就变成了一堆难以维护的代码。

这个系列想走的是中间路线：

先理解最小可运行链路，再逐步加上记忆、检索、工具、图编排、观测和工程化能力。

所以整个系列其实是一条递进路线。

二、第一阶段：从模型调用开始

系列前几篇解决的是最基础的问题：如何把大模型接入应用。

1. 为什么需要 LangChain？

第一篇里，我们讨论了 LangChain 出现的原因。

直接调用模型 API 可以完成最小 demo。

但真实应用需要的不只是：

1

输入一句话 -> 返回一段话

还需要：

  • Prompt 模板。
  • 输出格式约束。
  • 多步骤编排。
  • 文档检索。
  • 工具调用。
  • 多轮记忆。
  • 调试和观测。
  • 工程化组织。

LangChain 的价值不是替你“变聪明”，而是提供一套组织 LLM 应用的组件和抽象。

2. 核心模块总览

第二篇把 LangChain 的主要模块串了一遍：

这一篇的重点不是记住所有 API。

而是建立一个心智模型：

LangChain 应用通常不是一个模型调用，而是一条由多个组件组成的链路。

3. 第一个大模型应用

第三篇做了快速开始。

最小链路是：

1

Prompt -> Model -> Output Parser

对应代码：

1

chain = prompt | model | parser

这条链路非常简单，但它是后面所有复杂应用的基础。

无论是 RAG、Agent 还是 LangGraph，本质上都离不开：

  • 组织输入。
  • 调用模型。
  • 处理输出。

三、第二阶段：Prompt、输出解析和 LCEL

当模型能调用之后，下一个问题是：如何让调用变得可维护、可组合、可控。

1. PromptTemplate

Prompt 不是随手写在代码里的字符串。

它应该像代码一样被管理。

我们使用 ChatPromptTemplate 把 Prompt 拆成：

  • system message。
  • human message。
  • 变量。
  • 输出要求。
  • 约束条件。

例如：

1
2
3
4

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个严谨的技术解释助手。"),
    ("human", "请解释：{topic}"),
])

Prompt 管理的核心不是“写得更玄学”。

而是让它：

  • 可读。
  • 可改。
  • 可测试。
  • 可复用。

2. Output Parser

模型默认输出自然语言。

但应用经常需要结构化结果。

例如：

1
2
3
4
5

{
  "title": "...",
  "tags": ["..."],
  "summary": "..."
}

所以我们讲了 Output Parser，以及为什么不能只靠字符串切割。

结构化输出的关键是：

不要让下游系统猜模型输出格式。

如果业务依赖 JSON、分类结果、字段抽取，就要使用更稳定的输出约束方式。

3. LCEL

LCEL 是 LangChain 里非常重要的编排方式。

它让我们可以用管道语法组合组件：

1

chain = prompt | model | StrOutputParser()

也可以组合更复杂的输入：

1
2
3
4
5
6
7
8
9

chain = (
    {
        "context": retriever | format_docs,
        "question": RunnablePassthrough(),
    }
    | prompt
    | model
    | StrOutputParser()
)

LCEL 的价值在于：

  • 把步骤串起来。
  • 让组件可以复用。
  • 支持 stream、batch、invoke。
  • 为 tracing 和调试提供结构。

4. Runnable

Runnable 是 LCEL 背后的统一抽象。

如果理解了 Runnable，就能理解为什么不同组件可以被 | 连接。

一个应用里的 Prompt、Model、Parser、Retriever、函数转换，都可以看成 Runnable。

这让 LangChain 不只是“调用模型的库”，而是一个应用编排框架。

四、第三阶段：Memory 和多轮对话

单轮问答只是开始。

很多应用需要上下文。

例如：

1
2
3

用户：LangGraph 是什么？
助手：...
用户：它和普通 Chain 有什么区别？

第二个问题里的“它”依赖历史。

1. Memory 的本质

Memory 不是让模型真的拥有长期记忆。

它本质上是：

把必要的历史信息，以合适的方式放回模型上下文。

常见方式包括：

  • 保存最近 N 轮对话。
  • 对历史做摘要。
  • 按会话 ID 存储消息。
  • 把长期信息放入检索系统。

2. 多轮聊天机器人

我们构建了一个支持多轮对话的聊天机器人。

关键点是：

  • 每个用户或会话要有独立 history。
  • 历史不能无限增长。
  • 不能把 Memory 当数据库。
  • 敏感信息不要随便长期保存。

Memory 解决的是对话连续性。

但它不解决知识准确性。

如果要回答外部知识或企业资料，就需要 RAG。

五、第四阶段：RAG 让模型连接知识

RAG 是整个系列的核心之一。

它解决的问题是：

模型不知道你的私有资料，也不应该靠幻觉回答知识库问题。

RAG 的基本流程是：

1
2
3
4
5
6
7

用户问题
  ↓
Retriever 检索相关文档
  ↓
把文档放入 Prompt
  ↓
模型基于上下文回答

1. 为什么需要 RAG？

大模型有三个明显限制：

  • 训练知识可能过期。
  • 不知道企业或个人私有数据。
  • 容易在不知道时编造。

RAG 通过检索外部资料缓解这些问题。

核心思想是：

不要让模型凭空回答，让它基于检索到的资料回答。

2. Document Loader

RAG 的第一步是把文档加载成统一格式。

LangChain 里的文档通常是：

1

Document(page_content="...", metadata={...})

page_content 是文本内容。

metadata 是来源、标题、路径、更新时间、权限等信息。

很多 RAG 问题不是模型问题，而是文档加载阶段就丢了关键信息。

3. Text Splitter

长文档不能直接整体塞给模型，也不适合整体 embedding。

所以要切分。

切分的目标不是机械分段，而是保留语义完整性。

中文文档可以使用中文标点和标题作为分隔符：

1
2
3
4
5

splitter = RecursiveCharacterTextSplitter(
    chunk_size=700,
    chunk_overlap=120,
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
)

chunk 太小，语义不完整。

chunk 太大，检索不精准，Prompt 成本高。

4. Embedding 和 Vector Store

Embedding 把文本变成向量。

Vector Store 保存向量并支持相似度搜索。

我们用过 Chroma，也提到过 FAISS 等选择。

关键原则是：

  • 文档 embedding 应该离线构建。
  • 在线问答只加载已有索引。
  • 换 Embedding 模型通常需要重建索引。
  • metadata 要随 chunk 一起保存。

5. Retriever

Retriever 是 RAG 查询阶段的入口。

它不只是向量库搜索的薄封装。

在真实系统里，Retriever 可能包含：

  • top-k 控制。
  • score threshold。
  • MMR。
  • metadata filter。
  • query rewrite。
  • multi-query。
  • rerank。
  • 权限过滤。

RAG 优化时，第一步永远是看 Retriever 返回了什么。

如果没召回正确资料，再怎么改 Prompt 都很难解决。

六、第五阶段：从 RAG 到知识库问答系统

第 15 篇，我们把前面 RAG 组件串成了一个完整知识库问答系统。

它包含：

1
2
3
4

build_index.py
ask.py
data/docs/
data/chroma_db/

离线构建：

1

加载文档 -> 切分 -> Embedding -> 写入 Chroma

在线问答：

1

加载向量库 -> Retriever -> Prompt -> Model -> Answer

这个实战有两个重要结论。

1. 离线索引和在线问答分离

不要在用户每次提问时重新构建向量库。

这是 RAG 初学者最常见的问题之一。

2. 答案要带来源

知识库问答的可信度来自来源。

没有来源，用户无法判断答案是否可靠。

七、第六阶段：Agent 和工具调用

RAG 让模型能查资料。

Tool Calling 和 Agent 让模型能做事情。

1. Agent 是什么？

普通 Chain 的路径是固定的。

Agent 的特点是：

模型可以根据任务决定是否调用工具、调用哪个工具、用什么参数调用。

例如用户问：

1

帮我查订单 1001 的物流状态。

Agent 可能会：

  1. 调用订单工具查订单。
  2. 拿到物流单号。
  3. 调用物流工具查状态。
  4. 汇总回答。

2. Tool Calling

Tool Calling 的核心是：

  • 把函数声明成工具。
  • 让模型生成工具调用请求。
  • 程序执行工具。
  • 把工具结果交回模型。
  • 模型生成最终回答。

工具必须有清晰边界：

  • 名称明确。
  • 参数明确。
  • 返回稳定。
  • 不泄露敏感信息。
  • 高风险动作要确认。

3. ReAct

ReAct 的思想是：

1

Thought -> Action -> Observation -> Thought -> ... -> Answer

也就是把推理和行动结合起来。

它适合路径不固定的问题。

但也要控制：

  • 最大步数。
  • 工具数量。
  • 工具权限。
  • 失败处理。

Agent 很强，但不是所有场景都需要 Agent。

固定流程优先用 Chain 或 LangGraph。

八、第七阶段：多工具 Agent 实战

我们构建了一个多工具 Agent 智能助手。

它可以使用：

  • 加法工具。
  • 乘法工具。
  • 订单查询工具。
  • 物流查询工具。
  • 知识库检索工具。

这个实战想说明的是：

Agent 的能力不是来自模型“想象”，而是来自你给它设计的工具边界。

工具设计不好，Agent 就会不稳定。

常见问题包括：

  • 工具太多，模型选择困难。
  • 工具描述不清楚，模型误用。
  • 工具返回太长，浪费 token。
  • 工具权限过大，带来安全风险。
  • 固定流程也交给 Agent，导致成本和延迟上升。

所以 Agent 工程化的重点不是炫技。

而是让模型在可控范围内使用工具。

九、第八阶段：LangGraph 控制复杂流程

当 Agent 流程变复杂后，普通 Chain 和自动 Agent 都会遇到问题。

例如：

  • 有分支。
  • 有循环。
  • 有人工确认。
  • 有多个状态字段。
  • 有重试和反思。
  • 有条件结束。

这时 LangGraph 就很适合。

1. State、Node、Edge

LangGraph 的核心可以总结为一句话：

State 管数据，Node 管动作，Edge 管流程。

State 是共享状态。

Node 是处理步骤。

Edge 决定下一步走向。

2. 条件分支

例如：

1
2
3
4
5
6
7
8
9

builder.add_conditional_edges(
    "classify_intent",
    route_by_intent,
    {
        "order": "handle_order",
        "knowledge": "handle_knowledge",
        "chat": "handle_chat",
    },
)

这比把所有流程都放在一个巨大 Prompt 里更可控。

3. 反思 Agent

我们用 LangGraph 做了一个自我反思和修正的 Agent：

1

生成回答 -> 评价回答 -> 不通过则重写 -> 再评价 -> 结束

这里最重要的是控制循环：

  • 最多重写几次。
  • 什么条件算通过。
  • 每轮状态如何更新。
  • 最终输出哪个答案。

LangGraph 让 Agent 不再只是黑盒循环，而是可观察、可控制的图。

2. LangSmith

大模型应用的问题通常不是只看最终输出就能定位。

你需要看到：

  • Prompt 输入。
  • Model 输出。
  • Retriever 返回文档。
  • Tool 调用参数。
  • Agent 中间步骤。
  • LangGraph 节点状态。
  • token 消耗和耗时。

LangSmith 的价值是让链路可观察。

它帮助我们从：

1

感觉这个回答不对

变成：

1

Retriever 没召回正确文档

或者：

1

工具返回对了，但模型最终总结错了

3. 性能优化

性能优化不是只追求快。

它要平衡：

1
2
3
4

速度
稳定性
成本
质量

常见优化方向包括：

  • 用数据定位瓶颈。
  • 简单任务用小模型。
  • 控制 Prompt 和上下文 token。
  • 控制输出长度。
  • 使用 streaming 改善体感。
  • 使用 batch 和并发处理独立任务。
  • 缓存高频结果。
  • RAG 控制 k、chunk、filter、rerank。
  • Agent 限制工具数量和最大步数。
  • 设置超时和合理重试。

核心原则是：

先观测，再优化；优化后要评估。

十一、第十阶段：个人知识库和企业文档问答

系列最后两篇是综合实战。

1. 个人知识库 AI 助手

个人知识库助手适合练习完整 RAG。

它强调：

  • 加载本地 Markdown。
  • 中文友好切分。
  • Chroma 持久化。
  • Retriever 检索。
  • Prompt 拒答。
  • 答案带来源。
  • 命令行交互。
  • 调试检索结果。

核心结论是：

个人知识库助手的关键不是让模型自由发挥，而是让模型基于你的资料回答。

2. 企业内部文档问答系统

企业场景更复杂。

它不仅要回答，还要：

  • 权限控制。
  • 多租户隔离。
  • metadata 设计。
  • 文档增量更新。
  • 来源可信度。
  • 审计日志。
  • 评估集。
  • 部署和运维。

企业 RAG 的第一原则是：

模型不应该看到用户无权访问的文档。

Prompt 不能作为权限边界。

权限必须在系统层、检索层和数据层完成。

十三、最重要的几个原则

如果只保留这个系列里最重要的原则，我会选下面这些。

1. 不要让模型凭空回答

知识型问题尽量走 RAG。

工具型问题尽量调用工具。

模型适合理解、组织和生成语言，但事实来源应该尽量来自外部系统。

2. Prompt 不是安全边界

Prompt 可以约束模型表达。

但不能作为权限控制、数据隔离、风险操作确认的唯一手段。

安全边界必须写在系统层。

3. RAG 先看 Retriever

回答错了，先看检索结果。

如果 Retriever 错了，Prompt 很难救。

4. Agent 不是越多越好

固定流程用 Chain。

复杂可控流程用 LangGraph。

路径不固定、需要模型决策时再用 Agent。

5. metadata 是 RAG 工程的地基

来源引用、权限过滤、增量更新、审计追踪都依赖 metadata。

不要只保存文本。

6. 离线和在线流程要分开

Embedding、索引构建、批量评估这些工作应该离线处理。

用户请求里只做必要的在线检索和生成。

7. 观测比猜测重要

没有 trace、日志、评估集，优化就很容易变成玄学。

LangSmith 或类似工具的价值在于让链路透明。

8. 工程化不是过度设计

工程化不是一开始搭一个复杂框架。

而是在系统变复杂时，把边界拆清楚：配置、模型、Prompt、Retriever、Tool、Agent、服务、测试、日志。

十五、后续继续深入什么？

这个系列只是 LangChain 应用开发的起点。

如果继续深入，可以沿着几个方向走。

1. 更系统的 RAG 评估

包括：

  • 召回率。
  • 上下文相关性。
  • 忠实度。
  • 答案正确性。
  • 引用准确性。
  • 无答案拒答率。

RAG 真正难的不是搭起来，而是持续提升质量。

2. 更复杂的权限和多租户

企业场景里，权限会越来越复杂。

后续可以研究：

  • 文档级 ACL。
  • 行级权限。
  • 租户隔离。
  • 组织架构同步。
  • 权限变更后的索引更新。

3. LangGraph 深度实践

LangGraph 很适合做：

  • 人工审核。
  • 多 Agent 协作。
  • 长流程任务。
  • 状态恢复。
  • 可中断工作流。
  • 复杂工具编排。

如果 Agent 变复杂，LangGraph 值得深入。

4. 线上评估和反馈闭环

真实系统上线后，需要把失败案例收集回来。

形成：

1

线上问题 -> 加入评估集 -> 调整 Prompt/Retriever/Tool -> 跑评估 -> 灰度上线

这是大模型应用持续改进的核心。

5. 成本和性能治理

请求量上来后，成本会变得非常现实。

需要继续关注：

  • token 预算。
  • 缓存策略。
  • 模型分层。
  • 并发控制。
  • 超时重试。
  • batch 处理。
  • 向量库性能。

6. 安全和合规

特别是企业系统，要持续关注：

  • Prompt injection。
  • 数据泄露。
  • 工具滥用。
  • 敏感信息脱敏。
  • 审计留痕。
  • 权限边界。

大模型应用不是只要能回答就够了。

它也必须符合软件工程和安全工程的基本要求。

十六、常见学习误区

1. 只背 API，不理解链路

API 会变化。

但链路思想更稳定。

理解：

1

输入 -> 检索/工具 -> Prompt -> Model -> Parser -> 输出

比记住某个函数名更重要。

2. 把所有问题都交给 Agent

Agent 不是万能架构。

很多固定流程用普通 Chain 更简单、更快、更稳。

3. 忽略文档质量

RAG 的质量很大程度取决于文档质量。

文档乱、过期、重复、权限混乱，模型很难给出好答案。

4. 不做评估

随便问几个问题感觉不错，不代表系统可靠。

至少要准备一组固定评估问题。

5. 不看中间过程

只看最终回答，很难定位问题。

RAG 看检索。

Agent 看工具调用。

LangGraph 看状态流转。

6. 过早追求复杂架构

先让最小链路跑通。

再逐步加入权限、缓存、评估、观测和部署。

不要一开始就把项目做成平台。

十七、给自己的学习建议

如果现在重新学习这个系列，我建议按下面节奏来。

第一步：写最小 Chain

先跑通：

1

Prompt -> Model -> Parser

理解 invoke、stream、batch。

第二步：写一个小 RAG

用 3 到 5 篇 Markdown 文档。

跑通：

1

Loader -> Splitter -> Embedding -> Vector Store -> Retriever -> Answer

重点观察 Retriever 返回什么。

第三步：写一个工具调用示例

比如计算器、订单查询、天气查询。

理解模型生成 tool call 和程序执行工具之间的边界。

第四步：写一个小 Agent

给它 2 到 3 个工具。

观察它什么时候调用工具，什么时候直接回答。

第五步：用 LangGraph 控制流程

做一个有分支或循环的小流程。

例如：

1

分类 -> 检索/工具/闲聊 -> 生成回答

第六步：加观测和评估

开启 tracing。

准备 20 个问题。

每次调整都跑一遍。

第七步：再考虑工程化

当代码变多时，再拆：

1

config / models / prompts / chains / retrievers / tools / services

这样会比一开始设计复杂架构更自然。
