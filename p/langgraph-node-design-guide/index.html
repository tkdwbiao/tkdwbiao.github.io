LangGraph 实战笔记 05：如何设计可复用的执行节点？

2025-11-09 10:00
阅读时长: 11 分钟

前面几篇文章里，我们已经建立了 LangGraph 的基本心智模型：

State 管数据，Node 管动作，Edge 管流程。

上一篇重点讲了 State：如何设计 Agent 的运行状态，哪些字段应该放进 State，什么时候使用 TypedDict，什么时候使用 MessagesState，以及 reducer 解决什么问题。

这一篇，我们继续看第二个核心概念：Node。

Node 是图中真正“做事情”的地方。

它可以是一个普通函数，也可以调用 LLM、Retriever、Tool、数据库或外部 API。

一个 LangGraph 应用是否清晰，很大程度上取决于节点拆得是否合理。

一、前言

如果说 State 是工作流的数据骨架，那么 Node 就是工作流的执行单元。

在 LangGraph 里，一个节点通常对应流程中的一步：

1
2
3
4
5
6
7

分类意图
检索文档
调用工具
生成回答
检查质量
重写结果
等待人工审核

这些步骤都可以被建模成节点。

节点设计得好，整张图会非常清楚。

节点设计得不好，图也会变成另一种形式的“大泥球”。

常见问题包括：

  • 一个节点做太多事。
  • 节点之间依赖隐式变量。
  • 节点返回字段不稳定。
  • LLM 调用和业务判断混在一起。
  • Tool 调用结果没有结构化保存。
  • 节点名看不出职责。
  • 很多节点看起来可复用，实际耦合很深。

所以这一篇不只是讲 add_node 怎么用。

更重要的是讲：

如何把复杂 Agent 的执行步骤拆成清晰、可观察、可维护、可复用的节点。

二、Node 到底是什么？

在 LangGraph 里，Node 是图中的执行节点。

最常见的形式是一个函数：

1
2
3

def some_node(state: AgentState):
    ...
    return {"some_field": some_value}

这个函数有三个关键点：

  1. 接收当前 State。
  2. 执行某个动作。
  3. 返回状态更新。

例如：

1
2
3
4
5
6
7
8

def classify_node(state: AgentState):
    question = state["question"]

    if "订单" in question:
        return {"intent": "order"}
    if "制度" in question:
        return {"intent": "knowledge"}
    return {"intent": "chat"}

这个节点读取 question，写入 intent。

再例如：

1
2

def answer_node(state: AgentState):
    return {"answer": f"你问的是：{state['question']}"}

这个节点读取 question，写入 answer。

从形式上看，Node 很简单。

但在真实 Agent 中，Node 的设计质量会直接影响整个系统的复杂度。

三、Node 的基本输入输出模型

一个推荐的节点模型是：

1
2
3
4
5

读取 State 中需要的字段
  ↓
执行一个明确动作
  ↓
返回少量状态更新

例如：

from typing import TypedDict


class WritingState(TypedDict):
    topic: str
    draft: str
    review: str


def write_draft_node(state: WritingState):
    topic = state["topic"]
    draft = f"这是一篇关于 {topic} 的初稿。"
    return {"draft": draft}

这个节点很清楚：

项目内容
读取topic
执行生成初稿
写入draft

再看一个检查节点：

1
2
3
4

def review_draft_node(state: WritingState):
    draft = state["draft"]
    review = "通过" if len(draft) > 10 else "需要补充"
    return {"review": review}

它读取 draft，写入 review。

只要每个节点都能说清楚“读什么、做什么、写什么”，图就会更容易维护。

  • 数据格式转换。
  • 简单业务计算。
  • 状态字段初始化。
  • 工具结果解析。

from typing import TypedDict


class AgentState(TypedDict):
    question: str
    normalized_question: str
    intent: str


def normalize_question_node(state: AgentState):
    question = state["question"].strip()
    return {"normalized_question": question}


def rule_based_intent_node(state: AgentState):
    question = state["normalized_question"]

    if "订单" in question or "物流" in question:
        return {"intent": "order"}
    if "制度" in question or "文档" in question:
        return {"intent": "knowledge"}
    return {"intent": "chat"}

这类节点的优点是：

  • 可预测。
  • 容易测试。
  • 成本低。
  • 不依赖模型。

不要把所有判断都交给 LLM。

如果一个规则可以用普通代码稳定表达，就优先用普通函数节点。

例如：

1
2
3
4

用户问题里是否包含订单号
重试次数是否超过上限
回答是否为空
人工审核结果是否通过

这些都不需要模型参与。

五、LLM 节点

当节点需要自然语言理解或生成时，就可以调用 LLM。

例如：

  • 生成回答。
  • 改写问题。
  • 总结文档。
  • 判断复杂意图。
  • 评估回答质量。
  • 生成结构化计划。

from typing import TypedDict
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI


class QAState(TypedDict):
    question: str
    context: str
    answer: str


prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个严谨的问答助手，请只基于给定上下文回答。"),
    ("human", "问题：{question}\n\n上下文：{context}"),
])

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
chain = prompt | model | StrOutputParser()


def generate_answer_node(state: QAState):
    answer = chain.invoke({
        "question": state["question"],
        "context": state["context"],
    })
    return {"answer": answer}

这个节点把 LCEL Chain 包在 LangGraph Node 里。

这也体现了 LangChain 和 LangGraph 的关系：

LangChain 组件可以放进 LangGraph 的节点里，LangGraph 负责组织这些节点的流程。

LLM 节点要注意什么？

第一，输入要清楚。

不要让 LLM 节点从一堆模糊 State 里自己猜该用什么。

第二，输出要稳定。

如果后续节点需要结构化结果，就不要只返回一段自然语言。

例如，如果后续要根据质量判断路由，可以返回：

1

{"is_answer_valid": True, "review_reason": "回答覆盖了主要问题"}

而不是只返回：

1

这个回答看起来不错。

第三，LLM 节点不要承担太多职责。

不要一个节点同时完成：

1

理解问题 + 检索策略 + 生成回答 + 自我检查 + 决定下一步

这会让图失去结构。

六、Retriever 节点

RAG 工作流里常见一种节点：Retriever 节点。

它负责根据问题检索相关文档，并把结果写入 State。

例如：

from typing import TypedDict


class RagState(TypedDict):
    question: str
    docs: list[str]
    answer: str


def retrieve_docs_node(state: RagState):
    docs = retriever.invoke(state["question"])
    formatted_docs = [doc.page_content for doc in docs]
    return {"docs": formatted_docs}

这个节点的职责很单一：

1

读取 question -> 调用 retriever -> 写入 docs

生成回答则交给另一个节点：

1
2
3
4
5
6
7

def generate_answer_node(state: RagState):
    context = "\n\n".join(state["docs"])
    answer = rag_chain.invoke({
        "question": state["question"],
        "context": context,
    })
    return {"answer": answer}

不要把检索和生成总是塞进一个节点。

拆开之后，你可以更清楚地观察：

  • 检索到了什么文档。
  • 文档是否相关。
  • 生成失败是检索问题还是模型问题。

七、Tool 节点

Tool 节点负责连接外部动作。

例如：

  • 查询订单。
  • 查询天气。
  • 计算数值。
  • 查询数据库。
  • 调用内部 API。
  • 创建工单。

最简单的工具节点可以是普通函数：

from typing import TypedDict


class OrderState(TypedDict):
    question: str
    order_id: str
    order_status: str
    answer: str


def query_order_node(state: OrderState):
    order_id = state["order_id"]
    order_status = f"订单 {order_id} 当前状态：已发货。"
    return {"order_status": order_status}

如果你使用 LangChain Tool Calling，后面还会遇到 LangGraph 提供的 ToolNode。

不过在理解 ToolNode 之前，先掌握一个原则：

工具节点应该把外部结果结构化写回 State，而不是只把一段杂乱文本塞进 messages。

例如推荐：

1
2
3
4

return {
    "order_status": "已发货",
    "tracking_number": "SF1001",
}

而不是：

1
2
3

return {
    "context": "查了一下订单，是已发货，单号好像是 SF1001"
}

前者更容易被后续节点判断。

Tool 节点要注意风险边界

工具调用常常意味着系统要连接真实世界。

例如：

  • 删除数据。
  • 发送邮件。
  • 修改配置。
  • 创建订单。
  • 发起退款。

这类动作不要直接让模型自由执行。

更好的做法是拆成多个节点：

1

生成操作建议 -> 风险检查 -> 人工确认 -> 执行工具

这样才能把风险边界显式表达出来。

后面讲 Human-in-the-loop 时，我们会专门讨论这一点。

class ReviewState(TypedDict):
    answer: str

            "review_reason": "回答太短，需要补充细节。",

        "is_answer_valid": True,

九、节点命名：让图可读

节点名不是随便起的。

它会出现在图结构、日志、trace 和调试信息里。

十、节点可复用的前提

很多人会问：

怎么设计可复用节点？

这里要先说一个原则：

可复用不是靠抽象出来的，而是靠边界清楚自然形成的。

如果一个节点只读取明确字段、只做一类动作、只返回明确字段，它就更容易复用。

例如：

1
2

def normalize_question_node(state):
    return {"question": state["question"].strip()}

这个节点很容易复用。

但下面这种节点很难复用：

1
2
3
4
5
6
7

def process_node(state):
    # 读取 question、user_id、docs、history、config
    # 判断意图
    # 检索文档
    # 调用模型
    # 更新多个字段
    ...

因为它依赖太多上下文。

可复用节点的几个特征

一个可复用节点通常有这些特点：

  • 输入字段少而明确。
  • 输出字段少而稳定。
  • 不依赖外部隐式状态。
  • 节点名表达清楚。
  • 只做一类事情。
  • 失败模式可预期。

例如检索节点可以设计成：

1
2
3

def retrieve_docs_node(state: RagState):
    docs = retriever.invoke(state["question"])
    return {"docs": docs}

如果后续换模型、换生成 Prompt，这个节点不需要变。

十一、什么时候不要复用？

不要为了复用而牺牲可读性。

如果两个节点只是看起来相似，但业务语义不同，不一定要强行合并。

例如：

1
2
3

check_answer
check_risk
check_user_permission

它们都是“检查”，但含义不同。

强行抽象成一个 check_node 可能会让代码更难懂。

在 Agent 工作流里，清晰通常比过度复用更重要。

尤其是早期设计图时，宁可多写几个明确节点，也不要过早封装成复杂通用节点。

from typing import Literal, TypedDict
from langgraph.graph import StateGraph, START, END


class WritingState(TypedDict):
    topic: str
    draft: str
    is_draft_valid: bool
    review_reason: str
    final_answer: str


def write_draft_node(state: WritingState):
    draft = f"{state['topic']} 是一个重要概念。"
    return {"draft": draft}


def check_draft_node(state: WritingState):
    draft = state["draft"]

    if len(draft) < 30:
        return {
            "is_draft_valid": False,
            "review_reason": "初稿太短，需要补充解释和例子。",
        }

    return {
        "is_draft_valid": True,
        "review_reason": "初稿内容足够。",
    }


def route_after_check(state: WritingState) -> Literal["finish", "rewrite"]:
    if state["is_draft_valid"]:
        return "finish"
    return "rewrite"


def rewrite_draft_node(state: WritingState):
    final_answer = (
        f"{state['draft']}\n\n"
        f"进一步说明：{state['topic']} 的关键价值在于把复杂流程拆成清晰步骤，"
        "让系统更容易观察、控制和维护。"
    )
    return {"final_answer": final_answer}


def finish_node(state: WritingState):
    return {"final_answer": state["draft"]}


builder = StateGraph(WritingState)

builder.add_node("write_draft", write_draft_node)
builder.add_node("check_draft", check_draft_node)
builder.add_node("rewrite_draft", rewrite_draft_node)
builder.add_node("finish", finish_node)

builder.add_edge(START, "write_draft")
builder.add_edge("write_draft", "check_draft")
builder.add_conditional_edges(
    "check_draft",
    route_after_check,
    {
        "finish": "finish",
        "rewrite": "rewrite_draft",
    },
)
builder.add_edge("finish", END)
builder.add_edge("rewrite_draft", END)

graph = builder.compile()

result = graph.invoke({
    "topic": "LangGraph Node"
})

print(result["final_answer"])

这个例子里有几个清晰的节点：

节点职责
write_draft生成初稿
check_draft检查初稿质量
rewrite_draft根据检查结果重写
finish直接把初稿作为最终答案

每个节点都只做一类事情。

条件边只负责根据 is_draft_valid 决定下一步。

这就是一个比较健康的 LangGraph 节点设计。

十三、节点设计中的常见问题

1. 一个节点做太多事

最常见的问题是把多个步骤塞进一个节点。

例如：

1

classify_retrieve_generate_check_node

这会导致：

  • 中间结果不可观察。
  • 失败原因不好定位。
  • 后续无法插入人工审核。
  • 无法单独替换某一步。

2. 节点返回字段不稳定

例如某个节点有时返回：

1

{"answer": "..."}

有时返回：

1

{"result": "..."}

后续节点就会很难写。

节点输出字段应该稳定。

3. 节点依赖没有声明的字段

如果节点读取 state["context"]，就要确保所有到达该节点的路径都会写入 context。

否则某些分支会在运行时失败。

4. 把路由逻辑藏在节点内部

如果节点内部决定“下一步该去哪”，但图上没有体现，读者就看不出流程。

LangGraph 的优势是流程显式化。

不要把流程又藏回节点里。

5. 过度依赖 LLM 节点

不是所有判断都需要 LLM。

规则清楚的事情，用普通函数节点更稳定。

把 LLM 留给真正需要自然语言理解和生成的步骤。

十四、节点设计的实用流程

设计节点时，可以按下面流程来。

第一步：先写流程图

例如：

1

classify_intent -> retrieve_docs -> generate_answer -> check_answer

第二步：给每一步起一个动词名

例如：

1
2
3
4

classify_intent
retrieve_docs
generate_answer
check_answer

如果名字里出现太多 and，通常说明节点该拆了。

例如：

1

retrieve_and_generate_and_check

第三步：写出节点读写字段

节点读取写入
classify_intentquestionintent
retrieve_docsquestiondocs
generate_answerquestion, docsanswer
check_answeransweris_answer_valid

第四步：确认节点职责单一

问自己：

这个节点能不能用一句话说明？

如果不能，说明它可能太大。

第五步：把流程跳转交给 Edge

节点写状态。

Edge 根据状态决定下一步。

这能保持图的结构清晰。

十五、最佳实践

1. 节点只做一类动作

这是最重要的原则。

一个节点可以复杂，但职责要单一。

2. 明确节点读写字段

设计节点前先想清楚：

1
2

它读哪些 State 字段？
它写哪些 State 字段？

3. 节点名使用动作短语

推荐动词开头：

1
2
3
4

classify_intent
retrieve_docs
generate_answer
check_answer

4. LLM 节点输出尽量结构化

如果后续要路由或判断，不要只返回自然语言。

结构化字段更可靠。

5. 普通逻辑不要交给模型

规则判断、计数、格式转换、字段提取，能用代码稳定完成就用代码。

6. Tool 节点明确风险边界

涉及真实动作的工具节点，最好配合风险检查和人工确认。

不要让模型直接执行高风险操作。

7. 不要为了复用过早抽象

先让节点职责清晰，再谈复用。

过早抽象会让图变得不直观。

十六、总结

本文重点讲了 LangGraph 中的 Node 设计。

核心结论是：

Node 管动作。一个好的节点应该读取明确的 State 字段，执行一个清晰动作，并返回稳定的状态更新。

本文重点包括：

  • Node 是 LangGraph 的执行单元，通常是接收 State、返回状态更新的函数。
  • 普通函数节点适合规则判断、格式转换和简单业务逻辑。
  • LLM 节点适合自然语言理解、生成、总结和评估。
  • Retriever 节点负责检索资料，并把结果写入 State。
  • Tool 节点负责连接外部能力，但要注意风险边界。
  • 检查节点负责写入判断结果，条件边负责根据结果路由。
  • 节点命名会影响图的可读性和可观测性。
  • 可复用节点来自清晰边界，而不是过早抽象。
  • 一个节点只做一类事情，是最重要的设计原则。

到这里，我们已经分别深入了 State 和 Node。
