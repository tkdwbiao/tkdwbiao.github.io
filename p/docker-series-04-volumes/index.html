【Docker 系列 04】给容器加块硬盘：Docker 数据持久化 (Volumes) 完全指南

2025-06-26 10:00
阅读时长: 5 分钟

“老板，我不小心敲了 docker rm，昨天用户的注册数据全没了，我现在买站票跑路还来得及吗？”

在上一篇文章中，我们学会了用 Dockerfile 把代码打包成镜像。容器跑起来了，应用很完美。

但这引出了 Docker 世界里最致命的一个概念：容器是短暂的（Ephemeral）。 Docker 的文件系统是由一层层“只读镜像层”加上最上面一层“可读写容器层”组成的。当容器在运行时，你的程序产生的所有日志、新上传的图片、存入数据库的每一条记录，都写在这个最上层。

一旦你执行了 docker rm 删除了容器，这个可读写层就会伴随着里面的数据灰飞烟灭！

如果你用 Docker 部署了一个 MySQL 数据库，更新容器版本时随手一个删除，恭喜你，直接喜提“删库跑路”成就。

为了打破这种“人在塔在，人亡塔亡”的魔咒，Docker 提供了数据持久化技术。今天，我们就来学习如何给容器插上一块“外接硬盘”。

一、拯救数据的两种终极方案

在 Docker 中，要把数据保存到容器外部（宿主机的硬盘上），主要有两种玩法。很多人把它们搞混，但它们的适用场景完全不同。

1. Bind Mounts（绑定挂载）：简单粗暴的“随意门”

原理：直接把你电脑（宿主机）上的某个绝对路径，强行映射到容器内部的某个路径上。 在容器里往这个目录写文件，其实就是写在你电脑上；在你电脑上修改这个文件，容器里立刻就能看到变化。

  • 优点：非常适合本地开发。比如你可以把代码目录挂载进去，本地修改代码保存，容器里的 Web 服务器（如 Uvicorn/Nodemon）立刻热重载生效，不需要重新 build 镜像。
  • 缺点：极度依赖宿主机的目录结构，在 Windows、Mac、Linux 上路径写法不同，容易出幺蛾子。

2. Docker Volumes（数据卷）：官方正统的“专属U盘”

原理：这是由 Docker 全权管理的宿主机硬盘空间。你不需要知道它具体存在你电脑的哪个深层目录（通常在 /var/lib/docker/volumes/），你只需要给这块“U盘”起个名字。

  • 优点：跨平台兼容性极佳，安全性高，哪怕所有容器都删了，Volume 依然存活，非常适合生产环境的数据库存储。
  • 缺点：你想用宿主机的编辑器直接修改 Volume 里的文件比较麻烦，因为它们被 Docker 藏得比较深。

二、实战演练：不丢失数据的 MySQL 数据库

百闻不如一练，让我们用 Volumes（数据卷） 跑一个 MySQL 容器，看看数据是如何“永生”的。

第一步：创建一个数据卷（买一块U盘）

1

docker volume create my-db-data

(你可以用 docker volume ls 查看到它)

第二步：启动 MySQL 容器，并把数据卷插上去 注意这里的 -v (volume) 参数，冒号前面是数据卷名字，冒号后面是 MySQL 在容器里存数据的固定路径。

1
2
3
4
5

docker run -d \
  --name my-mysql \
  -e MYSQL_ROOT_PASSWORD=mysecret \
  -v my-db-data:/var/lib/mysql \
  mysql:8.0

第三步：搞点破坏（删库跑路测试） 现在数据库跑起来了。假设你在里面建了表，存了数据。然后你手抖了，删除了容器：

1

docker rm -f my-mysql

完了，容器没了！但是别慌，因为我们用了 Volume，数据还在。

第四步：浴火重生 你重新启动一个新的 MySQL 容器，只需再次挂载那个名叫 my-db-data 的数据卷：

1
2
3
4
5

docker run -d \
  --name new-mysql \
  -e MYSQL_ROOT_PASSWORD=mysecret \
  -v my-db-data:/var/lib/mysql \
  mysql:8.0

连上数据库一看，刚才建的表和数据完好无损！这就是 Volume 的魔力。

三、阿彪的血泪避坑指南：恐怖的 Permission Denied 权限陷阱

很多小伙伴在学完挂载后，在实际项目中会采用 Bind Mounts（绑定挂载） 把项目里的数据库文件挂载到本地（比如 ./volumes/etcd:/etcd）。

结果在本地用 Python 或者 Node.js 运行主程序代码时，突然程序崩溃，抛出如下惨不忍睹的报错：

1

PermissionError: Permission denied (os error 13) about ["/home/user/my-project/volumes/etcd/member"]

如果你开启了框架的“热重载”（Reload）功能，这个报错会像幽灵一样疯狂刷屏。

为什么会这样？（硬核原理解密）

这是无数开发者在 Docker 上踩过的最大的坑，没有之一。

  1. Docker 内部默认是上帝（Root）：Docker 容器内部的进程默认是以 root 用户运行的。
  2. 上帝创建了文件：当容器（比如 etcd、MySQL、Milvus）启动并向挂载的目录 ./volumes 写入数据时，这些在宿主机上生成的文件，其所有者（Owner）都是 root。
  3. 凡人试图访问：你在宿主机上是以普通用户（比如 jf234）的身份在写代码。你的 Web 框架（如 Uvicorn）为了实现热重载，会去扫描项目下的所有文件。
  4. 悲剧发生：当你的普通用户扫描到被 Docker root 锁定的 volumes 文件夹时，Linux 系统的权限管理机制无情地伸出手——Permission Denied（不准看）！ 程序当场暴毙。

如何破解这个权限诅咒？

解法一：夺回主权（最简单直接） 如果容器已经跑起来并且生成了数据，你可以直接在宿主机上用 sudo 把文件夹的所有权抢回来，改回你自己的用户。

1
2

# 将 volumes 文件夹的所有权改回当前用户和当前用户组
sudo chown -R $USER:$USER ./volumes

（每次 Docker 容器产生新级别的深层文件时，可能都需要再敲一次，适合开发阶段临时救急）

解法二：惹不起躲得起（最优雅） 修改你本地代码的热重载配置，明确告诉监控器（Watcher）不要去扫描 Docker 的数据文件夹。 以 Python FastAPI 为例，启动时加上 reload_dirs 或排除项：

1
2
3
4
5
6

uvicorn.run(
    "app.main:app", 
    reload=True,
    # 明确告诉框架，只监听 app 代码目录，不要去碰 volumes
    reload_dirs=["app"] 
)

解法三：让 Docker 以凡人的身份运行 在启动容器时，强制 Docker 使用你当前宿主机的用户身份运行，这样它生成的文件你天生就有权限访问：

1
2

# 使用 $(id -u):$(id -g) 获取当前用户的 UID 和 GID
docker run -d -u $(id -u):$(id -g) -v $(pwd)/data:/app/data my-image

结语

掌握了 Volume 和 Bind Mounts，你的 Docker 技能树就点亮了“数据不朽”的成就。

回顾最佳实践：

  1. 代码和配置文件：用 Bind Mounts 映射，方便你在本地用 VS Code 随时修改看效果。
  2. 数据库和大型中间件的存储：用 Docker Volumes 交给引擎托管，安全省心。
  3. 遇到权限报错：别慌，想想是不是 Docker 这个“上帝”在你的地盘创建了普通人无权访问的文件。

现在，我们解决了单个容器的打包和数据存储。但是，在真实的“智能 OnCall 项目”或微服务架构中，你往往需要同时运行 Web后端 + 日志服务 + 向量数据库 (Milvus) + MinIO 等 4、5 个容器。

如果全靠 docker run 一条条敲，不仅手酸，而且怎么让它们互相通过网络通信（比如后端怎么连上数据库）也是个大问题。
