大模型时代的数据采集工程 33：浏览器自动化常用 API 速查

2026-02-13 10:00
阅读时长: 13 分钟

上一篇扩展篇，我们整理了网页解析常用 API。

解析层解决的是：

1

HTML 已经拿到之后，如何稳定提取字段。

但有些页面并不是简单的静态 HTML。

它们可能需要：

1
2
3
4
5
6

等待前端渲染。
点击展开内容。
滚动加载列表。
填写自有系统表单。
截图诊断页面状态。
监听授权范围内的接口响应。

这时就会用到浏览器自动化。

常见工具包括：

1
2

Selenium。
Playwright。

本文整理浏览器自动化常用 API。

重点不是“如何模拟真人”，也不是“如何规避检测”。

而是：

在自有、测试、授权或合规的数据采集场景中，如何用浏览器自动化完成页面加载、元素定位、等待、截图、调试和诊断。

涉及验证码、权限、风控、登录异常、访问频率异常时，正确动作是暂停、降频、重新授权或人工复核，不是绕过。

一、浏览器自动化适合什么场景？

在爬虫工程里，浏览器自动化不是默认选择。

优先级通常是：

1
2
3
4
5

正式 API。
公开导出。
HTTP 接口。
静态 HTML 解析。
浏览器自动化。

浏览器自动化适合：

1
2
3
4
5

页面必须执行 JavaScript 才能得到内容。
需要观察页面最终渲染状态。
需要截图排查失败原因。
需要测试自有后台流程。
需要在授权范围内操作交互页面。

不适合：

1
2
3
4

只为绕过访问控制。
只为规避频率限制。
只为破解验证码。
只为隐藏自动化行为。

工程上要记住：

1
2
3
4

浏览器自动化成本更高。
浏览器自动化更慢。
浏览器自动化更占资源。
浏览器自动化更需要状态管理和监控。

所以它应该是采集系统中的一种能力，而不是所有任务的默认方式。

二、Selenium 和 Playwright 怎么选？

Selenium 是老牌 WebDriver 生态。

Playwright 是更现代的浏览器自动化框架。

可以简单对比：

1
2

Selenium：生态成熟，测试领域广，兼容 WebDriver。
Playwright：API 现代，自动等待好，多上下文隔离方便，网络监听体验好。

工程建议：

1
2
3

已有 Selenium 项目：继续维护即可。
新项目或自动化采集诊断：优先考虑 Playwright。
自动化测试团队已有标准：遵守团队工具链。

面试表达可以这样说：

我不会一上来就用浏览器自动化。会先看数据是否来自接口或静态 HTML。如果确实依赖渲染、交互或截图诊断，再用 Selenium 或 Playwright。新项目我更倾向 Playwright，因为自动等待、上下文隔离和网络监听更方便。

from dataclasses import dataclass

from selenium import webdriver
from selenium.webdriver.chrome.options import Options
from selenium.webdriver.common.by import By
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait


@dataclass
class BrowserArticle:
    title: str | None
    content: str | None
    screenshot_path: str | None
    error_type: str | None


def fetch_article_with_selenium(url: str) -> BrowserArticle:
    options = Options()
    options.add_argument("--headless=new")

    browser = webdriver.Chrome(options=options)
    browser.set_page_load_timeout(20)

    try:
        browser.get(url)
        wait = WebDriverWait(browser, 10)

        title_node = wait.until(
            EC.presence_of_element_located((By.CSS_SELECTOR, "h1.title"))
        )
        content_node = browser.find_element(By.CSS_SELECTOR, "div.content")

        return BrowserArticle(
            title=title_node.text.strip() or None,
            content=content_node.text.strip() or None,
            screenshot_path=None,
            error_type=None,
        )
    except Exception:
        screenshot_path = "failed-page.png"
        browser.save_screenshot(screenshot_path)
        return BrowserArticle(None, None, screenshot_path, "browser_fetch_failed")
    finally:
        browser.quit()

Playwright 很重要的概念是 BrowserContext。

1
2

Context 的价值：

1

3
4

常见 wait_until：

from dataclasses import dataclass

from playwright.sync_api import TimeoutError, sync_playwright


@dataclass
class RenderedArticle:
    title: str | None
    html: str | None
    screenshot_path: str | None
    error_type: str | None


def render_article(url: str) -> RenderedArticle:
    with sync_playwright() as p:
        browser = p.chromium.launch(headless=True)
        context = browser.new_context()
        page = context.new_page()

        try:
            page.goto(url, wait_until="domcontentloaded", timeout=20_000)
            page.wait_for_selector("h1.title", timeout=10_000)

            title = page.locator("h1.title").inner_text().strip()
            html = page.content()

            return RenderedArticle(title, html, None, None)
        except TimeoutError:
            screenshot_path = "render-timeout.png"
            page.screenshot(path=screenshot_path, full_page=True)
            return RenderedArticle(None, None, screenshot_path, "render_timeout")
        except Exception:
            screenshot_path = "render-failed.png"
            page.screenshot(path=screenshot_path, full_page=True)
            return RenderedArticle(None, None, screenshot_path, "render_failed")
        finally:
            context.close()
            browser.close()

上层可以根据 error_type 决定：

八、等待策略怎么设计？

浏览器自动化最容易出问题的是等待。

不要只靠固定睡眠。

十一、常见坑点

1. 用浏览器自动化替代所有请求

如果数据可以通过接口或静态 HTML 获取，不一定要启动浏览器。

浏览器成本更高。

2. 不设置超时

页面加载、元素等待、脚本执行都要有超时。

否则 Worker 会卡住。

3. 过度使用 sleep

sleep 不知道页面是否真的准备好。

应该等待具体元素、响应或状态。

4. 不关闭 browser / context

会导致进程泄漏和内存增长。

一定要 close() 或 quit()。

5. 不保存失败截图

没有截图时，很难判断页面到底发生了什么。

6. 混用会话状态

不同数据源、不同授权边界、不同账号状态不应该混在同一个 context 或 browser state 里。

7. 误把风控信号当普通失败

遇到：

1
2
3
4
5

验证码。
登录页。
权限不足。
访问过频。
安全验证。

应该暂停、降频、检查授权或人工复核。

不要继续自动化尝试。

十二、面试表达

如果面试官问：

1

Selenium 常用哪些 API？

可以这样回答：

常用的是 webdriver 启动浏览器、get 打开页面、find_element / find_elements 定位元素、WebDriverWait 做显式等待、click / send_keys 做交互、get_attribute 读属性、save_screenshot 截图、execute_script 做页面状态诊断。工程上要设置超时、失败截图和 finally 关闭浏览器。

如果问：

1

Playwright 常用哪些 API？

可以这样回答：

Playwright 常用 launch、new_context、new_page、goto、locator、wait_for_selector、click、fill、inner_text、get_attribute、content、screenshot、expect_response、expect_download。它的 locator 自动等待和 context 隔离比传统写法更适合工程化自动化。

如果问：

1

Selenium 和 Playwright 怎么选？

可以这样回答：

Selenium 生态成熟，适合已有 WebDriver 项目；Playwright API 更现代，自动等待、上下文隔离、网络监听更方便。新项目我更倾向 Playwright，但会结合团队已有工具链和运行环境选择。

如果问：

1

动态页面采集一定要浏览器吗？

可以这样回答：

不一定。应该先看数据是否来自授权范围内的接口或静态 HTML。如果接口可以稳定提供数据，直接请求更高效。浏览器自动化适合必须渲染、必须交互或需要截图诊断的场景。

如果问：

1

遇到验证码或风控页面怎么办？

可以这样回答：

我会把它当成风险信号，而不是普通解析失败。系统应保存截图和上下文，暂停任务或数据源，检查授权和访问频率，进入人工复核，不会继续尝试绕过验证码或风控。

十三、总结

本文整理了浏览器自动化常用 API。

核心结论包括：

  • 浏览器自动化适合渲染、交互、截图和授权页面诊断，不应该作为所有采集任务的默认方式。
  • Selenium 常用 API 包括 webdriver、Options、get、find_element、find_elements、WebDriverWait、expected_conditions、click、send_keys、get_attribute、save_screenshot、execute_script、quit。
  • Playwright 常用 API 包括 launch、new_context、new_page、goto、locator、wait_for_selector、click、fill、inner_text、get_attribute、content、screenshot、expect_response、expect_download。
  • Playwright 的 BrowserContext 适合隔离 Cookie、localStorage 和任务状态。
  • 等待策略要基于目标元素、loading 状态、URL 或接口响应，不要依赖固定 sleep。
  • 失败时建议保存截图和 HTML 样本，便于人工复核和规则维护。
  • 浏览器渲染和字段解析要分层，渲染后可以继续交给 BeautifulSoup、lxml 或 parsel 抽取。
  • 浏览器自动化也要设置超时、限制并发、关闭资源、记录错误类型。
  • 遇到验证码、权限异常、风控或访问过频，应暂停、降频或人工复核，不应绕过。
