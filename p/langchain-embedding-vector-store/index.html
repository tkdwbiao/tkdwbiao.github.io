LangChain 向量检索实战：Embedding 与 Vector Store 入门

2025-09-25 10:00
阅读时长: 11 分钟

前面两篇文章里，我们已经完成了 RAG 数据准备的前两步：

1
2

Document Loader：把原始文件加载成 Document
Text Splitter：把长文档切成适合检索的 chunk

但切分后的文本块还只是普通文本。

如果用户问：

1

LangChain 如何把文档接入知识库？

系统怎么知道哪几个 chunk 和这个问题最相关？

这就需要 Embedding 和 Vector Store。

一、前言

RAG 的核心是“先检索，再生成”。

检索听起来很简单，但真正的问题是：怎么检索？

最容易想到的是关键词搜索。

比如用户搜索：

1

报销流程

系统去文档里找包含“报销流程”这几个字的内容。

这种方式在很多场景有效，但也有明显局限。

用户可能问：

1

怎么申请费用报销？

文档里写的可能是：

1

员工应在系统中提交差旅费用申请。

这里没有完全相同的关键词，但语义是相关的。

这时就需要语义检索。

Embedding 的作用，就是把文本转换成向量，让语义相近的内容在向量空间中更接近。

Vector Store 的作用，就是保存这些向量，并根据用户问题找到最相近的文档片段。

本文会重点讲：

  1. Embedding 是什么。
  2. Vector Store 是什么。
  3. 向量检索和关键词检索有什么区别。
  4. 如何用 LangChain 构建一个最小向量检索示例。
  5. Chroma 和 FAISS 的基本用法。
  6. similarity_search 和 as_retriever 怎么用。
  7. metadata 过滤为什么重要。
  8. 向量库选型和最佳实践。

二、Embedding 是什么？

Embedding 可以理解为：

把文本转换成一组数字向量，用数字表示文本语义。

例如：

1

"LangChain 是什么？"

经过 Embedding 模型后，可能变成：

1

[0.012, -0.233, 0.104, ...]

这个向量可能有几百维、上千维，甚至更多。

我们不需要理解每一维具体代表什么，只需要知道：

语义相近的文本，它们的向量距离通常更近。

一个直观例子

下面几句话：

1
2
3

如何申请报销？
报销流程是什么？
费用申请在哪里提交？

字面上不同，但语义相近。

Embedding 后，它们在向量空间里应该比较接近。

而下面这句话：

1

LangChain 的 Runnable 是什么？

和报销主题无关，向量距离应该更远。

这就是语义检索的基础。

Embedding 不是 LLM 回答

Embedding 模型不是用来生成回答的。

它的任务是把文本变成向量。

在 RAG 中通常有两类模型：

模型作用
Embedding Model把文本和问题转换成向量
Chat Model / LLM基于上下文生成回答

不要混淆。

三、Vector Store 是什么？

有了向量之后，需要保存和查询。

Vector Store 就是向量数据库或向量索引。

它通常保存三类信息：

1
2
3
4
5

文本 chunk
  ↓
对应向量
  ↓
metadata

例如：

1
2
3
4
5
6
7
8

{
    "page_content": "RAG 是检索增强生成...",
    "embedding": [0.12, -0.03, ...],
    "metadata": {
        "source": "rag.md",
        "section": "RAG 入门"
    }
}

当用户提问时：

  1. 把问题也转换成向量。
  2. 在向量库中查找最相似的向量。
  3. 返回对应的 Document。

这就是向量检索。

常见 Vector Store

常见选择包括：

Vector Store特点
Chroma本地开发友好，入门简单
FAISS本地高性能向量索引，适合实验和离线场景
PGVector基于 PostgreSQL，适合已有 PG 技术栈
Milvus专业向量数据库，适合大规模场景
Qdrant向量数据库，过滤和服务化能力较好
Weaviate向量数据库，生态较完整
Pinecone托管向量数据库服务

学习阶段可以先用 Chroma 或 FAISS。

生产环境则要根据数据规模、部署方式、权限过滤、运维成本来选。

四、向量检索和关键词检索的区别

1. 关键词检索

关键词检索看的是字面匹配。

优点：

  • 简单直接。
  • 对精确词、编号、术语效果好。
  • 容易解释。

缺点：

  • 同义表达可能搜不到。
  • 对自然语言问法不够友好。
  • 不理解语义。

例如用户问：

1

怎么报销差旅费？

文档写的是：

1

员工需提交费用申请。

关键词检索可能匹配不好。

2. 向量检索

向量检索看的是语义相似度。

优点：

  • 能处理同义表达。
  • 更适合自然语言问题。
  • 适合文档问答。

缺点：

  • 对编号、代码、精确字符串不一定稳定。
  • 结果不如关键词检索直观。
  • 依赖 Embedding 模型质量。
  • 需要向量库和索引维护。

3. 混合检索

真实业务里，向量检索和关键词检索经常结合。

比如：

  • 语义问题用向量检索。
  • 错误码、合同编号、产品型号用关键词检索。
  • 最后用 reranker 重排。

后续 Retriever 篇会继续讲这些策略。

本文先专注向量检索入门。

import os
from dotenv import load_dotenv
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma
from langchain_core.documents import Document

load_dotenv()

documents = [
    Document(
        page_content="LangChain 是一个用于构建大模型应用的框架。",
        metadata={"source": "intro.md"},
    ),
    Document(
        page_content="LCEL 可以用管道语法组合 Prompt、Model、Parser 和 Retriever。",
        metadata={"source": "lcel.md"},
    ),
    Document(
        page_content="RAG 是检索增强生成，会先从知识库检索资料，再让模型基于资料回答。",
        metadata={"source": "rag.md"},
    ),
]

embeddings = OpenAIEmbeddings(
    model=os.getenv("EMBEDDING_MODEL", "text-embedding-3-small"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
)

vectorstore = Chroma.from_documents(
    documents=documents,
    embedding=embeddings,
)

results = vectorstore.similarity_search("什么是检索增强生成？", k=2)

for doc in results:
    print("=" * 40)
    print(doc.page_content)
    print(doc.metadata)

这段代码做了几件事：

  1. 创建三个 Document。
  2. 用 Embedding 模型生成向量。
  3. 把 Document 和向量写入 Chroma。
  4. 用自然语言问题做相似度检索。
  5. 返回最相关的两个 Document。

similarity_search

1

vectorstore.similarity_search("什么是检索增强生成？", k=2)

表示返回最相似的 2 条文档。

k 太小可能漏掉答案。

k 太大可能带入无关内容。

常见起点是：

1

k=3

或者：

1

k=5

具体要结合评估集测试。

八、查看相似度分数

有时你想知道检索结果的相似度分数。

可以使用：

1
2
3
4
5
6
7
8
9

results = vectorstore.similarity_search_with_score(
    "什么是检索增强生成？",
    k=3,
)

for doc, score in results:
    print("score:", score)
    print(doc.page_content)
    print(doc.metadata)

注意：不同向量库的 score 含义可能不同。

有的分数越小越相似，有的越大越相似。

不要在不了解实现的情况下，把 score 当成统一标准。

更稳妥的做法是结合具体向量库文档和实际测试。

九、持久化 Chroma 向量库

上面的示例是内存向量库。

程序结束后数据可能就没了。

可以使用持久化目录：

1
2
3
4
5

vectorstore = Chroma.from_documents(
    documents=documents,
    embedding=embeddings,
    persist_directory="data/chroma_db",
)

下次加载：

1
2
3
4

vectorstore = Chroma(
    persist_directory="data/chroma_db",
    embedding_function=embeddings,
)

这样就不需要每次重新 embedding 所有文档。

为什么持久化重要？

Embedding 调用有成本。

如果每次启动都重新向量化全部文档：

  • 启动慢。
  • 成本高。
  • 容易触发限流。
  • 不利于增量更新。

真实项目通常会把索引构建和在线查询分开。

1
2

离线索引：加载文档 -> 切分 -> embedding -> 写入向量库
在线查询：用户问题 -> 检索 -> 生成回答

import os
from dotenv import load_dotenv
from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import FAISS
from langchain_core.documents import Document

load_dotenv()

documents = [
    Document(page_content="LangChain 用于构建大模型应用。", metadata={"source": "intro"}),
    Document(page_content="RAG 会先检索资料，再生成回答。", metadata={"source": "rag"}),
    Document(page_content="Vector Store 用于保存文本向量并进行相似度检索。", metadata={"source": "vector"}),
]

embeddings = OpenAIEmbeddings(
    model=os.getenv("EMBEDDING_MODEL", "text-embedding-3-small"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
)

vectorstore = FAISS.from_documents(documents, embeddings)

results = vectorstore.similarity_search("向量库有什么用？", k=2)

for doc in results:
    print(doc.page_content)
    print(doc.metadata)

from langchain_core.runnables import RunnablePassthrough
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI


def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

prompt = ChatPromptTemplate.from_messages([
    ("system", "请只根据上下文回答问题。如果上下文没有答案，请说无法确定。"),
    ("human", "上下文：\n{context}\n\n问题：{question}"),
])

model = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
    temperature=0.2,
)

rag_chain = (
    {
        "context": retriever | format_docs,
        "question": RunnablePassthrough(),
    }
    | prompt
    | model
    | StrOutputParser()
)

answer = rag_chain.invoke("RAG 是什么？")
print(answer)

这就是一个完整的最小 RAG 链路。

十二、metadata 过滤

向量检索不仅要按语义找相似内容，有时还要按 metadata 过滤。

例如只检索某个来源：

    "LCEL 是什么？",

metadata 过滤适合：

  • 按文档类型过滤
  • 按部门过滤
  • 按时间过滤
  • 按权限过滤
  • 按租户过滤
  • 按知识库过滤

权限过滤示例

企业知识库中，不能所有人检索所有文档。

假设 metadata 有：

1
2
3
4

metadata={
    "department": "HR",
    "access_level": "internal",
}

检索时就可以根据当前用户权限过滤。

不同向量库支持的 filter 语法不完全一样，生产项目要看具体实现。

但原则很明确：

权限信息要从 metadata 阶段就设计好，否则后面很难补。

import os
from dotenv import load_dotenv
from langchain_community.document_loaders import DirectoryLoader, TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma

load_dotenv()

loader = DirectoryLoader(
    "data/docs",
    glob="**/*.md",
    loader_cls=TextLoader,
    loader_kwargs={"encoding": "utf-8"},
)

docs = loader.load()

splitter = RecursiveCharacterTextSplitter(
    chunk_size=600,
    chunk_overlap=100,
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
)

chunks = splitter.split_documents(docs)

for chunk in chunks:
    chunk.metadata["kb_name"] = "langchain-demo"
    chunk.metadata["language"] = "zh-cn"

embeddings = OpenAIEmbeddings(
    model=os.getenv("EMBEDDING_MODEL", "text-embedding-3-small"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
)

vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    persist_directory="data/chroma_db",
)

results = vectorstore.similarity_search("LCEL 有什么作用？", k=3)

for doc in results:
    print("=" * 60)
    print(doc.metadata)
    print(doc.page_content[:500])

十四、如何选择 Vector Store？

学习阶段和生产阶段关注点不同。

1. 学习阶段

推荐：

  • Chroma
  • FAISS

原因：

  • 上手简单。
  • 本地运行方便。
  • 适合理解概念。
  • 不需要复杂运维。

2. 小型项目

可以考虑：

  • Chroma 持久化
  • FAISS 本地索引
  • PGVector

如果你已经在使用 PostgreSQL，PGVector 会比较自然。

3. 企业或大规模场景

需要考虑：

  • 数据规模
  • 并发查询
  • 权限过滤
  • 多租户
  • 高可用
  • 备份恢复
  • 监控运维
  • 成本

可能会选择：

  • Milvus
  • Qdrant
  • Weaviate
  • Pinecone
  • PGVector

不要只看 demo 简单，要结合长期维护成本。

十五、常见问题

1. Embedding 模型可以随便换吗？

不建议随便换。

如果你换了 Embedding 模型，已有向量通常需要重新生成。

因为不同模型生成的向量空间不一样。

不要用 A 模型生成文档向量，再用 B 模型生成查询向量。

2. 为什么检索结果不相关？

可能原因：

  • 文档切分不合理。
  • Embedding 模型效果不好。
  • 查询表达和文档差异太大。
  • top-k 太小。
  • metadata 过滤条件太严格。
  • 知识库里本来没有答案。

排查时先打印检索结果，而不是直接调 Prompt。

3. k 应该设置多大？

常见起点：

1

k=3

或者：

1

k=5

如果答案经常漏掉，可以增加 k。

如果上下文太长、无关内容太多，可以减少 k 或加 rerank。

4. 相似度分数能直接当置信度吗？

不能简单等同。

相似度分数只能说明向量距离，不等于答案正确率。

而且不同向量库的分数含义不同。

建议把分数作为调试参考，而不是最终用户置信度。

5. 向量库是否能替代数据库？

不能。

向量库适合语义检索，不适合所有查询。

例如：

  • 精确订单查询
  • 金额统计
  • 权限事务
  • 强一致更新

这些仍然应该使用数据库或业务 API。

向量库是 RAG 的检索组件，不是万能存储。

十六、最佳实践

1. 文档向量和查询向量使用同一个 Embedding 模型

这是基本原则。

不要混用不同模型。

2. 先测试 similarity_search，再接 LLM

RAG 效果差时，先检查检索结果。

1

docs = vectorstore.similarity_search(question, k=5)

如果检索结果都不对，后面模型再强也很难答对。

3. metadata 从一开始设计好

至少保留：

  • source
  • title
  • page
  • section
  • doc_id
  • updated_at

企业场景还要保留：

  • tenant_id
  • department
  • access_level

4. 持久化向量库

不要每次启动都重新 embedding 全部文档。

索引构建和在线查询应该分开。

5. 准备评估问题集

每次调整：

  • chunk_size
  • chunk_overlap
  • embedding model
  • vector store
  • k
  • filter

都应该用固定问题集测试效果。

6. 不要只依赖向量检索

对于错误码、编号、产品型号、合同号这类精确信息，关键词或结构化查询可能更合适。

真实系统里经常需要混合检索。

十七、总结

本文我们学习了 RAG 中非常关键的一环：Embedding 与 Vector Store。

核心结论是：

Embedding 把文本变成向量，Vector Store 保存向量并支持相似度检索，它们共同让 RAG 能够根据语义找到相关资料。

本文重点包括：

  • Embedding 是把文本转换成向量的过程。
  • Vector Store 保存文本、向量和 metadata。
  • 向量检索能处理语义相近但字面不同的问题。
  • Chroma 适合本地入门和简单持久化。
  • FAISS 适合本地向量索引实验。
  • similarity_search 用于相似度检索。
  • similarity_search_with_score 可以查看相似度分数。
  • as_retriever() 可以把向量库转成统一 Retriever 接口。
  • metadata 过滤对权限、来源和多租户非常重要。
  • 向量库不是数据库，也不能替代所有查询能力。
