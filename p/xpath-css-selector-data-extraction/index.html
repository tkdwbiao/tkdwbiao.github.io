大模型时代的数据采集工程 06：XPath 与 CSS Selector 核心技巧

2025-12-21 10:00
阅读时长: 15 分钟

上一篇文章里，我们用 BeautifulSoup 完成了 HTML 解析入门。

核心思路是：

1
2
3
4

先拿到 HTML。
再定位标签。
再提取文本或属性。
最后转成结构化数据。

但真实网页结构往往比示例复杂。

例如：

1
2
3
4
5

同一个页面里有很多相似卡片。
目标字段藏在多层嵌套里。
标题、价格、时间、链接分布在不同层级。
某些字段没有稳定 class。
页面改版后选择器容易失效。

这时，只会 find() 和 find_all() 就不够了。

你需要更系统地掌握两类定位工具：

1
2

CSS Selector。
XPath。

这一篇，我们不只是讲语法，而是重点讲：

如何设计稳定、可维护、可排查的网页数据选择器。

一、前言

网页解析中最核心的问题，其实不是“怎么写代码”，而是：

1

如何准确定位目标数据？

比如一个列表页：

 1

<div class="article-list">
  <article class="card">
    <h2><a href="/post/1">第一篇文章</a></h2>
    <span class="author">阿彪</span>
    <time datetime="2025-12-21">2025-12-21</time>
  </article>
  <article class="card">
    <h2><a href="/post/2">第二篇文章</a></h2>
    <span class="author">阿彪</span>
    <time datetime="2025-12-22">2025-12-22</time>

你可以写：

1
2
3
4

找所有 a 标签。
找所有 h2。
找 .card 里的 a。
找 .article-list > .card > h2 > a。

这些写法都可能拿到标题。

但稳定性不一样。

如果选择器太宽，会拿到导航、推荐位、页脚链接。

如果选择器太窄，页面多一层 div 就失效。

如果依赖随机 class，前端重新构建后可能全部失效。

所以选择器设计是一种工程能力。

它决定了你的爬虫是“今天能跑”，还是“能维护”。

二、CSS Selector 和 XPath 分别适合什么？

先建立一个直观认识。

1. CSS Selector

CSS Selector 原本是前端用来选择元素并应用样式的语法。

爬虫中常用于：

1
2
3
4
5

按标签名查找。
按 class / id 查找。
按属性查找。
按父子层级查找。
按列表容器批量提取。

优点是：

  • 语法直观。
  • 和浏览器 DevTools 一致。
  • BeautifulSoup、parsel、Scrapy 都支持。
  • 适合 class/id 明确的页面。

2. XPath

XPath 是 XML / HTML 文档路径语言。

爬虫中常用于：

1
2
3
4
5
6

复杂层级定位。
按文本内容定位。
向上查找父节点。
查找兄弟节点。
按位置关系提取。
提取文本节点和属性。

优点是：

  • 表达能力强。
  • 支持父子、祖先、兄弟轴关系。
  • 适合结构复杂或 class 不稳定的页面。
  • Scrapy / lxml 中非常常用。

3. 怎么选？

简单建议：

场景推荐
class、id 清晰CSS Selector
列表卡片结构清晰CSS Selector
需要按文本定位XPath
需要找父节点、兄弟节点XPath
需要提取属性两者都可以
需要提取文本节点细节XPath 更灵活
页面结构简单CSS Selector 更易读
结构复杂、规则多XPath 更强

实际项目里，两者经常一起使用。

关键不是站队，而是选对工具。

from dataclasses import dataclass
from urllib.parse import urljoin
from bs4 import BeautifulSoup


@dataclass
class ArticleItem:
    item_id: str
    title: str
    url: str
    author: str | None
    publish_date: str | None
    summary: str | None


def parse_with_css(html: str, base_url: str) -> list[ArticleItem]:
    soup = BeautifulSoup(html, "lxml")
    items = []

    for card in soup.select("section.article-list article.card"):
        title_tag = card.select_one("h2.title a")
        if not title_tag:
            continue

        author_tag = card.select_one(".meta .author")
        time_tag = card.select_one(".meta time")
        summary_tag = card.select_one("p.summary")

        items.append(
            ArticleItem(
                item_id=card.get("data-id", ""),
                title=title_tag.get_text(" ", strip=True),
                url=urljoin(base_url, title_tag.get("href", "")),
                author=author_tag.get_text(strip=True) if author_tag else None,
                publish_date=time_tag.get("datetime") if time_tag else None,
                summary=summary_tag.get_text(" ", strip=True) if summary_tag else None,
            )
        )

    return items

这个写法有几个特点：

1
2
3
4
5

先限定列表容器 section.article-list。
再遍历 article.card。
字段在 card 内部查找，避免误抓其他区域。
可选字段不存在时返回 None。
链接用 urljoin 转成绝对 URL。

这就是比较稳的解析结构。

六、CSS Selector 的稳定性设计

写选择器时，常见目标不是“最短”，而是“稳定”。

1. 不要选择太宽

不推荐：

1

soup.select("a")

因为页面里可能有：

1
2
3
4
5
6

导航链接。
登录链接。
推荐文章。
广告链接。
页脚链接。
分页链接。

更好：

1

soup.select("section.article-list article.card h2.title a")

2. 不要过度依赖层级

过窄的选择器：

1

body > main > div > section > article > div > h2 > a

问题是页面只要多一层 div 就可能失效。

更稳：

1

section.article-list article.card h2.title a

它表达的是业务结构，而不是每一层 HTML 细节。

3. 优先使用语义稳定的属性

更稳定的依据通常是：

1
2
3
4
5
6
7

主体容器 class。
卡片 class。
字段 class。
data-id。
itemprop。
aria-label。
语义标签 article、time、main。

不稳定的依据可能是：

1
2
3
4
5

自动生成 class。
构建产物 hash class。
纯位置 nth-child。
样式布局类。
过深 DOM 层级。

例如：

1

<div class="css-1a2b3c x9f0a">标题</div>

这种 class 可能是构建工具生成的，不适合作为长期选择器。

4. 选择器要能表达业务含义

推荐：

1

article.product-card .price

不推荐：

1

div:nth-child(3) > span:nth-child(2)

前者表达“商品卡片里的价格”。

后者只是“第三个 div 里的第二个 span”。

页面稍微改版就可能失效。

XPath 的基本思想是：

1

常见语法：

from dataclasses import dataclass
from urllib.parse import urljoin
from lxml import html as lxml_html


@dataclass
class ArticleItem:
    item_id: str
    title: str
    url: str
    author: str | None
    publish_date: str | None


def first_text(values: list[str]) -> str | None:
    return values[0].strip() if values else None


def parse_with_xpath(html: str, base_url: str) -> list[ArticleItem]:
    root = lxml_html.fromstring(html)
    items = []

    for card in root.xpath('//section[contains(@class, "article-list")]//article[contains(@class, "card")]'):
        title = first_text(card.xpath('.//h2[contains(@class, "title")]/a/text()'))
        href = first_text(card.xpath('.//h2[contains(@class, "title")]/a/@href'))
        author = first_text(card.xpath('.//*[contains(@class, "author")]/text()'))
        publish_date = first_text(card.xpath('.//time/@datetime'))
        item_id = card.get("data-id", "")

        if not title or not href:
            continue

        items.append(
            ArticleItem(
                item_id=item_id,
                title=title,
                url=urljoin(base_url, href),
                author=author,
                publish_date=publish_date,
            )
        )

    return items

注意这里使用了：

1

.//

它表示从当前 card 节点内部查找，而不是从整个文档查找。

这很重要。

如果在循环里写 //h2/a/text()，每次都会从整个文档重新找，容易拿错数据。

九、XPath 的轴关系：它为什么更强？

XPath 比 CSS Selector 强的地方之一，是轴关系。

比如：

1
2
3
4

<div class="field">
  <span class="label">作者</span>
  <span class="value">阿彪</span>
</div>

如果你想根据“作者”这个文本找到旁边的值，可以写：

1

//span[text()="作者"]/following-sibling::span[1]/text()

含义是：

1
2
3

找到文本等于 作者 的 span。
再找它后面的第一个兄弟 span。
提取文本。

常见轴关系：

轴含义
parent::父节点
ancestor::祖先节点
following-sibling::后面的兄弟节点
preceding-sibling::前面的兄弟节点
descendant::后代节点

示例：

1

value = root.xpath('//span[text()="作者"]/following-sibling::span[1]/text()')

这种按标签关系和文本关系定位的能力，是 XPath 的优势。

十、按文本内容定位

有些页面没有稳定 class，但有稳定标签文本。

例如：

1
2
3
4

<dl class="meta">
  <dt>作者</dt><dd>阿彪</dd>
  <dt>日期</dt><dd>2025-12-21</dd>
</dl>

可以写：

1
2

author = root.xpath('//dt[normalize-space(text())="作者"]/following-sibling::dd[1]/text()')
date = root.xpath('//dt[normalize-space(text())="日期"]/following-sibling::dd[1]/text()')

normalize-space() 会去掉前后空白并合并中间空白。

它很适合处理 HTML 中换行和空格不稳定的情况。

例如：

1

normalize-space(.)

表示提取当前节点下所有文本并规范化空白。

十一、class 匹配的坑

XPath 中不要简单写：

1

//article[@class="card"]

因为 HTML class 可能有多个：

1

<article class="card featured">

这时 @class="card" 就匹配不到。

更稳的写法是：

1

//article[contains(concat(" ", normalize-space(@class), " "), " card ")]

虽然长，但更准确。

简单场景可以写：

1

//article[contains(@class, "card")]

但它可能误匹配：

1
2

card-list
product-card-large

所以在严谨解析里，要知道这两种写法的区别。

CSS Selector 的 .card 会按 class token 匹配，通常更自然。

这也是 class 场景下 CSS Selector 更舒服的原因。

十二、位置选择器要谨慎

CSS 和 XPath 都支持按位置选择。

CSS：

1

.article-card:nth-child(1)

XPath：

1

(//article[contains(@class, "card")])[1]

位置选择适合：

1
2
3

明确只要第一条。
表格列位置稳定。
分页按钮位置固定。

但不适合长期依赖页面布局。

例如：

1

//div[3]/span[2]/text()

这类选择器很脆弱。

页面多一个广告位、推荐位、包裹层，就可能全部错位。

工程上更推荐：

1
2
3
4
5

用稳定容器定位。
用字段标签定位。
用文本标签定位。
用属性定位。
最后才用位置兜底。

十三、选择器调试方法

写选择器时，不要靠猜。

建议流程：

1
2
3
4
5
6
7
8

打开浏览器 DevTools。
找到目标元素。
观察它所在的业务容器。
确认字段是否在原始 HTML 中。
先写容器选择器。
再写字段选择器。
在控制台或本地代码中验证命中数量。
记录选择器命中率。

1. 先确认数据来源

如果目标数据不在原始 HTML 中，选择器再好也没用。

要先确认：

1
2
3
4

数据是否在 HTML 源码里？
是否来自接口 JSON？
是否在 script 内嵌状态里？
是否由前端渲染后才出现在 DOM？

如果来自接口，优先解析接口 JSON。

如果必须渲染，才考虑浏览器自动化。

2. 检查命中数量

解析列表时，先看卡片数量：

1
2

cards = soup.select("section.article-list article.card")
print(len(cards))

如果数量为 0，不要继续提取字段。

先排查：

1
2
3
4

是否拿到错误页面？
是否被重定向到登录页？
是否选择器写错？
是否页面结构变化？

3. 保留样本 HTML

线上解析失败时，最好保存一小段脱敏 HTML 样本。

例如：

1
2
3
4
5
6

页面 URL。
状态码。
Content-Type。
选择器。
命中数量。
截取的主体 HTML。

这样后续才能复现问题。

十四、选择器命中率和质量监控

十五、选择器失效后的排查思路

当选择器突然解析不到数据时，不要立刻改代码。

十九、常见错误写法

1. 从全局提取字段

错误示例：

1
2

titles = soup.select("h2 a")
authors = soup.select(".author")

然后用下标拼接。

这样很容易错位。

更好：

1
2
3

for card in soup.select("article.card"):
    title = card.select_one("h2 a")
    author = card.select_one(".author")

始终在同一个 item 容器内部提取字段。

2. 选择器过度依赖 nth-child

1

main > div:nth-child(2) > div:nth-child(4) > span

这类选择器可读性差、稳定性差。

应该优先找业务容器、语义标签和稳定属性。

3. XPath 忘记当前节点点号

在循环里错误写法：

1
2

for card in cards:
    title = card.xpath('//h2/a/text()')

这会从整个文档查找。

正确：

1
2

for card in cards:
    title = card.xpath('.//h2/a/text()')

4. 把 class 精确匹配写死

1

//article[@class="card"]

如果 class 变成 card featured，就匹配不到。

根据场景选择 contains 或更严谨的 class token 匹配。

5. 不验证选择器命中数量

写完选择器后直接入库，很容易把空数据写进去。

至少要检查：

1
2
3
4

列表数量是否合理。
必填字段是否存在。
URL 是否合法。
字段缺失率是否异常。

二十、面试表达

如果面试官问：

1

你平时怎么设计 XPath 或 CSS Selector？

可以这样回答：

我会先确认目标数据是否在原始 HTML 中，然后先定位稳定的业务容器，比如列表容器或详情主体，再在容器内部提取字段。选择器不会写得过宽，也不会过度依赖很深的 DOM 层级或 nth-child。我会优先使用稳定 class、语义标签、data 属性和字段标签。列表页会按 item 容器循环提取，避免全局字段错位。解析后还会记录命中数量和必填字段缺失率，方便发现页面改版或选择器失效。

如果问：

1

XPath 和 CSS Selector 怎么选？

可以这样回答：

class、id、属性比较清晰的页面，我通常优先用 CSS Selector，因为可读性好，也和浏览器 DevTools 一致。如果需要根据文本定位，或者需要找父节点、兄弟节点、祖先节点，XPath 更合适。实际项目里两者可以结合使用，关键是选择器要稳定、可维护，并且要配合日志和 Schema 校验。

如果问：

1

解析结果突然为空你怎么排查？

可以这样回答：

我会先区分请求层和解析层。先看状态码、最终 URL、Content-Type，确认没有跳转到登录页或错误页。然后检查原始 HTML 中是否还有目标数据，如果数据改成接口异步返回，就不应该继续用 HTML 选择器硬解析。如果数据还在 HTML 中，再检查容器选择器和字段选择器的命中数量，比较历史样本，看是否页面结构改版或字段变成可选。最后根据情况更新选择器、Schema 或任务状态。

二十一、总结

本文讲了 XPath 与 CSS Selector 在网页数据提取中的核心技巧。

核心结论包括：

  • 选择器设计的重点不是最短，而是稳定、可读、可维护。
  • CSS Selector 适合 class、id、属性清晰的页面。
  • XPath 适合复杂层级、文本定位、父子兄弟关系定位。
  • 列表页解析应该先定位 item 容器，再在容器内部提取字段。
  • 不要全局提取标题、作者、时间后再用下标拼接，容易错位。
  • 不要过度依赖深层级和 nth-child。
  • XPath 循环内部要使用 .//，避免从整个文档重新查找。
  • 选择器失效时要先排查请求结果、登录态、Content-Type 和原始 HTML。
  • 解析层也需要日志、命中率和字段缺失率监控。
  • LLM / Agent 可以辅助选择器诊断，但上线前必须验证和校验。
