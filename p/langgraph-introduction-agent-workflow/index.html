LangGraph 入门：用图结构编排复杂 Agent 工作流

2025-10-09 10:00
阅读时长: 11 分钟

前面几篇文章里，我们从 Agent 的基本概念一路讲到了多工具 Agent。

我们已经知道：

  • Agent 可以根据任务目标选择工具。
  • Tool Calling 让模型生成结构化工具调用请求。
  • ReAct 让模型在推理、行动和观察之间循环。
  • 多工具 Agent 可以连接订单、物流、知识库、计算等多个外部能力。

但当 Agent 任务越来越复杂时，一个新问题会出现：

如果所有流程都让模型自由决定，系统会越来越难控制、难调试、难恢复。

这时就需要 LangGraph。

一、前言

Agent 很灵活。

但灵活也意味着不确定。

例如你构建了一个智能客服 Agent，它可以：

  • 查询订单。
  • 查询物流。
  • 查询知识库。
  • 判断是否需要创建工单。
  • 在高风险操作前请求人工确认。
  • 保存多轮对话状态。
  • 在工具失败后重试。

如果全部交给一个普通 Agent 循环，问题会变得复杂：

  • 哪些步骤必须执行？
  • 哪些步骤可以跳过？
  • 工具失败后应该重试还是终止？
  • 用户确认前能不能执行写操作？
  • 如何保存当前任务状态？
  • 如何让流程从失败处恢复？
  • 如何观察每一步到底发生了什么？

这类问题，不只是 Prompt 能解决的。

我们需要一种更工程化的方式来组织 Agent 工作流。

LangGraph 的思路是：

把复杂 Agent 流程表示成图。节点负责执行一步，边负责决定下一步，状态贯穿整个流程。

这篇文章会重点讲：

  1. LangGraph 是什么。
  2. 为什么复杂 Agent 需要图结构。
  3. State、Node、Edge 分别是什么。
  4. LangGraph 和普通 Chain、Agent 有什么区别。
  5. 如何实现一个最小 LangGraph 示例。
  6. 如何加入条件分支。
  7. 如何理解 LangGraph 的工程价值。
  8. LangGraph 的常见问题和最佳实践。

二、为什么需要 LangGraph？

前面我们写过普通 Chain：

1

输入 -> Prompt -> Model -> Parser -> 输出

也写过 RAG Chain：

1

问题 -> Retriever -> Context -> Prompt -> Model -> Answer

这些链路适合流程固定的场景。

后来我们写了 Agent：

1

用户目标 -> 模型判断 -> 调用工具 -> 观察结果 -> 继续判断 -> 最终回答

Agent 适合流程不固定的场景。

但真实项目经常处在两者之间：

  • 既需要模型做判断。
  • 又不能让模型完全自由。
  • 有些步骤必须按顺序执行。
  • 有些步骤需要条件分支。
  • 有些节点需要人工确认。
  • 有些状态需要长期保存。

例如一个客服处理流程：

1
2
3
4
5
6
7
8
9

用户问题
  ↓
判断意图
  ↓
订单问题？ -> 查询订单 -> 是否需要查物流 -> 回答
  ↓
制度问题？ -> 检索知识库 -> 回答
  ↓
投诉问题？ -> 收集信息 -> 创建工单 -> 回答

这不是一条简单链。

也不适合完全交给 Agent 自由发挥。

更适合用图结构表达。

三、图结构的直觉

图由两类东西组成：

1
2

节点 Node
边 Edge

节点表示一步操作。

边表示从一个节点走到另一个节点。

例如：

1
2
3
4
5
6

开始
  ↓
识别意图
  ├── 订单问题 -> 查询订单 -> 回答
  ├── 知识库问题 -> 检索知识库 -> 回答
  └── 其他问题 -> 普通回答

这就是一个图。

它比普通 Chain 多了分支。

比纯 Agent 更可控。

因为你可以明确规定：

  • 哪些节点存在。
  • 节点之间如何流转。
  • 哪些条件进入哪个分支。
  • 每个节点读写哪些状态。

四、LangGraph 的三个核心概念

入门 LangGraph，先抓住三个概念：

1
2
3

State
Node
Edge

1. State：状态

State 是整个图运行过程中共享的数据。

可以理解为：

每个节点都可以读取和更新的上下文对象。

例如：

1
2
3
4

class AgentState(TypedDict):
    question: str
    intent: str
    answer: str

状态里可以放：

  • 用户问题。
  • 对话消息。
  • 意图分类结果。
  • 检索结果。
  • 工具结果。
  • 中间判断。
  • 最终回答。

LangGraph 的关键是：

节点不是孤立运行，而是围绕同一个 State 逐步更新。

2. Node：节点

Node 是图中的一个处理步骤。

通常是一个函数。

例如：

1
2
3
4

def classify_intent(state: AgentState):
    question = state["question"]
    ...
    return {"intent": "order"}

节点输入是当前 state。

节点输出是对 state 的更新。

它不一定要返回完整 state，只需要返回要更新的字段。

3. Edge：边

Edge 决定节点之间如何连接。

普通边表示固定流转：

1

A -> B

条件边表示根据状态选择下一步：

1
2

A -> 如果 intent=order，走 order 节点
A -> 如果 intent=kb，走 knowledge 节点

这让 LangGraph 可以表达分支、循环和工作流。

from typing import TypedDict
from langgraph.graph import StateGraph, START, END


class WritingState(TypedDict):
    topic: str
    draft: str
    final: str


def write_draft(state: WritingState):
    topic = state["topic"]
    return {"draft": f"这是一段关于 {topic} 的初稿。"}


def polish_text(state: WritingState):
    draft = state["draft"]
    return {"final": f"润色后：{draft} 内容更清晰，表达更自然。"}


builder = StateGraph(WritingState)

builder.add_node("write_draft", write_draft)
builder.add_node("polish_text", polish_text)

builder.add_edge(START, "write_draft")
builder.add_edge("write_draft", "polish_text")
builder.add_edge("polish_text", END)

graph = builder.compile()

result = graph.invoke({"topic": "LangGraph"})

print(result)

输出类似：

    "final": "润色后：这是一段关于 LangGraph 的初稿。 内容更清晰，表达更自然。"
}

这个例子没有用到模型，但它展示了 LangGraph 的基本形态：

  1. 定义 State。
  2. 定义 Node。
  3. 添加 Node。
  4. 添加 Edge。
  5. 编译 Graph。
  6. 调用 Graph。

七、理解 StateGraph

StateGraph 是 LangGraph 中最常用的入口之一。

1

builder = StateGraph(WritingState)

它表示：这个图会围绕 WritingState 运行。

每个节点接收 state：

1
2

def write_draft(state: WritingState):
    ...

每个节点返回 state 更新：

1

return {"draft": "..."}

LangGraph 会把这些更新合并回整体 state。

所以执行过程可以理解为：

1
2
3
4
5
6
7
8
9

初始 state：{"topic": "LangGraph"}
  ↓
write_draft 返回：{"draft": "..."}
  ↓
state 变成：{"topic": "LangGraph", "draft": "..."}
  ↓
polish_text 返回：{"final": "..."}
  ↓
最终 state：{"topic": "LangGraph", "draft": "...", "final": "..."}

这就是 LangGraph 的状态流转。

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langchain_openai import ChatOpenAI


class QAState(TypedDict):
    question: str
    answer: str


model = ChatOpenAI(model="gpt-4o-mini", temperature=0)


def answer_question(state: QAState):
    question = state["question"]
    response = model.invoke(f"请用简洁中文回答：{question}")
    return {"answer": response.content}


builder = StateGraph(QAState)
builder.add_node("answer_question", answer_question)
builder.add_edge(START, "answer_question")
builder.add_edge("answer_question", END)

graph = builder.compile()

result = graph.invoke({"question": "LangGraph 是什么？"})
print(result["answer"])

这仍然是一个很简单的图。

但你已经可以把任意 LangChain 组件放进节点里。

例如：

  • Prompt。
  • Model。
  • Parser。
  • Retriever。
  • Tool。
  • Agent。
  • 普通 Python 函数。

from langgraph.graph import StateGraph, START, END

builder = StateGraph(AssistantState)

builder.add_node("classify_intent", classify_intent)
builder.add_node("handle_order", handle_order)
builder.add_node("handle_knowledge", handle_knowledge)
builder.add_node("handle_chat", handle_chat)

builder.add_edge(START, "classify_intent")

builder.add_conditional_edges(
    "classify_intent",
    route_by_intent,
    {
        "order": "handle_order",
        "knowledge": "handle_knowledge",
        "chat": "handle_chat",

)

十、LangGraph 和 Agent 的关系

LangGraph 不是 Agent 的替代品。

它更像是 Agent 的工程化编排层。

你可以在图的某个节点里运行 Agent：

1
2
3
4
5

节点 A：识别任务类型
节点 B：运行订单 Agent
节点 C：运行知识库 RAG
节点 D：人工确认
节点 E：生成最终总结

也可以不用 Agent，只用普通函数和 Chain。

LangGraph 的核心价值不是“让模型更聪明”，而是：

让复杂 AI 流程更可控、更可观察、更容易维护。

十一、为什么不用普通 if else？

看到这里，你可能会问：

1

这些分支用 Python if else 也能写，为什么要 LangGraph？

如果流程很简单，确实可以用 if else。

但当流程复杂后，LangGraph 的优势会更明显：

  • 状态统一管理。
  • 节点边界清晰。
  • 条件分支显式。
  • 可以表达循环。
  • 更容易插入人工确认。
  • 更容易做持久化和恢复。
  • 更适合观察和调试。
  • 更容易演进为复杂工作流。

简单脚本用 if else 没问题。

复杂 Agent 系统用图更清晰。

十二、一个更真实的客服工作流

我们可以把前一篇多工具 Agent 改成图：

1
2
3
4
5
6

START
  ↓
classify_intent
  ├── order -> query_order -> need_shipping? -> query_shipping -> final_answer
  ├── knowledge -> retrieve_docs -> final_answer
  └── chat -> direct_answer

这个结构有几个好处：

  1. 订单问题必须先查订单。
  2. 是否查物流由状态决定。
  3. 知识库问题不会误调用订单工具。
  4. 普通聊天不会进入复杂流程。
  5. 每个节点都能单独测试。

这比把所有工具都交给一个 Agent 更可控。

十三、什么时候用 LangGraph？

适合用 LangGraph 的场景：

1. 流程有多个阶段

例如：

1

理解问题 -> 检索资料 -> 调用工具 -> 校验答案 -> 人工确认 -> 输出

2. 有条件分支

例如：

1
2
3

订单已发货 -> 查询物流
订单未发货 -> 查询未发货原因
订单不存在 -> 提醒用户确认订单号

3. 有循环

例如：

1

生成答案 -> 检查是否满足要求 -> 不满足则重写 -> 再检查

4. 需要人工介入

例如：

1

Agent 生成退款方案 -> 用户确认 -> 执行退款

5. 需要状态持久化

例如长任务、多轮任务、可恢复任务。

6. 需要更强观测和调试

复杂流程中，你需要知道每个节点的输入输出。

十四、什么时候不需要 LangGraph？

LangGraph 很强，但不是所有任务都需要它。

不需要的场景包括：

  • 简单 Prompt -> Model -> Parser。
  • 简单 RAG 问答。
  • 一次性工具调用。
  • 几行 if else 就能解决的小流程。
  • 不需要状态恢复和复杂分支的 demo。

不要为了用图而用图。

如果普通 Chain 已经清晰，就先用普通 Chain。

十五、LangGraph 常见问题

1. State 应该放什么？

放流程中需要跨节点传递的信息。

例如：

  • 用户输入。
  • 中间分类结果。
  • 检索结果。
  • 工具结果。
  • 最终答案。

不要把所有临时变量都塞进 State。

State 太大也会难维护。

2. Node 应该多大？

一个节点最好代表一个清晰步骤。

例如：

1
2
3
4

classify_intent
retrieve_docs
generate_answer
check_answer

不要一个节点做完所有事情。

也不要拆得过碎。

3. 条件边应该由模型决定还是规则决定？

都可以。

简单规则用代码更稳定。

复杂语义判断可以让模型分类。

例如：

  • 是否包含订单号：规则。
  • 用户意图分类：模型或规则都可以。
  • 是否需要人工确认：业务规则优先。

4. LangGraph 能不能调用工具？

可以。

工具可以放在节点里调用。

也可以把 Agent 放进节点，让 Agent 自己处理工具调用。

5. LangGraph 是否只能用于 Agent？

不是。

任何复杂 AI 工作流都可以用 LangGraph：

  • RAG 流程。
  • 文档处理。
  • 代码审查。
  • 数据分析。
  • 多轮对话。
  • 人工审核流程。

十六、最佳实践

1. 先画流程图再写代码

如果你说不清节点和边，代码也会混乱。

先画出：

1
2
3
4

有哪些节点？
每个节点做什么？
从哪里到哪里？
哪些地方需要条件分支？

2. State 不要过度膨胀

只放跨节点需要的字段。

局部变量留在节点内部。

3. 节点职责单一

一个节点做一件清楚的事。

这样更容易测试和调试。

4. 条件分支尽量显式

不要把所有路由逻辑藏在 Prompt 里。

能用代码规则表达的，就用代码规则。

5. 高风险动作单独成节点

例如：

1
2

confirm_refund
execute_refund

不要让模型在一个节点里直接完成判断和执行。

6. 从简单图开始

先写：

1

START -> node -> END

再加分支。

再加循环。

最后再加持久化和人工确认。

十七、从 LangChain 到 LangGraph 的思维变化

学习 LangChain 时，我们常常从链路开始思考：

1
2
3
4

十八、总结

本文我们入门了 LangGraph。

核心结论是：

LangGraph 用图结构编排复杂 AI 工作流：State 保存上下文，Node 执行步骤，Edge 决定流转，让 Agent 系统更可控、更可观察、更容易维护。

本文重点包括：

  • 普通 Chain 适合固定流程，Agent 适合动态工具选择，LangGraph 适合复杂可控工作流。
  • LangGraph 的核心概念是 State、Node、Edge。
  • State 贯穿整个流程，节点读取并更新 State。
  • Node 是一个清晰的处理步骤，可以调用模型、工具、Retriever 或普通函数。
  • Edge 定义节点之间的流转，条件边可以根据状态选择下一步。
  • LangGraph 不是 Agent 的替代品，而是复杂 Agent 的工程化编排层。
  • 简单任务不必强行使用 LangGraph，复杂分支、循环、人工确认和状态恢复才是它的价值所在。

到这里，我们已经从 Agent 的自由循环，进入了图结构工作流。
