【Docker 系列 02】不再害怕命令行：20个必备的容器生命周期管理指令

2025-06-12 09:15
阅读时长: 6 分钟

“我的容器去哪了？为什么我一关终端服务就挂了？怎么看报错日志？”

在上一篇文章中，我们成功运行了 hello-world，初步领略了 Docker 的魅力。但回到现实工作，真正的服务器是没有图形界面的（哪怕你本地用着漂亮的 Docker Desktop）。

在真实的开发和运维场景中，命令行（CLI）才是你唯一的武器。

很多新手看到 Docker 那几十个命令和成百上千的参数会感到恐惧。别怕！今天这篇文章，我会按照“找镜像 -> 创建容器 -> 查看状态 -> 进入内部 -> 销毁清理”的生命周期逻辑，带你彻底吃透日常开发中最常用的 20 个高频指令。

只要掌握了它们，你在公司里处理 Docker 故障就能横着走。

一、镜像（Image）操作：获取你的“系统安装盘”

容器是从镜像启动的，所以我们得先有镜像。

1. docker search：在镜像市场“淘宝”

如果你想跑一个 Nginx 服务器，但不确定官方镜像叫什么，可以搜一下：

1

docker search nginx

你会看到一个列表，优先选择带有 [OK] 官方认证（OFFICIAL）的镜像。

2. docker pull：把镜像拉取到本地

确定了名字，我们把它下载下来。

1

docker pull nginx:latest

💡 阿彪避坑指南： 冒号后面的叫 标签（Tag），通常用来标识版本。如果不加标签（直接 docker pull nginx），Docker 会默认拉取 :latest（最新版）。在生产环境中，强烈建议写死版本号（如 nginx:1.24.0），避免哪天 latest 偷偷更新导致你的代码不兼容。

3. docker images：查看本地有哪些镜像

下载完后，看看你的“仓库”里有什么存货：

1
2

docker images
# 或者使用新版命令：docker image ls

输出会显示镜像名、标签、Image ID（镜像身份证号）以及占用的磁盘大小。

4. docker rmi：删除不需要的镜像

硬盘空间不够了？把不用的镜像删掉（注意是 rmi，rm 代表 remove，i 代表 image）：

1
2

docker rmi nginx:latest
# 也可以用 Image ID 来删除：docker rmi a1b2c3d4e5f6

二、容器（Container）生命周期：生与死

有了镜像，重头戏来了：让它跑起来！

5. docker run：万物起源（最重要、参数最多的命令）

这不仅是启动容器，这是创建并运行一个全新的容器。

我们来运行刚才下载的 Nginx：

1

docker run -d --name my-web-server -p 8080:80 nginx:latest

看不懂参数？别慌，我们逐一拆解：

  • -d (detach)：后台运行。如果不加它，容器的日志会一直霸占你的终端，你一按 Ctrl+C 或者关掉窗口，容器就当场暴毙。加了 -d，它就会在后台乖乖运行。
  • --name：给容器起个好记的名字（这里叫 my-web-server）。如果不加，Docker 会随机给你起个奇葩名字（比如 crazy_einstein），以后排错时你会找得痛不欲生。
  • -p (port)：端口映射。格式是 宿主机端口:容器内部端口。Nginx 内部默认跑在 80 端口，这里把它映射到你电脑的 8080 端口。

现在，打开浏览器访问 http://localhost:8080，你就能看到 Nginx 的欢迎页面了！

6. docker ps：查看活着的容器

想知道当前有哪些容器在运行？

1

docker ps

7. docker ps -a：查看“停尸房”（所有容器）

有时候你跑了一个容器，但 docker ps 里却没有。它可能是报错秒退了！ 加个 -a (all)，能看到所有活着的和已经停止（Exited）的容器：

1

docker ps -a

8. docker stop / docker start / docker restart

这三个很好理解：停止、启动、重启容器。你可以用容器名字，也可以用 Container ID 的前几位。

1
2
3

docker stop my-web-server
docker start my-web-server
docker restart my-web-server

9. docker kill：拔电源

docker stop 是温柔地发送终止信号，给程序时间保存数据；如果程序卡死了，不听指挥，直接用 kill 拔电源：

1

docker kill my-web-server

10. docker rm：火化（删除容器）

一个停止的容器依然会占用少量磁盘空间，并且它的名字还被占用着。不需要了就删掉它：

1

docker rm my-web-server

💡 进阶技巧： 正在运行的容器是删不掉的，必须先 stop。如果你嫌麻烦，可以加 -f (force) 强制删除运行中的容器：docker rm -f my-web-server。

三、进阶探查：黑盒排错，里面到底发生了什么？

部署只是第一步，真正的挑战在于排错 (Debug)。当你把代码跑在 Docker 里却报错时，下面这几个命令是你的救命稻草。

11. docker logs：看日志（排错第一神技）

项目起不来？看日志！

1

docker logs my-web-server

高频参数组合：

  • docker logs -f my-web-server：-f (follow) 会实时滚动显示最新日志，就像 Linux 的 tail -f 一样。
  • docker logs --tail 100 my-web-server：只看最后 100 行，避免日志太长刷屏。

12. docker exec：进入容器内部（深入敌后）

虽然容器是隔离的，但我们有时需要进去敲几个命令，比如看看里面的配置文件对不对。

1

docker exec -it my-web-server /bin/bash

（注意：如果是 Alpine 等精简版镜像，可能没有 bash，需要把 /bin/bash 换成 sh）

硬核知识点：-it 到底是什么意思？ 绝大多数教程只告诉你加 -it，但不说为什么。

  • -i (interactive)：保持标准输入打开，让你可以持续输入命令。
  • -t (tty)：分配一个伪终端，让终端显示颜色、提示符，看起来像个正常的 Linux 命令行。 结合起来，你就能像 SSH 登录服务器一样，在容器里面自由探索了。输入 exit 可以退出容器。

13. docker inspect：核磁共振（查看详细元数据）

如果你想知道容器内部的 IP 地址、环境变量、挂载的目录路径，用它：

1

docker inspect my-web-server

它会输出一坨巨大的 JSON 数据，包含了这个容器的所有身世秘密。配合 grep 食用更佳。

14. docker stats：实时资源监控（容器版的 top）

服务器变卡了？想知道哪个容器在狂吃 CPU 和内存？

1

docker stats

它会实时显示每个容器的 CPU、内存占用率、网络 IO 和磁盘 IO。

15. docker top：查看容器内的进程

看看容器内部到底有哪些进程在跑：

1

docker top my-web-server

四、系统清理与维护：拯救你的磁盘焦虑

用了一段时间 Docker 后，你会发现 C 盘（或服务器磁盘）被塞满了各种废弃的镜像、停止的容器和悬空（dangling）的数据。

16. docker system df：查看磁盘使用情况

先查查 Docker 到底占了多少空间：

1

docker system df

17. docker system prune：一键瘦身（危险但爽快）

这是一个非常解压的命令，它会自动清理所有停止的容器、没有任何容器使用的网络、以及悬空镜像。

1

docker system prune

如果想更狠一点，连没有被使用的正常镜像也一起干掉，可以加 -a 参数：

1

docker system prune -a

⚠️ 警告： 在生产服务器上千万慎用 -a！万一你只是把服务停下来维护一会，结果敲了这个命令，镜像被删了，等会启动又得重新下载半天。

18. 镜像/容器重命名与导出（扩展补充）

  • 改名 (tag)：docker tag nginx:latest my-repo/nginx:v1
  • 打包容器为镜像 (commit)：如果你在进入容器后修改了配置，想把它保存成一个新的镜像：docker commit my-web-server my-custom-nginx:v1 (注：虽然能用，但极度不推荐这种方式，正确的做法是写 Dockerfile，这将在下一篇讲解)。
  • 导出镜像 (save)：如果在内网环境无法上网，可以把镜像打包成压缩包拷贝过去：docker save -o nginx.tar nginx:latest。

总结：你的 Docker 武器库

恭喜你，至此你已经掌握了 95% 甚至更多的 Docker 日常使用命令！

让我们复习一下典型的排错流程：

  1. 发现服务不通。
  2. 敲 docker ps -a 发现容器挂了 (Exited)。
  3. 敲 docker logs 容器名 看报错原因。
  4. 发现是配置文件写错了。
  5. 敲 docker start 容器名 强行启动，然后马上 docker exec -it 容器名 sh 进去改配置。
  6. docker restart 容器名，服务恢复正常！

但是，刚才我们提到 docker commit 不是一种好习惯。如果我们需要部署一个自己写的包含 Python 代码的复杂项目，难道要拉一个基础镜像，手动进去 pip install，然后再 commit 吗？

这太 low 了，而且完全不可复现。

在真正的工程实践中，我们希望代码就是基石，通过一份代码清单，让 Docker 自动帮我们“构建”出想要的镜像。
