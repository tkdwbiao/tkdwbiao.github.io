LangChain 入门：为什么我们需要一个大模型应用开发框架？

2025-09-01 10:00
阅读时长: 16 分钟

如果你已经写过大模型 API 调用代码，大概率会有一种感觉：

调一次模型很简单，但要把它做成一个稳定、可维护、可扩展的应用，事情马上就复杂起来了。

最开始，我们可能只是写几行代码，把用户输入发给模型，然后拿到回答。这个阶段看起来很轻松：一个 HTTP 请求、一个 API Key、一个 prompt，就能让模型帮我们写总结、改文案、回答问题。

但一旦你想继续往前走，比如让模型记住上下文、读取私有文档、调用外部工具、根据任务自动决策、把执行过程记录下来、上线后还能调试和优化，你就会发现：大模型应用开发并不只是“调用一次模型”这么简单。

这正是 LangChain 出现的原因。

一、前言

LangChain 是一个面向大模型应用开发的开源框架。它的核心价值不是“替你调用模型”，而是帮助你把模型、提示词、工具、知识库、检索、记忆、Agent 和工程化能力组织成一个完整应用。

用一句话概括：

LangChain 让大模型不再只是一个聊天接口，而是可以被编排、被扩展、能连接外部世界的应用核心。

在这个系列中，我们会从最基础的模型调用开始，逐步讲到 Prompt、LCEL、Runnable、Memory、RAG、Tool Calling、Agent、LangGraph 和工程化实践。本文是第一篇，重点解决一个问题：

为什么我们需要 LangChain？它到底解决了哪些大模型应用开发中的问题？

读完本文，你应该能够建立这样几个认知：

  1. 直接调用 LLM API 为什么不够用。
  2. LangChain 在大模型应用中扮演什么角色。
  3. LangChain 的核心模块分别解决什么问题。
  4. 哪些场景适合使用 LangChain，哪些场景不一定需要。
  5. 如何用一个最小示例感受 LangChain 的基本编排方式。

二、为什么直接调用大模型 API 还不够？

我们先从最简单的大模型调用说起。

假设你想做一个“文章标题生成器”，直接调用模型 API 的思路通常是：

  1. 准备一段 prompt。
  2. 把 prompt 和用户输入拼在一起。
  3. 调用模型接口。
  4. 读取模型返回结果。
  5. 展示给用户。

这个流程对于 demo 来说完全够用。问题是，一旦需求稍微复杂一点，代码就会迅速膨胀。

1. Prompt 很快会变得难以维护

一开始的 prompt 可能只有一句：

1

请帮我给下面这篇文章生成 5 个标题。

后来你可能会不断加要求：

1
2
3
4
5
6
7
8

请帮我给下面这篇文章生成 5 个标题。
要求：
1. 标题要适合技术博客。
2. 不要标题党。
3. 每个标题不超过 25 个字。
4. 输出 JSON 格式。
5. 每个标题附带一句推荐理由。
文章内容：{article}

再后来，你需要区分系统提示、用户输入、历史对话、变量模板、输出格式约束。此时如果继续用字符串拼接，代码会越来越难维护。

你会遇到这些问题：

  • prompt 分散在多个函数里，不知道哪个版本是最新的。
  • 变量靠手动拼接，容易漏字段或拼错格式。
  • 不同场景的 prompt 很难复用。
  • 输出格式依赖模型“自觉”，不稳定。

LangChain 的 PromptTemplate 和 ChatPromptTemplate 就是为了解决这类问题：它们把 prompt 从“随手写的字符串”变成“可复用、可组合、可检查的模板”。

2. 模型调用只是应用链路中的一环

真正的大模型应用通常不是一次调用模型就结束。

以一个知识库问答系统为例，用户问：

1

我们公司报销制度里，差旅住宿标准是多少？

如果直接把问题丢给模型，模型可能会一本正经地编一个答案。因为它并不知道你公司的内部制度。

一个更可靠的流程应该是：

  1. 接收用户问题。
  2. 从公司文档中检索相关制度片段。
  3. 把检索结果和用户问题一起交给模型。
  4. 要求模型只能基于资料回答。
  5. 返回答案，并附上引用来源。

这就是典型的 RAG（Retrieval-Augmented Generation，检索增强生成）流程。

在这个流程里，模型只是其中一个环节。你还需要：

  • Document Loader：加载 PDF、Markdown、网页、CSV 等文档。
  • Text Splitter：把长文档切分成适合检索的小块。
  • Embedding：把文本转换成向量。
  • Vector Store：存储和检索向量。
  • Retriever：根据问题找出相关文档片段。
  • Prompt：把检索结果组织成模型能理解的上下文。
  • Output Parser：把模型输出解析成稳定格式。

如果全部自己写，当然也可以，但会重复造很多轮子。LangChain 的价值就在于，它把这些常见组件抽象出来，让我们可以用统一的方式组合它们。

3. 多轮对话需要上下文管理

再看聊天机器人。

用户第一轮说：

1

我想学习 LangChain。

模型回答之后，用户第二轮继续问：

1

那我应该先学哪一部分？

人类知道“哪一部分”指的是 LangChain，但模型本身并没有真正的长期记忆。每一次调用模型，本质上都是一次新的请求。它能理解上下文，是因为我们把历史消息一起传给了它。

所以多轮对话系统必须处理：

  • 历史消息如何保存。
  • 哪些历史消息需要传给模型。
  • 上下文太长超过 token 限制怎么办。
  • 是否需要把历史对话总结成摘要。
  • 不同用户的会话如何隔离。

这就是 Memory 和消息历史管理要解决的问题。

4. Agent 需要模型自己决定下一步做什么

普通 Chain 更像固定流水线：

1

输入 → Prompt → 模型 → 解析输出

但有些任务不是固定流程。

比如你想做一个研究助手，让它回答：

1

帮我查一下 LangChain 和 LangGraph 的关系，并总结适合初学者的学习路径。

它可能需要：

  1. 判断是否需要搜索资料。
  2. 调用搜索工具。
  3. 阅读搜索结果。
  4. 再决定是否需要继续搜索。
  5. 汇总信息。
  6. 给出最终答案。

这类任务的关键不只是“生成文本”，而是“根据当前情况决定下一步行动”。这就是 Agent 的典型场景。

LangChain 提供了 Agent 和 Tool Calling 相关能力，让模型可以在一定约束下调用外部工具，例如搜索、计算、数据库查询、文件读取、API 请求等。

5. 上线后还需要调试、观测和优化

Demo 跑通之后，真正麻烦的事情才开始：

  • 为什么这次回答质量突然下降？
  • 模型到底收到了什么 prompt？
  • RAG 检索到了哪些文档？
  • Agent 为什么调用了错误工具？
  • 哪一步耗时最长？
  • 每次调用消耗了多少 token？
  • 用户反馈差的样本如何复盘？

这些问题都属于工程化和可观测性范畴。LangChain 生态中的 LangSmith 就是用来追踪、调试和评估大模型应用链路的工具。

三、LangChain 到底是什么？

根据官方文档的定位，LangChain 是一个用于构建 LLM 应用和 Agent 的开源框架。它提供了模型集成、Agent 架构、工具调用、检索增强生成、与 LangGraph 的结合，以及通过 LangSmith 进行调试和观测的能力。

但如果只看这句话，还是有点抽象。

我们可以把 LangChain 理解成三层能力。

1. 第一层：统一模型调用

不同模型厂商的 API 形式并不完全一样。

你可能今天用 OpenAI，明天想换成 Anthropic、DeepSeek、通义千问，后天又想接入本地模型。每个模型都有自己的 SDK、参数命名、消息格式和返回结构。

LangChain 提供了统一的模型抽象，比如 Chat Model。这样你的上层业务代码可以尽量少关心底层模型来自哪里。

当然，这并不意味着换模型永远零成本。不同模型的能力、上下文长度、工具调用格式、结构化输出稳定性都可能不同。但统一抽象至少能让代码结构更清晰，迁移成本更低。

2. 第二层：标准化应用组件

LangChain 把大模型应用中常见的能力拆成了一组组件：

组件解决的问题
Chat Model / LLM如何调用大模型
PromptTemplate如何管理和复用提示词
Output Parser如何解析模型输出
Runnable / LCEL如何把多个步骤组合成链
Document Loader如何加载外部文档
Text Splitter如何切分长文本
Embedding如何把文本向量化
Vector Store如何存储和检索向量
Retriever如何根据问题找资料
Tool如何让模型调用外部能力
Agent如何让模型动态决策下一步
Memory / Chat History如何管理多轮上下文

这些组件的意义在于：你不用每次从零开始设计应用骨架，而是可以像搭积木一样组合能力。

3. 第三层：面向复杂 Agent 的生态

随着 Agent 应用变复杂，单纯的链式调用就不够了。

复杂 Agent 往往需要：

  • 状态管理
  • 条件分支
  • 循环执行
  • 人工介入
  • 多 Agent 协作
  • 失败重试
  • 长时间运行
  • 可恢复执行

LangChain 生态中，LangGraph 更偏向底层编排，用图结构管理复杂、持久、有状态的 Agent 工作流。LangChain 则更常用于模型、工具、消息、检索等上层组件。

可以简单理解为：

1
2
3

LangChain：提供 LLM 应用常用组件
LangGraph：编排复杂、有状态、可循环的 Agent 工作流
LangSmith：观测、调试和评估 LLM 应用执行过程

这三者经常一起出现在实际项目中。

四、LangChain 解决了哪些核心问题？

1. Prompt 管理问题

没有框架时，prompt 经常散落在代码中：

1

prompt = "请根据" + context + "回答" + question

这种写法在 demo 阶段没问题，但在项目里会很痛苦。

LangChain 的 prompt 模板可以把变量、角色消息和模板结构明确分开。

例如：

1
2
3
4
5
6
7
8
9

from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一名专业的技术博客写作助手。"),
    ("human", "请用通俗语言解释：{topic}"),
])

messages = prompt.invoke({"topic": "LangChain 为什么有用"})
print(messages)

这里的 {topic} 是模板变量。你可以把 prompt 当成一个独立组件，而不是散落在业务代码里的字符串。

2. 链式编排问题

很多大模型任务不是一步完成，而是多个组件串起来。

例如：

1

Prompt → Model → Output Parser

LangChain 的 LCEL（LangChain Expression Language）提供了一种非常直观的管道式写法：

1

chain = prompt | model | parser

这行代码表达的意思是：

  1. 先用 prompt 把输入变量转换成模型消息。
  2. 再把消息交给 model。
  3. 最后用 parser 解析模型输出。

这种写法的好处是结构清晰，而且天然支持 invoke、stream、batch 等调用方式。

3. 结构化输出问题

模型默认输出的是自然语言，但应用通常需要结构化数据。

比如你让模型生成文章标题，业务系统可能希望得到 JSON：

1
2
3
4
5
6

{
  "titles": [
    "LangChain 入门：为什么我们需要它？",
    "从 API 调用到 Agent：LangChain 的真正价值"
  ]
}

如果只靠 prompt 说“请输出 JSON”，模型不一定每次都稳定。LangChain 提供了 Output Parser，可以帮助我们约束和解析输出。后续第 6 篇会专门讲这个主题。

4. RAG 组件复用问题

RAG 是 LangChain 最常见的应用场景之一。

一个标准 RAG 系统通常包括：

1

文档加载 → 文本切分 → 向量化 → 向量存储 → 检索 → 生成回答

这些步骤涉及不同技术栈，如果完全自己集成，会有很多重复工作。LangChain 提供了大量文档加载器、文本切分器、向量数据库集成和 Retriever 抽象，可以让我们更快搭出知识库问答系统。

5. Tool Calling 和 Agent 问题

当模型需要访问外部世界时，就需要工具。

例如：

  • 查询数据库
  • 调用天气 API
  • 执行计算
  • 搜索网页
  • 读取文件
  • 调用公司内部系统

LangChain 可以把普通 Python 函数包装成 Tool，让模型在需要时调用它。更进一步，Agent 可以根据当前任务动态决定调用哪个工具、调用几次、什么时候停止。

这也是大模型应用从“聊天机器人”走向“智能助手”的关键一步。

五、代码实践：用 LangChain 构建一个最小应用

下面我们用一个非常小的例子，感受一下 LangChain 的基本使用方式。

这个例子要实现的功能是：

输入一个技术主题，让模型用适合初学者的方式解释它，并给出一个学习建议。

1. 安装依赖

1

1

export OPENAI_API_KEY="你的 API Key"

1

$env:OPENAI_API_KEY="你的 API Key"

如果你使用兼容 OpenAI API 格式的模型服务，也可以通过 base_url 配置对应地址。

from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

model = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0.7,
)

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一名擅长讲解复杂技术概念的 AI 工程师。"),
    ("human", "请用适合初学者的方式解释 {topic}，并给出一个学习建议。"),
])

parser = StrOutputParser()

chain = prompt | model | parser

result = chain.invoke({"topic": "LangChain"})

print(result)

这段代码虽然很短，但已经体现了 LangChain 的基本思想。

它不是把所有逻辑混在一起，而是拆成三个组件：

1

PromptTemplate → ChatModel → OutputParser

对应到代码就是：

1

chain = prompt | model | parser

这就是 LangChain 里非常重要的 LCEL 风格。

3. 这段代码背后发生了什么？

当你执行：

1

result = chain.invoke({"topic": "LangChain"})

LangChain 会按顺序执行：

  1. prompt 接收 {"topic": "LangChain"}。
  2. prompt 把变量填入模板，生成聊天消息。
  3. model 接收聊天消息，调用底层大模型。
  4. parser 把模型返回结果解析成字符串。
  5. 最终返回给 result。

从应用开发视角看，这比手写字符串拼接和接口调用更清晰。

4. 使用兼容 OpenAI API 的模型

很多模型服务都提供兼容 OpenAI 的接口。如果你的服务支持这种格式，可以这样写：

1
2
3
4
5
6
7

from langchain_openai import ChatOpenAI

model = ChatOpenAI(
    model="deepseek-chat",
    api_key="你的 API Key",
    base_url="https://api.deepseek.com",
)

实际项目中，不建议把 API Key 写死在代码里，更推荐通过环境变量或配置文件管理。

5. 流式输出示例

对于聊天应用来说，流式输出很重要。用户不希望等模型全部生成完才看到结果。

LangChain 的模型和链通常支持 stream：

1
2

for chunk in chain.stream({"topic": "RAG"}):
    print(chunk, end="", flush=True)

这类能力对于构建真实聊天界面非常有用。

    print("---")
    print(result)

相比自己写循环，batch 的优势在于它是 LangChain Runnable 体系的一部分，后续可以和并发、重试、配置等能力结合。

六、LangChain 适合哪些场景？

LangChain 不是所有大模型项目的必选项。它适合的是那些需要“应用编排”的场景。

1. 适合：知识库问答和 RAG 系统

如果你要构建：

  • 企业内部文档问答
  • 个人知识库助手
  • PDF 问答系统
  • 产品手册问答
  • 法规、合同、论文检索问答

LangChain 非常适合。因为 RAG 涉及文档加载、切分、向量化、检索、Prompt 组装、答案生成等多个步骤，正好对应 LangChain 的组件体系。

2. 适合：多轮对话应用

如果你的应用需要保存上下文，例如：

  • AI 客服
  • 学习助手
  • 编程助手
  • 写作助手
  • 面试陪练机器人

你就需要处理历史消息、上下文窗口和会话隔离。LangChain 的消息抽象、Memory 和 RunnableWithMessageHistory 等能力可以提供帮助。

3. 适合：需要工具调用的智能助手

如果你希望模型不只是回答问题，还能调用工具完成任务，比如：

  • 查询数据库
  • 调用业务 API
  • 执行计算
  • 搜索资料
  • 读取文件
  • 生成报告

那么 LangChain 的 Tool 和 Agent 能力会很有价值。

4. 适合：需要快速验证 LLM 应用原型

LangChain 的一个优势是生态丰富。它集成了很多模型、向量数据库、文档加载器和工具。做原型时，你可以更快把想法跑通。

比如你想验证一个 RAG demo，用 LangChain 通常可以更快搭起完整链路。

5. 不一定适合：非常简单的单次模型调用

如果你的需求只是：

1

输入一句话 → 调用模型 → 返回结果

而且没有复杂 prompt、没有工具调用、没有 RAG、没有多轮上下文，那么直接使用模型厂商 SDK 可能更简单。

框架不是越多越好。简单任务用简单方案，复杂任务再引入框架，这才是更健康的工程判断。

6. 不一定适合：高度定制的底层推理服务

如果你在做的是：

  • 模型推理引擎
  • 高性能 serving
  • CUDA 优化
  • 分布式推理调度
  • 极致低延迟模型网关

这些更偏底层系统工程，LangChain 不是主要工具。它更适合应用层编排，而不是替代 vLLM、TensorRT-LLM、SGLang 这类推理系统。

七、LangChain 和传统后端框架有什么区别？

很多人第一次接触 LangChain，会把它和 Django、FastAPI、Spring Boot 这类框架类比。

这个类比有一定帮助，但并不完全准确。

传统后端框架主要解决：

  • 路由
  • 请求响应
  • 数据库访问
  • 认证鉴权
  • 中间件
  • 服务组织

LangChain 主要解决：

  • Prompt 编排
  • 模型调用
  • 输出解析
  • RAG 检索链路
  • 工具调用
  • Agent 决策
  • 多轮消息上下文
  • LLM 应用观测和评估

所以在真实项目中，它们经常是配合关系，而不是替代关系。

例如一个 AI 知识库应用可能是这样：

1
2
3
4
5
6
7

前端页面
  ↓
FastAPI / Django 后端
  ↓
LangChain RAG Chain / Agent
  ↓
LLM + 向量数据库 + 业务 API

FastAPI 负责 Web 服务，LangChain 负责编排大模型应用链路。

九、常见问题

1. LangChain 会不会过度封装？

会有这种可能。

任何框架都有抽象成本。如果你只是做一个非常简单的 API 调用，引入 LangChain 可能显得重。但当你的应用开始涉及 RAG、Agent、工具调用、多轮上下文和可观测性时，LangChain 的抽象会明显减少重复代码。

关键不是“要不要用 LangChain”，而是判断你的问题是否已经复杂到需要应用编排框架。

2. 学 LangChain 之前要先学大模型原理吗？

不需要先成为算法专家，但需要理解一些基本概念：

  • 什么是 token
  • 什么是 prompt
  • 什么是上下文窗口
  • 什么是 embedding
  • 什么是向量检索
  • 什么是 tool calling
  • 什么是 RAG

这些概念会在本系列中逐步展开。

3. LangChain 和 LangGraph 是什么关系？

简单说：

  • LangChain 更关注 LLM 应用组件和常见链路。
  • LangGraph 更关注复杂 Agent 的状态图编排。

如果你的流程是固定的，LangChain 的 LCEL 通常就够了。如果你的流程需要循环、条件分支、状态持久化、多 Agent 协作，LangGraph 会更合适。

4. LangChain 是否只能用 OpenAI？

不是。

LangChain 支持很多模型提供商和集成方式。OpenAI 只是常见选择之一。你也可以接入 Anthropic、Google、Azure OpenAI、DeepSeek、通义千问，或者兼容 OpenAI API 的本地/云端模型服务。

5. LangChain 是否适合生产环境？

可以用于生产环境，但要注意工程化。

生产环境不能只关注“能不能跑”，还要关注：

  • 超时控制
  • 错误重试
  • 日志追踪
  • 成本统计
  • Prompt 版本管理
  • RAG 评估
  • 数据安全
  • 工具调用权限边界
  • 模型输出稳定性

后续工程化篇会专门展开这些问题。

十、最佳实践

1. 先用最小链路跑通，再逐步增加组件

不要一开始就把 Memory、Retriever、Agent、LangGraph 全部加上。

更推荐：

1
2
3
4
5

先完成 prompt | model | parser
再加入结构化输出
再加入检索
再加入工具
最后考虑 Agent 和 LangGraph

这样每一步的问题都更容易定位。

2. 不要把 Prompt 当成临时字符串

Prompt 是大模型应用的核心资产。应该像代码一样管理它：

  • 明确变量
  • 明确角色消息
  • 明确输出格式
  • 明确适用场景
  • 保留可测试样例

LangChain 的 PromptTemplate 可以帮助你把 prompt 管理得更清楚。

3. 对 RAG 系统保持敬畏

RAG 不是“把文档塞进向量库”就结束了。

真正影响效果的因素包括：

  • 文档清洗质量
  • chunk size
  • chunk overlap
  • embedding 模型选择
  • top-k 设置
  • rerank 策略
  • prompt 设计
  • 是否要求引用来源
  • 是否评估召回质量

LangChain 能帮你搭链路，但不能自动保证答案质量。RAG 的效果仍然需要不断评估和调优。

4. Agent 要控制边界

Agent 很强，但也更不稳定。

它可能：

  • 调错工具
  • 循环调用
  • 过度推理
  • 产生幻觉
  • 对工具返回结果理解错误

所以真实项目中，要给 Agent 设置清晰边界：

  • 工具描述要准确
  • 工具权限要最小化
  • 参数要校验
  • 最大调用次数要限制
  • 关键操作要有人确认
  • 执行过程要可追踪

5. 从第一天开始关注可观测性

大模型应用很难只靠最终结果排查问题。

你需要知道：

  • 输入是什么
  • prompt 是什么
  • 检索到了什么
  • 模型输出了什么
  • 工具调用了什么
  • 哪一步失败了
  • token 消耗是多少

这也是 LangSmith 这类工具存在的原因。

十一、总结

本文是 LangChain 系列的第一篇，我们重点回答了一个问题：

为什么我们需要一个大模型应用开发框架？

直接调用大模型 API 可以完成 demo，但当应用逐渐复杂时，我们会遇到 Prompt 管理、链式编排、结构化输出、多轮上下文、RAG、工具调用、Agent 决策和工程化观测等一系列问题。

LangChain 的价值就在于，它把这些常见能力抽象成可组合的组件，让我们可以更系统地构建 LLM 应用。

你可以把 LangChain 理解为：

1
2

模型不是终点，应用才是目标；
调用不是难点，编排才是核心。

下一篇文章，我们会进入 LangChain 的整体知识地图，系统梳理它的核心模块：Model、Prompt、Output Parser、Chain、Retriever、Tool、Agent、Memory 和 LangGraph，看看它们之间到底是什么关系。
