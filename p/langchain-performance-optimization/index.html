LangChain 性能优化：如何让大模型应用更快、更稳、更省钱？

2025-10-19 10:00
阅读时长: 12 分钟

前面几篇文章里，我们已经把 LangChain 应用从 demo 推到了工程化阶段。

我们讲了：

  • 如何组织项目结构。
  • 如何管理配置、Prompt、Chain、Tool 和 Agent。
  • 如何用 LangSmith 观察和调试完整链路。

当应用真正开始被使用后，另一个问题很快就会出现：

它能不能更快？更稳定？更省钱？

这就是性能优化要解决的问题。

一、前言

大模型应用的性能问题，和传统 Web 应用不太一样。

传统应用慢，通常会看：

  • 数据库查询。
  • 缓存命中率。
  • 网络请求。
  • CPU 和内存。
  • 并发和锁。

大模型应用还要额外关注：

  • 模型响应时间。
  • Prompt token 数。
  • 输出 token 数。
  • Retriever 延迟。
  • Embedding 成本。
  • Agent 工具调用次数。
  • RAG 上下文长度。
  • 是否重复调用模型。
  • 是否每次都重新构建向量库。

很多 LangChain 应用在 demo 阶段看起来很好。

但一旦进入真实使用，就会遇到：

  • 回答慢。
  • token 成本高。
  • 高峰期不稳定。
  • Agent 一直调用工具。
  • RAG 上下文太长。
  • 每次请求都重复做 embedding。
  • 模型输出格式不稳定导致重试变多。

性能优化不是最后才做的装饰。

它应该从设计阶段就进入你的思考。

本文会重点讲：

  1. LangChain 应用的性能瓶颈在哪里。
  2. 如何用观测数据定位问题。
  3. 如何优化模型选择和参数。
  4. 如何减少 Prompt 和上下文 token。
  5. 如何优化 RAG 检索链路。
  6. 如何使用 streaming、batch、并发和缓存。
  7. 如何控制 Agent 工具调用成本。
  8. 如何让应用更稳定。
  9. 性能优化的常见误区和最佳实践。

二、先定义什么是“性能好”

性能优化不是只追求快。

一个大模型应用通常要平衡三件事：

1
2
3

速度
稳定性
成本

1. 速度

用户最直接感受到的是响应时间。

常见指标：

  • 首 token 时间。
  • 完整回答时间。
  • Retriever 耗时。
  • 工具调用耗时。
  • 端到端耗时。

对于聊天应用，首 token 时间尤其重要。

如果用户能快速看到模型开始输出，体感会好很多。

2. 稳定性

稳定性包括：

  • 模型调用失败率。
  • 超时率。
  • Parser 解析失败率。
  • Agent 循环次数是否可控。
  • 工具调用是否可靠。
  • RAG 是否稳定召回正确资料。

一个应用如果偶尔快，但经常失败，不算性能好。

3. 成本

成本包括：

  • 输入 token。
  • 输出 token。
  • Embedding 调用。
  • 向量库服务。
  • Rerank 服务。
  • 工具 API 调用。
  • 重试带来的额外调用。

大模型应用的成本经常不是单次很贵，而是随着请求量增长迅速放大。

所以性能优化的目标是：

在满足质量要求的前提下，用更少的时间、更少的调用和更少的 token 完成任务。

三、先观测，再优化

不要凭感觉优化。

优化前先回答几个问题：

1
2
3

到底慢在哪里？
到底贵在哪里？
到底不稳定在哪里？

可以从 LangSmith 或日志中看：

  • 每个 Chain 的耗时。
  • 每次模型调用的输入输出 token。
  • Retriever 耗时。
  • Agent 调用了多少次工具。
  • Parser 失败后重试了几次。
  • 哪些问题最容易失败。

例如一次 RAG 请求耗时 8 秒。

不要直接说“模型太慢”。

可能真实情况是：

1
2
3
4

Retriever：300ms
Prompt 构造：20ms
Model：7.5s
Parser：10ms

也可能是：

1
2
3

Retriever：5s
Model：2s
其他：很少

优化方向完全不同。

所以第一条原则是：

没有观测数据，不要盲目优化。

四、模型选择：不是越强越好

模型选择对速度和成本影响最大。

很多人一开始会直接选最强模型。

这在复杂任务上合理，但不一定适合所有步骤。

LangChain 应用里经常有多种任务：

任务是否需要最强模型
意图分类通常不需要
简单改写通常不需要
JSON 抽取视复杂度而定
最终高质量回答可能需要
多步 Agent 推理可能需要
简单格式化不需要

一个常见优化思路是：

不同步骤使用不同模型。

例如：

1
2
3
4

from langchain_openai import ChatOpenAI

fast_model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
strong_model = ChatOpenAI(model="gpt-4o", temperature=0.2)

可以这样分工：

1
2

fast_model：意图分类、问题改写、简单结构化输出
strong_model：复杂回答、复杂推理、最终总结

不要让所有任务都走最贵最慢的模型。

五、控制 temperature

性能优化不只是速度。

稳定性也很重要。

对于工具调用、结构化输出、分类任务，建议：

1

temperature=0

原因是这些任务更需要稳定，而不是创造性。

例如：

1
2
3
4

model = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0,
)

适合：

  • 意图分类。
  • JSON 输出。
  • Tool Calling。
  • 路由判断。
  • 评价器。

对于写作、总结、润色，可以适当提高：

1

temperature=0.2

不要为了“有创造力”给所有链路都设置高 temperature。

这可能导致：

  • 输出不稳定。
  • Parser 更容易失败。
  • 工具调用参数变化更大。
  • 评估结果波动。

六、减少输入 token

大模型调用的成本和延迟通常和 token 数相关。

输入越长，越贵，也可能越慢。

常见 token 浪费来自：

  • Prompt 太啰嗦。
  • 系统提示重复。
  • RAG 上下文太多。
  • 历史消息无限增长。
  • 工具描述过长。
  • metadata 全量塞进 Prompt。
  • 多轮 Agent 中间消息不压缩。

1. 精简 Prompt

不好：

1

你是一个非常非常专业、严谨、友好、耐心、细致、善良、热情的助手……

更好：

1

你是严谨的知识库问答助手。只根据上下文回答；资料不足时说明无法确定。

Prompt 要清楚，不是越长越好。

2. 不要塞无用 metadata

RAG 中常见做法：

1
2
3
4
5

def format_docs(docs):
    return "\n\n".join(
        f"来源：{doc.metadata}\n{doc.page_content}"
        for doc in docs
    )

这可能把一堆无用 metadata 都塞进去。

更好：

1
2
3
4
5

def format_docs(docs):
    return "\n\n".join(
        f"来源：{doc.metadata.get('source', 'unknown')}\n{doc.page_content}"
        for doc in docs
    )

只保留模型回答需要的信息。

3. 控制历史消息

多轮对话不要无限追加历史。

可以考虑：

  • 只保留最近 N 轮。
  • 对历史进行摘要。
  • 只保留与当前问题相关的历史。
  • 把长期记忆放入检索系统。

否则聊天越久，成本越高，延迟越大。

七、控制输出 token

输出越长，也越慢越贵。

如果业务不需要长篇回答，要明确限制。

例如：

1

请用 3 到 5 句话回答。

或者：

1

请用不超过 200 字回答。

代码中也可以设置模型参数。

不同模型集成支持的参数可能不同，示意：

1
2
3
4
5

model = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0.2,
    max_tokens=500,
)

但不要只靠 max_tokens 粗暴截断。

更好的方式是 Prompt 中说明输出长度要求。

八、Streaming：改善体感速度

如果完整回答需要 5 秒，但第 1 秒就开始输出，用户体验会好很多。

这就是 streaming 的价值。

示例：

1
2

for chunk in chain.stream({"topic": "LangChain 性能优化"}):
    print(chunk, end="", flush=True)

对于聊天产品，streaming 几乎是标配。

它不一定减少总耗时，但能显著降低用户感知等待时间。

适合：

  • 长回答。
  • 总结。
  • 写作。
  • 对话。

不一定适合：

  • 后端批处理。
  • 必须完整 JSON 解析后才能返回的场景。
  • 需要先完成所有工具调用的 Agent 流程。

九、Batch：批量处理更高效

如果你有多个独立输入，不要一个一个串行调用。

LangChain Runnable 支持 batch：

1
2
3
4
5
6
7

questions = [
    "RAG 是什么？",
    "LCEL 是什么？",
    "Agent 是什么？",
]

answers = chain.batch(questions)

适合：

  • 批量生成摘要。
  • 批量分类。
  • 批量抽取结构化信息。
  • 批量评估。

如果服务商和环境支持并发，batch 可以显著减少总体时间。

但要注意：

  • API 限流。
  • 并发过高导致失败。
  • 成本瞬间升高。
  • 需要重试策略。

十、并发：别把独立任务串行做

有些任务可以并行执行。

例如：

1

同时生成标题、摘要、标签

可以用 RunnableParallel：

1
2
3
4
5
6
7
8
9

from langchain_core.runnables import RunnableParallel

parallel_chain = RunnableParallel({
    "title": title_chain,
    "summary": summary_chain,
    "tags": tags_chain,
})

result = parallel_chain.invoke(article)

如果三个任务互不依赖，并行会比串行更快。

但并发也要控制。

不要无限并发请求模型服务。

真实项目要考虑：

  • 服务商限流。
  • 超时。
  • 重试。
  • 任务队列。
  • 降级策略。

十一、缓存：避免重复工作

很多请求是重复或高度相似的。

例如：

  • 系统提示不变。
  • 常见 FAQ 问题重复出现。
  • 同一文档反复 embedding。
  • 同一评估集反复运行。

缓存可以明显降低成本。

1. 不要重复 embedding 文档

RAG 索引构建应该离线执行。

不要每次启动都：

1

Chroma.from_documents(docs, embeddings)

应该持久化：

1
2
3
4
5

Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    persist_directory="data/chroma_db",
)

在线查询时加载：

1
2
3
4

vectorstore = Chroma(
    persist_directory="data/chroma_db",
    embedding_function=embeddings,
)

2. 缓存高频问答

对于非常固定的 FAQ，可以在应用层缓存最终回答。

例如用 Redis：

1
2
3
4
5
6

cache_key = normalize(question)
if cache exists:
    return cached_answer
else:
    answer = chain.invoke(question)
    save cache

注意：

  • 用户权限不同，缓存不能混用。
  • 知识库更新后要失效。
  • 个性化回答不适合全局缓存。

3. 缓存工具结果

例如天气、商品详情、配置查询等短时间内不变的数据，可以缓存。

但订单状态、库存、价格等实时性强的数据要谨慎。

十二、RAG 检索优化

RAG 的性能不仅看模型。

检索链路也会影响速度和成本。

1. 控制 k

k 越大，返回上下文越多。

1

retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

如果 k 太大：

  • 检索上下文变长。
  • Prompt token 增加。
  • 模型更慢更贵。
  • 无关内容干扰回答。

从 k=3 或 k=5 开始，用评估集调参。

2. 优化 chunk_size

chunk 太小：

  • 语义不完整。
  • 需要召回更多 chunk。

chunk 太大：

  • 检索不精准。
  • 上下文浪费。

中文知识库可以从：

1
2

chunk_size=600
chunk_overlap=100

开始测试。

不要只凭感觉。

3. 使用 metadata filter

如果用户只查某个知识库，不要全库检索。

1
2
3
4
5
6

retriever = vectorstore.as_retriever(
    search_kwargs={
        "k": 3,
        "filter": {"kb_name": "hr-policy"},
    }
)

过滤范围越准确，检索越快，也更不容易误召回。

4. 对无答案问题使用阈值

普通 similarity search 总会返回最相近结果。

无答案问题可能带来无关上下文。

可以考虑：

1
2
3
4
5
6
7

retriever = vectorstore.as_retriever(
    search_type="similarity_score_threshold",
    search_kwargs={
        "k": 5,
        "score_threshold": 0.7,
    },
)

阈值要结合具体向量库和评估集调整。

5. Rerank 要谨慎使用

Rerank 可以提升质量，但会增加延迟和成本。

适合：

  • 文档量大。
  • top-k 噪声多。
  • 答案准确性要求高。

不适合所有场景默认开启。

十三、Prompt 压缩和上下文压缩

RAG 常见问题是上下文太长。

可以考虑压缩上下文。

例如：

1
2
3
4
5

先检索 10 条
  ↓
用 rerank 或规则选出 3 条
  ↓
只把最相关内容放进 Prompt

也可以对长文档片段做摘要。

但要注意：摘要可能丢失细节。

对于制度、金额、条款这类精确信息，不要随便摘要。

更推荐：

  • 改进 chunk。
  • 减少 k。
  • 使用 metadata filter。
  • 使用 rerank。
  • 只截取相关段落。

十四、Agent 性能优化

Agent 通常比普通 Chain 更慢更贵。

原因是它可能多次调用模型和工具。

1. 限制最大步数

不要让 Agent 无限循环。

手写循环时：

1

max_steps = 5

LangGraph 中也要通过状态控制循环次数。

2. 减少工具数量

工具越多，模型选择越困难。

如果一个 Agent 有 20 个工具，它可能更容易选错，也可能需要更多推理。

初期建议 3 到 5 个工具。

3. 工具描述简洁明确

工具描述太长会增加 token。

太短又会导致模型选错。

目标是：

1

清楚说明什么时候用、输入是什么、返回什么。

4. 固定流程不要交给 Agent

如果流程明确：

1

查订单 -> 查物流 -> 回答

直接写 Chain 或 LangGraph 可能更快更稳。

Agent 适合路径不固定的任务。

5. 工具结果要简洁

不要把完整 API 原始响应丢给模型。

只返回模型需要的字段。

这样可以减少 token，也减少误解。

十五、稳定性优化

性能不只是快。

稳定性同样重要。

1. 设置超时

外部 API、工具调用、模型服务都可能卡住。

需要设置超时。

2. 合理重试

模型服务偶发失败可以重试。

LangChain Runnable 支持 with_retry：

1

reliable_chain = chain.with_retry(stop_after_attempt=3)

但不要对所有错误无脑重试。

例如：

  • API Key 错误，重试没用。
  • 输入太长，重试没用。
  • Parser schema 设计错误，重试没用。

3. 降级策略

当强模型不可用时，可以降级到较小模型。

当 rerank 服务不可用时，可以退回普通检索。

当 Agent 工具失败时，可以返回清晰错误。

4. 输出解析要稳

结构化输出建议使用 schema。

不要依赖模型自由输出后再硬解析。

例如：

1

structured_model = model.with_structured_output(MySchema)

解析失败会带来重试和额外成本。

十六、成本估算

优化前先知道成本来自哪里。

一个 RAG 请求成本大致来自：

1
2
3
4
5
6

问题 token
+ 系统 Prompt token
+ 检索上下文 token
+ 输出 token
+ 可能的 query rewrite token
+ 可能的 rerank 成本

一个 Agent 请求成本可能来自：

1
2
3
4
5

每一轮模型调用输入输出
+ 工具描述 token
+ 工具结果 token
+ 多轮中间消息 token
+ 重试成本

所以降低成本可以从这些方向入手：

  • 减少无用上下文。
  • 减少工具数量。
  • 缩短工具返回。
  • 减少 Agent 轮次。
  • 用小模型处理简单步骤。
  • 缓存重复结果。
  • 控制输出长度。

十七、评估优化是否有效

性能优化不能只看单次结果。

应该用固定问题集对比：

版本平均耗时平均 token正确率失败率备注
v16.2s420082%6%k=8
v24.1s260084%4%k=4 + filter
v33.8s220078%4%k=2，召回下降

优化不是只看更快。

如果 v3 更快但正确率下降明显，就不一定值得。

要同时看：

  • 质量。
  • 延迟。
  • 成本。
  • 稳定性。

十八、常见误区

1. 只换更快模型

模型快了，但如果检索、Prompt、工具调用没优化，整体仍然慢。

2. k 越小越省钱

k 太小可能漏召回，导致回答质量下降。

省下 token，却损失正确性。

3. 一上来就加缓存

缓存要考虑权限、数据更新和失效策略。

不要把不该共享的回答缓存给其他用户。

4. 所有步骤都用 Agent

Agent 灵活，但成本高、延迟高、不可控性更强。

固定流程用 Chain 或 LangGraph 更好。

5. 无脑重试

重试会增加成本。

先判断错误是否可恢复。

6. 只看平均延迟

还要看 P95、P99。

用户更容易感受到慢请求，而不是平均值。

二十、最佳实践

1. 用数据定位瓶颈

先用 LangSmith 或日志看链路。

不要凭感觉优化。

2. 分步骤选择模型

简单任务用快模型。

复杂任务用强模型。

3. 控制 Prompt 和上下文长度

少即是多。

只给模型完成任务需要的信息。

4. RAG 先优化召回质量，再压缩上下文

不要为了省 token 牺牲关键资料。

5. Agent 要限制轮次和工具集

多工具不是越多越好。

6. 离线任务不要放在线上请求里

文档 embedding、索引构建、批量评估都应该离线。

7. 缓存要有失效策略

尤其是知识库、权限和实时数据场景。

8. 优化后要跑评估集

确认速度变快的同时，质量没有明显下降。

二十一、总结

本文我们系统梳理了 LangChain 应用的性能优化。

核心结论是：

大模型应用的性能优化不是单纯让模型更快，而是在质量、延迟、稳定性和成本之间做平衡。优化前先观测，优化后要评估。

本文重点包括：

  • LangChain 应用的性能瓶颈可能来自模型、Prompt、Retriever、Tool、Agent、Parser 和重试。
  • 优化前要先用 LangSmith 或日志定位每一步耗时和 token 消耗。
  • 不同任务可以使用不同模型，简单步骤不一定需要最强模型。
  • 控制输入和输出 token 是降低成本和延迟的重要手段。
  • Streaming 可以显著改善用户体感速度。
  • Batch 和并发适合处理多个独立任务，但要注意限流。
  • RAG 优化要关注 k、chunk_size、metadata filter、阈值和上下文长度。
  • Agent 要限制工具数量、最大步数和工具返回长度。
  • 稳定性需要超时、合理重试、降级策略和稳定的结构化输出。
  • 性能优化必须结合评估集，不能只看单次速度。

到这里，我们已经从功能实现、工程化、观测和性能优化几个角度完善了 LangChain 应用的基本能力。
