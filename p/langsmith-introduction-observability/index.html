LangSmith 入门：调试和观测你的 LangChain 应用

2025-10-17 10:00
阅读时长: 12 分钟

上一篇文章里，我们从工程化角度梳理了 LangChain 应用如何从 Demo 走向可维护项目。

我们提到，大模型应用的调试对象不是一行输出，而是一条链路。

在一个真实 LangChain 应用中，一次用户请求可能经过：

API
  ↓
Prompt
  ↓

Output Parser

Agent
  ↓
Final Answer

如果最终回答错了，你需要知道到底是哪一步出了问题。

这就是 LangSmith 要解决的问题。

一、前言

很多人刚开始写 LangChain 应用时，调试方式很简单：

1
2

print(prompt)
print(answer)

这在 demo 阶段够用。

但当链路变复杂后，print 很快就不够了。

比如一个 RAG 应用回答错了，你要排查：

  • 用户原始问题是什么？
  • Retriever 检索到了哪些文档？
  • 文档 metadata 是什么？
  • Prompt 最终长什么样？
  • 模型输入和输出是什么？
  • Output Parser 有没有解析失败？
  • 哪一步耗时最长？
  • 本次请求用了多少 token？
  • 相同问题之前有没有出现过？

再比如一个 Agent 应用执行错了，你要排查：

  • Agent 调用了哪些工具？
  • 工具调用参数是什么？
  • 工具返回了什么？
  • 模型为什么继续调用下一个工具？
  • 是否出现了重复调用？
  • 最终回答是否忠于工具结果？

这些问题靠零散 print 很难稳定解决。

LangSmith 的价值就是：

帮你追踪、调试、评估和观察 LangChain 应用的完整运行链路。

本文会重点讲：

  1. LangSmith 是什么。
  2. 为什么大模型应用需要可观测性。
  3. Trace、Run、Project、Dataset、Evaluation 分别是什么。
  4. 如何在 LangChain 应用中开启 LangSmith tracing。
  5. 如何观察普通 Chain、RAG 和 Agent 的执行过程。
  6. 如何用 LangSmith 做数据集和评估。
  7. LangSmith 在工程化项目中的最佳实践。

二、为什么需要 LangSmith？

传统 Web 应用出问题时，我们通常看：

  • 日志。
  • HTTP 状态码。
  • 数据库查询。
  • 错误栈。
  • APM 链路追踪。
  • 指标监控。

大模型应用也需要类似能力。

但它的问题更特殊。

因为 LLM 应用的输出不仅取决于代码，还取决于：

  • Prompt。
  • 模型版本。
  • 模型参数。
  • 检索结果。
  • 工具返回。
  • 历史消息。
  • 输出解析。
  • Agent 中间步骤。

例如用户说：

1

公司差旅住宿标准是多少？

最终回答错了。

原因可能是：

可能原因排查方式
知识库没有相关文档看 Retriever 返回
检索到了错误文档看 top-k docs 和 metadata
Prompt 没有限制只根据上下文回答看最终 Prompt
模型忽略了上下文看模型输入输出
Parser 解析失败看 Parser run
Agent 调错工具看 tool calls

如果没有链路追踪，你只能猜。

LangSmith 能把这些步骤记录下来，让你看到一次请求的完整执行树。

三、LangSmith 是什么？

LangSmith 是 LangChain 生态中的调试、观测和评估平台。

它主要帮助你做几件事：

  1. Trace：追踪每次链路调用。
  2. Debug：查看每一步输入输出。
  3. Monitor：观察延迟、错误、token 等运行情况。
  4. Dataset：保存测试样本。
  5. Evaluation：对模型、Prompt、RAG、Agent 做评估。

可以把它理解为大模型应用的“链路观测台”。

对于普通 Chain，它能记录：

1
2
3

Prompt 输入
Model 输入输出
Parser 输出

对于 RAG，它能记录：

1
2
3
4

用户问题
Retriever 返回文档
Prompt 最终上下文
Model 回答

对于 Agent，它能记录：

1
2
3
4
5

用户目标
模型中间消息
工具调用
工具结果
最终回答

这些信息对调试非常关键。

四、核心概念

使用 LangSmith 前，先理解几个核心概念。

1. Trace

Trace 是一次完整调用的追踪记录。

例如用户问了一次：

1

RAG 是什么？

整个链路从输入到输出，就是一个 trace。

Trace 里可能包含多个子步骤。

2. Run

Run 是 trace 中的一个执行单元。

例如：

  • 一次 Chain 调用。
  • 一次 Prompt 格式化。
  • 一次 Model 调用。
  • 一次 Retriever 调用。
  • 一次 Tool 调用。

一个 Trace 通常由多个 Run 组成。

3. Project

Project 用来组织 traces。

比如你可以为不同环境创建不同 project：

1
2
3
4

langchain-demo-dev
langchain-demo-prod
rag-qa-test
agent-debug

这样调试时不会混在一起。

4. Dataset

Dataset 是评估样本集合。

例如你准备一组 RAG 测试问题：

1
2
3
4
5

问题：RAG 是什么？
期望：检索增强生成，先检索再生成。

问题：一线城市住宿标准是多少？
期望：每天不超过 600 元。

这些可以组成一个 dataset。

5. Evaluation

Evaluation 是对应用输出进行评估。

可以评估：

  • 回答是否正确。
  • 是否引用了正确来源。
  • 是否包含关键事实。
  • 是否拒答了知识库没有的问题。
  • Agent 是否调用了正确工具。

这对持续优化 Prompt、Retriever 和 Agent 非常重要。

from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

load_dotenv()

model = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),

chain = prompt | model | StrOutputParser()

from langchain_core.runnables import RunnablePassthrough
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser


def format_docs(docs):
    return "\n\n".join(
        f"来源：{doc.metadata.get('source', 'unknown')}\n{doc.page_content}"
        for doc in docs
    )

prompt = ChatPromptTemplate.from_messages([
    ("system", "请只根据上下文回答问题。如果上下文没有答案，请说无法确定。"),
    ("human", "上下文：\n{context}\n\n问题：{question}"),
])

rag_chain = (
    {
        "context": retriever | format_docs,
        "question": RunnablePassthrough(),
    }
    | prompt
    | model
    | StrOutputParser()
).with_config({"run_name": "rag_answer_chain"})

answer = rag_chain.invoke("RAG 的流程是什么？")

在 LangSmith 中，你可以查看：

  • Retriever 输入是什么。
  • Retriever 返回了哪些 Document。
  • 每个 Document 的 metadata 是什么。
  • format_docs 后上下文长什么样。
  • Prompt 最终发给模型的内容。
  • 模型输出是什么。

这对 RAG 调试非常关键。

如果回答错了，先看 Retriever。

如果 Retriever 返回错误资料，问题在检索。

如果 Retriever 返回正确资料，但模型回答错，问题可能在 Prompt 或模型。

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langchain.agents import create_agent

load_dotenv()


@tool
def get_order_status(order_id: str) -> dict:
    """Get order status by order id."""
    if order_id == "1001":
        return {
            "status": "已发货",
            "shipping_company": "顺丰",
            "tracking_no": "SF123456",
        }

    return {"error": "订单不存在"}


model = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
    temperature=0,
)

agent = create_agent(
    model=model,
    tools=[get_order_status],
    system_prompt="回答订单问题前必须查询订单工具，不要编造工具结果中没有的信息。",
)

result = agent.invoke({
    "messages": [
        {"role": "user", "content": "订单 1001 发货了吗？"}
    ]
})

print(result["messages"][-1].content)

开启 tracing 后，LangSmith 可以帮助你看到：

  • 模型是否生成了工具调用。
  • 调用工具名称是什么。
  • 工具参数是什么。
  • 工具返回是什么。
  • 模型最终如何组织回答。

对于多工具 Agent，这比本地 print 清楚很多。

示例：

十一、手动打标签和 metadata

在复杂系统中，建议给调用添加 tags 和 metadata。

result = chain.invoke(
    {"topic": "RAG"},
    config={
        "tags": ["rag", "production"],
        "metadata": {
            "user_id": "user_123",
            "session_id": "session_abc",
            "feature": "knowledge_qa",

这样你可以在 LangSmith 中更容易筛选：

  • 某个用户的请求。
  • 某个功能的请求。
  • 某个版本的请求。
  • 某类实验的请求。

注意：metadata 不要放敏感信息。

例如不要直接放：

  • 密码。
  • token。
  • 身份证号。
  • 银行卡号。
  • 过多个人隐私。

十二、LangSmith 和本地日志的关系

LangSmith 不是完全替代本地日志。

两者关注点不同。

工具关注点
本地日志系统运行、错误、业务事件
LangSmithLLM 链路、模型输入输出、工具调用、评估

本地日志适合记录：

4

6

HTTP status
异常栈

业务状态

LangSmith 适合记录：

1

3
4
5
6

Model output
Retriever docs
Tool calls
Agent steps
LangGraph nodes

真实项目里两者应该结合。

可以在本地日志中记录 request_id，同时在 LangSmith metadata 中也带上它。

这样线上问题可以关联排查。

十三、从调试到评估

Tracing 解决的是：

某一次请求发生了什么？

但工程化还需要回答另一个问题：

这套应用整体效果怎么样？

这就需要评估。

例如你改了 RAG 的 k：

1

search_kwargs={"k": 3}

改成：

1

search_kwargs={"k": 5}

你怎么知道效果变好了还是变差了？

不能只靠感觉。

你需要固定问题集。

这就是 Dataset 和 Evaluation 的意义。

十四、准备评估数据集

假设我们有一组 RAG 问题：

examples = [
    {
        "inputs": {"question": "RAG 是什么？"},
        "outputs": {"answer": "RAG 是检索增强生成，会先检索资料再生成回答。"},
    },
    {
        "inputs": {"question": "一线城市住宿标准是多少？"},
        "outputs": {"answer": "一线城市住宿标准为每天不超过 600 元。"},

这些样本可以上传到 LangSmith dataset。

学习阶段你也可以先保存在本地 JSON 文件里。

关键是要有一组固定问题。

每次改 Prompt、Retriever、Embedding、模型时，都跑同一组问题。

十五、评估什么？

不同应用评估指标不同。

1. RAG 应用

关注：

  • 是否召回正确文档。
  • 答案是否基于上下文。
  • 是否包含关键事实。
  • 无答案问题是否拒答。
  • 引用来源是否正确。

2. Agent 应用

关注：

  • 是否调用正确工具。
  • 工具参数是否正确。
  • 是否多调或漏调工具。
  • 工具失败时是否合理处理。
  • 最终回答是否忠于工具结果。

3. 结构化输出应用

关注：

  • JSON 是否可解析。
  • 字段是否完整。
  • 类型是否正确。
  • 是否满足业务规则。

4. 写作总结应用

关注：

  • 是否覆盖关键点。
  • 是否忠于原文。
  • 是否结构清晰。
  • 是否存在幻觉。

评估不是一个统一答案，而是要围绕业务目标设计。

十六、自动评估和人工评估

评估有两种常见方式。

1. 自动评估

用规则或模型评估输出。

例如规则：

1
2

def contains_keyword(output: str) -> bool:
    return "检索" in output and "生成" in output

适合简单事实检查。

也可以用 LLM 作为 evaluator，判断回答是否满足标准。

自动评估适合批量运行，但要注意 evaluator 自身也可能出错。

2. 人工评估

人工看输出并打分。

适合：

  • 主观质量。
  • 表达风格。
  • 复杂语义正确性。
  • 高风险业务场景。

实际项目中通常两者结合。

先用自动评估筛选，再人工复查关键样本。

十七、LangSmith 在开发流程中的位置

LangSmith 的价值不只是记录日志。

更重要的是帮助你建立一个持续改进闭环。

十八、隐私和安全注意事项

开启 tracing 后，模型输入输出、检索内容、工具结果可能会被记录。

所以要注意：

  • 不要上传敏感个人信息。
  • 不要记录密钥、token、密码。
  • 工具返回给模型前先过滤敏感字段。
  • metadata 中不要放敏感值。
  • 企业环境要遵守数据合规要求。
  • 对生产数据开启 tracing 前要确认策略。

这不是 LangSmith 独有的问题。

任何 LLM 链路观测系统都要考虑数据安全。

如果某些字段敏感，应在进入链路前脱敏。

十九、常见问题

1. 为什么看不到 trace？

检查环境变量：

1
2
3

LANGSMITH_TRACING=true
LANGSMITH_API_KEY=...
LANGSMITH_PROJECT=...

还要确认：

  • .env 是否被加载。
  • API Key 是否正确。
  • 网络是否能访问 LangSmith。
  • 当前代码是否真的调用了 LangChain Runnable。

2. 为什么 trace 名称很乱？

给关键 Chain、Agent、Graph 设置 run_name。

1

chain = chain.with_config({"run_name": "rag_answer_chain"})

也可以使用 tags 区分环境和功能。

3. RAG 调试应该先看什么？

先看 Retriever 返回。

如果检索错了，不要急着改 Prompt。

如果检索对了但回答错，再看 Prompt 和模型输出。

4. Agent 调试应该先看什么？

先看工具调用。

关注：

  • 工具名称。
  • 工具参数。
  • 工具返回。
  • 最终回答是否使用了工具结果。

5. 是否所有请求都要 tracing？

开发环境建议开启。

生产环境要结合成本、隐私和合规策略。

可以按环境、采样率或功能开关控制。

二十、最佳实践

1. 项目名称要区分环境

例如：

1
2
3

my-rag-dev
my-rag-staging
my-rag-prod

不要所有环境混在一个 project。

2. 给关键链路设置 run_name

例如：

1
2
3
4

rag_answer_chain
query_rewrite_chain
order_agent
reflection_graph

后续排查会轻松很多。

3. 用 tags 和 metadata 辅助筛选

例如：

1
2
3
4

config={
    "tags": ["rag", "v2"],
    "metadata": {"feature": "knowledge_qa"},
}

4. 不要记录敏感信息

观测系统不是秘密仓库。

该脱敏就脱敏。

5. 把失败案例加入评估集

线上发现一个错误问题，不要只修一次。

应该加入 dataset，防止以后回归。

6. 评估要围绕业务目标

不要只看“回答像不像”。

RAG 要看是否基于资料。

Agent 要看是否调用正确工具。

结构化输出要看 schema 是否正确。

7. LangSmith 和日志结合使用

LangSmith 看 LLM 链路。

日志看系统运行。

两者用 request_id 或 metadata 关联。

二十一、总结

本文我们入门了 LangSmith。

核心结论是：

LangSmith 让 LangChain 应用的运行过程从黑盒变成可观察链路，帮助我们调试每一步输入输出，并用数据集和评估建立持续改进闭环。

本文重点包括：

  • 大模型应用的问题往往出现在 Prompt、Retriever、Model、Tool、Agent 中间步骤，而不只是最终回答。
  • LangSmith 可以记录 Trace 和 Run，帮助查看完整调用树。
  • Project 用来组织不同应用或环境的 traces。
  • Dataset 和 Evaluation 可以帮助我们从“凭感觉调参”走向“用固定样本评估”。
  • 开启 tracing 通常只需要配置 LANGSMITH_TRACING、LANGSMITH_API_KEY 和 LANGSMITH_PROJECT。
  • RAG 调试要重点看 Retriever 返回和最终 Prompt。
  • Agent 调试要重点看工具调用和工具结果。
  • LangGraph 调试要关注每个节点的状态更新和条件流转。
  • 生产环境使用 tracing 要注意隐私、安全、采样和合规。

到这里，我们已经补上了工程化中的观测和评估能力。
