一、前言

个人知识库是最适合练习 RAG 的场景之一。

因为每个人都有大量零散资料：

  • 技术笔记。
  • 学习总结。
  • 博客草稿。
  • 会议纪要。
  • 读书笔记。
  • 项目文档。
  • 常用命令。
  • 问题排查记录。

这些资料通常存放在 Markdown、PDF、网页剪藏、Notion、Obsidian 或本地文件夹里。

如果只是靠文件名搜索，很难充分利用它们。

我们希望做一个 AI 助手，可以这样提问：

1

我之前关于 LangGraph 的笔记里，是怎么解释 State 的？

或者：

1

帮我总结一下我所有 RAG 相关笔记里的最佳实践。

再或者：

1

我有没有记录过 Chroma 持久化的写法？

这类问题非常适合 RAG。

因为答案不应该靠模型凭空生成，而应该来自你的个人资料。

本文会从零设计一个个人知识库 AI 助手，重点包括：

  1. 需求和能力边界。
  2. 项目结构。
  3. 文档加载和 metadata 设计。
  4. 文档切分策略。
  5. 向量库构建。
  6. Retriever 和 Prompt 设计。
  7. 问答链实现。
  8. 来源引用和无答案处理。

import os
from dataclasses import dataclass
from dotenv import load_dotenv

load_dotenv()


@dataclass(frozen=True)
class Settings:
    openai_api_key: str | None = os.getenv("OPENAI_API_KEY")
    openai_base_url: str | None = os.getenv("OPENAI_BASE_URL") or None
    model_name: str = os.getenv("MODEL_NAME", "gpt-4o-mini")
    embedding_model: str = os.getenv("EMBEDDING_MODEL", "text-embedding-3-small")
    docs_dir: str = os.getenv("DOCS_DIR", "data/docs")
    chroma_persist_dir: str = os.getenv("CHROMA_PERSIST_DIR", "data/chroma_db")
    retrieval_k: int = int(os.getenv("RETRIEVAL_K", "4"))


settings = Settings()

这样其他模块不需要到处读取环境变量。

统一从 settings 获取配置。

from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from src.config import settings


def create_chat_model(temperature: float = 0.2):
    return ChatOpenAI(
        model=settings.model_name,
        api_key=settings.openai_api_key,
        base_url=settings.openai_base_url,
        temperature=temperature,
    )


def create_embedding_model():
    return OpenAIEmbeddings(
        model=settings.embedding_model,
        api_key=settings.openai_api_key,
        base_url=settings.openai_base_url,
    )

这里把 Chat Model 和 Embedding Model 分开。

因为它们职责不同：

模型作用
Chat Model生成回答
Embedding Model把文档和问题转换成向量

不要混用。

# RAG 笔记

RAG 是 Retrieval-Augmented Generation，也就是检索增强生成。

它的核心流程是：先从知识库检索相关资料，再把资料放入 Prompt，让模型基于资料生成回答。

RAG 的关键组件包括 Document Loader、Text Splitter、Embedding、Vector Store、Retriever 和 Prompt。

调试 RAG 时要先看 Retriever 返回了什么，不要只看最终回答。

# LangGraph 笔记

LangGraph 用图结构编排复杂 Agent 工作流。

它的核心概念包括 State、Node 和 Edge。

State 保存跨节点共享的上下文，Node 负责执行具体步骤，Edge 控制节点之间的流转。

当流程存在分支、循环、人工确认或状态恢复需求时，LangGraph 比普通 Chain 更适合。

# Prompt 工程笔记

Prompt 应该清晰说明任务、输入、输出格式和限制条件。

对于知识库问答，Prompt 应该要求模型只根据上下文回答。

如果上下文没有答案，模型应该说明资料不足，而不是编造答案。

Prompt 不是权限边界，权限控制必须在系统或工具层完成。

实际使用时，你可以把自己的 Obsidian、博客草稿、项目文档放进这个目录。

from langchain_community.document_loaders import DirectoryLoader, TextLoader
from src.config import settings


def load_documents():
    loader = DirectoryLoader(
        settings.docs_dir,
        glob="**/*.md",
        loader_cls=TextLoader,
        loader_kwargs={"encoding": "utf-8"},
    )

    docs = loader.load()

    for doc in docs:
        doc.metadata["kb_name"] = "personal-kb"
        doc.metadata["language"] = "zh-cn"

    return docs

from langchain_text_splitters import RecursiveCharacterTextSplitter


def split_documents(docs):
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=700,
        chunk_overlap=120,
        separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
    )

    return splitter.split_documents(docs)

个人知识库通常以中文 Markdown 为主。

所以加入中文标点作为分隔符。

参数不是固定答案。

可以从：

1
2

chunk_size=700
chunk_overlap=120

开始，再根据检索效果调整。

如果你的笔记很短，可以降低 chunk size。

如果你的笔记是长篇技术文档，可以适当增大。

from langchain_chroma import Chroma
from src.config import settings
from src.models import create_embedding_model


def create_vectorstore(chunks):
    return Chroma.from_documents(
        documents=chunks,
        embedding=create_embedding_model(),
        persist_directory=settings.chroma_persist_dir,
    )


def load_vectorstore():
    return Chroma(
        persist_directory=settings.chroma_persist_dir,
        embedding_function=create_embedding_model(),
    )

这里有两个函数：

函数作用
create_vectorstore离线构建向量库
load_vectorstore在线加载已有向量库

不要在每次用户提问时重新构建向量库。

from langchain_core.prompts import ChatPromptTemplate


def create_qa_prompt():
    return ChatPromptTemplate.from_messages([
        ("system", """
你是一个个人知识库 AI 助手。
请只根据提供的上下文回答问题。
如果上下文中没有答案，请回答：根据当前知识库资料无法确定。
回答时要清晰、准确，并尽量引用来源信息。
不要编造上下文中没有的事实。
"""),
        ("human", """
上下文：
{context}

问题：{question}
"""),
    ])

这里最重要的是三条约束：

1
2
3

只根据上下文回答。
资料不足时说无法确定。
不要编造事实。

个人知识库助手的可信度，来自它能基于资料回答，而不是像普通聊天机器人一样自由发挥。

from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough
from src.models import create_chat_model
from src.prompts import create_qa_prompt


def format_docs(docs):
    return "\n\n".join(
        f"来源：{doc.metadata.get('source', 'unknown')}\n{doc.page_content}"
        for doc in docs
    )


def unique_sources(docs):
    sources = []

    for doc in docs:
        source = doc.metadata.get("source", "unknown")
        if source not in sources:
            sources.append(source)

    return sources


def create_rag_chain(retriever):
    prompt = create_qa_prompt()
    model = create_chat_model(temperature=0.2)

    return (
        {
            "context": retriever | format_docs,
            "question": RunnablePassthrough(),
        }
        | prompt
        | model
        | StrOutputParser()
    )


def answer_with_sources(question: str, retriever):
    docs = retriever.invoke(question)

    if not docs:
        return {
            "answer": "根据当前知识库资料无法确定。",
            "sources": [],
        }

    context = format_docs(docs)
    prompt = create_qa_prompt()
    model = create_chat_model(temperature=0.2)
    chain = prompt | model | StrOutputParser()

    answer = chain.invoke({
        "context": context,
        "question": question,
    })

    return {
        "answer": answer,
        "sources": unique_sources(docs),
    }

这里提供了两个方式：

  1. create_rag_chain：标准 LCEL 链。
  2. answer_with_sources：手动拿到 docs，方便返回来源。

如果你需要展示来源，第二种方式更直观。

from src.retriever import create_retriever
from src.chains import answer_with_sources


def main():
    retriever = create_retriever()

    print("个人知识库 AI 助手已启动，输入 exit 退出。")

    while True:
        question = input("\n请输入问题：")

        if question.lower() in {"exit", "quit"}:
            break

        result = answer_with_sources(question, retriever)

        print("\n回答：")
        print(result["answer"])

        if result["sources"]:
            print("\n来源：")
            for source in result["sources"]:
                print("-", source)


if __name__ == "__main__":
    main()

但检索结果没有 langgraph.md，那问题在检索层，而不是模型层。

可能需要调整：

  • chunk_size。
  • chunk_overlap。

  • k。
  • 文档内容。

十八、处理无答案问题

普通相似度检索通常会返回最相近的文档，即使知识库没有答案。

例如：

1

今天北京天气怎么样？

知识库没有天气信息，但 Retriever 仍可能返回 RAG 或 Prompt 笔记。

要降低误答风险，可以做三件事。

1. Prompt 明确拒答

1

如果上下文中没有答案，请回答：根据当前知识库资料无法确定。

2. 使用阈值检索

可以改造 Retriever：

def create_retriever():
    vectorstore = load_vectorstore()

    return vectorstore.as_retriever(
        search_type="similarity_score_threshold",
        search_kwargs={
            "k": settings.retrieval_k,
            "score_threshold": 0.7,
        },
    )

阈值要结合实际向量库调试。

3. 准备无答案评估问题

例如：

1
2
3

今天北京天气怎么样？
某某股票明天涨不涨？
我的银行卡余额是多少？

确认助手不会乱答。

十九、加入多轮对话能力

当前版本是单轮问答。

如果想支持追问，可以结合前面 Memory 篇。

例如用户问：

1

LangGraph 是什么？

接着问：

1

它和普通 Chain 有什么区别？

第二个问题里的“它”需要结合历史。

一种常见做法是：

1

历史消息 + 当前问题 -> 改写成独立问题 -> RAG 检索 -> 回答

例如改写成：

1

LangGraph 和普通 Chain 有什么区别？

这可以单独做一个 query rewrite chain。

不要直接把大量历史消息都塞进 RAG Prompt。

历史越长，成本越高，也越容易干扰检索。

二十、加入文档增量更新

学习阶段可以每次全量重建。

但个人知识库会持续更新。

后续需要考虑增量更新：

  • 新增文件：只处理新文件。
  • 修改文件：删除旧 chunk，再写入新 chunk。
  • 删除文件：从向量库删除对应 chunk。
  • 文档版本：记录 updated_at。

metadata 中可以加入：

1
2
3
4
5
6

metadata={
    "source": "data/docs/rag.md",
    "doc_id": "stable-doc-id",
    "chunk_id": "stable-chunk-id",
    "updated_at": "2025-10-21",
}

有了稳定 ID，后续才容易做更新和删除。

你可以观察：

  • 用户问题。
  • Retriever 返回了哪些文档。
  • Prompt 最终上下文。
  • 模型回答。
  • 每一步耗时。

这对调试非常有帮助。

二十二、性能优化建议

个人知识库助手常见性能优化点：

1. 不要重复构建索引

build_index.py 离线运行。

app.py 只加载已有向量库。

2. 控制 k

不要把太多文档塞进 Prompt。

从 k=4 开始评估。

3. 控制 chunk 大小

如果答案经常缺上下文，增大 chunk 或 overlap。

如果检索结果太宽泛，减小 chunk 或优化文档结构。

4. 使用来源引用

来源可以帮助你判断是否检索正确。

也能提升用户信任。

5. 对高频问题做缓存

如果你经常问固定问题，可以缓存答案。

但知识库更新后要失效。

二十四、常见问题

1. 为什么回答不准确？

先运行：

1

python debug_retrieval.py

看检索结果是否包含答案。

如果检索错了，调 Retriever。

如果检索对了但回答错，调 Prompt。

2. 为什么知识库没有答案时还会回答？

普通相似度检索总会返回相近文档。

可以使用阈值检索，并在 Prompt 中要求资料不足时拒答。

3. 为什么来源不对？

检查 metadata 是否保留了 source。

文档切分时要使用：

1

splitter.split_documents(docs)

而不是只切字符串。

4. 文档更新后为什么问不到新内容？

确认是否重新运行了：

1

python build_index.py

如果使用持久化向量库，要注意旧索引是否被更新。

学习阶段可以先删除 data/chroma_db/ 后重建。

5. 是否需要 Agent？

如果只是知识库问答，RAG Chain 足够。

如果你希望助手能根据问题选择工具、执行操作、处理多步任务，再考虑 Agent 或 LangGraph。

二十五、最佳实践

1. 从小规模文档开始

先放 5 到 10 篇代表性文档。

确认加载、切分、检索和回答都正常。

2. metadata 从第一天设计好

至少保留：

1
2
3
4

source
title
category
updated_at

后续引用、过滤、更新都依赖它。

3. 构建索引和在线问答分开

这是 RAG 工程化的基本原则。

4. 调试先看 Retriever

不要一上来就怪模型。

5. Prompt 明确拒答策略

知识库没有答案时，助手应该承认不知道。

6. 准备评估问题集

至少包括：

  • 能回答的问题。
  • 同义问法。
  • 跨文档问题。
  • 无答案问题。
  • 容易混淆的问题。

7. 不要把个人敏感信息随便入库

个人知识库可能包含账号、密钥、隐私信息。

构建索引前要清理敏感内容。

8. 逐步扩展，不要一开始做太大

先完成命令行 RAG。

再做 Web UI。

再做 Agent。

最后再做自动同步和权限控制。
