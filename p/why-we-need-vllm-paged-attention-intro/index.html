vLLM 系列(一)：破冰篇 —— 为什么我们需要 vLLM？

2026-04-06 17:15
阅读时长: 5 分钟

在 2026 年的今天，如果你还在用 HuggingFace 原生的 model.generate() 来写公司的线上推理服务，那你的简历大概率会被面试官直接丢进碎纸机。 作为 LLM 推理界的“扛把子”，vLLM 已经成为了工业界事实上的标准。但在学习它复杂的源码之前，我们要先弄清楚一个灵魂考问：既然原生推理能跑通，为什么我们还需要 vLLM？它到底解决了什么要命的问题？

一、 知识点详解：大模型推理的“两大病灶”

在没有 vLLM 之前，大模型推理部署面临着两个极其痛苦的瓶颈：

1. 静态批处理（Static Batching）的“木桶效应”

传统的推理框架在处理并发请求时，通常采用“静态批处理”。 假设 Batch Size 为 4，有 4 个请求同时进来。

  • 请求 A 需要生成 10 个词。
  • 请求 B 需要生成 100 个词。

在静态模式下，请求 A 在 1 秒钟就跑完了，但它不能返回！它必须在显存里干等着请求 B。因为框架要求这一批（Batch）必须同步结束。 这就好比 4 个人组队跑步，必须等跑得最慢的那个人到了终点，全队才能领奖券。在这个过程中，GPU 的算力被白白浪费在空转和 Padding 上。

2. 显存碎片化（Memory Fragmentation）的“显存墙”

在生成每一个词时，模型都要存储 KV Cache。 因为我们事先不知道用户到底会输入多长、模型会输出多长，传统框架只能按照“最大长度（Max Seq Len）”来给每个请求预分配一块连续的显存空间。

结果就是：

  • 用户只聊了 10 个字，你却给他留了 2048 个字的空间。
  • 显存里到处都是“占着坑不拉屎”的空位。
  • 最终由于显存碎片太多，明明还有剩余容量，却因为找不到连续大块空间而导致 OOM（显存溢出）。

二、 进阶拓展：vLLM 的终结者方案

针对上面两个病灶，vLLM 祭出了两把手术刀：

1. Continuous Batching（连续批处理）

vLLM 抛弃了“等大家一起结束”的旧思路。它在 Iteration（迭代）级别进行调度。 一旦请求 A 跑完了，调度器立刻把 A 踢出批处理队列，并把排队中的请求 E 塞进去。GPU 的每一个计算周期都被塞得满满当当，没有任何一个请求在“陪跑”。

2. PagedAttention（显存分页）

这是 vLLM 轰动业界的成名绝技。它借鉴了操作系统的虚拟内存管理思想： 它不再为每个请求分配连续显存，而是把 KV Cache 切成一个个小的 Block（块）。 这些块散落在显存的各个角落，通过一个 Block Table（块表） 进行映射。就像玩拼图一样，哪里有空位，KV Cache 就存到哪里。这让显存利用率从不足 30% 飙升到了 90% 以上。

import time

# 模拟四个请求的生成长度
requests = [5, 15, 5, 20] # 每个数字代表需要生成的 token 数

def static_batching_sim(reqs):
    """模拟静态批处理：以最长请求为准"""
    batch_size = len(reqs)
    max_len = max(reqs)
    print(f"【静态批处理】启动，Batch Size: {batch_size}")
    
    total_cycles = max_len # 必须跑完最长的那位
    wasted_cycles = sum([max_len - r for r in reqs])
    
    print(f"总计迭代次数: {total_cycles}")
    print(f"浪费的计算资源 (空转次数): {wasted_cycles}")
    return total_cycles

def continuous_batching_sim(reqs):
    """模拟连续批处理逻辑（简化版）"""
    print(f"\n【连续批处理】启动")
    # 假设系统可以随时补充新请求，这里简化为看利用效率
    # 实际上由于谁空出来谁就能接新活，资源利用率趋近于 100%
    active_tokens = sum(reqs)
    batch_size = len(reqs)
    
    # 理想情况下，总迭代时间是平均分布的，没有无效 Padding
    effective_cycles = active_tokens / batch_size
    print(f"理想平均迭代深度: {effective_cycles}")
    print(f"优势：一旦请求完成立即释放显存，不产生无效计算。")

# --- 阿彪的测试 ---
static_batching_sim(requests)
continuous_batching_sim(requests)

阿彪点评：在静态批处理中，那 3 个短请求产生的 wasted_cycles 就是公司白花花的银子（GPU 租金）在燃烧。vLLM 的出现，本质上是把推理从“作坊式凑单”变成了“流水线生产”。

四、 面试官会问到的问题及详细答案

❓ Q1：vLLM 主要优化的是 Latency（延迟）还是 Throughput（吞吐量）？

答： vLLM 的核心优化目标是 Throughput（吞吐量）。 虽然 PagedAttention 和优秀的内核实现对单次请求的 Latency 有一定帮助，但它真正强大的地方在于让单卡能够承载更多的并发请求（High Concurrency）。在相同的显存下，它能跑更多的 Batch，从而提升单位时间内处理的总 Token 数。

❓ Q2：在什么场景下，vLLM 的优势体现不出来？

答： 在 Batch Size = 1（极低并发） 的场景下。 当系统只有一个用户时，不需要 PagedAttention 来解决显存碎片，也不需要 Continuous Batching 来做调度。此时，推理速度完全取决于显存带宽和模型参数量。在这种“单挑”场景下，vLLM 甚至可能因为额外的调度开销，比极度精简的底层 C++ 实现慢一点点。

五、 阿彪碎碎念 [抱拳]

其实学习 vLLM 的过程，就是一个重新认识“工程之美”的过程。 很多同学总是纠结于 Transformer 里的注意力公式怎么写，但到了工业界你会发现，公式大家都有，真正的差距在于谁能把 80G 显存压榨到最后一滴。

PagedAttention 并不是什么新发明的黑科技，它就是把 50 年前的操作系统内存管理思想，跨界应用到了大模型上。 所以，别小看你本科课本上的那些“老古董”，在大模型时代，它们全是“降维打击”的核武器。 下一篇，我们将深入显存底层，手动拆解 PagedAttention 的 Block 映射机制，准备好，我们要动手术了！
