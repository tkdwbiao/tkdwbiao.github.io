LangChain 企业实践：构建内部文档问答系统

2025-10-23 10:00
阅读时长: 18 分钟

上一篇文章里，我们做了一个个人知识库 AI 助手。

它的核心链路是：

1

文档加载 -> 文档切分 -> Embedding -> Vector Store -> Retriever -> Prompt -> Model -> Answer + Sources

对于个人学习和小型知识库，这已经很有价值。

但如果把场景放到企业内部文档问答系统，问题会马上复杂很多。

因为企业知识库不仅要“能回答”，还要考虑：

  • 谁能看哪些文档。
  • 文档是否来自可信来源。
  • 答案是否带引用。
  • 文档更新后索引如何同步。
  • 不同部门、租户、项目之间是否隔离。
  • 用户提问和模型回答是否需要审计。
  • 生产环境如何监控、评估和回滚。

这一篇，我们把视角从个人知识库扩展到企业内部文档问答系统。

一、前言

企业内部文档问答，是 RAG 最常见的落地场景之一。

典型问题包括：

1

公司差旅报销标准是多少？

1

研发环境数据库变更流程怎么走？

1

新员工入职需要完成哪些系统权限申请？

1

某个项目的接口鉴权方式是什么？

这些问题看起来都适合交给大模型。

但大模型本身并不知道企业内部信息。

所以我们需要让模型基于企业文档回答，而不是凭空生成。

这就是企业 RAG 系统的基本目标：

从企业已有文档中检索可信内容，再让模型基于这些内容生成带来源的回答。

本文会重点讨论：

  1. 企业文档问答和个人知识库的区别。
  2. 需求边界和系统架构。
  3. 文档接入和 metadata 设计。
  4. 权限过滤和多租户隔离。
  5. 文档切分、索引构建和增量更新。
  6. Retriever、Prompt 和引用设计。
  7. API 服务封装。
  8. 审计、观测、评估和部署。
  9. 常见问题和最佳实践。

二、企业文档问答和个人知识库有什么不同？

个人知识库的关键是方便自己查资料。

企业文档问答的关键是：

1
2
3
4

正确
可信
可控
可追踪

1. 正确

企业场景里，答错可能带来真实影响。

例如：

  • 报销标准答错，影响财务流程。
  • 权限申请流程答错，影响工作效率。
  • 运维操作步骤答错，可能造成事故。
  • 合同条款答错，可能带来合规风险。

所以不能只追求“回答像那么回事”。

系统必须尽量保证答案来自文档。

2. 可信

企业用户通常会问：

1

这个答案是从哪来的？

所以回答必须带来源。

来源最好包含：

  • 文档标题。
  • 文档路径或 URL。
  • 章节标题。
  • 更新时间。
  • 相关片段。

否则用户很难判断答案是否可靠。

3. 可控

企业知识库里经常有不同级别的信息。

例如：

  • 全员可见的制度文档。
  • 部门内部文档。
  • 项目组文档。
  • 管理层文档。
  • 客户合同。
  • 安全应急预案。

不是每个用户都能检索所有文档。

权限控制不能交给 Prompt。

必须在检索层、服务层和数据层完成。

4. 可追踪

企业系统通常需要审计：

  • 谁问了什么问题。
  • 检索到了哪些文档。
  • 模型生成了什么回答。
  • 回答引用了哪些来源。
  • 是否命中了敏感内容。
  • 是否发生了拒答。

这些信息对问题复盘和合规都很重要。

三、先定义系统边界

我们先设计一个内部文档问答系统。

它支持：

  1. 接入 Markdown、PDF、HTML 或企业文档平台导出的文本。
  2. 构建企业文档向量索引。
  3. 用户提问时按权限检索文档。
  4. 模型只根据检索结果回答。
  5. 回答必须返回来源。
  6. 文档更新后支持增量重建。
  7. 记录检索、回答和用户行为审计日志。

暂时不做：

  • 自动修改企业文档。
  • 自动执行高风险操作。
  • 绕过权限读取文档。
  • 用 Prompt 代替权限系统。

系统目标可以写成一句话：

为企业内部用户提供一个基于权限、带来源、可审计的文档问答入口。

from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from app.config import settings


def create_chat_model(temperature: float = 0.2):
    return ChatOpenAI(
        model=settings.model_name,
        api_key=settings.openai_api_key,
        base_url=settings.openai_base_url,
        temperature=temperature,
    )


def create_embedding_model():
    return OpenAIEmbeddings(
        model=settings.embedding_model,
        api_key=settings.openai_api_key,
        base_url=settings.openai_base_url,
    )

和前面文章一样，Chat Model 和 Embedding Model 要分开。

在企业系统里，Embedding 模型的选择会影响：

  • 召回质量。
  • 多语言效果。
  • 成本。
  • 索引更新速度。
  • 向量维度和存储成本。

不要频繁更换 Embedding 模型。

因为换模型通常意味着要重建所有索引。

十一、文档清洗

企业文档经常有噪声。

例如：

  • 页眉页脚。
  • 导航菜单。
  • 版权声明。
  • 空表格。
  • 重复目录。
  • 导出的 HTML 样式文本。
  • OCR 错误。

这些内容如果直接入库，会影响检索质量。

可以先做简单清洗：

 1

def clean_text(text: str) -> str:
    lines = []

    for line in text.splitlines():
        line = line.strip()
        if not line:
            continue
        if line in {"目录", "返回顶部"}:
            continue
        lines.append(line)

    return "\n".join(lines)

清洗不是越狠越好。

制度条款、表格内容、编号标题都可能很重要。

不要为了看起来干净，把关键信息删掉。

十二、文档切分策略

企业文档切分要比个人笔记更谨慎。

因为企业文档里经常有：

  • 制度条款。
  • 操作步骤。
  • 表格。
  • FAQ。
  • 接口说明。
  • 故障处理流程。

普通固定长度切分可以作为起点。

app/documents/splitter.py：

from langchain_text_splitters import RecursiveCharacterTextSplitter


def split_documents(docs):
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=800,
        chunk_overlap=150,
        separators=["\n## ", "\n### ", "\n\n", "\n", "。", "；", "，", " ", ""],
    )

    return splitter.split_documents(docs)

这里把 Markdown 标题也放进分隔符。

对于企业文档，一个常见原则是：

尽量让一个 chunk 包含完整语义单元，而不是机械截断。

例如报销制度中：

1
2
3

一线城市住宿标准：每天不超过 600 元。
二线城市住宿标准：每天不超过 450 元。
超出标准需要部门负责人审批。

这几句话最好不要被切到不同 chunk 里。

否则用户问“超标怎么办”时，可能只召回金额，没有召回审批规则。

from app.config import settings

def create_vectorstore(chunks):
    return Chroma.from_documents(
        documents=chunks,
        embedding=create_embedding_model(),
        persist_directory=settings.chroma_persist_dir,
    )


def load_vectorstore():
    return Chroma(
        persist_directory=settings.chroma_persist_dir,
        embedding_function=create_embedding_model(),

十四、权限模型设计

企业文档问答最容易踩坑的地方是权限。

错误做法是只在 Prompt 里写：

1

不要回答用户无权查看的内容。

这不安全。

因为只要无权内容进入上下文，模型就可能泄露。

正确做法是：

1

用户身份 -> 权限集合 -> Retriever filter -> 只检索可见文档 -> Prompt

也就是说，模型根本不应该看到用户无权访问的文档。

from langchain_core.output_parsers import StrOutputParser
from app.models import create_chat_model
from app.prompts import create_enterprise_qa_prompt
from app.retrievers import create_enterprise_retriever


def format_docs(docs):
    return "\n\n".join(
        f"标题：{doc.metadata.get('title', '未命名文档')}\n"
        f"来源：{doc.metadata.get('source', 'unknown')}\n"
        f"更新时间：{doc.metadata.get('updated_at', 'unknown')}\n"
        f"内容：{doc.page_content}"
        for doc in docs
    )


def collect_citations(docs):
    citations = []
    seen = set()

    for doc in docs:
        source = doc.metadata.get("source", "unknown")
        if source in seen:
            continue

        seen.add(source)
        citations.append({
            "title": doc.metadata.get("title", "未命名文档"),
            "source": source,
            "url": doc.metadata.get("url", ""),
            "updated_at": doc.metadata.get("updated_at", "unknown"),
        })

    return citations


def answer_question(question: str, user):
    retriever = create_enterprise_retriever(user)
    docs = retriever.invoke(question)

    if not docs:
        return {
            "answer": "根据当前可访问文档无法确定。",
            "citations": [],
        }

    prompt = create_enterprise_qa_prompt()
    model = create_chat_model(temperature=0.2)
    chain = prompt | model | StrOutputParser()

    answer = chain.invoke({
        "context": format_docs(docs),
        "question": question,
    })

    return {
        "answer": answer,
        "citations": collect_citations(docs),
    }

这里没有使用一条纯 LCEL 链把 Retriever 藏起来。

原因是企业场景通常需要显式拿到 docs，用于：

  • 返回来源。
  • 写审计日志。
  • 评估召回质量。
  • 做权限检查。
  • 调试问题。

二十二、文档增量更新

企业文档会持续变化。

二十三、多租户隔离

如果系统服务多个组织或多个业务线，就要考虑多租户。

常见做法有三种。

1. 单库单 collection，通过 tenant_id 过滤

优点：简单。

缺点：权限过滤必须非常可靠。

1

filter={"tenant_id": user.tenant_id}

2. 每个租户一个 collection

优点：隔离更清晰。

缺点：管理成本更高。

1

collection_name = f"docs_{user.tenant_id}"

3. 每个租户独立向量库

优点：隔离最强。

缺点：部署和运维成本最高。

怎么选取决于：

  • 租户数量。
  • 数据敏感度。
  • 查询规模。
  • 运维能力。
  • 合规要求。

如果是强隔离场景，不要只依赖 Prompt 或简单 metadata。

二十八、常见问题

1. 为什么有权限问题？

通常是因为权限过滤发生得太晚。

如果无权文档已经进入 Prompt，模型就可能泄露。

权限必须在检索层之前或检索层中处理。

2. 为什么回答看起来对，但来源不相关？

可能是模型凭常识补全了答案。

要检查：

  • Prompt 是否要求只根据上下文回答。
  • Retriever 是否召回了正确文档。
  • format_docs 是否把来源传给了模型。
  • 回答是否真的来自引用片段。

3. 为什么更新文档后问不到新内容？

检查：

  • 文档同步是否执行。
  • 索引是否重建或增量更新。
  • 旧 chunk 是否删除。
  • metadata 是否正确。
  • 查询用户是否有权限访问新文档。

4. 是否必须用 Agent？

不一定。

企业文档问答的主链路通常是固定的：

1

权限过滤 -> 检索 -> 回答 -> 引用

这用 RAG Chain 就够了。

如果要让系统根据问题选择多个工具，例如查文档、查工单、查订单、查数据库，再考虑 Agent 或 LangGraph。

5. Prompt 能不能作为权限控制？

不能。

Prompt 只能约束模型行为，不能作为安全边界。

权限必须在系统层实现。

二十九、最佳实践

1. 权限优先

企业 RAG 的第一原则不是回答更聪明，而是不能泄露不该看的内容。

2. metadata 从一开始设计好

doc_id、tenant_id、department、visibility、updated_at、source 都会影响后续能力。

3. 索引构建和在线问答分离

不要在用户请求里加载、切分和 embedding 全部文档。

4. 回答必须带来源

没有来源的企业问答很难建立信任。

5. 调试先看 Retriever

回答错了，先看召回了什么。

不要一上来就改 Prompt。

6. 准备权限评估集

尤其要测试“无权用户是否能看到不该看的内容”。

7. 记录审计日志

至少记录用户、问题、来源、拒答状态和错误信息。

8. 不要把敏感信息写进观测系统

LangSmith、日志、metadata 都要注意脱敏。

9. 文档更新要有流程

没有同步和增量更新，RAG 系统很快会过期。

10. 固定流程优先用 Chain 或 LangGraph

不要把所有事情都交给 Agent。

文档问答主链路固定，用 RAG Chain 更稳定。

三十、总结

本文我们把个人知识库 RAG 扩展到了企业内部文档问答系统。

核心结论是：

企业文档问答不是简单把更多文档放进向量库，而是要在 RAG 链路中加入权限、metadata、引用、审计、增量更新、评估和部署运维能力。

本文重点包括：

  • 企业文档问答和个人知识库的差异在于正确、可信、可控和可追踪。
  • 系统要拆分离线索引链路和在线问答链路。
  • metadata 是企业 RAG 的基础，直接影响权限、引用、更新和审计。
  • 权限过滤必须发生在检索前或检索中，不能依赖 Prompt。
  • 回答要带来源，并尽量包含标题、路径、URL 和更新时间。
  • 文档更新需要稳定 doc_id 和 chunk_id，否则难以增量维护。
  • 多租户场景要根据隔离要求选择 collection、向量库或 filter 策略。
  • LangSmith、审计日志和评估集可以帮助系统持续改进。
  • 企业上线前要关注部署、监控、灰度、隐私和合规。
