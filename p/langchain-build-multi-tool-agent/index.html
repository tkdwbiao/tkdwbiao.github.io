LangChain 实战：构建一个多工具 Agent 智能助手

2025-10-07 10:00
阅读时长: 14 分钟

前面几篇文章里，我们已经把 Agent 的关键概念拆开讲了一遍。

我们知道：

  • Agent 不是神秘魔法，而是模型、工具和执行循环的组合。
  • Tool Calling 让模型可以生成结构化工具调用请求。
  • ReAct Agent 会在推理、行动和观察之间循环。

这一篇我们把这些内容串起来，构建一个更接近真实应用的多工具 Agent 智能助手。

一、前言

只会调用一个工具的 Agent，更多是概念演示。

真实应用里的助手通常需要多个能力。

例如一个企业内部助手，用户可能这样问：

1

订单 1001 现在到哪里了？

也可能问：

1

公司差旅报销标准是什么？

还可能问：

1

帮我计算一下 12873 乘以 9831。

这些问题需要不同工具：

用户问题可能使用的工具
查订单订单查询工具
查物流物流查询工具
查制度知识库检索工具
做计算计算工具

如果用固定 Chain，每类问题都要写分支。

而多工具 Agent 的目标是：

让模型根据用户问题，自主选择合适工具，必要时多步调用，最后组织回答。

本文会实现一个本地多工具 Agent demo。

它包含：

  1. 计算工具。
  2. 订单查询工具。
  3. 物流查询工具。
  4. 知识库检索工具。
  5. 一个统一 Agent 入口。
  6. 调试中间工具调用的方法。
  7. 多工具 Agent 的问题和最佳实践。

from langchain_core.tools import tool


@tool
def multiply(a: int, b: int) -> int:
    """Multiply two integers."""
    return a * b


@tool
def add(a: int, b: int) -> int:
    """Add two integers."""
    return a + b

为什么计算也要做成工具？

因为模型虽然能做简单计算，但大数计算不稳定。

例如：

1

12873 * 9831

让模型直接心算，可能出现错误。

交给工具更可靠。

@tool
def get_order_status(order_id: str) -> dict:
    """Get order status, shipping company, and tracking number by order id."""
    order_id = str(order_id).strip()

    if not order_id:
        return {"error": "订单号不能为空"}

    return ORDERS.get(order_id, {"error": "订单不存在"})


@tool
def get_shipping_status(tracking_no: str) -> dict:
    """Get shipping status by tracking number."""
    tracking_no = str(tracking_no).strip()

    if not tracking_no:
        return {"error": "物流单号不能为空"}

    return SHIPPING.get(tracking_no, {"error": "物流单号不存在"})

这里有一个原则：

工具返回值要清晰、简洁、面向模型理解。

不要把内部系统一大段复杂 JSON 原样返回给模型。

更好的工具返回是：

1
2
3
4
5

{
    "status": "已发货",
    "shipping_company": "顺丰",
    "tracking_no": "SF123456"
}

这样模型更容易基于结果回答。

工具函数签名要写对，否则示例代码无法运行。

# RAG

RAG 是 Retrieval-Augmented Generation，也就是检索增强生成。

它的基本流程是：先根据用户问题从知识库中检索相关资料，再把资料放入 Prompt，最后让模型基于资料生成回答。

RAG 适合解决大模型缺少私有知识、最新知识和可追溯来源的问题。

import os
from pathlib import Path
from dotenv import load_dotenv
from langchain_community.document_loaders import DirectoryLoader, TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma

load_dotenv()

DOCS_DIR = "data/docs"
PERSIST_DIR = "data/chroma_db"


def create_embeddings():
    return OpenAIEmbeddings(
        model=os.getenv("EMBEDDING_MODEL", "text-embedding-3-small"),
        api_key=os.getenv("OPENAI_API_KEY"),
        base_url=os.getenv("OPENAI_BASE_URL") or None,
    )


def build_vectorstore_if_needed():
    if Path(PERSIST_DIR).exists():
        return

    loader = DirectoryLoader(
        DOCS_DIR,
        glob="**/*.md",
        loader_cls=TextLoader,
        loader_kwargs={"encoding": "utf-8"},
    )

    docs = loader.load()

    splitter = RecursiveCharacterTextSplitter(
        chunk_size=600,
        chunk_overlap=100,
        separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
    )

    chunks = splitter.split_documents(docs)

    Chroma.from_documents(
        documents=chunks,
        embedding=create_embeddings(),
        persist_directory=PERSIST_DIR,
    )


def load_retriever():
    build_vectorstore_if_needed()

    vectorstore = Chroma(
        persist_directory=PERSIST_DIR,
        embedding_function=create_embeddings(),
    )

    return vectorstore.as_retriever(search_kwargs={"k": 3})

这个模块做了两件事：

  1. 如果本地还没有向量库，就构建一个。
  2. 返回一个 Retriever，供工具调用。

学习阶段这样写比较方便。

生产环境更推荐把构建索引和在线查询拆开。

from knowledge_base import load_retriever

retriever = load_retriever()


@tool
def search_knowledge_base(query: str) -> str:
    """Search the knowledge base for RAG concepts and company travel reimbursement policy."""
    docs = retriever.invoke(query)

    if not docs:
        return "没有检索到相关资料。"

    return "\n\n".join(
        f"来源：{doc.metadata.get('source', 'unknown')}\n{doc.page_content}"
        for doc in docs
    )

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain.agents import create_agent
from tools import (
    add,
    multiply,
    get_order_status,
    get_shipping_status,
    search_knowledge_base,
)

load_dotenv()

model = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
    temperature=0,
)

tools = [
    add,
    multiply,
    get_order_status,
    get_shipping_status,
    search_knowledge_base,
]

agent = create_agent(
    model=model,
    tools=tools,
    system_prompt="""
你是一个企业智能助手，可以帮助用户查询订单、查询物流、检索知识库和完成简单计算。

规则：
1. 订单相关问题必须先调用 get_order_status。
2. 如果订单已发货且有物流单号，可以继续调用 get_shipping_status。
3. 公司制度、RAG、LangChain 相关问题应调用 search_knowledge_base。
4. 数学计算应使用 add 或 multiply，不要心算。
5. 最终回答必须基于工具返回结果，不要编造工具中没有的信息。
6. 如果信息不足，请说明无法确定，并提示用户补充必要信息。
""",
)

这里的 system prompt 很关键。

多工具 Agent 如果没有清晰规则，容易出现：

  • 不调用工具。
  • 调错工具。
  • 工具结果和回答不一致。
  • 对缺失信息强行猜测。

            print_debug_messages(result)

这个 demo 已经具备多工具 Agent 的基本形态。

十四、多工具 Agent 的执行过程

以这个问题为例：

1

订单 1001 发货了吗？现在物流到哪里了？

Agent 可能执行：

1
2
3
4
5
6
7

1. 判断这是订单问题。
2. 调用 get_order_status(order_id="1001")。
3. 工具返回已发货、物流单号 SF123456。
4. 判断用户还问了物流状态。
5. 调用 get_shipping_status(tracking_no="SF123456")。
6. 工具返回当前物流状态。
7. 模型组织最终回答。

如果用户问：

1

一线城市住宿标准是多少？

Agent 可能执行：

1
2
3
4

1. 判断这是公司制度问题。
2. 调用 search_knowledge_base(query="一线城市住宿标准")。
3. 工具返回差旅报销制度片段。
4. 模型基于资料回答。

如果用户问：

1

12873 乘以 9831 是多少？

Agent 可能执行：

1
2
3
4

1. 判断这是计算问题。
2. 调用 multiply(a=12873, b=9831)。
3. 工具返回结果。
4. 模型回答。

这就是多工具 Agent 的核心：

同一个入口，根据问题选择不同工具。

十五、工具数量越多越好吗？

不是。

工具越多，Agent 的选择空间越大，也越容易出错。

常见问题包括：

  • 该调用工具时没调用。
  • 调用了相似但错误的工具。
  • 参数填错。
  • 工具调用顺序不合理。
  • 多次重复调用工具。

所以多工具 Agent 要遵循一个原则：

工具数量要够用，但不要堆砌。

初期建议只给 Agent 3 到 5 个高质量工具。

等链路稳定后再扩展。

十六、工具职责要避免重叠

不要同时给 Agent 这些工具：

1
2
3
4

query_order
get_order
search_order
find_order_status

如果它们作用相近，模型很难选择。

更好的方式是：

1
2
3
4
5

get_order_status：查询订单状态
get_shipping_status：查询物流状态
search_knowledge_base：检索知识库
multiply：乘法计算
add：加法计算

每个工具职责清晰，模型更容易判断。

十七、什么时候应该拆工具？

工具太粗会让模型难以控制。

例如：

1
2
3

@tool
def business_api(action: str, payload: dict) -> dict:
    ...

这看似灵活，但模型需要同时决定 action 和 payload，错误空间很大。

更推荐拆成多个明确工具：

1
2
3

get_order_status(order_id: str)
get_shipping_status(tracking_no: str)
create_support_ticket(title: str, description: str)

但也不要拆得太碎。

如果一个任务必须连续调用三个几乎固定的内部函数，可以在工具内部封装成一个更高层工具。

工具粒度要围绕用户意图设计，而不是围绕数据库表设计。

十八、错误处理

工具可能失败。

例如：

1

return {"error": "订单不存在"}

系统提示中要告诉模型如何处理错误：

1

如果工具返回 error 字段，请向用户说明问题，不要编造结果。

也可以在工具返回中提供更明确的信息：

1
2
3
4
5

{
    "success": False,
    "error": "订单不存在",
    "suggestion": "请确认订单号是否正确"
}

这样模型更容易给出友好回答。

十九、安全和权限

多工具 Agent 更容易触达多个系统，所以安全边界更重要。

1. 权限不要交给模型

不能只靠 Prompt 说：

1

如果用户没有权限，请不要查询。

权限必须在工具内部或后端服务中校验。

2. 写操作要确认

本文 demo 都是读取类工具和计算工具。

如果加入写操作，例如：

  • 创建工单。
  • 发送邮件。
  • 发起退款。
  • 修改订单。

必须增加确认流程。

3. 工具参数要校验

模型生成的参数仍然是不可信输入。

工具侧要检查：

  • 是否为空。
  • 格式是否正确。
  • 是否属于当前用户权限范围。
  • 是否超过业务限制。

4. 不要返回敏感信息

工具返回给模型的数据要最小化。

不需要的字段不要返回。

尤其是：

  • token。
  • 密码。
  • 身份证号。
  • 手机号。
  • 内部权限字段。

二十、如何评估多工具 Agent？

不要只试一两个问题。

应该准备一组评估用例。

例如：

问题期望工具期望结果
订单 1001 发货了吗get_order_status返回已发货
订单 1001 到哪里了get_order_status + get_shipping_status返回物流状态
一线城市住宿标准search_knowledge_base返回 600 元
RAG 的流程是什么search_knowledge_base返回 RAG 流程
12873 乘以 9831multiply返回正确结果
订单 9999 状态get_order_status说明订单不存在

评估时关注：

  • 是否调用了正确工具。
  • 参数是否正确。
  • 是否多调或漏调工具。
  • 工具错误时回答是否合理。
  • 最终回答是否忠于工具结果。

多工具 Agent 的质量，不只是最终回答对不对，还包括过程是否可靠。

二十一、从 demo 到真实项目

本文 demo 是本地脚本。

真实项目通常还要增加：

1. API 服务

用 FastAPI 包装：

1
2
3
4

POST /chat
{
  "message": "订单 1001 发货了吗？"
}

返回：

1
2
3
4

{
  "answer": "...",
  "tool_calls": [...]
}

2. 用户身份上下文

工具需要知道当前用户是谁。

但用户身份不应该由模型生成。

应该由系统注入。

3. 日志和观测

记录：

  • 请求 ID。
  • 用户 ID。
  • 工具调用。
  • 工具参数。
  • 工具结果。
  • 模型输出。
  • 总耗时。

后续可以接入 LangSmith 做链路观测。

4. 权限和审计

企业应用必须考虑：

  • 用户能访问哪些工具。
  • 用户能访问哪些数据。
  • 哪些操作需要确认。
  • 操作日志保存多久。

5. 状态管理

如果任务跨多轮对话，需要保存：

  • 历史消息。
  • 已查询结果。
  • 用户确认状态。
  • 当前任务阶段。

这类复杂状态管理，后续可以用 LangGraph 更好地实现。

二十二、常见问题

1. Agent 为什么没有调用知识库工具？

可能是工具描述不够清楚。

把描述写得更具体：

1
2
3
4

@tool
def search_knowledge_base(query: str) -> str:
    """Search the knowledge base for RAG concepts, LangChain notes, and company travel reimbursement policy."""
    ...

同时在 system prompt 中明确哪些问题应该调用该工具。

2. Agent 为什么查订单后不查物流？

检查订单工具返回是否包含 tracking_no。

如果工具返回不清楚，模型不知道下一步需要物流单号。

3. Agent 为什么计算不用工具？

系统提示中明确：

1

数学计算应使用 add 或 multiply，不要心算。

也可以把工具描述写清楚。

4. 多工具 Agent 是否一定比 RAG Chain 好？

不是。

如果你的应用只是知识库问答，RAG Chain 更简单、更稳定。

多工具 Agent 适合需要在多个能力之间动态选择的场景。

5. 工具调用结果能直接展示给用户吗？

不一定。

有些工具结果适合展示，例如物流状态。

有些工具结果是内部结构，需要模型整理后再展示。

敏感字段不要展示，也不要交给模型。

二十三、最佳实践

1. 先做小工具集

从 3 到 5 个工具开始。

不要一开始就给 Agent 十几个工具。

2. 工具命名要明确

使用：

1
2
3

get_order_status
get_shipping_status
search_knowledge_base

避免：

1
2
3

query
process
handle

3. 工具返回结构要稳定

字段名不要频繁变化。

模型和下游逻辑都依赖这些结构。

4. 打印中间消息

多工具 Agent 出错时，先看中间步骤。

不要只看最终回答。

5. 明确工具使用规则

系统提示中告诉模型：

  • 哪类问题用哪个工具。
  • 工具失败时如何回答。
  • 不要编造工具结果中没有的信息。

6. 工具侧做安全控制

权限、参数校验、审计，都要在工具层或后端服务完成。

7. 固定流程不用强行 Agent 化

如果流程固定，用普通代码和 Chain 更稳定。

Agent 适合不确定的工具选择和多步任务。

二十四、总结

本文我们构建了一个多工具 Agent 智能助手。

它可以根据用户问题选择不同工具：

1
2
3
4

计算问题 -> add / multiply
订单问题 -> get_order_status
物流问题 -> get_shipping_status
知识库问题 -> search_knowledge_base

核心结论是：

多工具 Agent 的价值在于让模型在多个外部能力之间做选择，但工具越多，越需要清晰的工具设计、提示约束、调试日志和安全边界。

  • 如何定义计算工具、订单工具、物流工具和知识库工具。

  • 如何使用 create_agent 创建多工具 Agent。
  • 如何通过 system prompt 约束工具使用规则。
  • 如何打印中间消息调试工具调用过程。
