RAG 解决的是“模型如何使用外部知识”的问题。

但真实应用里，模型经常不只是需要读资料，还需要做动作：查数据库、调用 API、计算结果、搜索信息、创建工单、发送通知、分析文件。

这时就进入了 Agent 的范围。

一、前言

很多人第一次听到 Agent，会觉得它很神秘。

好像只要把模型叫做 Agent，它就能自动规划任务、调用工具、完成复杂工作。

但工程上不能这么理解。

更实用的理解是：

Agent 是一种让大模型根据任务目标，自主决定是否调用工具、调用哪个工具、如何使用工具结果继续推进任务的应用模式。

普通 LLM 应用更像这样：

1

6

用户问题
  ↓
Prompt
  ↓
LLM
  ↓
回答

  ↓
LLM 判断下一步
  ↓
调用工具
  ↓
观察工具结果
  ↓
继续判断
  ↓
最终回答或完成任务

二、为什么需要 Agent？

先看一个普通聊天模型能做什么。

如果你问：

1

帮我总结一下 RAG 的流程。

模型可以直接回答。

因为这是语言生成任务。

但如果你问：

1

帮我查询订单 20250929001 的物流状态。

模型自身并不知道你的订单系统。

它不能凭空知道：

  • 订单是否存在。
  • 物流单号是什么。
  • 当前运输到哪里。
  • 是否已经签收。

这时模型需要调用外部系统。

再比如你问：

1

计算 12873 * 9831，然后根据结果判断是否超过一亿。

模型可以尝试心算，但不一定可靠。

更稳妥的方式是调用计算工具。

所以 Agent 的核心价值不是让模型“更会聊天”，而是让模型能：

在需要时使用外部工具，弥补自身能力边界。

三、普通 Chain 和 Agent 的区别

前面我们写过很多 Chain。

例如：

1

chain = prompt | model | parser

这个链路是固定的。

输入来了以后，总是按同样步骤执行：

1

Prompt -> Model -> Parser

RAG Chain 也是固定的：

1

Question -> Retriever -> Context -> Prompt -> Model -> Answer

Agent 不一样。

Agent 的路径不是完全固定的。

它会根据当前任务决定下一步。

例如用户问：

1

帮我查一下订单 1001 的状态，如果已经发货，告诉我物流公司。

Agent 可能会执行：

1
2
3
4
5
6
7

1. 判断需要查询订单。
2. 调用 get_order_status(order_id="1001")。
3. 观察订单状态为已发货。
4. 判断还需要查询物流。
5. 调用 get_shipping_info(order_id="1001")。
6. 观察物流公司为顺丰。
7. 组织最终回答。

所以可以这样对比：

类型执行路径适合场景
Chain预先固定稳定流程、明确步骤
Agent模型动态决定需要工具选择、步骤不固定

这也是 Agent 强大的地方，也是它更难控制的地方。

四、Agent 的核心组成

一个基础 Agent 通常包含四部分：

1. 模型

模型负责理解任务、决定是否调用工具、生成最终回答。

在 LangChain 中常用：

1
2
3

from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

Agent 场景通常建议先用低温度：

1

temperature=0

因为工具调用更需要稳定和可控。

2. 工具

工具是模型可以调用的外部能力。

例如：

  • 计算器。
  • 搜索接口。
  • 数据库查询。
  • 订单系统 API。
  • 天气 API。
  • 文件读取。
  • RAG Retriever。
  • 代码执行环境。

工具通常有：

返回结果

3. 提示词

提示词告诉模型：

  • 它的角色是什么。
  • 有哪些工具可用。
  • 什么时候应该调用工具。
  • 如何根据工具结果回答。

在现代 Tool Calling 模式下，工具 schema 会由模型接口接收，Prompt 不需要手写所有工具格式。

但仍然需要给模型明确任务边界。

4. 执行循环

Agent 不是只调用一次模型。

它通常会循环：

1
2
3
4
5
6
7
8
9

模型思考下一步
  ↓
如果需要工具，调用工具
  ↓
把工具结果交还模型
  ↓
模型继续判断
  ↓
直到输出最终答案

这就是 Agent 的基本运行机制。

五、Tool 是什么？

Tool 可以理解为：

暴露给模型调用的函数。

普通函数是给程序员调用的。

Tool 是给模型调用的。

例如一个普通函数：

1
2

def multiply(a: int, b: int) -> int:
    return a * b

把它变成工具后，模型就可以在需要计算乘法时调用它。

在 LangChain 中可以用 @tool 装饰器：

1
2
3
4
5
6
7

from langchain_core.tools import tool


@tool
def multiply(a: int, b: int) -> int:
    """Multiply two integers."""
    return a * b

这里的 docstring 很重要。

它会告诉模型这个工具是做什么的。

但不要写得太复杂。

工具描述应该清楚说明：

  • 什么时候用。
  • 输入是什么。
  • 返回什么。

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

load_dotenv()


@tool
def multiply(a: int, b: int) -> int:
    """Multiply two integers."""
    return a * b


model = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
    temperature=0,
)

model_with_tools = model.bind_tools([multiply])

response = model_with_tools.invoke("12873 乘以 9831 是多少？")

print(response)
print(response.tool_calls)

如果模型决定调用工具，response.tool_calls 中会包含工具调用信息。

例如类似：

1
2
3
4
5
6

        "name": "multiply",
        "args": {"a": 12873, "b": 9831},
        "id": "call_xxx",
    }
]

注意，这一步只是让模型生成工具调用请求。

真正执行工具，还需要后续逻辑处理。

LangChain 的 Agent 会帮我们组织这个循环。

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langchain.agents import create_agent

load_dotenv()


@tool
def multiply(a: int, b: int) -> int:
    """Multiply two integers."""
    return a * b


@tool
def add(a: int, b: int) -> int:
    """Add two integers."""
    return a + b


model = ChatOpenAI(
    model=os.getenv("MODEL_NAME", "gpt-4o-mini"),
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL") or None,
    temperature=0,
)

agent = create_agent(
    model=model,
    tools=[multiply, add],
    system_prompt="你是一个严谨的计算助手。需要计算时请使用工具，不要心算。",
)

result = agent.invoke({
    "messages": [
        {"role": "user", "content": "先计算 12873 乘以 9831，再加上 100。"}
    ]
})

print(result)

这个 Agent 可以根据任务决定调用：

  • multiply
  • add

并把工具结果继续用于下一步。

八、理解 Agent 输入和输出

在上面的例子中，输入是：

这和前面普通 Chain 的字符串输入不同。

Agent 更接近聊天模型的消息结构。

因为 Agent 过程中会产生多轮消息：

工具调用消息
工具结果消息
模型最终回答

最终 result 里通常也会包含消息列表。

你可以取最后一条消息作为最终回答：

messages = result["messages"]

实际项目里，建议把最终回答和中间步骤分开处理：

  • 最终回答展示给用户。
  • 中间工具调用用于日志、调试和观测。

十、Agent 的运行循环

一个典型 Agent 循环可以简化成：

  ↓
模型判断：是否需要工具？
  ↓
如果需要：生成工具调用
  ↓
执行工具
  ↓
把工具结果返回给模型
  ↓
模型继续判断或输出最终回答

用伪代码表示：

 1
 2

 4
 5
 6
 7
 8
 9
10

14

messages = [user_message]

while True:
    ai_message = model.invoke(messages)
    messages.append(ai_message)

    if not ai_message.tool_calls:
        break

    for tool_call in ai_message.tool_calls:
        tool_result = run_tool(tool_call)
        messages.append(tool_result)

final_answer = messages[-1]

LangChain Agent 帮我们封装了这个循环。

但理解这个循环很重要。

因为出问题时，你要知道该查哪一步：

  • 模型是否生成了正确工具调用？
  • 工具是否执行成功？
  • 工具结果是否返回给模型？
  • 模型是否正确使用了工具结果？
  • 循环是否过多或提前结束？

十一、Agent 和 RAG 的关系

Agent 和 RAG 不是互斥的。

RAG 可以成为 Agent 的一个工具。

例如你有一个知识库检索函数：

1
2
3
4
5

@tool
def search_knowledge_base(query: str) -> str:
    """Search internal knowledge base for information related to the query."""
    docs = retriever.invoke(query)
    return "\n\n".join(doc.page_content for doc in docs)

然后交给 Agent：

1
2
3
4
5

agent = create_agent(
    model=model,
    tools=[search_knowledge_base, get_order_status],
    system_prompt="你是企业助手。需要资料时搜索知识库，需要订单信息时查询订单工具。",
)

这样 Agent 可以根据问题决定：

  • 问制度、文档、说明：调用知识库检索。
  • 问订单状态：调用订单工具。
  • 问计算问题：调用计算工具。
  • 普通闲聊：直接回答。

这也是 Agent 比单一 RAG 更灵活的地方。

但也意味着系统更难调试。

十二、什么时候适合用 Agent？

Agent 适合这些场景：

1. 工具选择不固定

例如用户可能问：

1

查一下这个客户最近的订单，如果有未付款订单，提醒我应该发什么消息。

可能需要：

  • 查客户信息。
  • 查订单列表。
  • 判断订单状态。
  • 生成提醒话术。

步骤不是固定的一条链。

2. 任务需要多步推理和行动

例如：

1

帮我分析这个项目的构建失败原因，并给出修复建议。

可能需要：

  • 查看日志。
  • 搜索错误信息。
  • 读取配置。
  • 判断依赖版本。
  • 输出建议。

3. 用户目标比较高层

例如：

1

帮我安排一次客户回访。

背后可能包含：

  • 查询客户。
  • 查询最近沟通记录。
  • 生成回访摘要。
  • 创建日程。
  • 发送通知。

4. 需要模型决定下一步

如果流程分支很多，用固定 Chain 会很复杂。

Agent 可以把部分决策交给模型。

十三、什么时候不适合用 Agent？

Agent 不是万能方案。

有些场景更适合普通 Chain 或传统代码。

1. 流程非常固定

例如：

1

用户输入 -> 提取字段 -> 调接口 -> 返回结果

如果步骤明确，不需要模型决定下一步，普通 Chain 或直接代码更稳定。

2. 强一致事务

例如：

  • 扣款。
  • 删除数据。
  • 修改权限。
  • 发起退款。
  • 发布生产配置。

这些操作不能让模型自由决定。

即使使用 Agent，也必须加人工确认、权限控制、审计日志和幂等保护。

3. 工具结果必须 100% 精确解释

模型可能误读工具结果。

如果业务要求绝对精确，例如财务结算、法律条款执行、医疗诊断，不应该只靠 Agent 自主判断。

4. 简单问答

如果只是普通知识库问答，RAG Chain 往往比 Agent 更简单、更可控。

不要为了用 Agent 而用 Agent。

十四、Agent 工具设计原则

工具设计会直接影响 Agent 稳定性。

1. 工具名称要清晰

不好：

1
2
3

@tool
def handle(data: str) -> str:
    ...

更好：

1
2
3
4

@tool
def get_order_status(order_id: str) -> dict:
    """Get order status by order id."""
    ...

模型会根据工具名和描述判断是否使用。

2. 一个工具只做一件事

不要把工具设计成：

1
2

def do_everything(action: str, payload: dict) -> dict:
    ...

这会让模型很难稳定调用。

更好的是拆成：

  • get_order_status
  • get_shipping_info
  • create_refund_request
  • search_knowledge_base

3. 输入参数要结构化

优先使用明确参数：

1
2

def get_order_status(order_id: str) -> dict:
    ...

    ...

结构化参数更容易验证和调试。

4. 工具返回结果要简洁

工具不应该返回一大堆无关字段。

例如订单状态工具返回：

    "order_id": "1001",
    "status": "已发货",
    "shipping_company": "顺丰",
    "tracking_no": "SF123456"

比返回整个数据库行更适合模型理解。

5. 高风险工具要加确认

例如：

  • 删除文件。
  • 修改数据库。
  • 发送邮件。
  • 创建订单。
  • 发起退款。

十五、Agent 常见问题

1. Agent 不调用工具怎么办？

可能原因：

  • 工具描述不清楚。
  • Prompt 没有要求必须使用工具。
  • 用户问题看起来可以直接回答。
  • 模型能力不支持工具调用。

可以改进：

1

system_prompt="回答订单问题前必须调用 get_order_status 工具。"

或者让工具描述更明确。

2. Agent 调错工具怎么办？

检查：

  • 工具名称是否相似。
  • 工具描述是否重叠。
  • 是否给了太多工具。
  • 用户意图是否模糊。

工具越多，选择难度越高。

初期建议少量工具开始。

3. Agent 参数提取错误怎么办？

例如用户说：

1

查一下 1001

模型可能不知道 1001 是订单号还是用户 ID。

解决方式：

  • Prompt 要求缺少信息时追问。
  • 工具参数命名清晰。
  • 对工具输入做校验。
  • 在业务层限制模糊调用。

4. Agent 循环太多怎么办？

Agent 可能反复调用工具或迟迟不结束。

需要设置最大迭代次数或超时。

同时检查工具结果是否足够清楚。

如果工具返回含糊，模型可能不断尝试。

5. Agent 回答和工具结果不一致怎么办？

这很常见。

解决方向：

  • Prompt 要求严格依据工具结果。
  • 工具返回结果更结构化。
  • 对最终答案做校验。
  • 高风险场景不要让模型自由组织关键数值。

十六、Agent 的安全边界

Agent 能调用工具，也意味着它可能影响真实系统。

所以安全边界非常重要。

1. 不要把权限交给模型判断

模型不能作为权限系统。

例如：

1

如果用户没有权限，请不要查询工资。

这不够。

权限应该在工具或后端服务中强制校验。

2. 工具侧必须校验输入

即使模型生成了参数，也要当成外部输入处理。

例如：

  • 订单 ID 是否属于当前用户。
  • SQL 参数是否安全。
  • 文件路径是否在允许目录内。
  • 操作金额是否在限制范围内。

3. 高风险动作必须可审计

至少记录：

  • 谁发起的。
  • 用户原始请求。
  • Agent 调用了哪个工具。
  • 工具参数是什么。
  • 工具返回什么。
  • 最终执行结果。

4. 生产环境避免直接暴露任意执行能力

不要轻易给 Agent：

  • 任意 shell 执行。
  • 任意 SQL 执行。
  • 任意文件读写。
  • 无限制 HTTP 请求。

这些能力必须有沙箱、白名单和权限控制。

十七、Agent 和工作流的取舍

很多复杂任务看起来都可以用 Agent。

但实际工程中，经常会在 Agent 和 Workflow 之间做取舍。

Agent 更灵活

适合：

  • 步骤不固定。
  • 工具选择依赖上下文。
  • 用户目标开放。
  • 允许一定探索。

Workflow 更稳定

适合：

  • 流程明确。
  • 合规要求强。
  • 每一步都要可控。
  • 错误成本高。

例如报销审批系统，可能更适合工作流。

例如研究助手、排障助手、数据分析助手，Agent 更有发挥空间。

用图结构把 Agent 的灵活性和工作流的可控性结合起来。

from langchain_openai import ChatOpenAI

十九、最佳实践

1. 先从少量工具开始

不要一开始给 Agent 十几个工具。

工具越多，模型选择越难，调试也越难。

先用 2 到 3 个工具跑通。

2. 工具描述写清楚

工具描述是模型选择工具的重要依据。

描述不清楚，Agent 就容易不用工具或用错工具。

3. 工具函数保持小而明确

一个工具做一件事。

不要设计万能工具。

4. 对工具输入做校验

模型生成的参数不一定可靠。

工具侧必须校验。

5. 记录中间步骤

Agent 调试不能只看最终回答。

要记录：

  • 工具调用名称。
  • 工具参数。
  • 工具返回值。
  • 最终回答。

6. 高风险动作加人工确认

凡是会影响外部系统状态的动作，都要谨慎。

比如：

  • 发邮件。
  • 改数据库。
  • 删除资源。
  • 提交订单。
  • 发起支付。

先确认，再执行。

7. 不要用 Agent 替代所有代码

Agent 适合处理不确定性。

确定性的业务规则，应该写在代码里。

二十、总结

本文我们正式进入 Agent 部分。

核心结论是：

Agent 不是一个神秘魔法，而是一种让模型根据任务目标动态选择工具、观察结果并继续推进任务的应用模式。

本文重点包括：

  • 普通 Chain 的执行路径固定，Agent 的下一步可以由模型动态决定。
  • Agent 的核心组成是模型、工具、提示词和执行循环。
  • Tool 是暴露给模型调用的函数，要有清晰名称、描述和结构化参数。
  • Tool Calling 是模型生成工具调用请求的能力。
  • Agent 会在模型调用和工具执行之间循环，直到得到最终答案。
  • RAG 可以作为 Agent 的一个工具。
  • Agent 适合工具选择不固定、多步任务和开放目标。
  • 流程固定、强一致、高风险操作不一定适合直接交给 Agent。
  • 工具侧必须做权限、校验、审计和安全控制。

到这里，我们已经理解了 Agent 的基本概念。
