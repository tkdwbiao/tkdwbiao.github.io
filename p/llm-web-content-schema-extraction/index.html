大模型时代的数据采集工程 27：网页正文提取与 Schema 化抽取实战

2026-02-01 10:00
阅读时长: 13 分钟

上一篇文章里，我们讨论了 LLM 如何赋能爬虫数据抽取。

核心结论是：

1
2

LLM 不应该替代所有解析规则。
更合理的方式是：规则抽取负责稳定字段，LLM 负责复杂语义理解，Schema 和校验负责工程可靠性。

这一篇继续往实践推进。

我们会用一个安全、通用、可复现的本地示例，演示：

如何从 HTML 中提取正文。
如何把正文转换为 Markdown 或纯文本。
如何定义 Pydantic Schema。
如何让 LLM 输出结构化 JSON。
如何校验、重试和进入人工复核。

本文不依赖真实网站，也不讨论绕过访问控制、验证码或风控。

重点是：

把“LLM 看懂网页”变成一个可落地的数据抽取流程，而不是一次随意的聊天式提问。

from bs4 import BeautifulSoup


NOISE_TAGS = ["script", "style", "noscript", "nav", "footer", "aside"]


def extract_main_text(html: str) -> str:
    soup = BeautifulSoup(html, "html.parser")

    for tag in soup(NOISE_TAGS):
        tag.decompose()

    article = soup.find("article") or soup.body or soup
    text = article.get_text("\n", strip=True)
    lines = [line.strip() for line in text.splitlines() if line.strip()]
    return "\n".join(lines)

四、HTML、Markdown 和纯文本怎么选？

LLM 输入可以有三种形式。

1. HTML

优点：

1
2

保留结构。
保留链接、标题层级和表格关系。

缺点：

1
2
3

噪声多。
Token 成本高。
脚本、样式和无关标签会干扰。

适合：

1

需要理解表格、列表、链接上下文的场景。

2. Markdown

优点：

1
2
3

比 HTML 简洁。
保留一定结构。
适合标题、列表、链接、表格。

缺点：

1
2

需要转换步骤。
复杂页面转换可能丢失信息。

适合：

1

文档、文章、说明页、博客页。

3. 纯文本

优点：

1
2
3

最短。
噪声少。
成本低。

缺点：

1
2

结构信息较少。
表格和列表关系可能丢失。

适合：

1

文章正文、新闻、公告、描述性文本。

本文使用纯文本，因为示例是文章抽取。

工程中可以根据页面类型选择输入形式。

from pydantic import BaseModel, Field


class ExtractedArticle(BaseModel):
    title: str = Field(description="文章标题")
    author: str | None = Field(default=None, description="作者，没有则为 null")
    published_at: str | None = Field(default=None, description="发布日期，格式 YYYY-MM-DD")
    summary: str = Field(description="不超过 120 字的摘要")
    keywords: list[str] = Field(default_factory=list, description="3 到 6 个关键词")
    category: str = Field(description="主题分类，例如 科技、财经、教育、交通、医疗、其他")
    risks: list[str] = Field(default_factory=list, description="文中提到的风险、挑战或注意事项")
    confidence: float = Field(ge=0, le=1, description="抽取置信度")

Schema 解决的问题是：

能不能自动校验。

它让 LLM 抽取从“文字回答”变成“结构化数据生产”。

def build_prompt(text: str) -> str:
    return f"""
你是数据采集系统中的结构化抽取助手。
请根据输入文本抽取文章信息。

要求：
1. 只能基于输入文本抽取，不要编造。
2. 如果字段不存在，返回 null 或空列表。
3. published_at 必须尽量使用 YYYY-MM-DD 格式。
4. summary 不超过 120 个中文字符。
5. keywords 输出 3 到 6 个。
6. category 只能从：科技、财经、教育、交通、医疗、其他 中选择。
7. risks 只提取文本中明确提到的风险、挑战或注意事项。
8. 只输出 JSON，不要输出 Markdown 或解释文字。

输出 JSON 字段：
- title
- author
- published_at
- summary
- keywords
- category
- risks
- confidence

输入文本：
{text}
""".strip()

这里有几个重点。

第一，要求只能基于输入。

1

避免模型补充背景知识。

第二，限制枚举。

1

category 只能从给定列表选择。

第三，只输出 JSON。

1

减少解析难度。

第四，说明字段缺失怎么处理。

1

不要让模型为了完整而编造。

import json
from pydantic import ValidationError


def parse_extraction(raw_output: str) -> ExtractedArticle | None:
    try:
        data = json.loads(raw_output)
        return ExtractedArticle.model_validate(data)
    except (json.JSONDecodeError, ValidationError):
        return None

ALLOWED_CATEGORIES = {"科技", "财经", "教育", "交通", "医疗", "其他"}


def validate_business_rules(item: ExtractedArticle) -> list[str]:
    errors = []

    if not item.title.strip():
        errors.append("title_empty")

    if len(item.summary) > 120:
        errors.append("summary_too_long")

    if item.category not in ALLOWED_CATEGORIES:
        errors.append("invalid_category")

    if not 3 <= len(item.keywords) <= 6:
        errors.append("invalid_keywords_count")

    if item.confidence < 0.6:
        errors.append("low_confidence")

    return errors

十、重试策略

LLM 抽取失败可以重试，但要有限。

常见失败类型：

3

重试策略可以是：

1
2
3
4

JSON 解析失败：用更严格 Prompt 重试一次。
模型超时：延迟后重试一次。
低置信度：不重试，进入人工复核。
业务规则失败：根据错误类型决定。

示例决策：

1
2
3
4
5

def should_retry(error_type: str, retry_count: int) -> bool:
    if retry_count >= 1:
        return False

    return error_type in {"json_decode_error", "model_timeout"}

重试不是为了掩盖质量问题。

它只处理临时或格式类问题。

对于内容不确定，人工复核更可靠。

def run_extraction(task_id: str, html: str) -> ExtractionStatus:
    text = extract_main_text(html)
    prompt = build_prompt(text)

    raw_output = call_llm(prompt)
    item = parse_extraction(raw_output)

    if item is None:
        if should_retry("json_decode_error", retry_count=0):
            schedule_retry(task_id)
            return ExtractionStatus.RETRYING

        save_review_case(task_id, text, raw_output, "parse_failed")
        return ExtractionStatus.REVIEW_REQUIRED

    errors = validate_business_rules(item)
    if errors:
        save_review_case(task_id, text, raw_output, ",".join(errors))
        return ExtractionStatus.REVIEW_REQUIRED

    save_extraction_result(task_id, item)
    return ExtractionStatus.SUCCEEDED

十六、常见错误写法

1. 整页 HTML 直接丢给模型

这会增加成本和噪声。

应先做正文提取和清洗。

2. 不定义 Schema

没有 Schema，输出就难以入库和校验。

3. 只看模型回答是否“像样”

工程系统需要 JSON 解析、类型校验和业务规则校验。

4. 不处理低置信度

低置信度结果不应该直接入库。

5. 无限重试

LLM 调用有成本。

格式失败可以有限重试，内容不确定应人工复核。

6. 不记录模型版本

模型和 Prompt 变化会影响输出。

应记录模型版本、Prompt 版本和 content_hash。

7. 忽略隐私和敏感信息

输入模型前应脱敏，不要发送 Token、Cookie、手机号等敏感内容。

十七、面试表达

如果面试官问：

1

你怎么做网页正文抽取？

可以这样回答：

我会先用 BeautifulSoup 或解析规则去掉 script、style、nav、footer、aside 等噪声标签，再优先提取 article、main 或正文候选区域，转成干净文本或 Markdown。这样可以减少输入长度和噪声，再根据页面类型决定是否交给 LLM 做进一步结构化抽取。

如果问：

1

Schema 化抽取怎么做？

可以这样回答：

我会先用 Pydantic 定义目标 Schema，比如 title、author、published_at、summary、keywords、category、confidence。Prompt 要求模型只输出 JSON，字段缺失返回 null。输出后先做 JSON 解析，再做 Pydantic 校验和业务规则校验，只有通过后才入库。

如果问：

1

LLM 输出不稳定怎么办？

可以这样回答：

我会从四个层面处理：第一，输入清洗，减少噪声；第二，Prompt 明确字段、格式、枚举和禁止编造；第三，Schema 和业务规则校验；第四，失败分类、有限重试和人工复核。不会直接把模型输出当成可信结果。

如果问：

1

怎么判断是否需要人工复核？

可以这样回答：

低置信度、JSON 解析失败、Schema 校验失败、业务规则不满足、字段缺失严重或输入疑似异常页面时，都应该进入人工复核。复核结果可以反过来优化 Prompt、正文清洗规则和 Schema。

如果问：

1

LLM 抽取如何落到爬虫系统里？

可以这样回答：

我会把 LLM 抽取做成独立 Worker，抓取 Worker 先保存 HTML 或正文，抽取 Worker 异步读取内容，调用模型生成 JSON，校验后入库或进入复核队列。这样可以单独限流、监控成本和延迟，也不会阻塞抓取主流程。

十八、总结

本文用一个本地示例讲了网页正文提取与 Schema 化抽取流程。

核心结论包括：

  • LLM 抽取不应该从整页 HTML 直接开始，而应先做正文提取和清洗。
  • HTML、Markdown 和纯文本各有适用场景，文章正文通常可以使用清洗后的纯文本。
  • Schema 是结构化抽取的核心，建议用 Pydantic 定义字段、类型和约束。
  • Prompt 要明确角色、字段、格式、枚举、缺失处理和禁止编造。
  • LLM 输出必须经过 JSON 解析、Pydantic 校验和业务规则校验。
  • Schema 校验保证类型正确，业务规则校验保证内容合理。
  • LLM 抽取失败要分类处理，格式类错误可以有限重试，低置信度应人工复核。
  • 人工复核记录可以反向优化 Prompt、正文清洗规则和 Schema。
  • 结果入库时建议保存 content_hash、模型版本、Prompt 版本和 confidence。
  • LLM 抽取任务也应该有状态机，便于恢复、重试和监控。
  • 质量监控要关注成功率、解析失败率、Schema 校验失败率、人工复核比例、延迟和成本。
  • 面试表达要突出“正文提取 + Schema + 校验 + 复核 + 监控”的工程闭环。
