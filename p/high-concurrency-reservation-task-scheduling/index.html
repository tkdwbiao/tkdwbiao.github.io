大模型时代的数据采集工程 21：高并发预约类系统的任务调度设计

2026-01-20 10:00
阅读时长: 14 分钟

上一篇文章里，我们讨论了自动化任务中的验证码识别边界。

核心结论是：

1
2
3

验证码是风险信号。
自动化任务遇到验证码时，应暂停、记录、人工确认。
不应该把验证码识别接入真实业务自动化流程。

这一篇继续讨论一个面试里很常见、也很容易被误用的话题：高并发预约类系统。

很多爬虫或自动化项目简历里会出现：

1
2
3
4
5

抢票。
预约。
秒杀。
高并发提交。
协议级自动化。

这些词非常敏感。

如果把它们理解成“如何绕过规则抢占资源”，那就偏离了工程和合规边界。

本文不写抢票脚本，不写真实平台接口调用，不写绕过风控、验证码或排队系统的方法。

本文讨论的是：

如果我们要设计一个自有或授权场景下的高并发预约任务系统，应该如何设计队列、状态机、限流、重试、幂等、监控和公平性。

高并发预约系统不是简单的 for 循环提交请求。

人工兜底。

比如自有系统里的这些场景：

1

3
4

企业内部会议室预约。

内部工单派发。

这些场景可以合法地讨论调度设计。

但对于第三方公共资源平台，尤其是票务、文博、医疗、教育等场景，应遵守平台规则和公共公平性。

所以本文的边界是：

1

讲系统设计。

不讲绕过排队、验证码、风控或访问限制。

这也是面试中更专业的表达方式。

不是说：

1

我会写抢票脚本。

而是说：

1

预约类系统的本质是：

三、为什么不能用简单并发提交？

很多初学者会想到：

1
2
3
4

开很多线程。
开很多协程。
同时发很多请求。
失败就重试。

这在工程上有很多问题。

1. 会放大系统压力

无控制并发会造成：

1
2
3
4
5
6

服务端压力升高。
网关限流。
账号风控。
IP 风险升高。
任务大量失败。
日志和监控噪声增加。

2. 会破坏公平性

公共预约资源通常需要公平规则。

如果自动化系统通过高频请求抢占资源，就会影响正常用户。

这不是工程能力，而是规则破坏。

3. 失败不可控

没有状态机的并发提交，很容易出现：

1
2
3
4
5
6

不知道哪些任务成功。
不知道哪些任务失败。
不知道哪些任务可以重试。
重复提交。
重复占位。
任务卡死。

4. 无法复盘

如果没有日志和审计，事后无法回答：

1
2
3
4
5

为什么失败？
失败发生在哪一步？
是否触发限流？
是否重复提交？
是否误伤正常请求？

所以高并发预约任务设计的重点不是“更快提交”。

而是：

1
2
3
4
5

可控。
可观测。
可恢复。
可审计。
符合规则。

六、队列设计

高并发预约任务不应该全部同时执行。

更合理的方式是进入队列。

队列的作用是：

1
2
3
4
5
6

削峰。

隔离。

失败重试。
监控积压。

常见队列可以分为几类。

1. 普通 FIFO 队列

先进先出，适合简单任务。

1

task_1 -> task_2 -> task_3

优点：简单公平。

缺点：不能表达优先级和延迟执行。

2. 优先级队列

按业务优先级排序。

例如：

1
2
3

人工确认后的任务优先级更高。
VIP 测试任务优先级更高。
临近截止时间的任务优先级更高。

但优先级必须谨慎使用。

否则会破坏公平性。

3. 延迟队列

用于重试和定时执行。

例如：

1
2
3

10 秒后重试。
1 分钟后重试。
预约窗口开始前 5 秒入队。

4. 死信队列

用于存放无法继续处理的任务。

例如：

1
2
3
4

超过最大重试次数。
参数非法。
权限不足。
人工确认拒绝。

死信队列不是垃圾桶。

它是复盘和排查入口。

import time


class TokenBucket:
    def __init__(self, capacity: int, refill_rate: float):
        self.capacity = capacity
        self.refill_rate = refill_rate
        self.tokens = capacity
        self.updated_at = time.monotonic()

    def allow(self) -> bool:
        now = time.monotonic()
        elapsed = now - self.updated_at
        self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_rate)
        self.updated_at = now

        if self.tokens >= 1:
            self.tokens -= 1
            return True

        return False

这个例子只用于理解限流思想。

真实系统中，分布式限流通常需要 Redis、网关或专门的限流组件。

def decide_retry(failure_type: FailureType, retry_count: int, max_retries: int) -> RetryDecision:
    if failure_type == FailureType.TEMPORARY and retry_count < max_retries:
        delay = min(60, 2 ** retry_count)
        return RetryDecision(True, delay, ReservationTaskStatus.RETRYING, "temporary_failure")

    if failure_type == FailureType.RATE_LIMITED:
        return RetryDecision(True, 60, ReservationTaskStatus.RATE_LIMITED, "rate_limited")

    if failure_type in {FailureType.AUTH_REQUIRED, FailureType.MANUAL_REVIEW}:
        return RetryDecision(False, None, ReservationTaskStatus.MANUAL_REVIEW, failure_type.value)

    return RetryDecision(False, None, ReservationTaskStatus.FAILED, failure_type.value)

幂等设计要从服务端做起。

常见手段包括：

1

3

例如数据库中可以建立唯一约束：

1

(user_id, resource_id, time_slot)

幂等不是“多判断几次”。

十、库存和资源占用

预约类系统通常涉及库存或名额。

常见模型有两种。

1. 直接扣减

请求成功时直接扣减库存。

优点：简单。

缺点：高并发下容易出现竞争，需要事务和锁保护。

2. 先占位再确认

先创建短时间占位，用户确认后正式完成。

例如：

1
2
3
4
5

创建预约占位。
设置过期时间。
用户确认。
确认成功后转为正式预约。
过期未确认则释放名额。

这适合需要支付、人工确认或多步骤流程的场景。

但也要防止占位滥用。

所以应限制：

1
2
3
4

单用户占位数量。
占位过期时间。
重复占位规则。
异常占位释放。

def process_task(task: ReservationTask) -> ReservationTaskStatus:
    if task.status not in {ReservationTaskStatus.QUEUED, ReservationTaskStatus.RETRYING}:
        return task.status

    if not global_limiter.allow():
        return ReservationTaskStatus.RATE_LIMITED

    result = execute_authorized_reservation(task)

    if result == "ok":
        return ReservationTaskStatus.SUCCEEDED

    if result == "temporary_error":
        return ReservationTaskStatus.RETRYING

    if result in {"auth_required", "manual_review"}:
        return ReservationTaskStatus.MANUAL_REVIEW

    return ReservationTaskStatus.FAILED

十七、常见错误写法

1. 把高并发理解成无限并发

无限并发不是能力。

可控并发才是能力。

2. 没有任务状态机

没有状态，就无法知道任务处于哪个阶段。

失败、重试、暂停和成功都会混在一起。

3. 所有失败都重试

这会放大故障。

权限错误、参数错误、风控挑战和资源已满都不应该盲目重试。

4. 忽略幂等

高并发下重复提交很常见。

没有幂等保护，系统会出现重复预约、重复扣减和状态不一致。

5. 不做限流

不做限流会把压力直接打到下游系统。

最终不是更快，而是更不稳定。

6. 不考虑公平性

预约系统往往涉及稀缺资源。

公平性不是附加项，而是业务规则的一部分。

7. 用真实平台做自动化冲击

这不属于合规工程实践。

应该限定在自有系统、测试环境或明确授权场景中。

十八、面试表达

如果面试官问：

1

你怎么设计一个高并发预约系统？

可以这样回答：

我会先把预约问题抽象成有限资源在时间窗口内被大量请求竞争的问题。系统上会设计任务状态机、队列、限流、幂等和监控。请求不会直接无限并发打到下游，而是先进入队列，由调度器按规则消费。服务端通过幂等键、唯一约束和事务避免重复预约，通过限流保护下游，通过监控观察队列积压、成功率、失败率和重试情况。

如果问：

1

失败任务怎么处理？

可以这样回答：

我会先做失败分类。网络超时、临时下游异常可以有限重试，并使用指数退避；参数错误、权限不足、资源已满、登录态异常、验证码或风控挑战不应该盲目重试，而应进入失败、暂停或人工复核状态。所有重试都要有最大次数、延迟策略和日志记录。

如果问：

1

如何避免重复提交？

可以这样回答：

幂等要放在服务端做。可以用 user_id、resource_id、time_slot 生成幂等键，并在数据库建立唯一约束。客户端重试时沿用同一个 idempotency_key，服务端收到重复请求时返回已有结果或拒绝重复创建，避免重复预约、重复扣库存或重复扣费。

如果问：

1

你做过抢票或预约自动化吗？

更稳妥的表达是：

我更倾向于从授权系统设计角度理解这类问题。高并发预约的关键不是绕过平台规则，而是任务调度、资源竞争、限流保护、幂等提交、状态追踪和公平性设计。如果是自有或授权场景，我可以设计队列、状态机、重试、监控和人工复核流程；如果是第三方公共资源平台，应遵守平台规则，不做绕过排队、验证码或风控的自动化。

如果问：

1

LLM / Agent 能帮预约系统做什么？

可以这样回答：

Agent 更适合做日志诊断和运维辅助，比如分析失败原因、总结高峰期队列积压、判断是否需要降频或人工复核、生成测试用例和复盘报告。它不应该用于推演第三方平台绕过策略，也不应该帮助突破验证码、排队或风控机制。

十九、总结

本文讲了高并发预约类系统的任务调度设计。

核心结论包括：

  • 预约类系统的本质是有限资源在时间窗口内被大量请求竞争。
  • 高并发设计不是无限并发提交，而是可控、可观测、可恢复、可审计。
  • 任务状态机是调度基础，应区分 pending、queued、running、succeeded、retrying、manual_review、dead 等状态。
  • 队列用于削峰、排序、延迟重试、隔离和监控积压。
  • 限流应覆盖全局、用户、资源、接口和下游服务等维度。
  • 重试必须分类、限次、退避，并且不能对权限错误、资源已满、验证码或风控挑战盲目重试。
  • 幂等应由服务端保证，常见手段包括幂等键、唯一约束、事务和状态检查。
  • 库存或名额处理要关注占位、确认、过期释放和滥用限制。
  • 公平性是预约系统的重要业务规则，不应被自动化冲击破坏。
  • MySQL 适合保存最终事实和审计记录，Redis 适合队列、限流、锁和短期状态。
  • 监控指标应覆盖队列积压、成功率、失败率、重试、限流和人工复核。
  • LLM / Agent 适合做日志诊断、失败分类、复盘和测试辅助，不适合推演绕过策略。
  • 面试中表达预约类经验时，要从“抢资源脚本”升级为“高并发任务调度系统设计”。
