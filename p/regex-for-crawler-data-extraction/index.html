大模型时代的数据采集工程 07：正则表达式在数据提取中的应用

2025-12-23 10:00
阅读时长: 15 分钟

上一篇文章里，我们讲了 XPath 与 CSS Selector。

它们解决的是：

1
2
3

如何从 HTML 结构中定位元素。
如何从标签、属性和层级关系中提取字段。
如何设计稳定、可维护的选择器。

但在真实数据采集里，还有一类问题很常见：

1
2
3
4
5
6

从一段文本里提取日期。
从价格字符串里提取金额。
从 URL 里提取 ID。
从 script 片段里提取 JSON。
从正文里提取电话、编号、标签、规格。
清理多余空白和特殊符号。

这些问题不一定适合 XPath，也不一定适合 BeautifulSoup。

这时，正则表达式就是非常重要的补充工具。

这一篇我们重点讲：

正则表达式在爬虫数据提取中的正确用法、常见场景、工程边界和面试表达。

一、前言

正则表达式很强。

但它也很容易被滥用。

爬虫初学者常见两种极端。

第一种是完全不用正则，所有东西都靠字符串切割。

例如：

1
2

text = "价格：¥ 199.00 元"
price = text.split("¥")[1].split("元")[0]

这种写法一旦格式稍微变化就容易失效。

第二种是过度依赖正则，甚至用正则硬解析整段 HTML。

例如：

1
2
3
4

import re

html = "<h1>标题</h1>"
title = re.findall(r"<h1>(.*?)</h1>", html)[0]

这在简单示例里能跑，但在真实 HTML 中很脆弱。

因为 HTML 可能有：

1
2
3
4
5
6

属性。
换行。
嵌套标签。
大小写差异。
多余空白。
不完整标签。

更合理的原则是：

1
2

HTML 结构定位优先用 BeautifulSoup、CSS Selector、XPath。
局部文本模式提取再用正则。

正则不是替代 HTML 解析器的工具。

它更适合在解析之后，对字段进行二次提取和清洗。

二、正则适合解决什么问题？

在爬虫工程中，正则适合处理这些场景：

1
2
3
4
5
6
7
8
9

日期提取。
价格提取。
数字、编号、ID 提取。
URL 参数提取。
文件扩展名提取。
文本中的标签、关键词、规格提取。
script 中局部 JSON 片段提取。
空白字符清理。
字段格式校验。

不适合优先用正则处理的场景：

1
2
3
4
5

解析完整 HTML 结构。
解析复杂嵌套 JSON。
替代 XPath / CSS Selector。
替代业务规则和 Schema 校验。
处理动态渲染问题。

可以这样理解：

1
2
3
4

选择器负责找到位置。
正则负责处理局部模式。
Schema 负责验证结构。
清洗逻辑负责统一格式。

这四层不要混在一起。

在工程代码里，finditer 更适合复杂提取。

import re


def parse_price(text: str) -> float | None:
    if "免费" in text:
        return 0.0
    if "面议" in text:
        return None

    match = re.search(r"[¥￥]?\s*([\d,]+(?:\.\d+)?)", text)
    if not match:
        return None

    return float(match.group(1).replace(",", ""))


print(parse_price("¥199.00"))
print(parse_price("免费"))
print(parse_price("价格面议"))

这体现了一个重要原则：

1
2

正则解决模式提取。
业务规则解决特殊语义。

不要为了处理所有情况写一个巨大正则。

十、贪婪与非贪婪

正则里最常见的坑之一是贪婪匹配。

示例：

1
2
3
4

import re

html = "<h1>标题一</h1><h1>标题二</h1>"
print(re.findall(r"<h1>(.*)</h1>", html))

结果可能是：

1

['标题一</h1><h1>标题二']

因为 .* 是贪婪的，会尽可能多匹配。

改成非贪婪：

1

print(re.findall(r"<h1>(.*?)</h1>", html))

输出：

1

['标题一', '标题二']

但这里仍然不推荐用正则解析 HTML 标签。

更好的方式是：

1
2
3
4
5

from bs4 import BeautifulSoup

soup = BeautifulSoup(html, "lxml")
titles = [h1.get_text(strip=True) for h1 in soup.select("h1")]
print(titles)

贪婪和非贪婪要掌握，但不要因此把正则用错场景。

import json
import re
from bs4 import BeautifulSoup

html = """
<script>
window.__INITIAL_STATE__ = {"title":"示例文章","author":"阿彪"};
</script>
"""

soup = BeautifulSoup(html, "lxml")
script_text = soup.get_text("\n")

match = re.search(r"window\.__INITIAL_STATE__\s*=\s*(\{.*?\});", script_text, re.S)

    data = json.loads(match.group(1))
    print(data)

这里的 re.S 表示让 . 也能匹配换行。

更稳的做法是：

1
2
3

能找到 application/json script，就直接 json.loads。
复杂 JS 状态提取要谨慎，必要时使用更合适的解析工具。

from dataclasses import dataclass
from urllib.parse import urljoin
import re

from bs4 import BeautifulSoup


PRICE_PATTERN = re.compile(r"[¥￥]?\s*([\d,]+(?:\.\d+)?)")
DATE_PATTERN = re.compile(r"(\d{4})年(\d{1,2})月(\d{1,2})日")


@dataclass
class ProductItem:
    title: str
    url: str
    price: float | None
    publish_date: str | None


def parse_price(text: str) -> float | None:
    if "免费" in text:
        return 0.0
    if "面议" in text:
        return None

    match = PRICE_PATTERN.search(text)
    if not match:
        return None

    return float(match.group(1).replace(",", ""))


def parse_date(text: str) -> str | None:
    match = DATE_PATTERN.search(text)
    if not match:
        return None

    year, month, day = match.groups()
    return f"{int(year):04d}-{int(month):02d}-{int(day):02d}"


def parse_products(html: str, base_url: str) -> list[ProductItem]:
    soup = BeautifulSoup(html, "lxml")
    items = []

    for card in soup.select(".product-card"):
        title_tag = card.select_one("a.title")
        price_tag = card.select_one(".price")
        date_tag = card.select_one(".date")

        if not title_tag:
            continue

        raw_price = price_tag.get_text(" ", strip=True) if price_tag else ""
        raw_date = date_tag.get_text(" ", strip=True) if date_tag else ""

        items.append(
            ProductItem(
                title=title_tag.get_text(" ", strip=True),
                url=urljoin(base_url, title_tag.get("href", "")),
                price=parse_price(raw_price),
                publish_date=parse_date(raw_date),
            )
        )

    return items

这段代码的分层是：

1
2
3

BeautifulSoup / CSS Selector：找到卡片和字段。
正则函数：清洗价格和日期。
dataclass：表达结构化结果。

这就是推荐的使用方式。

正则是字段处理工具，不是整个解析流程的全部。

十六、性能与安全：避免灾难性回溯

正则写得不好，可能带来性能问题。

例如一些复杂嵌套模式，在长文本上会出现灾难性回溯。

危险倾向包括：

1
2
3
4

多个重复量词嵌套。
过度使用 .*。
在超长 HTML 上做全局复杂匹配。
没有限定匹配范围。

工程建议：

1
2
3
4
5

先用选择器缩小范围，再用正则处理局部文本。
给输入文本长度设上限。
避免在整页 HTML 上运行复杂正则。
尽量写明确边界。
对正则函数写测试样例。

例如，不推荐在整个页面上直接：

1

re.findall(r".*价格.*", html)

更好：

1
2

price_text = card.select_one(".price").get_text(" ", strip=True)
price = parse_price(price_text)

范围越小，正则越稳定。

def test_parse_date():

    assert parse_date("暂无日期") is None

哪怕项目没有完整测试框架，也应该至少保留一组样例。

因为正则很容易在改动时影响旧格式。

十九、LLM 与正则的关系

成本低。
速度快。
可测试。
可解释。
适合格式稳定的字段。

LLM 更适合：

1
2

4
5

语义理解。
复杂非结构化文本抽取。
字段含义判断。

1

例如：

1

这也是本系列的主线：

不是让大模型替代所有规则，而是让规则、工程系统和大模型各自做擅长的事情。

二十、常见错误写法

1. 用正则解析整个 HTML

不推荐：

1

re.findall(r"<div class='item'>(.*?)</div>", html)

更推荐：

1

soup.select(".item")

HTML 是树结构，应该用解析器处理。

2. 一个正则写完所有业务

不推荐写一个巨大正则同时处理：

1

日期、价格、标题、作者、URL、状态。

更好是拆成多个小函数。

1
2
3
4

parse_date
parse_price
extract_item_id
clean_whitespace

3. 不处理 match 为 None

错误：

1

price = re.search(r"\d+", text).group()

如果不匹配会报错。

正确：

1
2

match = re.search(r"\d+", text)
price = match.group() if match else None

4. 贪婪匹配范围过大

.* 很容易匹配过多内容。

要尽量缩小范围，或者使用更明确的边界。

5. 清洗逻辑和解析逻辑混在一起

不推荐在一个函数里同时：

1
2
3
4
5

请求页面。
解析 HTML。
正则提取。
数据清洗。
入库。

应该分层。

这样才容易测试和维护。

二十一、面试表达

如果面试官问：

1

正则在爬虫里一般怎么用？

可以这样回答：

我不会用正则硬解析整个 HTML，而是先用 BeautifulSoup、XPath 或 CSS Selector 定位到具体字段，再用正则处理局部文本模式。比如从价格文本里提取金额、从日期字符串里提取时间、从 URL 路径里提取 ID、从 script 片段里提取局部 JSON。提取后还会做归一化和 Schema 校验，避免把脏数据直接入库。

如果问：

1

正则和 XPath / CSS Selector 怎么配合？

可以这样回答：

XPath 和 CSS Selector 负责定位 HTML 中的元素，正则负责处理元素文本里的局部模式。比如先用 CSS Selector 找到商品卡片和价格标签，再用正则从“￥1,299.50 元”里提取数值。这样比在整段 HTML 上用正则更稳定，也更容易维护。

如果问：

1

正则有哪些坑？

可以这样回答：

常见坑包括贪婪匹配导致范围过大、match 为空没有处理、在整页 HTML 上做复杂匹配、一个正则承担太多业务逻辑、没有测试样例，以及复杂模式导致性能问题。我的做法是先缩小输入范围，正则函数化，处理 None 情况，并为日期、价格、编号等规则保留样例测试。

如果问：

1

有了 LLM 还需要正则吗？

可以这样回答：

需要。正则适合格式稳定、可确定提取的字段，比如日期、价格、编号和 URL 参数，速度快、成本低、可解释。LLM 更适合语义理解和非结构化信息抽取。工程上我会让规则和正则处理确定性部分，让 LLM 处理语义复杂部分，最后统一用 Schema 做校验。

二十二、总结

本文讲了正则表达式在爬虫数据提取中的应用。

核心结论包括：

  • 正则适合处理局部文本模式，不适合替代 HTML 解析器。
  • HTML 结构定位优先用 BeautifulSoup、XPath、CSS Selector。
  • 日期、价格、编号、URL 路径、空白清理是正则的典型场景。
  • search 适合找第一个，findall 适合找全部，finditer 适合复杂匹配。
  • 提取后要做归一化，例如日期统一格式、价格转 float。
  • 正则函数应该预编译、函数化，并配合样例测试。
  • 不要把所有业务逻辑塞进一个巨大正则。
  • 要避免贪婪匹配、空匹配未处理和复杂模式性能问题。
  • 正则结果仍然要经过 Schema 校验，不能直接当成可信数据。
  • LLM 不能替代所有规则，正则仍然是低成本、确定性强的工程工具。
