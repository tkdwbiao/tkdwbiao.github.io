大模型时代的数据采集工程 12：常见反爬策略分析

2026-01-02 10:00
阅读时长: 16 分钟

上一篇文章里，我们讲了浏览器自动化的反检测机制与合规边界。

核心观点是：

1
2

理解检测机制，不等于绕过规则。
掌握反爬认知，是为了降低误伤、控制风险、提升系统稳定性。

从这一篇开始，我们继续往反爬机制认知推进。

真实的数据采集项目里，经常会遇到：

1
2
3
4
5
6
7

请求突然变成 403。
访问频率稍高就返回 429。
接口要求 Referer 或 Token。
同一个页面浏览器能打开，Requests 拿不到数据。
登录态过期后拿到空页面。
动态参数缺失导致接口失败。
页面出现验证码、风险提示或登录页。

这些现象背后，往往就是常见反爬策略在起作用。

这一篇我们不写绕过教程，也不写具体平台参数还原。

我们要讲的是：

常见反爬策略的分类、原理、风险信号、合规应对思路，以及面试中如何把“反爬经验”表达成系统理解和工程能力。

一、前言

反爬不是一个单独技术点。

它更像一个系统。

这个系统可能包含：

1
2
3
4
5
6
7
8
9

网络层限制。
请求头校验。
登录态校验。
访问频率控制。
业务行为风控。
前端动态参数。
浏览器环境检测。
验证码验证。
数据权限控制。

很多初学者会把反爬理解成：

1
2
3

请求失败了 -> 加 Header。
又失败了 -> 换 IP。
再失败了 -> 上浏览器。

这种思路太粗糙。

真实工程里，应该先判断：

1
2
3
4
5
6

失败发生在哪一层？
是未授权，还是频率过高？
是请求格式不对，还是状态失效？
是页面改版，还是接口限制？
是否有正式 API 或授权导出方式？
是否应该暂停任务？

反爬分析的价值不是“绕过一切限制”。

而是帮助你设计一个：

1

更稳定。
更低影响。
更可解释。
更可审计。
更符合授权边界。

的数据采集系统。

面试里也是一样。

如果你只说“我会反爬”，容易显得不专业。

更好的表达是：

我理解常见反爬策略，包括频率限制、Header 校验、Cookie / Token 状态、Referer、JS 参数、浏览器环境和业务行为风控。工程上我会先判断数据来源和授权边界，优先使用官方 API 或合规接口；如果必须采集页面，也会做限速、重试退避、状态隔离、失败暂停和审计日志。

二、反爬策略的本质是什么？

反爬策略的本质是风险控制。

目标系统通常不是为了“为难爬虫工程师”，而是为了保护：

1
2
3
4
5
6
7

系统稳定性。
用户体验。
数据权益。
账号安全。
交易公平性。
业务规则。
隐私和合规要求。

比如：

1
2
3
4
5
6

频率限制：防止高频请求压垮服务。
登录态校验：防止未授权访问。
Token 校验：确认请求来自正常流程。
验证码：区分高风险自动化行为。
行为风控：识别异常业务路径。
权限控制：保护敏感数据。

所以反爬不是单纯的技术对抗。

它背后是业务安全和系统治理。

从工程师角度，我们要学会区分三件事：

1
2
3

机制理解：知道为什么会失败。
合规应对：知道什么时候应该暂停、降频、申请授权或改用接口。
违规对抗：试图绕过访问控制、风控或付费接口。

本系列只讨论前两者。

三、常见反爬策略总览

可以把常见反爬策略分成几类。

类型常见表现工程理解
IP / 频率限制429、访问变慢、请求被拒绝请求节奏异常或超过服务承载
Header 校验403、返回空内容、返回不同页面请求上下文不完整或不符合预期
Cookie / Session跳转登录页、401、403登录态缺失、过期或权限不足
Referer / Origin接口调用失败、跨来源限制请求来源不符合业务流程
Token / CSRF表单提交失败、接口返回校验错误缺少页面生成的状态令牌
JS 动态参数接口要求签名、时间戳、nonce参数绑定前端流程或请求上下文
浏览器环境浏览器能看，脚本拿不到页面依赖 JS、环境或事件状态
行为风控验证码、风险提示、限制访问行为路径、频率或账号状态异常
数据权限有页面但无字段、接口返回脱敏账号或业务角色无权访问

这张表最重要的不是“怎么绕过”。

而是帮助你判断：

1
2
3

问题发生在哪一层？
应该从哪里排查？
是否属于授权或权限问题？
是否应该暂停任务？

import time
from dataclasses import dataclass
from email.utils import parsedate_to_datetime

import requests


@dataclass
class FetchDecision:
    should_retry: bool
    should_pause: bool
    wait_seconds: float
    reason: str


def parse_retry_after(value: str | None) -> float | None:
    if not value:
        return None

    if value.isdigit():
        return float(value)

    try:
        retry_time = parsedate_to_datetime(value)
        return max(0.0, retry_time.timestamp() - time.time())
    except (TypeError, ValueError):
        return None


def classify_rate_limit(response: requests.Response) -> FetchDecision:
    if response.status_code == 429:
        wait_seconds = parse_retry_after(response.headers.get("Retry-After")) or 60.0
        return FetchDecision(
            should_retry=False,
            should_pause=True,
            wait_seconds=wait_seconds,
            reason="rate_limited",
        )

    if response.status_code in {500, 502, 503, 504}:
        return FetchDecision(
            should_retry=True,
            should_pause=False,
            wait_seconds=5.0,
            reason="temporary_server_error",
        )

    return FetchDecision(False, False, 0.0, "ok")

这段代码的重点是：

1
2
3
4

遇到 429 不继续冲。
读取 Retry-After。
暂停任务。
记录原因。

这才是工程化处理。

from dataclasses import dataclass, field


@dataclass
class RequestProfile:
    name: str
    base_headers: dict[str, str] = field(default_factory=dict)
    timeout_seconds: float = 10.0


def build_headers(profile: RequestProfile, extra: dict[str, str] | None = None) -> dict[str, str]:
    headers = dict(profile.base_headers)
    if extra:
        headers.update(extra)
    return headers


profile = RequestProfile(
    name="authorized-api-client",
    base_headers={
        "Accept": "application/json",
        "Content-Type": "application/json",
    },
)

from dataclasses import dataclass

import requests
from bs4 import BeautifulSoup


@dataclass
class FormPage:
    action: str
    csrf_token: str


def parse_form_page(html: str) -> FormPage | None:
    soup = BeautifulSoup(html, "lxml")
    form = soup.select_one("form#demo-form")
    token_input = soup.select_one("input[name='csrf_token']")

    if not form or not token_input:
        return None

    return FormPage(
        action=form.get("action", ""),
        csrf_token=token_input.get("value", ""),
    )


session = requests.Session()
response = session.get("https://example.com/demo-form", timeout=10)
form_page = parse_form_page(response.text)

重点是理解：

1
2
3

Token 是业务状态的一部分。
Token 不是可以随便伪造的字符串。
Token 失效时应重新授权或暂停。

from dataclasses import dataclass
from enum import Enum


class FailureType(str, Enum):
    OK = "ok"
    RATE_LIMITED = "rate_limited"
    AUTH_REQUIRED = "auth_required"
    PERMISSION_DENIED = "permission_denied"
    RISK_CONTROL = "risk_control"
    SERVER_ERROR = "server_error"
    UNKNOWN = "unknown"


@dataclass
class ResponseSignal:
    status_code: int
    final_url: str
    text_excerpt: str


@dataclass
class FailureDecision:
    failure_type: FailureType
    should_retry: bool
    should_pause: bool
    reason: str


def classify_signal(signal: ResponseSignal) -> FailureDecision:
    if signal.status_code == 429:
        return FailureDecision(FailureType.RATE_LIMITED, False, True, "too_many_requests")

    if signal.status_code == 401 or "login" in signal.final_url:
        return FailureDecision(FailureType.AUTH_REQUIRED, False, True, "auth_required")

    if signal.status_code == 403:
        return FailureDecision(FailureType.PERMISSION_DENIED, False, True, "permission_denied")

    if "验证码" in signal.text_excerpt or "风险" in signal.text_excerpt:
        return FailureDecision(FailureType.RISK_CONTROL, False, True, "risk_control")

    if signal.status_code >= 500:
        return FailureDecision(FailureType.SERVER_ERROR, True, False, "server_error")

    return FailureDecision(FailureType.OK, False, False, "ok")

这个函数体现了一个关键思想：

2

涉及权限、限流、风控时，优先暂停。

十六、常见错误写法

1. 请求失败就盲目加 Header

十七、面试表达

如果面试官问：

1

你遇到过哪些常见反爬策略？

可以这样回答：

常见反爬策略包括 IP 和频率限制、User-Agent 和 Header 校验、Cookie / Session 登录态校验、Referer / Origin 来源校验、Token / CSRF 状态参数、JS 动态参数、浏览器环境检测、行为频率风控和数据权限控制。我通常会先根据状态码、页面内容、最终 URL 和日志判断失败发生在哪一层，再决定是降频、重新授权、更新选择器、改用浏览器渲染，还是暂停并申请正式接口。

如果问：

1

遇到 403 或 429 你会怎么处理？

可以这样回答：

429 我会认为是限流信号，优先读取 Retry-After，暂停任务并降低频率，不会继续高频重试。403 则要判断是权限不足、登录态失效、来源不符合要求还是访问范围不被允许。涉及权限或风控限制时，我会暂停任务并确认授权范围，而不是盲目重试。工程上会把这些失败分类写入日志，方便后续监控和复盘。

如果问：

1

你怎么设计一个稳定的反爬应对机制？

可以这样回答：

我会先做失败分类，把网络错误、超时、服务端错误、限流、登录态失效、权限不足、风险控制、页面改版区分开。不同类型有不同策略：临时错误可以有限重试，限流要退避和暂停，登录态失效要重新授权，权限不足要人工确认，页面改版要更新选择器。系统层面还要限制并发、设置最大重试次数、记录审计日志，并优先使用官方 API 或授权数据源。

如果问：

1

LLM 能不能帮你处理反爬问题？

可以这样回答：

LLM 可以辅助诊断，但不应该用于生成绕过策略。比如把状态码、页面标题、最终 URL、错误日志、HTML 摘要和历史成功样本交给 Agent，它可以帮助判断是登录态失效、选择器失效、限流、权限不足还是页面改版。对于工程问题可以给修复建议；如果涉及风控、验证码或权限限制，系统应该暂停并进入人工确认流程。

十八、总结

本文讲了常见反爬策略的分类和工程化应对思路。

核心结论包括：

  • 反爬策略本质上是系统稳定性、数据权益、账号安全和业务规则的保护机制。
  • 常见反爬维度包括 IP / 频率、Header、Cookie / Session、Referer / Origin、Token、JS 参数、浏览器环境、行为风控和数据权限。
  • 遇到反爬问题时，应该先分类诊断，而不是盲目加 Header、换工具或无限重试。
  • 429 通常意味着限流，应暂停、退避并降低频率。
  • 401 / 403 往往涉及登录态、权限或访问边界，应确认授权范围。
  • Token、CSRF、动态参数通常绑定业务流程和请求上下文，不应在未授权场景中尝试绕过。
  • 合规采集要有任务边界、访问频率限制、失败分类、暂停机制和审计日志。
  • robots.txt、服务条款、授权协议和业务审批都是数据采集前需要考虑的边界。
  • LLM / Agent 可以辅助失败诊断和日志分析，但不能替代授权和合规判断。
  • 面试中表达反爬经验时，要从“会绕过”升级为“理解机制、能设计稳定合规的数据采集系统”。
