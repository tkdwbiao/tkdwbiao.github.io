项目可以定位为：

十七、常见面试追问

1. 为什么不用纯规则？

可以回答：

1
2
3

规则适合稳定结构，成本低、速度快、可解释。
但对于半结构化文本、字段归一化、摘要、主题分类和异常诊断，LLM 更有优势。
所以我采用规则 + LLM 的分层方式。

2. LLM 输出不稳定怎么办？

可以回答：

1

先定义 Schema，要求输出 JSON，再用 Pydantic 校验和业务规则校验。低置信度、校验失败或异常页面进入人工复核，不直接入库。

3. 系统如何扩展？

可以回答：

1

任务通过队列解耦，Crawler Worker、LLM Worker、Agent Worker 都可以独立扩容。数据源限流独立配置，避免扩容后失控。

4. 如何保证数据不重复？

可以回答：

1

URL 规范化后计算 url_hash，用 Redis 做短期去重，MySQL 唯一索引兜底。结果层用 business_key 或 canonical_url_hash 去重，content_hash 判断内容变化。

5. 如何处理验证码或风控？

可以回答：

1

系统会把验证码或风控识别为风险信号，任务进入 manual_review，记录截图、页面摘要、状态码和上下文，然后检查授权、频率和数据源配置，不做自动绕过。

十九、常见错误写法

1. 项目只讲脚本

只讲脚本很难体现系统能力。

要讲任务、状态、队列、存储和监控。

2. LLM 只是噱头

如果只是“把网页丢给大模型”，不够工程化。

要讲 Schema、校验、成本、复核和质量评估。

3. Agent 没有边界

Agent 必须受动作枚举、系统提示词和人工复核约束。

4. 没有失败分类

高并发系统里失败很多，不分类就无法稳定运行。

5. 没有数据源配置

没有数据源配置，就无法管理授权范围、频率和启停。

6. 没有部署和监控

项目必须能说明如何部署、如何看日志、如何发现问题。

二十、总结

本文把前面 28 篇内容整合成一个完整项目：大模型增强的智能数据采集系统。

核心结论包括：

  • 一个优秀的爬虫面试项目不应该只是脚本，而应该是可管理、可恢复、可观测的数据采集系统。
  • 系统可以拆成管理平台、任务调度、采集执行、解析清洗、LLM 抽取、Agent 诊断、存储监控七层。
  • FastAPI 负责接口和管理平台，Worker 负责异步执行任务。
  • Redis 适合队列、限流、锁和短期状态，MySQL 适合任务、结果、配置和审计等长期事实。
  • Crawler Worker 负责抓取和失败分类，Parser / Cleaner 负责规则解析和文本清洗。
  • LLM 抽取层适合处理复杂非结构化字段，但必须配合 Schema、JSON 输出、校验和人工复核。
  • Agent 诊断层适合分析失败原因、选择器失效、字段缺失和数据质量问题。
  • 系统必须内置合规边界：授权范围、频率限制、敏感字段脱敏、异常暂停和人工复核。
  • Docker 和 Linux 部署体现工程落地能力，监控和日志体现长期运行能力。
  • 面试表达要从“我会写爬虫”升级为“我能设计一个稳定、合规、智能的数据采集系统”。
