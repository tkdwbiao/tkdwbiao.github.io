大模型时代的数据采集工程 36：LLM 与 Agent 数据采集接口设计

2026-02-19 10:00
阅读时长: 12 分钟

上一篇扩展篇，我们整理了 FastAPI 管理平台接口设计。

管理平台解决的是：

状态怎么查询。

复核怎么处理。
日志和指标怎么暴露。

这一篇是扩展篇收尾。

我们整理 LLM 与 Agent 在数据采集系统中的接口设计。

LLM 适合复杂非结构化文本抽取。
Agent 适合失败诊断、流程编排和复核摘要。

本文就围绕这些接口展开。

重点仍然是合规、可控、可观测。

LLM 和 Agent 用于抽取、清洗、诊断、复核建议，不用于绕过登录、验证码、风控、访问控制或频率限制。

def parse_and_validate(raw_output: str) -> tuple[ExtractedArticle | None, str | None]:
    data = parse_json_output(raw_output)
    if data is None:
        return None, "json_decode_error"

    try:
        return ExtractedArticle.model_validate(data), None
    except ValidationError:
        return None, "schema_validation_error"

ALLOWED_CATEGORIES = {"科技", "财经", "教育", "交通", "医疗", "其他"}


def validate_business_rules(item: ExtractedArticle) -> list[str]:
    errors = []

    if not item.title.strip():
        errors.append("title_empty")

    if item.category not in ALLOWED_CATEGORIES:
        errors.append("invalid_category")

    if len(item.keywords) > 8:
        errors.append("too_many_keywords")

    if item.confidence < 0.7:
        errors.append("low_confidence")

    return errors

因为模型可能输出：

def run_extraction(request: ExtractionRequest) -> ExtractionResult:
    prompt = build_extraction_prompt(
        text=request.text,
        schema_description=get_schema_description(request.schema_name),
    )

    model_response = call_llm(prompt, request.model_name)
    item, error_type = parse_and_validate(model_response.raw_output)

    if error_type:
        return handle_extraction_error(request, model_response.raw_output, error_type)

    business_errors = validate_business_rules(item)
    if business_errors:
        return create_review_required_result(
            request=request,
            raw_output=model_response.raw_output,
            error_type=",".join(business_errors),
        )

    return save_extraction_success(
        request=request,
        item=item,
        raw_output=model_response.raw_output,
        model_response=model_response,
    )

def build_diagnosis_system_prompt() -> str:
    return """
你是数据采集系统的合规诊断助手。
你只能根据任务日志、状态码、页面摘要、字段缺失和数据源配置进行诊断。

允许建议：
- 稍后重试。
- 降低访问频率。
- 暂停任务或数据源。
- 检查授权。
- 更新解析规则。
- 进入人工复核。

禁止建议：
- 绕过登录、权限、验证码或风控。

HIGH_RISK_ACTIONS = {
    DiagnosisAction.PAUSE_SOURCE,
    DiagnosisAction.UPDATE_RULE,
    DiagnosisAction.CHECK_AUTHORIZATION,
}


def apply_diagnosis(result: DiagnosisResult) -> None:
    if result.confidence < 0.7:
        move_to_manual_review(result.task_id)
        return

    if result.action in HIGH_RISK_ACTIONS:
        create_review_case(result.task_id, result.reason)
        return

    if result.action == DiagnosisAction.RETRY_LATER:
        schedule_retry(result.task_id, delay_seconds=300)
        return

    if result.action == DiagnosisAction.MANUAL_REVIEW:
        move_to_manual_review(result.task_id)

二十、常见坑点

1. 把整页 HTML 直接丢给模型

成本高、噪声多、效果不稳定。

应先清洗正文。

2. 不定义 Schema

没有 Schema，输出无法稳定入库。

3. 不做 JSON 校验

模型可能输出解释文字、Markdown 或格式错误 JSON。

4. 不做业务规则校验

类型正确不等于内容合理。

5. 不记录模型版本和 Prompt 版本

后续无法复现和对比结果。

6. 低置信度直接入库

会污染数据质量。

7. Agent 输出自然语言动作

系统无法校验和审计。

8. 高风险动作自动执行

暂停数据源、修改规则、恢复授权任务都应人工确认。

9. 不做脱敏

传入 Cookie、Token、账号密码等敏感信息会带来安全风险。

10. 不统计成本和效果

无法判断 LLM / Agent 是否值得使用。

二十一、面试表达

如果面试官问：

1

LLM 抽取接口怎么设计？

可以这样回答：

我会把 LLM 抽取设计成独立 Worker 或内部接口，输入包括 task_id、source_id、content_hash、清洗后的 text、schema_version、prompt_version 和 model_name。模型输出必须先做 JSON 解析，再做 Pydantic 校验和业务规则校验，通过后入库，失败或低置信度进入人工复核。

如果问：

1

如何保证 LLM 输出可靠？

可以这样回答：

我会从输入清洗、Prompt 约束、Schema 校验、业务规则校验、置信度阈值、有限重试和人工复核几个层面保证。不会直接把模型回答当成可信结果。

如果问：

1

Agent 在爬虫系统里怎么接？

可以这样回答：

Agent 主要接在失败诊断和人工复核环节。输入是任务状态、状态码、失败类型、字段缺失、页面摘要和最近日志，输出是结构化诊断结果，包括 reason、action、confidence 和 evidence。action 必须是白名单枚举。

如果问：

1

如何防止 Agent 误操作？

可以这样回答：

我会限制 Agent 只能输出动作枚举，系统只接受白名单动作；低置信度进入人工复核；暂停数据源、修改规则、授权相关操作等高风险动作必须人工确认；上下文先脱敏，系统提示词明确禁止绕过登录、验证码、风控和限流。

如果问：

1

LLM / Agent 接入后怎么评估效果？

可以这样回答：

我会看抽取成功率、JSON 解析失败率、Schema 校验失败率、人工复核比例、平均延迟、平均成本、Agent 诊断采纳率、误判率和重复失败减少比例。如果效果不稳定，就优化正文清洗、Prompt、Schema、动作枚举和复核闭环。

二十二、总结

本文整理了 LLM 与 Agent 数据采集接口设计。

核心结论包括：

  • LLM 抽取和 Agent 诊断是两个不同接口，不应该混在一起。
  • LLM 抽取输入应包含 task_id、source_id、content_hash、text、schema_version、prompt_version 和 model_name。
  • Prompt 要版本化，模型调用要统一封装。
  • 模型输出必须经过 JSON 解析、Pydantic 校验和业务规则校验。
  • LLM 抽取要有状态机，包括 pending、running、succeeded、retrying、review_required、failed。
  • 相同 content_hash、schema_version、prompt_version、model_name 可以做缓存，降低成本。
  • 低置信度、校验失败和异常输出要进入人工复核。
  • Agent 输入应该是脱敏后的任务上下文，而不是敏感凭证或完整无关数据。
  • Agent 输出必须使用动作枚举、原因、置信度和证据。
  • 低风险动作可以自动执行，高风险动作必须人工确认。
  • LLM / Agent 调用要记录 token、延迟、成本、成功率、失败率和复核比例。
  • 安全边界必须内置在系统提示词、动作白名单、脱敏、审计和人工复核中。
