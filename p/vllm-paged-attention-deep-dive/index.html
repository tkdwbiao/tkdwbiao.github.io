vLLM 系列(二)：显存手术刀 —— 深度拆解 PagedAttention 机制

2026-04-06 17:20
阅读时长: 5 分钟

如果说 vLLM 是大模型推理的皇冠，那么 PagedAttention 就是皇冠上最耀眼的明珠。在上一篇中我们提到，传统框架的显存利用率低得离谱，原因在于它们把显存当成“大豪宅”预分配。 今天阿彪带你拿起手术刀，深入显存底层，看看 vLLM 到底是怎么把“虚拟内存分页”这套老技术，在 GPU 显存里玩出花来的。

一、 核心逻辑：从逻辑块到物理块

在 PagedAttention 中，KV Cache 不再是连续存储的一长条数组，而是被拆分成了固定大小的 Block（块）（默认通常是 16 个 token）。

1. 三大核心组件

  • Logical Blocks (逻辑块)：对模型来说，它看到的依然是连续生成的 token 序列（0~15 在块 0，16~31 在块 1…）。
  • Physical Blocks (物理块)：在 GPU 显存池（Memory Pool）中真实存在的空间。这些块在显存里是不连续的。
  • Block Table (块表)：这是核心“中介”。它负责记录：第 $i$ 个逻辑块对应显存里的哪一个物理块。

2. 动态分配流程

当模型产生第 17 个 token 时（假设 Block Size=16）：

  1. 系统发现逻辑块 1（对应 token 16~31）还没有分配物理空间。
  2. 调度器从空闲物理块池里随机抓一个块（比如索引为 77 的块）。
  3. 在块表里记录：Logical Block 1 -> Physical Block 77。
  4. 模型继续写入，直到第 32 个 token 产生，再申请下一个物理块。

结论：这种按需分配的方式，彻底解决了“预分配”导致的内部碎片。除了每个请求生成的最后一个 Block 可能没填满，其他地方都是满载的。

二、 进阶黑科技：Copy-on-Write 与显存共享

这部分是 PagedAttention 最迷人的地方，也是面试官最喜欢问的显存零拷贝。

1. 案例场景：并行采样 (Parallel Sampling)

假设你让模型写一个故事，要求生成 5 个不同的结局。

  • 传统做法：你需要把 Prompt 的 KV Cache 复制 5 份，显存占用直接翻 5 倍。
  • vLLM 做法：
    1. 5 个请求的前文（Prompt）一模一样，它们的块表都指向同一组物理块。
    2. 这些物理块的 引用计数（Reference Count） 被设为 5。
    3. 显存里只存了一份 Prompt，节省了 80% 的空间。

2. 写时复制 (Copy-on-Write, CoW)

当这 5 个请求开始生成不同的结局时：

  • 请求 A 要写第 1 个不同的字，它发现要写入的物理块引用计数 > 1。
  • 系统触发 CoW：为请求 A 单独拷贝一个该块的副本，把请求 A 的块表指向新块，引用计数减 1。
  • 只有在发生差异时，才真正占用新显存。 这不仅是省钱，更是极致的优雅。

三、 实战案例：高并发下的显存计算对比

我们来算一笔账，看看 PagedAttention 到底多牛。

实验环境：

  • 模型：Llama-3-7B (FP16)
  • 显存：一张 A100 (80GB)
  • 场景：100 个并发请求，每个请求平均 Seq_Len = 2048。

1. 传统预分配方式：

  • 每个 token 的 KV Cache 大小约 0.5 MB（见Q0：请写出 KV Cache 占用显存的计算公式）。
  • 每个请求预分配 2048 个空间 $\to 2048 \times 0.5 \text{ MB} = 1024 \text{ MB} = 1 \text{ GB}$。
  • 100 个请求就要 100 GB。
  • 结果：80GB 的显存根本装不下，直接 OOM。

2. vLLM (PagedAttention) 方式：

  • 假设 100 个请求中，有很多是共享 System Prompt 的（比如 1024 个 token 的 Prompt 是公共的）。
  • 公共部分显存：$1024 \times 0.5 \text{ MB} = 0.5 \text{ GB}$ (只需存一份)。
  • 剩余生成部分：假设平均已生成 512 个 token。
  • 总占用：$0.5 \text{ GB} + (100 \times 512 \times 0.5 \text{ MB}) = 0.5 \text{ GB} + 25 \text{ GB} = 25.5 \text{ GB}$。
  • 结果：显存还剩下 50 多 GB，轻轻松松再接 200 个请求。

四、 面试官会问到的问题及详细答案

❓ Q0：请写出 KV Cache 占用显存的计算公式，并估算 Llama-7B（FP16）在 Batch=1，Seq_Len=1024 时的显存占用。

答： 核心公式：KV Cache 显存 = 2 (K和V) × 批次(Batch) × 层数(Layers) × 头数(Heads) × 头维度(Head_Dim) × 序列长度(Seq_Len) × 字节数(Bytes)。

以典型的 7B 模型为例：层数 = 32，头数 = 32，头维度 = 128，FP16 占用 2 Bytes。 代入公式：$2 \times 1 \times 32 \times 32 \times 128 \times 1024 \times 2 = 536,870,912$ bytes。 约等于 0.5 GB。
(顺便向面试官抛出：如果并发请求量达到 Batch=32，且生成长度达到 4K，单单是 KV Cache 就会暴增到 64 GB，一张 80G 的 A100 瞬间就满了！这也是为什么要做 PagedAttention 的核心原因。)

❓ Q1：PagedAttention 的块大小（Block Size）设为 16 是最优的吗？

答： 这是一个权衡（Trade-off）问题。

  • 设太小（如 4）：显存碎片极小，但块表管理开销大。CPU 需要频繁计算物理地址，且 GPU 做 Attention 时的访存不连续，会导致吞吐量下降。
  • 设太大（如 128）：利于 GPU 并行计算和访存合并，但在长文本末尾或短请求场景下，会产生较严重的内部碎片。
  • 结论：vLLM 经过大量实验，发现 16 是一个在“访存性能”和“显存利用率”之间最均衡的数字。

❓ Q2：在 PagedAttention 中，如果不连续的物理块会导致 GPU 访存变慢，vLLM 是怎么解决的？

答： 这是 vLLM 团队最硬核的地方。他们手写了专门的 CUDA Kernel 来执行 PagedAttention。 在这个 Kernel 中，每个线程块（Thread Block）在计算注意力时，会先通过 Block Table 查找当前逻辑块对应的物理地址。虽然块与块之间不连续，但因为每个块内部（16个 token）是严格连续存储的，Kernel 可以通过对齐内存访问，保证极高的计算效率。

❓ Q3：PagedAttention 如何支持多轮对话（Multi-turn Chat）的显存优化？

答： 通过 Prefix Caching（前缀缓存）。 在多轮对话中，前面的聊天记录（History）其实也是重复的。vLLM 会计算 History 的 Hash 值，将其 KV Cache 物理块缓存在显存中。当同一个用户的下一轮请求，或者不同用户的相同前缀请求进来时，直接复用物理块，连重新推理（Prefill）的计算量都省了。

五、 阿彪碎碎念 [抱拳]

学完 PagedAttention，你是不是有一种“众里寻他千百度，蓦然回首，那人却在灯火阑珊处”的感觉？ 现在的 AI 行业，天天在刷榜、在卷模型架构。但真正让大模型能像水电煤一样普及的，反而是这些扎根于操作系统内核思想、在 CUDA 算子层精雕细琢的底层工程。

千万不要觉得底层技术枯燥。 当你能站在面试官面前，手绘出 Block Table 的映射逻辑，讲清楚 Copy-on-Write 的引用计数时，你才真正触碰到了 LLM 推理的脉搏。记住，在大模型时代，最好的算法工程师，首先必须是一个顶级的系统工程师。
