【Docker 系列 06】告别繁琐的长命令：Docker Compose 一键启动多服务架构

2025-07-10 09:00
阅读时长: 6 分钟

“我的项目要连数据库、要连缓存、还要连消息队列。每次重启，我都得小心翼翼地按顺序敲 6 个长达四五行的 docker run 命令，错一个字母就全盘崩溃。有没有救？”

通过前面五篇文章的学习，你已经掌握了 Docker 的四大神器：镜像、容器、Volume（数据卷）和 Network（网络）。

但在真实的商业项目中，一个系统绝对不只有一个容器。 以我最近正在开发的 “智能 OnCall AI 助手项目” 为例，为了让大模型具备记忆，我需要用到 Milvus 向量数据库。但 Milvus 不是一个单体软件，它底层依赖 Etcd 存元数据，依赖 MinIO 存实际文件，最后还要加上我自己的 FastAPI 后端服务和 Attu 可视化面板。

如果纯靠 docker run 命令手动启动这 5 个容器：

  1. 你必须先建好自定义网络。
  2. 你得算准启动顺序（先起 Etcd，再起 Milvus）。
  3. 你的终端历史记录里会塞满长达几百个字符的变态命令。
  4. 最惨的是交接：当新同事入职，你要怎么教他把这套环境在本地跑起来？

为了消灭这种反人类的操作，Docker 官方推出了终极杀器：Docker Compose。今天，我们就来学习如何用一份优雅的文件，一键指挥千军万马。

一、什么是 Docker Compose？（从命令式到声明式）

docker run 是一种 命令式（Imperative） 操作：“嘿，Docker，给我用 80 端口、挂载 A 目录、连接 B 网络，跑一个 C 容器！”

而 Docker Compose 是一种 声明式（Declarative） 操作：“嘿，Docker，这是我的架构图（一份 YAML 文件），我不管你怎么弄，反正我要 5 个容器按照这个图纸跑起来，互相能连通，你看着办吧。”

Docker Compose 的核心就只有一个名为 docker-compose.yml 的文本文件。你在这个文件里定义好所有的服务（Services）、网络（Networks）和数据卷（Volumes），然后只需要敲一个单词，一切就会按照剧本自动上演。

二、扒开 docker-compose.yml 的外衣：核心语法解析

不要被几十行的代码吓到，docker-compose.yml 的结构其实非常清晰，主要分为三大部分：services（服务）、volumes（数据卷声明）和 networks（网络声明）。

我们直接拿一个高度简化的真实 AI 项目数据库架构来解剖。这份图纸包含了向量数据库主体（Standalone）及其依赖（Etcd 和 MinIO）：

# docker-compose.yml
services:
  # 服务1：Etcd (元数据存储)
  etcd:
    container_name: milvus-etcd
    image: quay.io/coreos/etcd:v3.5.18
    volumes:
      - ./volumes/etcd:/etcd
    command: etcd -advertise-client-urls=http://etcd:2379 -listen-client-urls http://0.0.0.0:2379 --data-dir /etcd

  # 服务2：MinIO (底层文件存储)
  minio:
    container_name: milvus-minio
    image: minio/minio:RELEASE.2023-03-20T20-16-18Z
    environment:
      MINIO_ACCESS_KEY: minioadmin
      MINIO_SECRET_KEY: minioadmin
    ports:
      - "9001:9001"
      - "9000:9000"
    volumes:
      - ./volumes/minio:/minio_data
    command: minio server /minio_data --console-address ":9001"

  # 服务3：Milvus 主体 (依赖前两个服务)
  standalone:
    container_name: milvus-standalone
    image: milvusdb/milvus:v2.5.10
    ports:
      - "19530:19530"
    environment:
      ETCD_ENDPOINTS: etcd:2379      # 重点：直接使用服务名通信
      MINIO_ADDRESS: minio:9000      # 重点：直接使用服务名通信
    depends_on:
      - etcd
      - minio

# 声明自定义网络
networks:
  default:
    name: milvus_network

核心标签大扫盲：

  1. services：在这个标签下的缩进列表，每一个节点（如 etcd, minio, standalone）就是一个容器。
  2. image vs build：
    • image: nginx:latest 表示直接去网上拉取现成的镜像。
    • 如果是你自己写的项目，可以用 build: .，它会自动寻找当前目录的 Dockerfile 现场帮你打包镜像并启动！
  3. environment：注入环境变量，相当于 docker run -e。非常适合配置账号密码（如 MinIO 的密钥）。
  4. depends_on（重点！）：决定了容器的启动顺序。在上面的例子中，standalone 声明了依赖 etcd 和 minio。所以当你按下一键启动时，Compose 会聪明地先启动存储引擎，最后再启动 Milvus 主服务。
  5. 内置网络 DNS 魔法：还记得上一篇我们大费周章创建的自定义网络吗？在 Compose 里，这全是自动的！ 它会自动创建一个以当前文件夹命名的网络，并把所有服务放进去。看 standalone 的配置：它直接用 etcd:2379 就能连上 Etcd 容器，省去了所有 IP 配置烦恼。

三、Docker Compose 的日常“四板斧”命令

有了这份 docker-compose.yml，你的命令行生活将变得极其枯燥且安逸。

1. 魔法开启：docker compose up -d

进入 docker-compose.yml 所在的目录，敲下这行命令（-d 表示后台运行）。 Docker 会自动去下载镜像、自动建网络、自动按顺序启动所有服务。

💡 阿彪小科普：在老版本中命令是带横杠的 docker-compose up。现在新版 Docker 已经把 Compose 吸收为了官方内置插件，统一使用 docker compose（中间是空格）。

2. 查看群雄：docker compose ps

如果你想看看这个“项目集”里所有的容器状态，不用再全局 docker ps 了。 这个命令只会列出当前图纸管控下的容器运行状况。

3. 上帝视角看日志：docker compose logs -f

当微服务多了，不知道错误出在哪个环节？ 敲下这个命令，你会看到一个极其壮观的画面：所有容器的日志交织在一起实时滚动，而且 Compose 非常贴心地给每个服务分配了不同的颜色标明前缀！（例如蓝色的 minio |，红色的 etcd |）。排障效率瞬间提升十倍。

4. 毁尸灭迹：docker compose down

不想用了？不要再一个个 docker stop 和 docker rm。 执行 down 命令，它会：

  1. 优雅地停止所有相关容器。
  2. 删除这些容器。
  3. 最重要的是：它会自动清理掉为了这个项目创建的临时内部网络，绝不给你的系统留下一丝垃圾。 (注：默认情况下，挂载的数据卷 Volumes 会被保留，保证你的数据安全)

四、高阶避坑：.env 环境隔离大法

在真实开发中，我们绝不会把真实的数据库密码或者通义千问的 DASHSCOPE_API_KEY 明文写在 docker-compose.yml 里然后推送到 GitHub 上。这等同于把金库钥匙挂在菜市口。

最佳实践是使用环境变量文件隔离。

Docker Compose 原生支持读取同目录下的 .env 文本文件。

1. 创建 .env 文件（不要把它提交到 Git）：

1
2

MYSQL_ROOT_PASSWORD=SuperSecretPass_888
DOCKER_VOLUME_DIR=./my_data

2. 在 docker-compose.yml 中使用 ${变量名} 占位：

1
2
3
4
5

services:
  db:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
    volumes:
      - ${DOCKER_VOLUME_DIR}/mysql:/var/lib/mysql

这样，你的 YAML 文件就是一套干净的、可随意分享的架构模板，而真正的机密和本地差异化配置，全部留在了每个人电脑的 .env 文件里。

结语

从手敲 10 遍 docker run 到写一份 docker-compose.yml 一键启动，你完成了从“搬砖工”到“包工头”的华丽转变。

如今，无论是本地开发还是单机服务器部署，你只需把代码和这份 YAML 文件发给同事，他只要敲下 docker compose up -d，他的电脑上就会完美复刻出一个包含 Nginx、Python、MySQL、Redis 且互相连通的庞大微服务帝国。这，就是容器编排的魅力。

但是，随着我们打包的项目越来越多，你可能会发现一个尴尬的问题： “为什么我用 Dockerfile 随便打包一个跑着简单 Web 服务的 Python 镜像，体积竟然高达 1.5 GB？这上传和下载的速度简直要命啊！”

你的镜像里是不是塞满了编译工具、多余的缓存和根本用不到的源代码？ 如何为你的镜像做一场“抽脂手术”，把它从 1.5GB 压榨到仅仅几十 MB？
