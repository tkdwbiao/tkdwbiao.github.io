LangGraph 实战笔记 08：构建一个会自我反思的 Agent

2025-11-15 10:00
阅读时长: 12 分钟

上一篇文章里，我们构建了一个可以根据状态选择下一步的多分支 Agent。

它会先识别用户问题类型，然后在知识库问答、订单查询和普通聊天之间选择不同路径。

这一篇，我们继续往前走一步：让 Agent 具备“自我反思”和“自我修正”的能力。

也就是：

1
2
3
4
5
6
7
8
9

先生成一个结果
  ↓
检查这个结果是否合格
  ↓
如果不合格，就修改
  ↓
再检查
  ↓
直到合格或达到最大次数

这类流程是 LangGraph 非常典型的使用场景，因为它天然包含循环、状态更新和终止条件。

一、前言

很多 Agent 示例看起来都很聪明。

用户问一个问题，模型生成一个答案，然后直接返回。

但真实业务里，我们经常不能只依赖第一次生成结果。

例如：

  • 回答可能太短。
  • 回答可能没有引用来源。
  • 回答可能没有覆盖用户问题。
  • 生成的文案可能不符合风格。
  • 生成的代码可能缺少关键步骤。
  • 计划可能不完整。

这时就需要一个检查和修正过程。

最简单的形式是：

1

生成 -> 检查 -> 修改

如果修改后还不合格，就继续：

1

生成 -> 检查 -> 修改 -> 检查 -> 修改 -> 检查

这就是 Reflection Agent 的基本思想。

不过，循环能力是一把双刃剑。

如果没有终止条件，Agent 可能会一直反思、一直修改，永远不结束。

所以本篇重点不是让 Agent 无限自我反思，而是学习如何在 LangGraph 中安全地表达循环。

二、为什么需要自我反思 Agent？

普通 LLM 调用通常是一次性的。

1

输入 -> 模型 -> 输出

但很多任务需要“先生成，再检查”。

例如写文章：

1

生成初稿 -> 检查是否结构完整 -> 不完整则补充

例如写代码：

1

生成代码 -> 检查是否满足需求 -> 不满足则修改

例如 RAG 问答：

1

生成回答 -> 检查是否基于文档 -> 不基于则重写

例如客服回复：

1

生成回复 -> 检查是否有风险表达 -> 有风险则改写

这些流程都有一个共同点：

第一次输出不一定可靠，需要经过检查和修正。

如果用普通代码写，可能是：

1
2
3
4
5

answer = generate(question)
review = check(answer)

if not review.passed:
    answer = rewrite(question, answer, review)

这只能修改一次。

如果要多次修改，就会变成循环：

1
2
3
4
5

for i in range(max_attempts):
    answer = generate_or_rewrite(...)
    review = check(answer)
    if review.passed:
        break

LangGraph 可以把这个循环显式建模成图。

这样我们能清楚看到：

  • 哪个节点负责生成。
  • 哪个节点负责检查。
  • 哪个节点负责修改。
  • 哪个字段记录检查结果。
  • 哪个字段记录循环次数。
  • 什么条件下继续。
  • 什么条件下结束。

三、本篇要构建的 Reflection Agent

我们要构建一个简化的内容生成 Agent。

用户输入一个主题，Agent 会生成一段解释。

然后检查这段解释是否合格。

检查标准简化为三个：

  1. 内容长度是否足够。
  2. 是否包含“为什么需要”。
  3. 是否包含“如何使用”。

如果不合格，就进入重写节点。

重写后再次检查。

如果合格，就结束。

如果重写次数达到上限，也结束，并返回当前最好结果。

整体流程如下：

1
2
3
4
5
6
7
8
9

START
  ↓
generate_draft
  ↓
review_draft
  ↓
  ├── pass -> finalize -> END
  ├── retry -> rewrite_draft -> review_draft
  └── give_up -> finalize -> END

这里有一个关键点：

1

rewrite_draft -> review_draft

这是一条回边。

它让流程形成循环。

    feedback = []

这个节点不决定下一步去哪里。

下一步由条件边决定。

这仍然符合前面的原则：

Node 管动作，Edge 管流程。

七、路由函数：决定继续、结束还是放弃

检查完成后，需要根据 State 选择下一步。

如果 revision_count < max_revisions -> rewrite_draft
否则 -> finalize

from typing import Literal


def route_after_review(state: ReflectionState) -> Literal["pass", "retry", "give_up"]:
    if state["review_passed"]:
        return "pass"

    if state["revision_count"] < state["max_revisions"]:
        return "retry"

    return "give_up"

这个路由函数只读取状态，不做复杂业务逻辑。

它返回三个路由 key：

路由结果含义
pass检查通过，进入最终输出
retry还可以修改，进入重写节点
give_up达到最大次数，结束

这里的 give_up 很重要。

它是循环的失败出口。

没有这个出口，流程可能一直循环。

九、最终输出节点：finalize

最终输出节点负责把当前草稿写入最终答案。

如果检查通过，就直接输出。

如果达到最大次数仍然不通过，也输出当前最好结果，并附上检查意见。

复杂 Agent 不一定每次都能达到完美结果。

当超过预算、次数或时间限制时，系统应该有一个可控出口。

from typing import Literal, TypedDict
from langgraph.graph import StateGraph, START, END


class ReflectionState(TypedDict):
    topic: str
    draft: str
    review_passed: bool
    review_feedback: str
    revision_count: int
    max_revisions: int
    final_answer: str


def generate_draft_node(state: ReflectionState):
    draft = f"{state['topic']} 是一个重要概念。"
    return {
        "draft": draft,
        "revision_count": 0,
    }


def review_draft_node(state: ReflectionState):
    draft = state["draft"]
    feedback = []

    if len(draft) < 80:
        feedback.append("内容太短，需要更详细。")

    if "为什么需要" not in draft:
        feedback.append("缺少为什么需要这个概念的说明。")

    if "如何使用" not in draft:
        feedback.append("缺少如何使用这个概念的说明。")

    if feedback:
        return {
            "review_passed": False,
            "review_feedback": "；".join(feedback),
        }

    return {
        "review_passed": True,
        "review_feedback": "内容已经满足要求。",
    }


def route_after_review(state: ReflectionState) -> Literal["pass", "retry", "give_up"]:
    if state["review_passed"]:
        return "pass"

    if state["revision_count"] < state["max_revisions"]:
        return "retry"

    return "give_up"


def rewrite_draft_node(state: ReflectionState):
    revision_count = state["revision_count"] + 1

    revised_draft = (
        f"{state['draft']}\n\n"
        f"第 {revision_count} 次修改：\n"
        f"为什么需要：{state['topic']} 可以帮助我们把复杂问题拆成更清晰的结构。\n"
        f"如何使用：先理解它解决的问题，再结合具体场景逐步实践。"
    )

    return {
        "draft": revised_draft,
        "revision_count": revision_count,
    }


def finalize_node(state: ReflectionState):
    if state["review_passed"]:
        final_answer = state["draft"]
    else:
        final_answer = (
            f"当前已达到最大修改次数，返回当前版本：\n\n"
            f"{state['draft']}\n\n"
            f"未完全通过原因：{state['review_feedback']}"
        )

    return {"final_answer": final_answer}


builder = StateGraph(ReflectionState)

builder.add_node("generate_draft", generate_draft_node)
builder.add_node("review_draft", review_draft_node)
builder.add_node("rewrite_draft", rewrite_draft_node)
builder.add_node("finalize", finalize_node)

builder.add_edge(START, "generate_draft")
builder.add_edge("generate_draft", "review_draft")

builder.add_conditional_edges(
    "review_draft",
    route_after_review,
    {
        "pass": "finalize",
        "retry": "rewrite_draft",
        "give_up": "finalize",
    },
)

builder.add_edge("rewrite_draft", "review_draft")
builder.add_edge("finalize", END)

graph = builder.compile()

result = graph.invoke({
    "topic": "LangGraph Reflection Agent",
    "max_revisions": 2,
})

print(result["final_answer"])
print("修改次数：", result["revision_count"])
print("检查结果：", result["review_passed"])

十二、为什么必须有最大循环次数？

循环是 Agent 中很常见的结构。

例如：

1

生成 -> 检查 -> 重写 -> 检查

或者：

1

计划 -> 执行 -> 观察 -> 修正计划

但循环也有风险。

如果模型一直生成不合格结果，或者检查条件永远无法满足，系统就可能无限执行。

所以只要有循环，就至少需要一个终止机制。

常见终止条件包括：

  • 最大循环次数。
  • 质量检查通过。
  • 时间预算耗尽。
  • 用户取消。
  • 工具调用失败次数超限。
  • 人工审核拒绝。

在本文示例中，我们使用：

1

revision_count < max_revisions

控制是否继续重写。

这是最简单、也最常用的方式。

十三、LangGraph 自身的递归限制

LangGraph 对图执行也有递归限制，用来防止无限循环。

如果图一直循环，没有到达 END，就可能触发类似递归限制的错误。

这是一种保护机制，但不应该把它当成业务终止条件。

更好的做法是你自己在 State 中设计明确的控制字段。

例如：

1
2

revision_count: int
max_revisions: int

然后在路由函数中显式判断。

换句话说：

框架限制是安全网，业务终止条件才是主逻辑。

from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI


review_prompt = ChatPromptTemplate.from_messages([
    ("system", "你是内容审稿人，请判断草稿是否清晰、完整，并给出修改建议。"),
    ("human", "主题：{topic}\n\n草稿：{draft}\n\n请返回是否通过和原因。"),
])

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
review_chain = review_prompt | model


def review_draft_node(state: ReflectionState):
    response = review_chain.invoke({
        "topic": state["topic"],
        "draft": state["draft"],
    })

    content = response.content
    passed = "通过" in content and "不通过" not in content

    return {
        "review_passed": passed,
        "review_feedback": content,
    }

不过这里要注意，LLM 输出可能不稳定。

这样条件边才能稳定工作。

十五、Reflection Agent 适合哪些场景？

Reflection Agent 适合那些“生成结果需要检查和改进”的任务。

例如：

1. 内容生成

1

写初稿 -> 检查结构 -> 修改 -> 输出

2. 代码生成

1

生成代码 -> 检查需求覆盖 -> 修改 -> 输出

3. RAG 问答

1

生成答案 -> 检查是否引用资料 -> 不合格则重新生成

4. 数据分析报告

1

生成分析结论 -> 检查是否包含关键指标 -> 补充报告

5. Agent 计划执行

1

制定计划 -> 检查计划是否完整 -> 修改计划

不过它并不适合所有任务。

如果任务本身很简单，例如翻译一句话、提取一个关键词，就没必要引入反思循环。

十六、设计 Reflection Agent 的常见问题

1. 没有终止条件

这是最大问题。

只要有循环，就必须明确什么时候停止。

2. 检查标准太模糊

如果检查节点只是说“看起来不错”或“还可以”，后续很难路由。

最好输出结构化字段：

1
2

review_passed: bool
review_feedback: str

3. 重写节点没有利用反馈

如果重写节点不读取 review_feedback，它可能每次都犯同样错误。

重写应该基于反馈进行。

4. 每次都从头生成

有些任务适合从头生成，有些任务适合在原稿基础上修改。

要根据场景决定。

本文示例使用的是“基于原稿追加修改”。

5. 把检查和重写塞进一个节点

不推荐：

1

review_and_rewrite

更推荐拆开：

1

review_draft -> rewrite_draft

这样更容易观察每一步。

6. 忽略成本控制

如果每轮都调用大模型，循环成本会快速增加。

需要控制：

  • 最大轮数。
  • 模型选择。
  • 输入上下文长度。
  • 是否真的需要重写。

十七、最佳实践

1. 循环必须有终止条件

最简单的是最大次数。

1

revision_count < max_revisions

2. 检查结果要结构化

推荐字段：

1
2

review_passed: bool
review_feedback: str

3. 重写要基于反馈

不要盲目重写。

让重写节点读取检查意见。

4. 区分检查节点和路由函数

检查节点负责判断并写状态。

路由函数负责根据状态选择下一步。

5. 失败也要有出口

达到最大次数后，不要继续循环。

可以返回当前最好结果，并附带未通过原因。

6. 不要过度反思

不是所有任务都需要 Reflection Agent。

简单任务直接生成即可。

7. 观察每一轮状态变化

调试 Reflection Agent 时，要重点观察：

  • 每轮 draft 变了什么。
  • review_feedback 是否有效。
  • revision_count 是否正确增加。
  • 为什么继续或结束。

十八、总结

本文构建了一个会自我反思和修正的 LangGraph Agent。

核心结论是：

Reflection Agent 的关键不是让模型无限思考，而是把“生成、检查、修改、终止”建模成可观察、可控制的状态图。

本文重点包括：

  • 自我反思适合需要生成、检查、修改的任务。
  • 循环流程可以用 LangGraph 的回边表达。
  • State 中需要保存 revision_count、max_revisions、review_passed 和 review_feedback 等控制字段。
  • 检查节点负责写入结构化检查结果。
  • 路由函数根据检查结果和循环次数决定通过、重试或放弃。
  • 重写节点应该基于检查反馈修改结果。
  • 最大循环次数是 Reflection Agent 的基本安全边界。
  • 框架递归限制是安全网，业务终止条件才是主逻辑。
