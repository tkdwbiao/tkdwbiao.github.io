LangChain Text Splitter：RAG 文档切分的关键细节

2025-09-23 10:00
阅读时长: 12 分钟

上一篇文章里，我们讲了 Document Loader：如何把 Markdown、PDF、CSV、网页等原始资料加载成 LangChain 的 Document 对象。

但加载完成之后，还不能直接把整篇文档丢进向量库。

真实文档往往很长，一篇产品手册、员工制度、技术文档、论文报告，可能有几千字、几万字，甚至上百页。如果不切分，检索效果通常会很差。

所以 RAG 数据处理的第二步，就是 Text Splitter。

一、前言

RAG 的目标是：用户提问时，系统能从知识库里找到最相关的资料片段，再交给模型回答。

这里的关键词是“资料片段”。

不是整本手册，也不是整篇文档，而是和问题最相关的几段内容。

比如用户问：

1

公司差旅住宿标准是多少？

系统最好检索出员工手册里“差旅住宿标准”那一小节，而不是把整本员工手册都塞给模型。

如果文档没有切分，可能出现几个问题：

  • 一整篇文档太长，超过 embedding 模型输入限制。
  • 向量表示过于粗糙，语义被稀释。
  • 检索结果包含大量无关内容。
  • Prompt 上下文太长，成本和延迟增加。
  • 模型在长上下文里找不到重点。

所以 Text Splitter 的任务是：

把加载后的 Document 切分成适合检索和生成的文本块，也就是 chunk。

这一篇我们重点讲：

  1. 为什么文档必须切分。
  2. chunk size 和 chunk overlap 是什么。
  3. RecursiveCharacterTextSplitter 为什么最常用。
  4. Markdown 文档如何按标题切分。
  5. 代码、表格、PDF 文档切分要注意什么。
  6. 如何保留 metadata。
  7. 如何判断切分质量好不好。
  8. Text Splitter 的常见问题和最佳实践。

二、为什么需要 Text Splitter？

1. 整篇文档的向量太粗糙

Embedding 会把文本转换成向量。

如果文本很短，比如一句话：

1

RAG 是检索增强生成，会先检索资料，再让模型基于资料回答。

它的语义比较集中。

但如果你把一篇 5000 字的长文整体做 embedding，里面可能包含：

  • LangChain 简介
  • LCEL
  • Runnable
  • Memory
  • RAG
  • Agent
  • LangGraph

这个向量会混合很多主题。

当用户只问 RAG 时，整篇文档的向量不一定能精准代表 RAG 那一节。

这就像给一本书只贴一个标签，很难精确到某一页。

2. 检索需要的是相关片段

用户问题通常只对应文档中的一部分。

例如：

1

如何配置 OPENAI_BASE_URL？

答案可能只在文档的几行里。

如果检索返回整篇文档，模型需要在大量无关内容中找答案。

更好的做法是把文档切成小块：

1
2
3
4

chunk 1：环境准备
chunk 2：API Key 配置
chunk 3：OPENAI_BASE_URL 配置
chunk 4：常见报错

这样检索可以直接命中 chunk 3。

3. 上下文窗口和成本有限

即使模型上下文窗口越来越大，也不代表可以随便塞资料。

长上下文会带来：

  • 更多 token 成本
  • 更高延迟
  • 更难定位重点
  • 更容易引入干扰信息

RAG 的核心不是“塞更多”，而是“塞更相关”。

Text Splitter 正是为了让检索更精准。

三、chunk size 和 chunk overlap

Text Splitter 里最常见的两个参数是：

  • chunk_size
  • chunk_overlap

1. chunk size 是什么？

chunk_size 表示每个 chunk 的目标长度。

例如：

1

chunk_size=500

意思是尽量把文本切成 500 个字符左右的片段。

注意：具体长度单位取决于 length_function，默认常见情况是按字符长度计算。

2. chunk overlap 是什么？

chunk_overlap 表示相邻 chunk 之间保留多少重叠内容。

例如：

1
2

chunk_size=500
chunk_overlap=80

示意：

1
2
3

chunk 1: 0    - 500
chunk 2: 420  - 920
chunk 3: 840  - 1340

重叠的目的是避免重要信息刚好被切断。

例如原文是：

1

LangChain 的 Runnable 是 LCEL 的核心抽象。它让 Prompt、Model、Parser、Retriever 都能用统一接口组合。

如果刚好从中间切开，某个 chunk 可能只保留半句话。

适当 overlap 可以让上下文更完整。

3. overlap 不是越大越好

chunk_overlap 太大也有问题：

  • chunk 重复内容变多。
  • 向量库体积变大。
  • 检索结果重复。
  • token 成本上升。

所以它是一个平衡。

常见起点可以是：

1
2

chunk_size=500
chunk_overlap=50

或者：

1
2

chunk_size=800
chunk_overlap=100

具体要根据文档类型和模型上下文调整。

四、最常用：RecursiveCharacterTextSplitter

LangChain 中最常用的通用切分器是 RecursiveCharacterTextSplitter。

它的思路是：按照一组分隔符从大到小递归切分文本。

默认常见分隔符类似：

1

["\n\n", "\n", " ", ""]

也就是优先按：

  1. 段落
  2. 换行
  3. 空格
  4. 字符

来切分。

这比简单粗暴地每 500 个字符切一刀更自然。

安装：

1

from langchain_text_splitters import RecursiveCharacterTextSplitter

text = """
LangChain 是一个用于构建大模型应用的框架。

LCEL 可以用管道语法组合 Prompt、Model 和 Parser。

RAG 会先检索资料，再让模型基于资料回答问题。
"""

splitter = RecursiveCharacterTextSplitter(
    chunk_size=50,
    chunk_overlap=10,
)

chunks = splitter.split_text(text)

for index, chunk in enumerate(chunks, start=1):
    print("=" * 20, index)
    print(chunk)

split_text 接收字符串，返回字符串列表。

2. 切分 Document

RAG 中更常见的是切分 Document。

from langchain_community.document_loaders import TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter

loader = TextLoader("data/intro.md", encoding="utf-8")
docs = loader.load()

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=80,
)

chunks = splitter.split_documents(docs)

print("原始文档数：", len(docs))
print("切分后 chunk 数：", len(chunks))
print(chunks[0].page_content)
print(chunks[0].metadata)

这里要注意：

1

splitter.split_documents(docs)

它会尽量保留原始 Document 的 metadata。

例如原始文档 metadata：

1

{"source": "data/intro.md"}

切分后的 chunk 通常也会保留 source。

这对后续引用来源非常重要。

五、参数详解

RecursiveCharacterTextSplitter 常用参数包括：

1
2
3
4
5
6

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=80,
    length_function=len,
    separators=["\n\n", "\n", "。", "，", " ", ""],
)

1. chunk_size

控制 chunk 的目标长度。

选太小：

  • 语义不完整
  • 检索碎片化
  • 需要召回更多 chunk

选太大：

  • 语义不够聚焦
  • 上下文浪费
  • 可能超过 embedding 输入限制

2. chunk_overlap

控制相邻 chunk 的重叠。

适合保留上下文衔接。

但不要设置过大。

3. length_function

默认可以用 len，即按字符数计算。

但有些场景更希望按 token 计算。

例如英文、代码、混合语言文档，字符数和 token 数不完全一致。

后续如果对成本和上下文长度要求很严格，可以考虑使用 token-based splitter 或自定义长度函数。

4. separators

对于中文文档，可以增加中文标点作为分隔符：

1
2
3
4
5

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=80,
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
)

这样切分时更可能在自然句子边界断开。

如果只是按空格切分，中文文本效果通常不如英文自然。

六、Markdown 文档切分：按标题保留结构

技术文档、博客、产品说明常常是 Markdown。

Markdown 最大的特点是有标题层级：

## LCEL

### Runnable

1

但不知道“它”指的是 Runnable。

这时可以先按 Markdown 标题切分，再用递归切分器细切。

from langchain_text_splitters import MarkdownHeaderTextSplitter

markdown_text = """
# LangChain 入门

LangChain 是一个大模型应用开发框架。

## LCEL

LCEL 用于组合 Runnable。

## RAG

RAG 会先检索资料，再生成回答。
"""

headers_to_split_on = [
    ("#", "Header 1"),
    ("##", "Header 2"),
    ("###", "Header 3"),
]

splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=headers_to_split_on
)

docs = splitter.split_text(markdown_text)

for doc in docs:
    print(doc.metadata)
    print(doc.page_content)

输出中的 metadata 会包含标题信息。

例如：

1

{"Header 1": "LangChain 入门", "Header 2": "LCEL"}

这对检索很有价值。

from langchain_text_splitters import MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter

headers_to_split_on = [
    ("#", "Header 1"),
    ("##", "Header 2"),
    ("###", "Header 3"),

markdown_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=headers_to_split_on

section_docs = markdown_splitter.split_text(markdown_text)

这样有两个好处：

  1. 先按标题保留文档结构。
  2. 再按长度控制 chunk 大小。

最终 chunk 仍然能带着标题 metadata。

3. 为什么标题 metadata 很重要？

假设 chunk 内容是：

1

它负责把模型输出转换成字符串、JSON 或 Pydantic 对象。

如果 metadata 里有：

1
2
3
4

{
    "Header 1": "LangChain Output Parser",
    "Header 2": "为什么需要 Output Parser"
}

模型和系统就更容易知道这段内容属于哪个主题。

回答时也可以引用：

1

来源：LangChain Output Parser / 为什么需要 Output Parser

七、代码文档切分

代码文档和普通文本不一样。

不能随便从函数中间切开。

例如：

1
2

def add(a, b):
    return a + b

如果切成：

1

def add(a,

和：

1
2

b):
    return a + b

就很糟糕。

LangChain 的 RecursiveCharacterTextSplitter 支持一些语言相关的分隔方式。

例如 Markdown：

1
2
3
4
5
6
7

from langchain_text_splitters import RecursiveCharacterTextSplitter, Language

splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.MARKDOWN,
    chunk_size=500,
    chunk_overlap=80,
)

对于代码文档，应该尽量按：

  • 类
  • 函数
  • 方法
  • 标题
  • 代码块

来保留结构。

如果构建代码问答系统，切分策略会直接影响检索质量。

八、PDF 文档切分要注意什么

PDF 的加载和切分都比较复杂。

用 PyPDFLoader 加载后，通常一页是一个 Document。

 1
 2

from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter

loader = PyPDFLoader("data/handbook.pdf")
pages = loader.load()

splitter = RecursiveCharacterTextSplitter(
    chunk_size=800,
    chunk_overlap=100,
)

chunks = splitter.split_documents(pages)

这里切分后的 chunk 通常会继承 page metadata。

PDF 常见问题

PDF 切分要注意：

  • 页眉页脚会重复进入 chunk。
  • 表格可能被打散。
  • 多栏排版顺序可能错乱。
  • 扫描件需要 OCR。
  • 一页中多个主题可能混在一起。

如果是严肃业务场景，不要只看代码能跑，还要抽样检查 chunk。

页码 metadata 很重要

用户很可能需要：

1

答案来自《员工手册》第 12 页。

所以 PDF chunk 一定要保留：

1

metadata={"source": "...", "page": 12}

九、如何判断切分质量好不好？

Text Splitter 没有一个永远正确的参数。

好的切分要结合业务和文档类型判断。

1. 人工抽样检查

最简单有效的方法：打印几个 chunk 看看。

1
2
3
4
5

for index, chunk in enumerate(chunks[:10], start=1):
    print("=" * 60)
    print("chunk:", index)
    print("metadata:", chunk.metadata)
    print(chunk.page_content)

检查：

  • 是否乱码。
  • 是否语义完整。
  • 是否太短或太长。
  • 是否标题丢失。
  • 是否表格被破坏。
  • metadata 是否保留。

2. 用问题测试检索

切分不是为了切分，而是为了检索。

所以要用真实问题测试：

1
2
3
4
5
6

question = "报销住宿标准是多少？"
docs = retriever.invoke(question)

for doc in docs:
    print(doc.metadata)
    print(doc.page_content[:500])

看检索出来的 chunk 是否真的包含答案。

3. 看重复率

overlap 太大时，检索结果可能都是类似内容。

例如 top-5 结果里有 4 个 chunk 基本一样。

这说明：

  • overlap 可能太大。
  • chunk size 可能不合适。
  • 文档中有大量重复模板内容。

4. 看引用来源是否可用

如果 chunk metadata 只有：

1

{}

那就很难追溯来源。

好的 chunk 应该至少知道：

  • 来自哪个文件
  • 哪一页
  • 哪个章节
  • 文档更新时间

十、常见切分策略

不同文档适合不同切分策略。

1. 普通文本

推荐从：

1
2
3
4

RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=80,
)

开始。

适合：

  • 普通文章
  • 笔记
  • 说明文档
  • 已清洗文本

2. Markdown 技术文档

推荐：

1
2
3

MarkdownHeaderTextSplitter
  ↓
RecursiveCharacterTextSplitter

先保留标题结构，再控制长度。

适合：

  • 技术博客
  • API 文档
  • 产品文档
  • README
  • 知识库文章

3. PDF 制度文档

推荐：

  • 先按页加载。
  • 保留 page metadata。
  • 清理页眉页脚。
  • 再递归切分。

适合：

  • 员工手册
  • 政策制度
  • 合同模板
  • 研究报告

4. FAQ / 问答对

FAQ 不一定适合按固定字符切。

更适合一条问答一条 Document。

例如：

1
2

Q: 如何申请报销？
A: 登录系统，填写报销单并上传发票。

这种结构本身就是一个知识单元。

不要把多个 FAQ 混在一个 chunk，也不要把一个问答拆开。

5. 表格数据

表格要谨慎。

有些表格适合按行转成 Document。

有些表格需要保留整张表上下文。

例如价格表、规格参数表，如果切坏了，模型可能看不懂列之间的关系。

from langchain_text_splitters import MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter

headers_to_split_on = [
    ("#", "Header 1"),
    ("##", "Header 2"),
    ("###", "Header 3"),
]

markdown_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=headers_to_split_on
)

recursive_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=80,
)

all_section_docs = []

docs_dir = Path("data/docs")

for path in docs_dir.glob("*.md"):
    text = path.read_text(encoding="utf-8")
    section_docs = markdown_splitter.split_text(text)

    for doc in section_docs:
        doc.metadata["source"] = str(path)
        doc.metadata["file_name"] = path.name

    all_section_docs.extend(section_docs)

chunks = recursive_splitter.split_documents(all_section_docs)

print("章节文档数量：", len(all_section_docs))
print("切分后 chunk 数量：", len(chunks))

for chunk in chunks[:5]:
    print("=" * 60)
    print(chunk.metadata)
    print(chunk.page_content[:300])

十三、常见问题

1. chunk_size 应该设多大？

没有固定答案。

可以从 500 到 1000 字符开始测试。

如果文档是短 FAQ，可以更小。

如果文档是技术说明、政策条款，需要更多上下文，可以稍大。

最终要看检索效果，而不是只看参数。

2. chunk_overlap 应该设多大？

常见起点是 chunk_size 的 10% 到 20%。

例如：

1
2

chunk_size=500
chunk_overlap=50

或者：

1
2

chunk_size=800
chunk_overlap=100

如果发现答案经常被切断，可以增加 overlap。

如果发现检索结果重复严重，可以降低 overlap。

3. 为什么切分后 metadata 丢了？

优先确认你是否使用了：

1

splitter.split_documents(docs)

而不是只对字符串使用：

1

splitter.split_text(text)

split_documents 更适合保留 Document metadata。

4. MarkdownHeaderTextSplitter 是否会自动处理 chunk_overlap？

标题切分主要是按结构拆分文档，不是按固定长度切分。

如果你还需要控制 chunk_size 和 chunk_overlap，可以在标题切分后继续使用 RecursiveCharacterTextSplitter.split_documents()。

5. 文档切得越细越好吗？

不是。

太细会导致语义不完整。

例如只切出一句：

1

它支持流式输出。

没有上下文时，模型不知道“它”是谁。

6. 文档切得越大越好吗？

也不是。

太大会导致检索不精准，带入大量无关内容。

RAG 的关键是相关性，不是把尽可能多的文本塞进上下文。

十四、最佳实践

1. 不同文档类型使用不同策略

不要所有文档都套同一个 splitter。

Markdown、PDF、FAQ、代码、表格，适合的切分方式不同。

2. 先人工检查 chunk，再建向量库

建向量库前先打印 chunk。

检查内容是否完整、metadata 是否保留、是否有乱码和重复噪声。

3. 保留标题、页码和来源

RAG 系统要能回答：

1

这个答案来自哪里？

所以 chunk metadata 至少要保留：

  • source
  • title / header
  • page
  • section

4. 用真实问题评估切分效果

切分质量最终要靠检索验证。

准备一组问题，看检索出的 top-k chunk 是否包含答案。

5. 关注中文分隔符

中文文档不要只依赖英文空格。

可以增加：

1

["。", "！", "？", "；", "，"]

让切分更自然。

6. 控制重复和噪声

overlap 可以防止语义断裂，但也会带来重复。

页眉、页脚、导航、版权声明等重复内容也要清理。

否则向量库会充满噪声。

十五、总结

本文我们讲了 RAG 流程中的第二个关键环节：Text Splitter。

核心结论是：

文档切分不是简单地按长度切一刀，而是在“语义完整性”和“检索精准度”之间做平衡。

本文重点包括：

  • 整篇文档直接做 embedding 往往太粗糙。
  • RAG 检索需要的是相关 chunk，而不是整篇文档。
  • chunk_size 控制目标长度，chunk_overlap 保留相邻上下文。
  • RecursiveCharacterTextSplitter 是最常用的通用切分器。
  • 中文文档可以增加中文标点作为 separators。
  • Markdown 文档适合先用 MarkdownHeaderTextSplitter 保留标题结构，再递归切分。
  • PDF 要特别注意页码、页眉页脚、表格和扫描件问题。
  • 切分后必须检查 chunk 内容和 metadata。
  • 切分质量最终要用真实检索问题验证。

到这里，我们已经完成 RAG 数据准备的前两步：加载文档和切分文档。
