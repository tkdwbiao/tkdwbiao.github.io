【Docker 系列 05】容器间怎么通信？一文搞懂 Docker 网络模型 (Network)

2025-07-03 09:00
阅读时长: 5 分钟

“我的 Python 后端明明写了连接 127.0.0.1:3306，而且 MySQL 容器也跑起来了，为什么就是报 Connection Refused 连不上？！”

在上一篇文章中，我们解决了数据的生死存亡问题，学会了用 Volume 给容器挂载“外接硬盘”。

现在，你的手艺越来越熟练了。你分别用 docker run 启动了一个 Web 后端容器，又启动了一个 MySQL 数据库容器，还有一个 Redis 缓存容器。

但在你满怀期待地发起请求时，程序却崩溃了。后端容器疯狂报错：找不到数据库！ 你很纳闷：“我明明都在同一台电脑上跑着，而且数据库也映射了 3306 端口，凭什么连不上？”

欢迎来到 Docker 新手必踩的第二大坑：网络隔离陷阱。 今天，我们就来彻底搞懂 Docker 的网络模型，让你的容器们成功手牵手。

一、最致命的错觉：被误解的 localhost

在弄懂 Docker 网络之前，必须先破除一个根深蒂固的思维定势。

以前我们在物理机上开发，后端代码写 localhost:3306，它会去找这台电脑上的 3306 端口。 但是在 Docker 的世界里，容器是隔离的（Namespace 机制）。

  • 把你的宿主机想象成一栋大楼。
  • 每一个容器，就是大楼里的一间独立密室。
  • 在容器 A（Web后端）里面喊 localhost（我自己），它指的是密室 A 内部。它不可能跨过墙壁去访问密室 B（MySQL）的 3306 端口。

所以，在容器内部访问 127.0.0.1，永远只能访问它自己。这就是为什么你的后端连不上数据库的根本原因。

二、Docker 的三大基础网络模式

为了让这些“密室”既能隔离又能通信，Docker 在安装时就自动帮你建好了三种基础网络模式（你可以用 docker network ls 命令查看）：

1. none 模式：真正的“小黑屋”

  • 原理：在这个模式下，容器除了自己的回环网卡（localhost），没有任何外部网络接口。不能上网，别人也连不上它。
  • 场景：适用于极度强调安全、不需要联网的离线计算任务（比如生成机密密钥）。

2. host 模式：打破次元壁

  • 原理：容器直接“剥夺”了隔离权，完全使用宿主机（大楼）的网络。容器里面监听了 80 端口，你的宿主机 80 端口就会被直接占用。
  • 优点：性能极高，因为没有 NAT（网络地址转换）的损耗。
  • 缺点：端口极易冲突。如果你跑了两个 Nginx 容器都用 host 模式，第二个肯定启动失败。

3. bridge 模式（默认）：大楼里的内部交换机

  • 原理：这是 Docker 最常用、也是默认的网络模式。Docker 会在你的宿主机上虚拟出一个名为 docker0 的网桥（就像一个内部交换机）。所有以默认模式启动的容器，都会连到这个交换机上，并被分配一个内部 IP（比如 172.17.0.2、172.17.0.3）。
  • 通信方式：容器 A 可以通过容器 B 的内部 IP互相访问。

💡 阿彪避坑指南：默认 Bridge 的致命缺陷！ 虽然容器分配了 IP，但是每次容器重启，Docker 给它的 IP 是会随机变化的！ 难道你每次重启数据库容器，都要去修改后端的配置文件吗？这简直是反人类！

三、终极杀器：自定义网络（User-Defined Bridge）

为了解决 IP 变动的问题，Docker 提供了高阶玩法：自定义网络。 这也是在企业级开发中，让多个容器通信的唯一正确姿势。

1. 魔法的核心：内嵌 DNS

当你使用自定义网络时，Docker 会启动一个内嵌的 DNS 服务器。 它的魔法在于：容器之间可以直接通过“容器名字（Container Name）”进行通信，完全不需要知道 IP 是多少！

2. 实战演练：让 Web 和 DB 手牵手

跟着我敲下面四行命令，见证奇迹：

第一步：创建一个属于你的内部网络

1

docker network create my-app-network

第二步：启动数据库，并加入这个网络

1
2
3
4
5

docker run -d \
  --name my-mysql \
  --network my-app-network \
  -e MYSQL_ROOT_PASSWORD=123456 \
  mysql:8.0

注意：这里我们将容器命名为 my-mysql。

第三步：启动一个用来测试的工具容器，也加入这个网络

1
2
3
4

docker run -it \
  --name my-tester \
  --network my-app-network \
  alpine sh

(这会让你进入一个名叫 my-tester 的极简版 Linux 命令行)

第四步：见证魔法（在 my-tester 的终端里） 试着 ping 一下数据库的名字：

1

ping my-mysql

输出结果：

1
2
3

PING my-mysql (172.18.0.2): 56 data bytes
64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.088 ms
...

通了！而且它自动把 my-mysql 解析成了真实的内部 IP！

结论

现在你应该明白了，如果要把后端和数据库都部署在 Docker 里，你的后端配置文件里的数据库地址，不要写 127.0.0.1，也不要写本机的公网 IP，而是直接写数据库容器的名字（比如 host="my-mysql"），只要它们在同一个网络下，Docker 就会帮你搞定一切。

四、网络排错必备指令

当你发现两个容器还是连不上时，这两个命令能帮你快速定位问题：

1. 查看网络详情 (docker network inspect)

1

docker network inspect my-app-network

这个命令会输出一个 JSON，在 Containers 节点下，你能清楚地看到到底有哪些容器加入了这个网络，以及它们被分配的 IP 是什么。如果你的 Web 容器不在列表里，那肯定连不上。

2. 将运行中的容器接入网络 (docker network connect) 如果你一开始忘加 --network 参数了，难道要删了重开？不需要：

1

docker network connect my-app-network my-web-container

这就像给运行中的机器临时拉了一根网线插上。

结语

学完今天的内容，我们来盘点一下你现在的 Docker 技能库：

  • 用 Dockerfile 打造灵魂（定制镜像）。
  • 用 Volumes 护住命脉（持久化数据）。
  • 用 Network 建立羁绊（容器互通）。

理论上，你已经具备了部署任何复杂微服务架构的能力。

但是，现实依然很骨感。 假设你要部署一个稍微复杂点的“智能 OnCall 项目”，你需要：

  1. 启动一个 Redis。
  2. 启动一个 MySQL，挂载数据卷。
  3. 启动一个 Milvus 向量数据库（这玩意甚至依赖 Etcd 和 MinIO）。
  4. 启动你的 FastAPI 后端。
  5. 记得给它们配置同一个自定义网络…

如果你每次上线都要手动敲 10 几条长达四五行的 docker run 命令，不仅容易敲错，而且交接给同事时，同事大概率会想打人。

有没有一种方法，可以像写代码一样，把这十几个容器的启动顺序、网络映射、端口配置全部写在一个文件里，然后敲一个命令，它们就按照剧本自动拉起？

有！这就是让无数运维工程师彻底解放双手的神器：Docker Compose。 请锁定下期：【Docker 高级】告别繁琐的长命令：Docker Compose 一键启动多服务架构。我们下周见！
