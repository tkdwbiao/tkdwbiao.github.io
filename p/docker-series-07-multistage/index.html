【Docker 系列 07】镜像太大了怎么办？多阶段构建 (Multi-stage Build) 瘦身术

2025-07-17 09:00
阅读时长: 6 分钟

“我就写了一个打印 Hello World 的简单后端接口，用 Dockerfile 打包完一看，好家伙，镜像体积 1.2 GB？！每次往服务器推送镜像都要花五六分钟，这谁受得了？”

在第 3 篇文章中，我们学会了如何自己编写 Dockerfile 来打包项目。很多新手在刚学会时，往往会得到一个极其庞大的“巨无霸”镜像。

为什么会这么大？ 因为在写代码、编译代码的时候，你需要各种“生产工具”：比如 GCC 编译器、Make 工具链、各种庞大的源码包（比如 Node.js 的 node_modules）。 但是，当程序真正跑到服务器上时，它只需要最后编译出来的那个“可执行文件”即可！

把整个编译环境一起打包进生产镜像，就好比 “为了给客户送一盘回锅肉，你把整个厨房、铁锅、煤气灶连同厨师一起打包寄了过去” 。这不仅浪费带宽、占用磁盘，而且厨房里的工具越多，被黑客利用的漏洞（安全攻击面）也就越多。

今天，我们就来学习 Docker 世界的高阶魔法：多阶段构建（Multi-stage Build），给你的镜像来一场疯狂的抽脂手术！

一、没有多阶段构建前，老前辈们是怎么受苦的？

在以前，为了得到一个小体积的镜像，老一代运维工程师通常要写 两个 Dockerfile 外加一个 Bash 脚本：

  1. 先用 Dockerfile.build 启动一个巨大的包含所有编译工具的容器。
  2. 在里面把代码编译成二进制文件。
  3. 退出容器，用 docker cp 命令把编译好的二进制文件“抠”到宿主机上。
  4. 再用一个 Dockerfile.prod，基于一个极简的基础系统（比如 Alpine），把刚才抠出来的文件塞进去，打成最终镜像。

这种方法极其割裂，项目代码里乱糟糟的，极难维护。直到 Docker 17.05 版本，官方推出了多阶段构建，彻底终结了这场噩梦。

二、多阶段构建的核心语法：一个剧本，多个舞台

多阶段构建的原理非常简单：在一个 Dockerfile 里面，写多个 FROM 指令。

每个 FROM 都代表一个全新的“舞台”（Stage）。 你可以把前一个舞台当成 “加工厂”，在里面肆意安装几 GB 的编译工具；然后在最后一个舞台（“最终产物”）里，只把加工厂里编译好的那一个小小的成果文件 COPY 过来。

加工厂在构建完成后会被自动丢弃，最终生成的镜像里只有最后一个舞台的内容！

三、震撼对比：Go 语言项目的 1GB 变 10MB

Go 语言是演示多阶段构建的完美案例。因为 Go 可以被编译成一个独立运行的二进制文件，完全不需要任何系统依赖。

# 使用官方 Go 镜像（体积约 800MB）
FROM golang:1.20

WORKDIR /app
COPY . .
# 编译代码
RUN go build -o myapp main.go

# 启动程序
CMD ["./myapp"]

结果：你得到一个高达 ~850MB 的镜像。里面包含了 Go 语言完整的 SDK、编译器、源码，而真正有用的那个 myapp 文件其实只有 10MB。

正确姿势（多阶段构建魔法）：

我们用两个 FROM 来改造它：

# ===== 第一阶段：编译加工厂 (命名为 builder) =====
FROM golang:1.20 AS builder
WORKDIR /app
COPY . .
# 禁用 CGO，静态编译出一个极其纯净的二进制文件
RUN CGO_ENABLED=0 GOOS=linux go build -o myapp main.go

# ===== 第二阶段：最终生产环境 =====
# 使用 scratch（Docker 宇宙中最原始、真正的“空无一物”镜像，0 MB）
FROM scratch

# 核心魔法：只从 builder 阶段，把那个编译好的 myapp 复制过来！
COPY --from=builder /app/myapp /myapp

# 启动程序
CMD ["/myapp"]

见证奇迹的时刻：执行 docker build 后，你最终得到的镜像体积竟然只有区区 10MB！ 从 850MB 到 10MB，整整缩小了 85 倍！部署时的上传、拉取几乎是秒级的。

四、Python/Node.js 等解释型语言怎么瘦身？

你会问：“阿彪，我做的是 AI 项目，用的是 Python。Python 代码不用编译成二进制文件，多阶段构建对我有用吗？”

非常有用！ 虽然 Python 是解释型语言，但我们经常会使用 pip install 安装大量依赖包（比如 NumPy、Pandas）。在安装过程中，pip 往往需要底层的 C++ 编译器（如 gcc）来构建一些 C 扩展库。

如果用单阶段构建，你的生产镜像里就会残留着庞大的 gcc 编译器和几十 MB 的缓存垃圾。

Python 的多阶段构建实战

我们的思路是：在第一阶段使用完整的 Python 镜像来编译依赖（打包成 wheels），然后在第二阶段使用极简的 Python 镜像（slim版）只复制运行所需的文件。

# ===== 第一阶段：构建依赖 (Builder) =====
FROM python:3.11 AS builder

WORKDIR /build
COPY requirements.txt .
# 告诉 pip 把依赖全部打包成 wheel 文件，放到 /build/wheels 目录下
RUN pip wheel --no-cache-dir --no-deps --wheel-dir /build/wheels -r requirements.txt


# ===== 第二阶段：生产运行 (Production) =====
# 使用 -slim 精简版基础镜像（体积小很多）
FROM python:3.11-slim

WORKDIR /app
# 从 builder 阶段把刚才打包好的轮子复制过来
COPY --from=builder /build/wheels /wheels
COPY requirements.txt .

# 直接从本地安装轮子，不需要再下载，也不需要 C 编译器了
RUN pip install --no-cache /wheels/*

# 复制业务代码
COPY . .

CMD ["python", "app.py"]

通过这种方式，你的最终镜像里将干净得连 gcc 都没有，极大降低了被黑客利用系统工具进行攻击的风险（提高了安全性），同时镜像体积通常能减小 40% ~ 60%。

五、阿彪的日常“微胖”克星：其他瘦身小技巧

如果你觉得多阶段构建写起来稍显复杂，在日常单阶段构建时，只要记住以下 3 点，也能避免镜像变得太臃肿：

1. 选好基础镜像（Base Image） 永远优先选择带有 -alpine（基于极简 Linux 系统 Alpine，仅 5MB 左右）或 -slim（精简版 Debian）后缀的镜像。坚决对体积庞大的基础 ubuntu 或 centos 说不。

2. 善用 && 合并 RUN 指令 Docker 镜像是由“层 (Layer)”组成的。你每写一个 RUN，就会叠加一层。

# ❌ 错误示范：产生了三个层，即使你最后执行了 rm，前面的层体积依然存在！
RUN apt-get update
RUN apt-get install -y wget
RUN rm -rf /var/lib/apt/lists/*

# ✅ 正确做法：合并为一层，清理垃圾的操作在同一层完成
RUN apt-get update && \
    apt-get install -y wget && \
    rm -rf /var/lib/apt/lists/*

3. 牢记 .dockerignore 在前几篇中我们反复强调过，一定要用 .dockerignore 排除掉 .git、本地的 .venv、本地的 logs 和大型数据文件。不要把测试数据和开发依赖一股脑塞进生产镜像。

结语

从巨大的“单体杂货铺”，到精致纯粹的“多阶段构建”，这标志着你从“能用 Docker”跨越到了“用好 Docker”的企业级标准。瘦身后的镜像能让你的 CI/CD 流水线（自动打包部署）跑得飞快。

现在，你的架构已经非常完美了：不仅有 Docker Compose 管理多服务，而且每一个微服务的镜像都极其轻量和安全。

但是，现实总是充满“惊喜”。 你把这些完美的代码推送到服务器，满怀信心地敲下 docker compose up -d，却发现：

  • 容器一直处于 Restarting (3) 的无限死循环状态…
  • 日志里报了一堆乱码…
  • 服务器的端口莫名其妙冲突了…
